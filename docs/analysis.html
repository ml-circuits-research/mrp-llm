Overview / Analysis procedures

Analysis procedures: checking a document with rules kept in memory

An analysis procedure is a set of rules stored in a base memory that the reasoners apply to the wires a document left in a session or a base memory. Typical uses are finding contradictions in a scientific paper, a book or a manual; detecting statements that cannot be right; computing KPIs and other indicators; and scoring a document against a quality rubric. Each result comes with the rule that produced it, the oracle's proof, and the document's own words: the document, the location and the exact quote. The normative contract is DS022 "Analysis procedures"; the wire is procedure (DS004).

No model is called by an analysis. A model may have written the document's wires (ingestion v2); the analysis itself is exact reasoning over those wires. Its quality therefore depends on the procedures, which are data you can read, and on how faithfully the document was formalized.

1. What a procedure is

A procedure is a procedure bundle wire whose scope carries the tag analysis. It holds:

  • members: the wires the procedure runs. These are integrity constraints that detect an issue, rule, default and aggregate wires that compute what the constraints and KPIs need, and fact wires for parameters, weights and reference data. A procedure is exactly its members. The analyzer runs these wires and nothing else from the memory, so a helper rule that two procedures share is a member of both. A member that reads a predicate which only a non-member rule derives would never fire; the analyzer reports it as member_dependency_missing.
  • findings: every violation of an integrity member, violation ID WITNESS. The integrity wire's message describes the issue and its severity (error or warning) grades it.
  • measures: the rows of its report lines (an atom pattern per line, such as report kpi_share ?part ?whole ?percent). KPIs and rubric scores are measures.
  • parameters: member facts of analysis_parameter NAME VALUE, such as a tolerance or a threshold. A run may override any of them by name.
  • description: what the procedure checks, in words.

2. The document layer and its view

The document layer is made of the circuits a document ingestion stored, identified by their provenance (kind: document, written by ingestion v1 and v2). It can also be named explicitly, by circuit name, by document name, or by the document's SHA-256. Each document wire keeps its quote and its source (for example "title, section, line N"), and the circuit's provenance gives the document's name and line range. A finding reports all three.

Some checks have to look at statements in general, whatever their predicate. Two examples: "an atom that is both asserted and denied" and "two values for one key". For these the analyzer builds the document view. It closes the document layer under the run's rules with the oracle, then writes one fact for each literal that rests on a document wire:

  • asserted_atom "TEXT": the atom has positive evidence, either stated or derived by the document's own rules.
  • denied_atom "TEXT": the atom has negative evidence, an explicit not.
  • keyed_value "P KEY" "REST": an atom of a predicate declared key N, written as its key and its remaining values.

The view is structure, not language understanding: it holds the canonical SOP text of each literal. Each view fact remembers the document wires behind it, so a contradiction found through the document's own rules is reported with the fact, the rule and the denial that make it up.

3. Writing a procedure as data

A procedure is added like any other knowledge: as SOP circuits, in a base memory layer or in a session, with no code. The library's document-analysis vocabulary is amount, unit_of, component_of, breakdown_complete, share_of, lower_limit, upper_limit, measure_of, starts_on, ends_on, precedes, born_in_year, age_years, as_of_year, claim_rests_on, premise_stated, disjoint_classes, period_amount, period_follows and ratio_definition. Dates are the integer YYYYMMDD, the date value ingestion v2 writes. A domain whose documents use relations of their own bridges them with a rule that is a member of its procedure.

A finding: an integrity constraint

@hr_min_leave integrity
  never all
    leave_days ?c ?d
    compare ?d below 20
  end
  witness ?c
  message "the legal minimum is 20 days of leave"
  severity error

@hr_policy procedure
  members $hr_min_leave
  description "Analysis: the HR rules of the domain."
  scope "analysis, findings"

A KPI: a rule and a report line

@q_margin fact
  holds ratio_definition net_margin net_profit revenue

@finance_ratios procedure
  members $an_k_ratio $q_margin
  description "Analysis: the net margin the analyst asks for."
  scope "analysis, kpis"
  report kpi_ratio ?name ?ratio

The rule an_k_ratio of the library computes numerator / denominator for every ratio_definition that is a member of the run. A zero denominator gives no value; it never causes a division by zero.

A rubric: rules plus weights

@an_w_consistent fact
  holds rubric_weight document_quality_v1 consistent 3

@an_q_consistent rule
  when rubric_weight document_quality_v1 consistent ?w
  when absent has_contradiction
  then criterion_met document_quality_v1 consistent

A criterion is a rule that concludes criterion_met RUBRIC CRITERION, and its weight is a fact. The aggregates an_q_score and an_q_max sum the weights of the criteria met and of all criteria, and criterion_failed names the rest. The rubric's report lines are rubric_score, rubric_max, criterion_met and criterion_failed.

A bridge from a domain's own relations

@fin_revenue_amount rule
  when revenue_of ?company ?year ?value
  then amount ?company ?value

Make the bridge a member of the domain's procedure. The library's checks and KPIs then apply to the domain's documents unchanged.

4. The starter library analysis-core-v1

The library is the seed memory config/knowledge/analysis-core-v1/ and imports core-min. To analyse a document, start a session on it, or on a memory that imports it.

ProcedureWhat it reports
analysis_contradictionsan_contradicted_atom: a statement asserted and denied, directly or through the document's own rules. an_conflicting_values: two values under one key of a functional relation. an_disjoint_membership: a thing in two classes that exclude each other.
analysis_numeric_consistencyParts that exceed their total. A complete breakdown that does not add up. Percentage shares above 100, or below 100 when the breakdown is complete. Values outside the plausible range of their kind of measurement (percentage, age, duration, count, price, temperature, probability). Parameters: total_tolerance (0) and share_tolerance (0.5 points).

analysis_kpisThe share of each component in its whole (in percent). The growth of a quantity from one period to the next. The average of the components of a whole. Ratios defined as data. A whole whose parts are in another unit gets no share and no average.

5. Running an analysis

  • JavaScript. analyzeSession(source, procedures, options) from lib/analysis/index.mjs. The source is a session {sessions, id}, a base memory {memories, id} or circuits {circuits}. procedures is null (every analysis procedure) or a list of ids. The options are documents, parameters, reasoning (auto or one engine id, run exactly), verify and budget. listProcedures(source) lists the procedures without running them.
  • HTTP. POST /v1/sessions/{id}/analyze and POST /v1/memories/{id}/analyze take the body {procedures?, parameters?, documents?, reasoning?, verify?, proofs?}. GET /v1/sessions/{id}/analysis-procedures and GET /v1/memories/{id}/analysis-procedures list the procedures (API). 
    curl -s -X POST localhost:9999/v1/sessions/$SESSION/analyze -H "authorization: Bearer $TOKEN" \
  -H 'content-type: application/json' -d '{"procedures": ["analysis_numeric_consistency"], "parameters": {"total_tolerance": 0.05}}'
  • ChatSOPAdapter. The mode analysis, registered through the adapter's extension point (lib/analysis/adapter.mjs). Call adapter.answer({message, mode: 'analysis', options: {analysis: {source, procedures?, parameters?, documents?}}}). The answer packet carries the report text, the findings and measures, and the proofs.
  • Ploinky Workers task. The template analyze-document (jobs/templates/analyze-document/) runs three steps. It ingests each attachment with ingestion v2 into the target: a base memory, a session, or, with target none, a new session on analysis-core-v1. It then analyses that document's circuits and writes analysis/<document>/analysis.json and report.md into the task folder. 
    pworker task --instructions "Check this report" \
  --attach report.md --target none --template analyze-document --params '{"rights": "owner-provided"}'

An analysis builds a single theory from four parts: the selected procedures' members, the declarations they and the document use, the document wires, and the document view. Each query of a procedure runs through the StrategyRouter; a small document stays on the oracle. Each row is then explained by the oracle (mode explain), which gives its proof and the document wires it rests on. An engine named explicitly runs exactly. A query that engine cannot express is listed under routes.unsupported and announced in the report. It is never answered by another engine.

6. Reading the report

The packet (object: chatsop.analysis) has these fields:

  • findings: each finding has its procedure, the rule that fired (id, message, severity, source), the witness and its label, and the evidence. The evidence lists the document wires with document, location, the exact quote and the wire's SOP. Each finding also has the other rules applied, the view atoms involved, the oracle proof and the route.
  • measures: KPI and rubric rows, each with its values, evidence, rules and proof.
  • counts, procedures (with the parameters in force), view (the number of view facts), routes (the engines, and any query an explicit engine could not run), and lint.
  • text: the report in English. Every sentence is a line_* reply wire of the conversation layer (config/knowledge/conversation-v1/0080-analysis-lines.sop), and the code holds no phrasing. A finding uses line_finding_<integrity id> when the layer has one, otherwise line_finding with the rule's own message. A measure uses line_report_<predicate>, otherwise line_report_row. A domain adds its own lines as data. If the conversation layer in use lacks these lines, for example a stored copy older than the shipped layer (renew it with node tools/refresh-seed-memories.mjs --apply), text is null and render_error says why. The findings and measures are unaffected.

7. Evaluation

The test set eval/analysis-v1/ has eight short documents we wrote for this purpose, so no third-party text is used. They cover a business report, a technical manual, a scientific abstract, a policy, a biography, a project status report, a lab note, and a control document with no planted issue. Together they plant 27 issues and give 23 KPI values to compute, with the ground truth in truth.json. node tools/eval/analysis/run.mjs measures (a) the procedures in isolation over hand-written SOP of each document. --mode analyses --dir DIR measures (b) end to end, over the packets of the analyze-document template. The procedures were written together with this set, so level (a) checks coverage and correctness; it does not show that the procedures generalise.

Results of 2026-10-03. At level (a) all 27 planted issues were found with no spurious finding, and all 23 KPI values and all 8 rubric scores were correct. Level (b) stopped after four documents. It found 2 of 15 planted issues and made 4 spurious findings, with every quote verified. The procedures fired correctly on the wires the ingestion wrote; ingestion v2 is the bottleneck. It wrote document-specific predicates instead of the library vocabulary, distributed statements about a whole to its parts, and wrote negations as separate predicates. Details are in eval/analysis-v1/README.md.

8. Limits

  • A procedure sees the document layer and its own members, not the rest of the memory. Background knowledge a check needs, such as disjoint classes or plausible ranges, is a member fact.
  • The generic checks need the document's wires in the library's vocabulary, or bridged to it. What ingestion v2 writes in a document's own relations is checked only by the view-based procedures (contradictions and keyed values) until a domain bridge exists.
  • Class membership is read from is_a facts. The kind line of an entity wire is not a fact the engines see.
  • The fixed-point engines (sql-sqlite, datalog-souffle, asp-clingo) decline the library's decimal divisions as not_expressible. prolog-tabling runs the whole library and agrees with the oracle on the test set.
