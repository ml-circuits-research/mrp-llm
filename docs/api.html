Overview / API

API

The server exposes an OpenAI-compatible chat endpoint and the endpoints around it (base memories, sessions, the direct author) under /v1. Normative contracts: DS009 for the server and DS022 for sessions and base memories. The commands below use $TOKEN, a bearer token minted on /admin or the CHATSOP_API_KEY value, and the default address http://127.0.0.1:9999. The JSON examples marked as product examples are executed against the live handlers by tests/docs/product-api-docs.test.mjs. The capability endpoints of the frozen small-model branch (/v1/symbolic/*, /v1/understand, /v1/language/proofread, /v1/text-to-clean-english, /v1/emotion/detect, /v1/server/models, /v1/route, /v1/sessions/{id}/scope-answer, /v1/models/{id}/start) are removed.

2. Conventions

  • Authentication. Authorization: Bearer <token>, or the administrator session cookie of /login (the chat page uses it). Without either: 401 unauthorized; before the administrator password is set: 403 setup_required.
  • Errors. An invalid request, a limit or authentication is an HTTP error, always {"error": {"message", "type": "invalid_request_error", "code"}}: 400 invalid_request, unsupported_parameter; 401 unauthorized; 403 forbidden; 404 not_found; 413 request_limit; 429 concurrency_limit. An unknown parameter is refused, not ignored.
  • Answer language. A message may be in any language: the request parser reads it and writes an English circuit, and the answer is first rendered deterministically in English. When the message does not look English, an optional last step (answerLanguage, section 3) phrases that answer in the message's language. The English rendering is always kept in chatSop.english_text. There is no language or parser field; the formalization strategy is a session setting (section 6).
  • No available model. When no model of the session's formalization strategy can write the circuit, the chat turn answers parse_unavailable honestly; there is no fallback parser and another strategy is never substituted.

3. POST /v1/chat/completions

Body: model (the facade id listed by GET /v1/models, chatsop-local by default; another value is 400 unknown_model), messages (exactly one new user message; the server owns the history), conversation_id (a stable id keeps the conversation-local statements), session_id (the session whose base memory, settings and drafts the turn uses; without it, one automatic session per user and conversation on the default base memory), stream (true sends the verified result as server-sent events), user (must equal the authenticated principal) chatSop.trustedSop (a trusted circuit of fact, event and remember wires run before the question) and adapter ({mode, options?}: the ChatSOPAdapter mode of this turn, stepwise, routed or direct-verified; options may set tiers {structure, formalizer, compute, direct} and routed {second, engineCodeLanguages, fallbackToFol, earlyStop}; without it the session's adapter_mode, else config/runtime.json adapter.mode, shipped stepwise; an unknown mode or option is 400). Any other field is refused. The answer is an OpenAI-style completion whose text is the deterministic English rendering of the result packet. The extension chatSop is the trace:

  • adapter: the ChatSOPAdapter answer packet (lib/adapter, the backend of the chat and of every evaluation): mode; path (what produced the answer: stepwise, B, jsEval, engineCode:<lang>, fol, direct); answer {values, answers, text}; verification {status, paths, alternatives?, model_answer?, check?, same_call?} with status verified (two different formalizations agree, or in direct-verified a symbolic path confirms the model's answer), unverified (one formalization, or the model's answer that nothing confirmed), contradicted (two symbolic paths agree on another value than the model's; that value is answered) or unresolved (the formalizations disagree, or nothing answered); route (the structure route: js for computation, fol otherwise, with the reason); paths (every path that ran: status, values, circuits, proofs, ms, tier, calls, cached); circuits and proofs of the answering path; timings (ms per stage and total); tiers (the Ploinky Workers tier of each role). In the modes routed and direct-verified the reply body states the status (conversation-v1 situations answer_verified, answer_model_verified, answer_contradicted, answer_formalized_unverified, answer_model_unverified, answer_unresolved, adapter_no_answer).
  • strategy: the step-by-step formalization strategy that assembled the circuit (LocalLLMStepByStep or InternalReasoningStepByStep; the one-shot LLMDirect is archived and a session that names it runs the default, noted in parse.strategy_note).
  • parse: parser, strategy, strategy_note (when an archived strategy name was asked for), model (the tier that answered, or the tiers joined by + after an escalation), ladder (the tiers in order), tiers (when more than one tier answered: {answered: {tier: count}, escalated: [{question, tier}]}), steps (number of questions), dialog ([{name, answer, tier?, escalated?}], one per question asked, a superseded answer marked escalated), backend, retrieval (predicate count, entity mentions, the schema neighbourhood), cost_usd, ms, cache.
  • pragmatic (the advisory pragmatic wires the formalizer wrote for courtesy and emotion, [{id, kind, score, span, near, source, basis}], never facts) , reply (the reply chosen by the JS oracle over the conversation layer: {opening, body, closing, style, facts, ms, layer}, each part {id, situation, priority, variants, why, outranked}; the former pragmatic_use is gone) near_miss ({candidates: [{id, label, description, distance, mention, relations: [{predicate, facts}]}], ms}: the closest names of the memory for a turn without an answer), instructions (the instruction wires of the message, [{id, do, kind, text, span, source}]) and behaviour ({turn, instructions: [{id, kind, text, since_turn}], changes?}: the user's active instructions; a message of instructions only has status: instruction). The reply parts are prefix, opening, body, aside, follow_up, closing and suffix (DS023 "Behaviour layer"). A message of pragmatic wires only is answered with status: courtesy and a reply from the conversation layer, with no computation; the same holds for POST /v1/sessions/{id}/query with message (DS023).
  • model_sop (the authored circuit), circuit (the generated execution circuit), linking (surface, symbol, matched form, alternatives), session_circuits (session definitions proposed this turn, each with draft_id; accept or reject them with POST /v1/sessions/{id}/drafts/{draft}/accept|reject), user_statements, carried_statements, model_assumptions, assumption_policy, assumption_branch, unclear, understood_as.
  • status, completeness, retrieval (the slice: size, predicates, bounds, complete or not and why), route (requested, chosen, rule, features, alternatives, backend, fallback), verification (the oracle check of a routed answer, route.verification), provenance, reinforcement, cnl and english_text (the deterministic English answer), answer_language ({mode, message_language, applied, model, ms, tried, reason}: whether and by which model the answer was phrased in the message's language), pendingSop and required for a clarification, session (id, base memory, formalizer, adapter mode), latency_ms and formalization_ms, turn_ms.

  -d '{"model": "chatsop-local", "session_id": "demo-session", "messages": [{"role": "user", "content": "Where does Maria work?"}]}'

Answer language. Settings answerLanguage in config/runtime.json: mode is auto (the default: on when the message does not look English, off for English), always or off; providers (default the Ploinky Workers tier small, Qwen3.8 27b) phrases the answer, entry by entry. The model works strictly from the English answer and a compact result packet (status, answers, count, facts used with their sources). Every number and Wikidata id of the English answer must appear in its text; otherwise the next model is tried, and in the end the English answer is returned.

Chat errors: 503 parse_unavailable (no model of the strategy can run; chatSop.status: parse_unavailable with the reason), 422 parse_failed (the models ran and no valid circuit came back after the last repair round), 422 model_output_rejected (a circuit was written but not admitted or not executable; chatSop carries model_sop and rejection), 409 the conversation is still answering, 429 the server is busy, 504 the time limit (limits.timeoutMs, 180,000 ms by default) was reached, 413 the message is too long. Every error with a chatSop carries the parse record. GET /v1/models lists the facade and whether a coding-agent model is available.

5. Base memories

Memory sizes: besides the storage counters circuits and facts (kept unchanged), GET /v1/status (memories), GET /v1/memories, GET /v1/memories/{id}, GET /v1/sessions/{id} and the knowledge browser list carry knowledge_files (files of all layers), sop_wires (wires in them) and wires_by_type (for example {"fact": 3, "entity": 8}). The chat pages show these as "N knowledge files · M SOP wires"; facts is the number of facts in the store, an index for fast lookup. The wire statistics are parsed once per memory content and cached.

Sections 5 to 8 are the product endpoints (sessions, base memories, the direct author). Their examples are executed against a live test server by tests/docs/product-api-docs.test.mjs, with a stub of the authoring model (no model is called), so the costs below are those of the stub.

A base memory is a named, forkable knowledge store of the one memory strategy the product offers (sqlite; the associative and scan engines of memory/ are research engines), kept under chat_data/base_memories/<id>/ (DS022). Reading needs any token; creating, importing, forking, adding knowledge and deleting need the administrator session (the cookie of /login), because adding knowledge is an approval recorded with the approver in the memory's provenance. Circuits are checked by the knowledge validator (sop/knowledge/) together with the circuits already stored; a failing circuit answers 422 validation_failed with problems and warnings and nothing is written. A circuit may not contain jsEval, model-surface wires, query wires or governance fields.

Create or import

default_base is the base memory that sessions naming none fork from: chatData.defaultBase, which is the encyclopedic world-v1. When world-v1 is not loaded, as on the test server above, the minimal default (which imports core-min) is used. kind (optional) chooses what a new memory is built on: encyclopedic is a copy-on-write fork of world-v1 and answers 409 not_available when it is not loaded; minimal imports core-min and is the default when neither kind nor imports is given; empty has no imports. kind and imports are exclusive. Without circuits the memory holds no circuits of its own; with them it is imported all or nothing. id is optional (lowercase letters, digits, _, -). imports (optional array of base memory ids, default ["core-min"], [] for none) names the memories whose circuits are the lower layers of the new one: their classes, predicates and lexemes are its vocabulary, snapshotted at creation (a later change of the imported memory does not reach it). Chats link words against the vocabulary of their session's memory.

Composing a base memory

The base-memory composer (DS022 "Composing a base memory"; the checkboxes of /admin) builds or refreshes a base memory from prepared layers through the ordinary import path: the seed layers of config/knowledge (core vocabulary, common sense, the conversation layer and its small-talk collections) and any other base memory. GET /v1/memory-composer lists the layers (seed or not, role knowledge or conversation, an exclusive group, licence and counts from seed.json, stale seeds) with the chat's reply memory and default base. POST /v1/memory-composer takes id, layers (in order), and optionally name and description; it refreshes an existing memory only when it is not a seed and holds no circuits of its own (409 otherwise), checks that the layers hold together (422 with problems), and when the rebuilt memory is the chat's reply memory the reply layer is reloaded (reply_layer).

curl -s -X GET http://127.0.0.1:9999/v1/memory-composer -H "Authorization: Bearer $TOKEN"

6. Sessions

A session works on its own copy of a base memory under chat_data/sessions/<id>/: the repository is cloned by hard links, the base circuits are copied. What the conversation adds stays in the session; it is visible to the user who started it and to an administrator. The chat request POST /v1/chat/completions carries session_id; without it one automatic session per user and conversation is used, on the default base memory. base in POST /v1/sessions is optional; without it the session forks the default base memory. Sessions abandoned for chatData.sessionTtlDays (14) are removed.

Settings

Body {formalizer_model?, formalizer?, adapter_mode?}; the same object is accepted as settings in POST /v1/sessions.

  • adapter_mode: the ChatSOPAdapter mode of the session's turns, stepwise, routed or direct-verified; null uses config/runtime.json adapter.mode (shipped stepwise). A request's adapter.mode overrides it for one turn (section 3).
  • formalizer: the formalization strategy of the session's chat turns, LocalLLMStepByStep or InternalReasoningStepByStep; null uses the server default (LocalLLMStepByStep). 7. The direct author: knowledge authoring

Attached instruction or source files go to the direct author: the configured authoring tier ingest.tier (shipped small), called through Ploinky Workers as a chat completion (no tools, no shell, no files; there is no omp), with the skill sop-wire-authoring. It writes SOP circuits that the server validates in a temporary folder. With a session, the circuits that pass the knowledge validator join that session's layer at once; there is no manual acceptance (owner, 2026-10-02): errors are corrected through tests and interactions. The model is the request's model, else ingest.tier; at most three repair rounds are made (DS022).

POST /v1/author

files are UTF-8 text files (at most 10, 2 MB each); session adds the validated circuits to that session's layer (without it only the circuits are returned and the temporary folder is under chat_data/tmp/); wait: false answers 202 at once and GET /v1/sessions/<id>/requests/<request> reports the progress and the result. The folder holds TASK.md, the skill, the input and the model's conversation; the validator checks the circuits and sends its problems back to the model in the same conversation, as patches, for a bounded number of rounds. The answer names model (the chain id that wrote the circuits) and cost_class (subscription for the openference plan, otherwise paid_api). Errors: 429 author_busy, 400 unknown_model.

Ingest documents into a base memory

Documents, books and other material become knowledge of a task-type base memory (DS022 "Ingesting documents into a base memory"). Every document states its rights (cleared, permissive-attribution or owner-provided, DS011); anything else is refused with 400 rights_required before a model runs. The document is cut into chunks along its headings; a model compiles each chunk over the memory's vocabulary and the chunks merged before it (author: "direct", the only author: one chat-completion conversation per chunk through Ploinky Workers; the retired omp author is refused with 400); the validator and the quote check (every quote must be words of the passage) run in the repair rounds; a fact that duplicates or contradicts the memory is held back. Every validated chunk is stored at once with its provenance (no acceptance step); the answer is the ingestion with its report. wait: false answers 202 with the status URL. A chunk stored earlier (same SHA-256) is skipped, so ingesting the same document again adds nothing.

Procedure library

A procedure is a bundle of definitions (predicates, rules, defaults) with a description of the question form it answers, stored in a base memory like any knowledge (DS022 "Procedure library"). When a message matches a description, the query author is offered the procedure's head predicate and its rules, and queries it instead of re-deriving the rule. A typical source is a session definition the formalizer wrote for one question.

The answer names the stored circuit (added) and the memory's new counters; the circuit is procedure-proc_grandparent with a @proc_grandparent procedure wire whose members are the definitions.

8. Using the session: theory, query, commit

Circuits for a message

A message becomes a query through lib/query-author: the formalizer writes the query circuit from the memory\'s vocabulary (DS022). POST /v1/sessions/{id}/query takes either query (a query circuit, run as written) or message (a request in any language; the answer carries parse, model_sop and circuit). Whoever wrote the query, it is linked, retrieved over a slice, routed, verified and rendered by the same symbolic path. The answer packet and chatSop carry parse: {model, backend, rounds, cost_usd, ms, cache, ...}; with no available model the answer is parse_unavailable. A clear question that no predicate of the memory expresses is answered unclear (relation_not_in_memory), never with an invented relation.

10. Chat feedback

Every answered turn of a session gets a number: the chat answer carries chatSop.turn and chatSop.trace_id (the completion id), and the session transcript keeps the turn record (the message, the formalization strategy and model, the authored and the execution circuit, the status, the answer text, the trace id). 11. Models and strategies

A Model is a base memory plus one strategy per slot (DS025). POST /v1/chat/completions takes model (a Model id) and an optional metadata object with language (the answer language: auto or a code such as ro) and slots (per-request strategy overrides, applied when the Model allows overrides). The response adds mrp: the Model, the original and English message, the detected and output languages, the reflex hit, the affect, the round-trip result, the effective slots, the applied overrides and one trace entry per slot. A Model whose slot names a strategy this server cannot run answers 503 strategy_unavailable.

POST /v1/mrp/models
{"id": "hr", "profile": "support-bot", "base": "hr-policies", "createBase": true,
 "language": {"output": "auto"},
 "slots": {"reflex": {"strategy": "faq-margin", "params": {"threshold": 0.55, "margin": 0.15}},
           "roundtrip": "lexical-sampled", "commit": "review-queue"},
 "faq": [{"q": "How many vacation days do I have?", "variants": ["Annual leave entitlement?"], "a": "21 working days per year."}]}

PUT /v1/mrp/models/{id} replaces the given fields (name, description, base, language, slots, faq, reflexes, allowOverrides); reflexes is a list of pattern reflexes {pattern?, affect?, mode: stop|continue|pragmatic, reply | tone, priority} (DS025 "Reflex boundary"; a base memory may also hold reflex wires); the slot reason takes strategy-router or {"strategy": "engine", "params": {"engine": "sql-sqlite"}}, the slot verify oracle-js, oracle-always or off; in GET /v1/mrp/strategies every strategy has a status: ready, missing-dependency or not-implemented; parameters are checked against the catalog. GET /v1/mrp/strategies?check=1 lists every slot with its strategies, parameters, costs and availability on this server. Sessions take the settings model, language and slots (POST /v1/sessions, POST /v1/sessions/{id}/settings); a session of a Model starts on the Model's base memory.

POST /v1/mrp/models/{id}/discover with {"passages": ["..."], "strategy": "llm-consolidate", "params": {"tier": "good", "batchChars": 12000}} proposes value-schema wires from the passages (DS028): the response lists proposed (each also queued as a review item of kind schema), known, invalid, unused, batches, calls and failures. The strategy manual runs nothing (400); a strategy of the strategy service answers 503 strategy_unavailable with the reason when the service cannot run it. term-stats and splade-stats answer candidates (lexemes and verbs without roles, never queued); frame-seed needs no passages and queues proposed lexemes; sae-sentence-embeddings and sae-llm-activations queue, per named feature, a proposed schema with an extractor whose trigger is the feature (kind schema-record; approving it writes the schema as reviewed).

12. Model gateway settings

These routes need the administrator session (a bearer token gets 403) and configure the Ploinky Workers home of the machine (DS027). PUT /v1/mrp/pworker/providers/deepseek/key {"key": "…"} checks the key against the provider's model list and stores it only in the Pworker home; an empty key removes it. PUT /v1/mrp/pworker/tiers/fast {"entries": [{"provider": "deepseek", "model": "deepseek-flash", "extraBody": {"thinking": {"type": "disabled"}}}]} sets a tier chain. Changes take effect after POST /v1/mrp/pworker/restart. GET /v1/mrp/pworker reports the proxy, the providers (whether a key is configured, never the key), the tier chains and what each tier serves now.
