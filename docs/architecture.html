Architecture

This page documents the product as the code is today: which components exist, how a message becomes an answer, where the trust boundaries are, and what is deliberately not part of the product. It is generated from the source tree (static import scan of lib/, sop/, memory/, reasoning/ and server/, then reading the call paths); every file:line citation is resolved by a pattern when the page is built, and a test fails when one stops holding. The contracts remain the specifications: DS002, DS009, DS014, DS022; the execution walk-through is Runtime and the names are in the Wiki.

a. Components and trust boundaries

Five boundaries matter. B1 is authentication: every route needs a bearer token or the administrator session cookie, except the documentation, the health check, the home and login pages and the administrator setup and login calls (server/http.mjs:214). B2 is the author boundary of DS014: the formalizer's model only answers short questions about the message and the vocabulary of the session memory, and the system assembles the circuit (the one-shot MRP strategies DirectSOP and SchemaGuidedLLM write a whole circuit, which the same validator admits); the request parser has no fallback parser (server/query-parser.mjs:12), and the Agent admits only declarative circuit types whose values the message supports (server/agent.mjs:150). B3 is the Ploinky boundary: a model is called only through the Ploinky proxy (lib/pworker.mjs) as a plain chat completion, with no tools and no shell (lib/ingest/direct-author.mjs:201, lib/formalize/strategies.mjs:215); what it returns is text that the validator checks. B4 is that stored knowledge changes only through the few explicit writers of diagram c; a base memory grows only through a validated, recorded addition. B5 is the solver rule: swipl and z3 run only when a wire names the backend (diagram d).

Static scan of the product entry points tools/serve-local.mjs, server/http.mjs, server/cli.mjs: 292 of 368 modules under lib/, sop/, memory/, reasoning/ and server/ are reachable through static or dynamic imports; 76 are not (listed in not in the product).

b. One chat turn, end to end

The chat call (server/http.mjs:240) answers through ChatSOPAdapter (server/http.mjs:291, lib/adapter/chat-turn.mjs:21, lib/adapter/index.mjs:88), the turn the evaluation harnesses run too (tools/eval/lib/chat-turn.mjs:22); in its default mode stepwise it builds a circuit author whose formalize calls the request parser with the lexicon of the session (lib/adapter/modes/stepwise.mjs:13) and hands it to Agent.turn (server/agent.mjs:33); the modes routed and direct-verified formalize the message with several paths and verify by agreement (lib/adapter/modes/routed.mjs:24). The request parser runs the session's step-by-step strategy (server/query-parser.mjs:122): the system asks short questions, each answered by the first tier of the ladder and escalated only when needed (lib/query-author/step-by-step/index.mjs:50), and assembles and validates the circuit. The formalizer never answers and never adds a fact: it produces a query, a constraint or a labelled unclear verdict.

Steps 5 to 7 are one pipeline. compileDeclarative (sop/declarative.mjs:162) never executes anything: it returns the authored SOP, the generated execution SOP and the reports (clause links, translations, untranslated words, copula readings, repairs, unresolved spans). runDeclarative (sop/declarative.mjs:603) then runs the execution SOP through Runtime.run with origin generated; a relation or entity that does not link produces a clarify wire instead of a guess (sop/declarative.mjs:647). In Runtime the solve wire expands into link, reason and binding wires (sop/runtime.mjs:111); link calls linkKnowledge (sop/runtime.mjs:109), which retrieves through reasoning/slice/ (reasoning/linker.mjs:11); reason picks the strategy with chooseReasoning (sop/runtime.mjs:56), by default the reference route (sop/runtime.mjs:30), and judges a sliced answer with the completeness guard (sop/runtime.mjs:143).

The answer text is written by cnl through renderAnswer (sop/cnl.mjs:11) from the result packet; the structured packet is never changed. The chain stops being read-only in exactly one place: the proof-use reinforcement of an admitted, metadata-verified observed fact after a real, non-hypothetical proof, allowed only when policy.reinforce and the retention configuration both permit it (sop/runtime.mjs:148).

c. Memory: base memories, sessions, layers, SQLite, retention

A base memory is a folder whose circuits are the source of truth; its repository is derived from the fact wires (lib/chat-data/memories.mjs:120). The product creates SQLite memories only (lib/chat-data/memories.mjs:38); the other engines of memory/banks/ stay for research. A session copies the base circuits, clones the repository with hard links (lib/chat-data/sessions.mjs:104) and compiles its own lexicon from the base circuits followed by the session circuits (lib/chat-data/sessions.mjs:140); the lexicon is cached by the hash of those circuits (lib/chat-data/lexicons.mjs:12). The query author reads the vocabulary of that lexicon, so the circuit it writes can only name predicates the memory has.

Repository.visible (memory/repository.mjs:111) lists the session's live layer, then the user chain, then the base chain, and retrieval reads across them. The shipped configuration keeps retention at mode: none with reinforceOnUse: true, and uses bounded sharding with a garbage collection every 32 writes (config/runtime.json:33). Temporary folders older than 24 hours and sessions idle for 14 days are removed by a scheduled cleanup (lib/chat-data/index.mjs:20).

There are two read paths with different inputs: a chat turn retrieves fact rows from the session repository through linkKnowledge, while POST /v1/sessions/{id}/query runs the oracle over the session theory, the circuits as text, through askMemory (server/product.mjs:220). The first sees only the facts stored in the repository; the second sees every wire of the circuits, rules and norms included, and answers a query circuit you send.

d. Reasoning strategies and backends, with rule 8

The registry has five ids: reference, js-reference and js-oracle (the same oracle, reasoning/registry.mjs:20) and the two external strategies prolog-tabling and z3-smt-bounded, each pinned to one backend (reasoning/registry.mjs:24). A wire that names backend prolog or backend z3 is routed to its strategy (sop/runtime.mjs:56). Rule 8 shows as four rejections (reasoning/registry.mjs:56, reasoning/registry.mjs:57, reasoning/registry.mjs:62, reasoning/registry.mjs:70) and as unsupported with fallback: null (reasoning/common.mjs:32) when a binary is missing (reasoning/registry.mjs:32). With Prolog, the oracle still answers first and the two results must agree (reasoning/bridge/external.mjs:64).

The StrategyRouter has two entries. On the typed path of a chat turn, reasoning auto reports the oracle with its features and the reason (reasoning/registry.mjs:42). On the knowledge-wire path of POST /v1/sessions/{id}/query, routedAsk (reasoning/slice/wire.mjs:264) may choose a wire engine, and the oracle re-checks the routed answer. The completeness guard judge (reasoning/slice/guard.mjs:90) decides whether an answer over a partial slice may be given. The other directories under reasoning/strategies/ are the comparison set, exercised by eval/smoke-reasoning/ and tests/strategy-*.test.mjs.

e. The authoring path

The direct author runs only on an explicit call (server/authoring.mjs:33). It is one chat-completion conversation through the Ploinky proxy with no tools and no shell (lib/ingest/direct-author.mjs:201); the repair loop is bounded by maxFixRounds (lib/ingest/direct-author.mjs:236). A validated result joins the session layer at once (lib/chat-data/sessions.mjs:158) and SessionRuntimes.refresh (server/session-runtime.mjs:51) makes it visible to open agents, including through a new session lexicon. Committing is a separate action (lib/chat-data/sessions.mjs:179).

Courtesy, emotion and the conversation layer

Part of the one understanding step: the step-by-step formalizer (LocalLLMStepByStep through its acts question) records what the message does besides asking or stating as advisory pragmatic wires (basis llm, a verbatim span when it has one). The compiler keeps them out of linking and execution. Every reply is data: the reply wires of the conversation layer conversation-v1; the result packet becomes facts, the layer rules and priorities derive the applicable replies and the JS oracle chooses the opening, body and closing (with the derivation in the trace). A turn without an answer gets the near-miss names of the memory; no word list or pattern reads the message and no sentence is written in code.

DS023

Request parser

Turns the message of a chat turn into a circuit with the session's step-by-step formalization strategy: LocalLLMStepByStep (the default) or InternalReasoningStepByStep. The system asks short questions; the Ploinky proxy answers them on the tier ladder (tiny, then small, then good), each question escalating only when the answer of the tier below cannot be read or the tier does not answer. The one-shot LLMDirect is archived; a session that names it runs the default with a note in the trace. It caches identical requests per memory version, strategy and ladder and fails honestly: a strategy is never replaced by another and there is no fallback parser.

Step-by-step formalizer

Retrieves the vocabulary of the session memory (candidate predicates, the schema neighbourhood, entity hints), asks the model short questions one at a time, reads each answer structurally and assembles the circuit itself; a question whose answer cannot be read twice, or whose tier does not answer, goes up the tier ladder with the same history. The validator admits the circuit; the model never writes SOP.
