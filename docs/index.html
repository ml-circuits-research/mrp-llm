MRP-LLM Documentation

MRP-LLM builds small neurosymbolic language models. A Model is a base memory plus one strategy per pipeline slot: the message is turned into English (normalize), may be answered at once from the Model's FAQ (reflex), is formalized into SOP circuits and answered by symbolic reasoning, may be checked by a round trip, and the answer is phrased in the user's language (voice). Every model call goes through Ploinky Workers by tier. The design specifications DS025 (Models, slots, strategies), DS026 (language), DS027 (model gateway), DS024 (SOP surfaces) and DS028 (schemas and benchmark) define this layer; the rest of this documentation describes the symbolic core it builds on, the ChatSOP runtime.

The symbolic core has one goal: to beat small LLMs at reasoning through symbolic processing, and to help small LLMs reason symbolically. A user submits a checked SOP circuit, or asks in plain language and lets a step-by-step formalization strategy build the circuit: LocalLLMStepByStep (the default) or InternalReasoningStepByStep asks short questions, Ploinky Workers tiers answer them (tiny first, escalating to small and good only for a question whose answer cannot be read), and the symbolic system writes the circuit. The validator checks it and the doubtful question is re-asked in bounded rounds, the KnowledgeLinker links its names to authorized, time-aware knowledge, only the slice of knowledge the question needs is retrieved, the StrategyRouter sends the problem to the oracle or an engine and verifies a routed answer against the oracle, and the result comes back with evidence and a deterministic English rendering. Run it with npm start (port 9999) and open /chat; the worked chat turn follows one real question end to end.

Current plan

Owner decisions of 2026-10-01 and 2026-10-02: the small-model research branch is frozen; the work focuses on reasoning; formalization is step by step (one-shot LLMDirect is archived): the circuit is assembled by one of two formalization strategies, chosen per session, from short questions about the message and the schema neighbourhood, answered by the tier ladder of Ploinky Workers, the one model gateway of the project; larger tiers answer the same questions, so tiers are compared like with like. There is no fallback parser and no silent substitution of a strategy, so without the first tier the answer is parse_unavailable. The validation procedure is the benchmark of symbolic reasoning against small LLMs (experiments/proposal/symbolic-vs-llm-benchmark.md). Progress is tracked in TODO.md and shown under /experiments; this page never asserts progress.

Reasoning benchmark procedure

tools/datasets/diversity/build-benchmark.mjs produces development cases with independent construction and oracle gold. tools/eval/symbolic-vs-llm/run.mjs compares direct English-evidence answers (A), explicit derivations (A'), step-by-step circuits answered by a named tier, and subscription answers (D); the one-shot circuit arms are archived with LLMDirect. The completion baseline selects an existing OpenAI-compatible endpoint without changing the product's formalizer. Evidence is rendered from the gold-retrieved slice; a capped sample is explicitly partial and scored separately. A development pilot is sanity evidence only. Sealed execution requires a frozen preregistration and proceeds in paired 100/300/600 stages; contracts and reporting rules are in DS012, DS007 and DS015.

The circuit in one example

The author sees the user's message and the schema neighbourhood of the memory and writes only circuits. "Where does Maria work?" becomes a query whose names are strings; the KnowledgeLinker links "Maria" to an entity, the router chooses a strategy, and the answer is rendered from the result packet.

@q query
  where match
    relation "works at"
    role subject "Maria"
    role object ?org
    polarity affirmed
  end
  select ?org

What the user stated stays turn-local evidence; anything the author adds is marked assumed or written as a labelled session definition that the user accepts or rejects; an unintelligible, empty or undecidably ambiguous message is unclear. The author never answers and never states a fact; a question the system cannot compute is answered "I understood the question as ...; I cannot compute this kind of answer yet".

The knowledge language

What the system knows is written separately from the chat, from sources, as knowledge wires (predicate, fact, rule, default, integrity, aggregate, action, method, norm, procedure) by the direct author or the owner, and validated by sop/knowledge/. Several reasoning strategies answer questions over the same wires and are compared on one smoke suite. The user manual is the section "Knowledge wires" of DS004, with one help page per wire; the task procedure for compiling a long text into wires is skills/sop-wire-authoring/SKILL.md.
