Overview / Input language

Input language: from what the user types to the circuit

Users write in any language, with typos and in several sentences. Since the owner decision of 2026-10-01 the system has no language pipeline of its own: the session's formalization strategy (by default LocalLLMStepByStep: short questions answered by Ploinky Workers tiers, smallest first, and a circuit assembled by the system) reads the message, in whatever language, and writes only circuits. Everything after it is symbolic and English: the validator, the KnowledgeLinker, the StrategyRouter, the reasoning strategies and the answer rendering. The small-model chain that used to clean, translate and parse the input (language identification, translation, proofing models, Stanza parsing) is frozen and archived in probably_obsolete/tinyLLMExperiments/.

1. The chain

  1. User messageAny language, with typos; one or several sentences.
  2. Request parserThe formalization strategy receives the message and the schema neighbourhood of the memory (the named entities and the relations around them, with roles and examples) and writes circuits: queries, constraints, unclear/unparsed markers, labelled session definitions and assumed lines. server/query-parser.mjs, lib/query-author/
  3. Admission and repairAdmits only what the circuit surface and the memory's declarations allow (DS014; guards such as condition_misuse and time_not_a_point); bounded repair rounds, and at most two vocabulary-dialog expansions when a term is missing.
  4. KnowledgeLinkerLinks entity strings to the base memory; asks when a name is ambiguous.
  5. Reasoning and English answerSlice retrieval with the completeness guard; the StrategyRouter chooses the oracle or an engine and verifies a routed answer against the oracle; the result packet is rendered in English with the origin of each step.

There is no fallback parser. When no model of the chosen strategy can run the turn answers parse_unavailable (another strategy is never substituted); the system never guesses a reading.

2. Behaviour on difficult input

  • Typos and mixed languages. The author normalizes them while writing the circuit. A name stays as the user wrote it and is resolved by the KnowledgeLinker through the labels and aliases of the memory.
  • Unknown words. The query author handles an unknown word agentically (decision of 2026-10-01): it defines the word as a session definition marked assumed, asks the user, or assumes a reading and says so. The validator admits only what DS014 allows, and an assumption is reported, never used silently.
  • Ambiguity. Two equally good readings give one unclear wire with kind ambiguous and two to four reading lines; one clearly better reading is written as the query and the choice is reported. Gibberish and a message with no request are unclear too.
  • What the user states. A statement is turn-local evidence held in the caller's conversation context; a supposition, a hedge or reported speech is used only conditionally. Nothing a chat turn does writes to a repository.
  • Several questions become several query wires, answered together.

3. How the input stage is evaluated

The author is measured, not trusted: the query-forms dev set (tools/eval/formalization/query-forms, one tier at a time with --tier) counts correct circuits, wrong circuits (a definite wrong answer after execution, the dangerous class) and honest unknowns apart, and the planned benchmark (experiments/proposal/symbolic-vs-llm-benchmark.md) compares circuits written by small models against the same models answering from text. Evaluation is an engineering check: tests are lexically disjoint variants of the forms the system was built on, staged with a paired bootstrap interval and preregistered stopping rules (DS007, DS012).
