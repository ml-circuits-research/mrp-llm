## Introduction

SOP (properly SOP Lang) stands for Standard Operating Procedure: SOP Lang is an attempt to formalize standard operating procedures, and the knowledge, questions and constraints they depend on, as typed, inspectable, executable text.

MRP-LLM (Meta Rational Pragmatics language models) is a framework for building **small neurosymbolic language models**, specialised by domain or by type of problem. Natural language is interpreted by specialised pragmatic interpreters (formalizers), knowledge lives in explicit knowledge bases, and answers are computed by reasoning engines and only *phrased* by a language model. The thesis of Meta Rational Pragmatics is that language has no fixed semantics but has a rational pragmatic meta-level: for a given domain, a well chosen interpreter knows what it is sensitive to, what it extracts and what reasoning it applies to what it extracted. MRP-LLM makes that interpreter explicit, replaceable and measurable. What a user or an API client talks to is a **Model** ([DS025](specsLoader.html?spec=DS025-models-slots-and-strategies.md)): a base memory plus one strategy per pipeline slot; every design question without a single right answer is a slot with documented strategies chosen per Model. Everything inside works in English; a model translates at the start of a turn and phrases the answer at the end ([DS026](specsLoader.html?spec=DS026-language-pipeline.md)). Every model call goes through Ploinky Workers by tier name ([DS027](specsLoader.html?spec=DS027-model-gateway-settings.md)). SOP Lang, in either of its two surfaces ([DS024](specsLoader.html?spec=DS024-sop-surfaces.md)), is the language every component exchanges.

The symbolic core of MRP-LLM is the ChatSOP runtime, whose goal is **symbolic reasoning that beats small language models, and that helps small language models reason symbolically**. A user message in any language is turned into a typed circuit by the formalizer (a model called through Ploinky Workers, the project's one model gateway), the circuit is validated and linked to reviewed, time-aware knowledge, a reasoning strategy executes it, and the answer is rendered deterministically in English from the result packet. The symbolic knowledge and reasoning stay separate from language-model weights; a model contributes only the circuit, never the answer.

## Core Content

### Purpose and authority

The pipeline of a chat turn is: the user message, then the request parser with the session's formalization strategy (step by step, owner decision 2026-10-02: LocalLLMStepByStep by default or InternalReasoningStepByStep; the system asks short questions, Ploinky Workers tiers answer them smallest first, and the system assembles the circuit; DS022 "Formalization strategies"); the validator; the [KnowledgeLinker](wiki.html#definition-linker), which links entity and relation strings to the memory and no longer parses language; the StrategyRouter (`reasoning/router`); a reasoning strategy or the JavaScript reference oracle; the deterministic English rendering of the answer from the result packet (`sop/answer-text.mjs`); and, for a non-English message, the answer formulation in the user's language from that answer and packet (DS009 "Answer language"). There is no fallback parser: when the formalizer's first tier is not available the turn returns an honest `parse_unavailable` instead of a guess. The core reads and answers English; in an MRP-LLM Model the `normalize` slot gives it the message in English and the `voice` slot phrases its answer in the output language ([DS026](specsLoader.html?spec=DS026-language-pipeline.md)), and with the `passthrough` strategy the formalizer's questions read the original message ([DS014](specsLoader.html?spec=DS014-model-surface.md)).

The validator admits the circuit, selects the user and permissions, and the runtime compiles the inspectable execution circuit. When identity is missing or ambiguous, or a required scalar cannot be uniquely obtained, symbolic orchestration can generate `clarify` and suspend dependent work rather than require the model to invent a question. A `stated` or `assumed` proposition is turn-local evidence that the runtime links and uses for the turn, not a sourced assertion or a repository write; explicit trusted `fact` and `remember` operations remain distinct, and nothing becomes knowledge without approval. A read must not hide a write. The formalizer and a supplied document must not grant their own permissions, install rules or policies, or certify a proof. A [verbalizer](wiki.html#definition-verbalizer) may restate an existing [CNL](wiki.html#definition-cnl) result but must not alter its truth status, provenance, quantities, time, or completeness. There is one executable SOP language with one circuit surface and no versions; other SOP dialects do not become compatible by sharing a name.

### Trust boundaries

1. **Circuit-authoring boundary.** The formalization strategy of the session (step by step: LocalLLMStepByStep by default, or InternalReasoningStepByStep; [DS022](specsLoader.html?spec=DS022-sessions-and-base-memories.md) "Formalization strategies") receives the user's message and the schema neighbourhood of the session's memory (candidate predicates with roles and examples, entity hints). The answering model only answers short questions; the strategy assembles only circuits: `query` and `constraint` wires, `unclear` and `unparsed` reports, `stated` suppositions of the message, labelled `assumed` lines, and session definitions that are used for the turn only and are stored in the session layer once the validator admits them. It never writes an answer and never writes a fact. Its output is data: the validator checks it against the memory vocabulary and the closed wire set, the doubtful question is re-asked in bounded rounds, and the rest is rejected.
2. **Knowledge boundary.** Accepted facts and approved definitions come from reviewed sources with provenance. Quoted source claims, reusable implicit-rule proposals, temporary problem state and reasoner capabilities stay separate; a candidate rule is not made global because it repairs one question.
3. **Execution boundary.** The runtime, the memory strategy and the reasoning strategy are selected independently by configuration and report their route, completeness and fallback. An explicitly requested backend is never substituted.
4. **Rendering boundary.** The answer is produced from the result packet by deterministic code; a model that formulates text may not change the packet's truth status.
5. **Language boundary.** The language models of the `normalize` and `voice` slots translate and phrase; they never answer. A failure at either edge falls back to the original message or to the deterministic English answer, never to a model's own answer ([DS026](specsLoader.html?spec=DS026-language-pipeline.md)).
6. **Strategy boundary.** A Model's strategy is never replaced silently by another one; a strategy that cannot run is reported with its reason ([DS025](specsLoader.html?spec=DS025-models-slots-and-strategies.md)).

### Distinct information roles

Original documents and traces remain identifiable sources; accepted facts and approved definitions are the evidence used by the runtime; patterns and hypotheses are candidate objects, not observations. Source-backed publication requires review and provenance ([DS008](specsLoader.html?spec=DS008-material-sources.md)). Adding approved knowledge need not retrain any model. The [memory engine](wiki.html#definition-memory-engine) and [reasoning strategy](wiki.html#definition-reasoning-strategy) are independently selected axes subject to their capability and completeness limits.

### Evidence boundaries

A symbolic demonstration or historical report cannot establish comparative superiority, production security or hardware readiness. External corpus rights and model weights are not supplied by the source-code license. Publication claims require fixed inputs, observed runs, documented omissions and fallback routes, and independently reviewed evaluation; see [DS012](specsLoader.html?spec=DS012-evaluation-metrics.md) and the benchmark plan `experiments/proposal/symbolic-vs-llm-benchmark.md`. Work remaining is tracked in `TODO.md`, not asserted as delivered product behavior.

The research direction and publication materials archived under `probably_obsolete/article-direction/` are source goals, not peer-reviewed results; the experiments and publication obligations are preregistered in [DS007](specsLoader.html?spec=DS007-experiment-preregistration.md). ### Research question and intended contribution

These statements are research direction (vision), not measured outcomes.

Can a persistent agent whose language component is a circuit-writing model, whose reasoning is symbolic and whose memory is reviewed and time-aware answer questions that small language models answer wrongly, and can its errors and costs be attributed to the right component? A fluent answer may use wrong facts, a syntactically valid circuit may encode the wrong question, and retrieval similarity does not prove a claim. The hypotheses to test are that a small or large model writing circuits that a symbolic engine executes (a) beats the same small model reasoning directly over the same evidence on tasks that need exact multi-hop chaining, counting, closed-world negation, transitive closure, constraints, temporal reasoning, rule chaining with exceptions and scale, and (b) gives the engine's verified answer a proof the direct model cannot supply. The families, arms, metrics and stopping rules are in the benchmark plan and are measured under [DS012](specsLoader.html?spec=DS012-evaluation-metrics.md); a negative result still tests the contract.

The proposed contribution is an operational and epistemic contract joining turn-local message statements and assumptions, approved knowledge and procedures, solver values, provenance, temporal validity and reported coverage — not a new universal solver, an invention of logic or hashing, or proof that a small model matches a large one. A common typed representation permits independent memory and solver substitutions only within their declared compatible capabilities; an incomplete retrieval cannot justify global uniqueness, absence, or optimum.

PAL, LINC and Logic-LM already separate language interpretation from execution or proof; the project must compare the *persistent* knowledge and procedure contract and its attribution of intermediate effects, not claim that NL-to-program-to-solver is new. Scallop's Datalog and provenance, LMQL's constrained model programming, DSPy's textual module optimization, PICARD's constrained decoding and MLIR's typed compilation are related but not interchangeable. RAG supplies external retrieval and may complement document selection; the proposed distinction is that approved retrieved material can become justified facts and procedures and is evaluated before CNL, rather than merely conditioning prose. Bloom filters and holographic reduced representations are antecedents to associative storage; the cortical analogy motivates complementary perspectives but is not biological validation, HRR equivalence, or lossless-compression evidence. This bibliography is selective, not a priority or exhaustive-survey claim.

Exact scan/SQLite, RecallMemory projections ([DS016](specsLoader.html?spec=DS016-recall-memory.md)), HoloMemory associative codes ([DS017](specsLoader.html?spec=DS017-holo-memory.md)) and exact-plus-hint hybrid storage do not provide equal retrieval coverage automatically; possible is not entailed, an explanation is not an observed cause, and a simulated plan is not a real-world action. Reinforcement due to legitimate use is a retention policy, not independent epistemic confirmation.
