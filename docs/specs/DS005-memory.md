## Introduction

The [repository](wiki.html#definition-repository) stores admitted claims and approved definitions so a user can ask about a time, correct knowledge, and maintain a private session without exposing it to other users or forks. The [memory engine](wiki.html#definition-memory-engine) retrieves candidate facts; it does not decide that a claim is true. This specification states the contracts every memory strategy shares; each strategy has its own specification with its mechanism, verified implementation status and the experiments it still needs.

Base memories and sessions ([DS022](specsLoader.html?spec=DS022-sessions-and-base-memories.md)): the chat names a **base memory**, a forkable store of any strategy below with its validated circuits and provenance, and works in a **session** that clones it; what a conversation adds stays in the session until an administrator commits it to a fork. Adding knowledge to a base memory is an approval recorded with its approver; there is no implicit write path.

## Core Content

### Temporal identity and isolation

A claim's validity interval and the time at which the repository learned it must remain separate. Intervals are half-open `[from, until)` over ISO dates or UTC timestamps (`lib/time.mjs`); a time of day is never guessed without a date and zone, and `timeless` is the whole line. `valid`, `at` and `during` concern the world; `knownAt` and `asof` concern the repository's knowledge and are supplied by the host. Retractions and corrections retain provenance: an `end` or `retract` event targets one claim id, never every claim about the same relation, and a question `asof` a time before the correction still sees the earlier version. A new job or changed location must not silently overwrite a previous claim or imply physical presence. Reviewed rule versions are filtered by their known time too. When evidence for `p` and `not p` overlaps in time the reasoner reports `both`; support in disjoint periods is `mixed_temporal`, not a contradiction ([DS006](specsLoader.html?spec=DS006-reasoning.md)).

Users, sessions, base forks, and referenced historical snapshots have distinct roots. `commit` publishes authorized session changes; `discard` removes uncommitted changes; an old referenced snapshot remains a valid [GC](wiki.html#definition-gc) root. `gc` without `--apply` reports unreachable candidates; deleting one still referenced is invalid. The full repository and generation contract is [DS021](specsLoader.html?spec=DS021-memory-retention-and-generations.md).

### Memory strategies

`memory.engine` selects the physical bank behind one SOP-facing interface; `policy.retrievalStrategy` separately selects how the available view is searched; the reasoning strategy is a third, independent choice ([DS006](specsLoader.html?spec=DS006-reasoning.md)).

| Strategy | `memory.engine` / retrieval | What it stores | Specification |
| --- | --- | --- | --- |
| RecallMemory | `recall-memory` | Multi-view hashed 4-bit counters with column-style consensus, inspired by *A Thousand Brains* | [DS016](specsLoader.html?spec=DS016-recall-memory.md) |
| HoloMemory | `holo-memory` | Superposed bipolar codes in fixed signed-counter banks, plus a known-handle wire plane | [DS017](specsLoader.html?spec=DS017-holo-memory.md) |
| SQLite | `sqlite` | Exact indexed tuples with optional literal full-text search; also a single-file memory | [DS018](specsLoader.html?spec=DS018-sqlite-memory.md) |
| Scan and exact sidecar | `scan`; retrieval `exact` | An unindexed exact map; optional exact tuple bodies beside an associative layer | [DS019](specsLoader.html?spec=DS019-exact-reference-memory.md) |
| Hybrid | `hybrid`; retrieval `hybrid`, `auto` | Exact SQLite evidence plus RecallMemory or HoloMemory hints; exact-first search policy | [DS020](specsLoader.html?spec=DS020-hybrid-memory.md) |
| Retention and generations | `memory.retention`, `memory.sharding` | Normal and pinned banks, adaptive cooling, bounded or archive generations, promotion, repository and GC | [DS021](specsLoader.html?spec=DS021-memory-retention-and-generations.md) |

The canonical engine names are exported as `MEMORY_ENGINES` by `memory/banks/factory.mjs`; legacy identifiers still accepted for existing configurations and snapshots are defined in DS016 and DS017.

### Common bank and retrieval contract

Every bank implements `add`, `recall`, `reinforce`, `decay`, `maintain`, `export`/`from` and `stats`, and exposes `domains` (predicate/arity routing) and `receipts` (tuple identity for the temporal layer). A bank is not a reasoner: it runs no rules and does not judge sources. A retrieval strategy (`memory/strategies.mjs`, `StrategyRegistry`) receives the host-authorized repository and session, a canonical partial atom, the question's time view and limits, and returns `rows`, `complete`, `probes` and `coverage`; each row carries the full atom, claim id, validity, source and a description of its verification. It never executes retrieved SOP as text and never creates conclusions. `policy.allowedStrategies` restricts the choice; an unknown name is an error, not a request to load code. The same SOP fact means the same thing in every engine: there is no second memory language, and the formalizer target does not change with the engine.

A retrieval candidate or associative score is not a proof, probability, independent fact, or permission to execute recovered code. Types stay distinct (`1` is not `"1"`), and a repeated variable is an equality constraint. A failed retrieval means "not retrieved", never "false"; explicit negation is a separate fact. Exhaustive enumeration, counting, and absence claims require an appropriate complete exact retained view; a successful bounded lookup alone does not certify that all historical facts survived retention. Probe counts are engine-specific units and are never compared as equal work.

### Closedness and completeness for the knowledge wires

The knowledge wires of [DS004](specsLoader.html?spec=DS004-sop.md) make the retrieved slice a question of correctness: a partial slice makes a missing fact look false. The memory side of the rules is this.

- **`closed` is declared, never inferred.** `closed true` on a `predicate` says the retained view holds every fact of that relation. An author may propose it with the source sentence that asserts exhaustiveness; the host accepts it only over an archive (`retention none`) or a pinned view, so that adaptive forgetting or bounded generations can never turn a forgotten fact into a false `absent`. A predicate is closed only relative to a complete retained view.
- **The pull contract.** A strategy may receive a materialised slice or pull from a fact source with `lookup(predicate, keys)` (rows and `complete`), `rulesFor(predicate)` (rules with `complete`), `count(predicate)` and `closed(predicate)`. The exact engines (SQLite, scan, the exact sidecar) answer `complete` and `closed`; RecallMemory and HoloMemory return candidates and estimates only (`declared: false`) and never close a predicate.
- **Completeness-sensitive answers.** `absent`, an aggregate, `mode count`, `mode every`, `no_plan`, an optimum and any `unknown` or `refuted` obtained by failure are valid only over predicates declared `closed` and fully retrieved for the relevant keys, recursively for derived predicates (every rule with that head, and the rules of the body predicates, must be in the slice). A default conclusion needs retrieval completeness for the keys of its strict contrary and of its exceptions, not a closed world. Otherwise the answer is withheld, widened, or reported incomplete with reason `partial_retrieval`. The host widens a retrieval (so that every strategy gets the same guard) from symbol-driven relevance: exact rule radius, constants and a bounded number of hops first.
- **Positive answers stay valid.** A positive answer derived without negation as failure, aggregates, counts or universal quantifiers remains valid when more wires are retrieved, because evidence is monotone (the status `both` is reported, it never retracts a derivation).
- **Reporting.** Every result packet carries `retrieval: {complete, truncated, keyed, steps, wires, probes}`, and a `supported` answer that rests on an incomplete slice says so ([DS006](specsLoader.html?spec=DS006-reasoning.md) "Completeness under partial retrieval").

**Implementation (reasoning/slice/, since 2026-10-01).** The host side of these rules runs on the product path from a memory to the reasoner:

- *The slice.* `linkKnowledge` (`reasoning/linker.mjs`) takes the rules that can reach the question (`planGoals`) and asks `SliceRetrieval` for the facts they and the question can use. The demand plan (`reasoning/slice/demand.mjs`, a magic-set style rewriting) orders conjunctions by sideways information passing. Every reachable rule has a separate instance for each caller lookup position, or an unkeyed scan; converse and mutually recursive calls therefore preserve their input direction. Input domains flow into rule heads and output domains flow back to callers without merging recursive input and output positions. KEYED atoms use one bound position (`predicate`, position, value), both polarities; SCANNED atoms have no bound input. Only facts reached by a call's input domain enlarge its variables. Newly arrived input keys revisit indexed rows already in the slice until the demand fixpoint, so caching cannot hide a later recursive premise. Domains conservatively overapproximate joins; no rule is evaluated during retrieval. A join that would look up many values reads the relation whole only when it fits the existing bounds.
- *Selectivity ordering.* Bound-variable joins take precedence over equally bound constant-only atoms, preserving a selective multi-hop prefix. Remaining ties can use indexed SQLite base-tuple cardinalities; a matching non-SQLite bank makes that estimate unavailable. These counts are cost estimates only: they ignore inferred facts, temporal visibility and provenance and never certify completeness. If either predicate has rule producers, the estimate must offer an eight-fold advantage before reversing the written order, because derived fanout is not counted. Unknown and zero derived cardinalities cannot be treated as proof of absence. Actual lookups still pass through the selected retrieval strategy and the same limits and guards.
- *Class-dependent bounds.* `SliceRetrieval` classifies selected rules by predicate/arity dependency cycle (including mutual recursion): `ordinary` retains 10,000 facts, 50,000 probes, 20,000 lookups and 10 s per expansion; `recursive` permits 100,000 facts, 500,000 probes, 200,000 lookups and 60 s per expansion. Both `linkKnowledge` and `askMemory` inherit these bounds when the caller supplies none. Explicit per-call limits override the corresponding defaults independently; the typed runtime's explicit policy limits still take precedence. A speculative complete-relation read may reuse admitted facts, but is complete only when the source certifies the entire relation and all new facts fit.
- *Bounded widening.* A speculative whole-relation probe admits no facts when its new rows do not fit the remaining fact bound; keyed retrieval can still find decisive evidence. A final probe cap clipped by the fact bound remains reachable even when geometric growth would otherwise skip it. Each polarity lookup counts against the hard lookup allowance; interrupted pairs are retried when that allowance grows. Grouping recursive keys is linear in their number.
- *Complete and settled.* A slice is COMPLETE when the demand reached its fixpoint, every demanded key is covered by an untruncated lookup or a complete whole-relation scan, the rule closure is complete and the schema knows every predicate. Caps, fact/probe/lookup allowances and `retrievalMs` can leave uncovered demand and therefore an incomplete slice. It is SETTLED when it is also EXACT: every lookup was answered by an exact view (R-P3: `retained-exact-records` or `visible-exact-snapshot`; an associative candidate list makes it unsettled).
- *The guard.* `reasoning/slice/guard.mjs` judges the answer the reasoner gave over the slice. A settled slice supports everything. Over an unsettled slice a proof (`exists`, `explain`), a counterexample (`every` decided by `all`, `none`, `not_all`, `at_least` evidence) and an opposing fact stay valid and are returned with `complete: false` (R-P1; on the knowledge-wire path a negated claim over a closed predicate, asked as `not` or `absent`, that is `refuted` by a proof of the atom itself is such an answer, rule `R-P1 refutation`, when the program has no negation as failure on the way; a `supported` answer to it may rest on the absence and stays R-P2); a `select` is widened and, when it cannot be completed, returned as the partial rows with `complete: false` and `reason: partial_retrieval`; a `count`, a universal answer that no counterexample decided, a ranking and a failure-derived `unknown` are widened and, when they cannot be settled, answered `status: incomplete`, `reason: partial_retrieval`, with the lower bound of a count as `at_least` (R-P2). `policy.closedWorld` is `view` (the default: the settled retained view is the world of the question) or `declared` (a count over a predicate not declared `closed` is `bound: at_least`, a universal answer over such a domain without a counterexample is `unknown`, `open_domain`; R-P4).
- *The report (R-P5).* The packet carries `retrieval: {complete, truncated, keyed, steps, wires, probes, facts, rules, predicates, class, bound, exact, lookups, scans, reasons, guard, trail}`: the slice's size, its predicates, its rule-dependency class (`ordinary` or `recursive`), the effective bounds in force (`facts`, `probes`, `lookups`, `cap`, `ms`), whether it is complete and, when it is not, why (`truncated:<predicate>[<position>=<value>]`, `fact_budget`, `probe_budget`, `lookup_budget`, `time_budget`, `rules_incomplete`, `unknown_predicate:<p>`), the guard rule that decided and one trail entry per widening step.
- *Reads write nothing (rule 7).* The source only recalls; nothing is reinforced by retrieval. The proof-use promotion after a real proof is the separate, policy-gated step of the runtime.
- *The knowledge-wire path.* `askMemory` (`reasoning/slice/wire.mjs`) answers a query circuit over a memory: the circuits of the memory without their facts are a `Theory` indexed by head predicate (rules, defaults with their exceptions and the strict contrary of each candidate, aggregates, integrity constraints), the facts come from the repository, and the oracle receives exactly the slice as wires with the `predicate` wires of the slice (so it reads `closed`). The decision uses the oracle's own `sensitivity` block (`monotone`, `over`, `defaults`, `aggregates`), so `absent`, aggregates and default conclusions are judged on the desugared program. Modes of work read the whole memory and are incomplete when it does not fit the budget.
- *Planning retrieval.* Typed planning retrieves goal atoms, action prerequisites and selected rule-body atoms as independent demands, not as a conjunction evaluated against initial-state bindings. This retains static premises needed after an action changes the state. Retrieval budgets and rule closure still apply; `no_plan` over an incomplete or inexact slice becomes `budget_exhausted`, `reason: partial_retrieval`, never a definite negative plan.

### Retention and reporting

Sharded profiles maintain generation-specific banks, pinned knowledge, and referenced snapshot data with budgets and explicit maintenance actions. Promotion must preserve the original valid interval and provenance; strengthening an actually used nonhypothetical fact does not confirm every retrieved hint. Roots from other users and sessions protect reachable shards during GC. Comparison reports must account for bank bytes **and** domains, receipts, claim metadata, indexes and serialization separately, together with retrieval limits, retention and completeness, and must keep unavailable backends or historical reports distinct from observed new runs ([DS010](specsLoader.html?spec=DS010-engine-and-solver-comparison.md)).

### Decisions and open experiments

**Decision 2026-09-28 (Q-ARCH-2).** Still-valid memory content from the archived requirements, registers and reference documents now lives in DS016–DS021; `probably_obsolete/` keeps only the raw historical evidence. The bounded fact-bank role of the current adapters is not declared final: each strategy specification lists the real experiments needed before any claim, including the unreproduced HoloMemory five-seed kernel table, total-byte and metadata measurements, partial-cue discovery, the RecallMemory view portfolio and occupancy thresholds, exact-storage baselines, hint benefit and long-stream retention. **Decision 2026-09-28 (Q-ARCH-3).** The system is named ChatSOP; its two associative strategies are RecallMemory and HoloMemory.
