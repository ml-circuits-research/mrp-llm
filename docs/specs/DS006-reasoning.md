## Introduction

A user submits a checked [SOP](wiki.html#definition-sop) query to receive a supported result with its facts, route, and completeness information. The [linker](wiki.html#definition-linker) selects applicable approved definitions and retrieves relevant facts before a reasoner solves a typed problem; external solvers do not discover missing rules in associative storage.

## Core Content

### Strategy contract

`policy.reasoningStrategy` selects a strategy id, independently of `memory.engine`. **`reference` is the `js-reference` oracle** (`reasoning/strategies/js-reference/`, see "The js-reference oracle") reached through the runtime bridge `reasoning/bridge/` (ids `reference`, `js-reference` and `js-oracle` are the same route): the bridge lowers the runtime's typed facts, rules and queries to knowledge wires, asks the oracle and projects its evidence back to the runtime packet; the bounded controllers for abduction, planning, simulation and the learning operations run over the oracle's closure. The former JavaScript reasoner (`reasoning/reasoner.mjs`, with its `closure`, `join` and `evaluate`) was retired on 2026-10-01 (owner decision in chat: the oracle does everything that route did); `reasoning/bridge/` replaces it and `tests/reasoning/reasoning-bridge.test.mjs` pins the packet. The two **explicit external strategies** are `prolog-tabling` (Horn work in SWI-Prolog tabling, checked against the oracle; the retired SWI adapter's successor) and `z3-smt-bounded` (integer constraints and optimization in Z3, typed-constraint module `ast.mjs`). A trusted `reason`/`solve` wire that names `backend prolog` or `backend z3` and no `reasoning` runs the strategy of that backend (`STRATEGY_OF_BACKEND` in `reasoning/registry.mjs`); the returned `reasoningStrategy` exposes the selection. The former `advanced` route (the oracle plus optional external backends, with a reported JavaScript fallback) was **removed on 2026-10-01** (hygiene H5, owner decision): an unknown strategy id is an error, and a requested backend is never substituted (AGENTS.md rule 8). A route must expose the backend actually used. Unavailable optional solvers do not justify reporting their execution.

**Status of the strategy set (hygiene H13).** Product reasoning is the oracle route: `reference` answers every question the chat and the API ask until the rule-based StrategyRouter v1 (Routing rules, below) passes its preregistered test. The other strategies under `reasoning/strategies/` (`prolog-tabling`, `z3-smt-bounded`, `asp-clingo`, `closure-template`, `conform`, `datalog-e10`, `datalog-souffle`, `dreaming-session`, `golog-swi`, `htn-strips-planner`, `llm-agent`, `modes`, `sql-sqlite`, `vrc-compressed-planning`, `worlds-sopr` and the stopped programming `code-sandbox`) are the **comparison set**: they are exercised by the shadow gate of `eval/smoke-reasoning/` (each must agree with the oracle on status, rows, counts and explanations) and by their own tests, and are selectable only by an explicit request. They are research and evaluation, not product routes, and no page describes them as part of the chat chain.

### Evidence, alternatives, and unsupported cases

Only admitted facts/observations and applicable reviewed rules support ordinary deduction. A hypothesis, pattern, trace, plan, analogy, or satisfiable constraint is not automatically an observed fact or proven conclusion. Abduction proposes explanations; diagnosis proposes discriminating tests; bounded induction and analogy retain candidate status; planning and what-if simulation do not mutate historical facts. Unsupported dialects and mixed constraints needing an explicit stage are reported rather than silently dropping requirements. Retrieval cutoff or incomplete search must remain visible in the result, especially before uniqueness, negation, or count claims. A solver route proves only a consequence of its admitted facts and declared search domain, not the ground truth of those facts.

### Evidence for comparison

Run fixed SOP and fixed approved facts when comparing reasoners; change only the selected reasoning route and record actual execution, answer, proof, cutoff, latency, and unavailable routes. Compare Horn-common semantics with SWI and supported constraint semantics with Z3 separately. This requirement does not assert the external binaries are installed or that every reasoning operation is supported by both.

### Assumption defeat across routes

Assumption handling is part of the shared Horn profile, not a route-specific extra: the reference route and the Prolog route both admit a declared assumption only while no admitted fact supports the explicit contrary atom (`reasoning/bridge/reason.mjs:admissibleAssumptions`), and both keep the same answer, proof and `hypothetical` marker for the same inputs. The Prolog route therefore filters defeated assumptions with the same rule before lowering to `prolog-tabling`, and its agreement check still guards backend divergence. A result that touches a kept assumption stays conditional; the reasoner never promotes it to an unconditioned support, and no fallback route may restore a defeated assumption. Defeat is atom-level and evidence-scoped: an assumption about one atom does not suppress derivations of unrelated atoms, and the reasoner reports the defeated assumption identifiers for audit instead of silently discarding them.

Historical setup record (2026-09, not a current run): on the prepared ARM64 host, private Z3 4.15.8 and SWI-Prolog 9.0.4 executables were acquired with pinned package/release hashes and licenses under ignored `tools/.solvers/`; no system package installation or global PATH change was made. Select them explicitly with `Z3_BIN` and `SWIPL_BIN`. `tools/check-solvers.mjs` and optional conformance checks honor those same variables. SWI's private extraction additionally requires the distribution's autoload-index bootstrap, recorded in its manifest.

Historical observation (2026-09; current solver results belong in `eval/reports/current/`): bounded probes observed JS and Z3 both derive the unique numeric output 840 with no fallback, and JS and SWI both retain conditional support under an explicit hypothesis. The latter reproduced and fixed an adapter bug: merging assumptions into SWI's input facts had erased the returned `hypothetical` marker. SWI computes its closure, while the adapter checks closure agreement and reconstructs proof with JS; report that composed cost and do not claim an independent SWI proof. These probes are not a broad solver benchmark or model evaluation.

Every rational packet reports `depth`: the number of rule applications in the minimal justification of the facts the answer actually used. A directly supplied or observed fact counts as `0`, one chained rule as `1`, and so on; when nothing is used the value is `0`. It is computed over the proof dependency graph (derived entries list their supporting ids in `from`) in `reasoning/bridge/reason.mjs` from the oracle's derivation, so Prolog-backed results inherit the same value (their proof is the oracle's), and it lets a caller state an expected derivation depth independently of the answer text.

## Strategy × backend matrix

A reasoning **strategy** chooses how an admitted problem is solved; a **backend** is the engine actually executed; `memory.engine` stores evidence and `policy.retrievalStrategy` searches it. These are separate selections. The actual route (`operation`, `backend`, `fallback`) and `reasoningStrategy` accompany ordinary results. On a trusted SOP `reason`/`solve` wire, an explicit non-JS `backend` selects the external strategy of that backend (`prolog-tabling`, `z3-smt-bounded`) when the wire has no explicit `reasoning` override. Explicit `reasoning reference` rejects an external backend, and an explicit external backend is never silently replaced with JS. The matrix records only the supported capabilities in `reasoning/registry.mjs`, `reasoning/bridge/solve.mjs` and `reasoning/bridge/external.mjs`; it does not claim universal logical coverage or installed optional binaries.

Numeric and Horn tests do not establish coverage for unadmitted extensions.

### The distinct `hybrid` settings

`memory.engine: hybrid` creates one physical fact bank: exact SQLite evidence plus RecallMemory or HoloMemory associative hints (`memory.hybrid.associative`; [DS020](specsLoader.html?spec=DS020-hybrid-memory.md)). Its exact answers cannot be erased by a failed hint. `policy.retrievalStrategy: hybrid` is a **search policy** over the available repository view: it first seeks exact coverage when an exact representation exists, and may consult the remaining approximate route after an incomplete exact search; without an exact representation it requests the automatic route. Neither setting chooses a reasoning solver. Other retrieval choices (`auto`, `exact`, `recall-memory`, `holo-memory`, `sqlite`, `scan`) are independent of the reasoning strategy (`reference` and the others); a storage-specific route requires a compatible stored representation rather than renaming the policy. This distinction does not imply that every memory engine can satisfy every retrieval profile.

### Read effects and reinforcement boundary

Calling `ReasoningRegistry.run` is a pure calculation over supplied facts and never reinforces observed facts. A host `link`/`recall` read or a candidate retrieval hit alone does not promote evidence. The trusted runtime's `reason` execution **may** reinforce a previously admitted, metadata-verified **observed** fact only when it occurs in a real, non-hypothetical proof/refutation, is nonlocal, `policy.reinforce !== false`, and the memory retention configuration permits promotion on use (`retention.reinforceOnUse`). The repository validates provenance and tuple identity before recording it. When promotion occurs the returned result includes `reinforcement: {facts, strength}`; no result with that effect may be described as an entirely side-effect-free read. Set `policy.reinforce: false` for read-only comparisons, alongside a fixed memory snapshot; hypothetical proofs, mere retrieval, local facts, candidate patterns and unsupported outcomes do not themselves reinforce. The capability declaration for the trusted `reason` wire is `may-reinforce-nonhypothetical-observed-proof` in `tools/capabilities.mjs`. Explicit `remember`, not `reason` or model-authored SOP, records new user facts. `solve` of a query expands to `link` and `reason` and therefore follows the same proof-use boundary; numeric `solve` does not use the observed-proof branch.

## Result projection

### Result packet and capability boundaries

The chat turn adds `parse` to its packet: which model of the chain wrote the circuit, the models tried, rounds, time and cost (DS022 "The query author in the chat turn"). The strategy and the router never see the parser: the circuit is executed and verified the same way whoever wrote it.

**Author self-check (archived).** The optional answer-shape self-check round belonged to the one-shot author LLMDirect and is archived with it (`probably_obsolete/one-shot-formalization/`, 2026-10-02); engine verification is unchanged.

`sop/runtime.mjs` produces a result packet; the evaluation harnesses read `result.packet ?? result`; `eval/contracts.mjs:epistemicResult` projects `status` into the result vocabulary while retaining `runtime_status`, `complete`, `hypothetical` and `guarantee`. Two explicit opposite `fact` wires produce runtime `both` and projected `CONFLICT`, and `complete:false`, `hypothetical:true`, `guarantee:'bounded'` survive a conflicting packet (test “result projection retains contradiction…”).

**One packet (owner decision of 2026-10-01).** The operations `abduce`, `diagnose`, `plan`, `simulate`, `associate`, `induce` and `analogize` answer in the packet of the oracle (proposal 5.3; `reasoning/bridge/packet.mjs`): `status`, `complete`, `guarantee` (`exact`, `bounded`, `approximate`), `budget {limit, used, exhausted, reason, partial}`, `used` (one sufficient support set of `{id, version}`), `proof` where the answer has one, `notes`, `ignored`, `strategy`, and the operation's own field named as in the oracle: `hypotheses` and `explanations` (`{hypotheses: [ids], atoms: [texts], cost}`) with `candidate_count`, `rejected` and `generator`; `tests` (`{query, separated_pairs, predictions}`) and `next_test`; `plan` (`{steps, cost, names, sequence: [{action, args, binding, adds, removes, cost}]}`); `whatif` (`{mode, intervention, factual_status, source_memory_modified}`) next to the relational answer; and `candidates`, `patterns`, `mappings` with status `approximate` (a learned or bounded answer without a guarantee, never a negative one). No operation packet carries an `epistemic` or `search` field, and there is no second packet constructor. A cut is `budget_exhausted` with a `reason` (`rounds probes horizon depth domain wall cancelled numeric_range` and, per operation, `hypotheses`, `candidates`, `nodes`, `facts`); a request the oracle cannot express is `not_expressible` with `features`. The relational answer of `deduce`, `temporal`, `classify` and `simulate` keeps the host projection of the oracle's rows (`answers` with validity, `proof` as typed facts with their rule and premises, `conflictedAnswers`), because the chat, the CNL (`sop/cnl.mjs`) and the execution signature (`probably_obsolete/tinyLLMExperiments/eval/signature.mjs`) read those; `rows`, `used` and the proof DAG are the oracle's own view of the same evidence. A missing runtime `status` throws; an unrecognized runtime status projects to `UNSUPPORTED`, never an invented hard entailment (test “executable decision rows…”). `complete:null` means the packet did not report completeness, **not** that a search is complete.

Reasoning and memory capabilities are declared in `reasoning/registry.mjs:CAPABILITIES`, `ReasoningRegistry.run`, `memory/repository.mjs:Repository.apply/commit` and `tools/capabilities.mjs` (exports `memoryEngines`, `reasoning`, `wires`). `reference.deduce` declares `finite-function-free-Horn`; the available memory engines are `recall-memory`, `holo-memory`, `sqlite`, `scan` and `hybrid` ([DS005](specsLoader.html?spec=DS005-memory.md)); `remember` is the recording wire. A trusted `fact` plus `remember input $f` returns `stored`, increments the session revision, and a subsequent `solve` reads the claim. `remember input $h` cannot store an unreviewed `hypothesis` and does not advance the revision. An uncompiled `theory dialect arbitrary` returns `unsupported` with `code:'unsupported_theory'`; neither memory selection nor a theory body silently makes it executable (test “memory and reasoning capabilities…”). `Repository.commit` is separate from session `remember`; neither a model `stated`/`assumed` proposition nor a proposed `pattern`/`hypothesis` becomes a published fact. These executable cases check the concrete admission and effect boundaries, not external-source truth or review quality.

### Executable decision table

`eval/contracts.mjs:STATUS_DECISIONS` is the executable table below. Every literal row is exercised by the table-driven assertion in “executable decision rows…”; the rows marked **runtime** additionally come from actual `Runtime.run` executions there or in the cited boundary test. The projection is not a new proof engine. The archived vision documents under `probably_obsolete/vision/` named `ENTAILED`, `CONTRADICTED`, `UNKNOWN`, `PLAUSIBLE`; `CONFLICT`, `POSSIBLE`, `UNSUPPORTED`, `AMBIGUOUS`, `BLOCKED` and operation receipts preserve distinctions the runtime already exposes.

**Precedence and qualification:** An explicit `both`, `inconsistent` or nonempty `conflictedAnswers` projects to `CONFLICT` before conditionality. Otherwise a `supported` or `entailed` packet with `hypothetical:true` projects to `PLAUSIBLE`; only then does the literal table apply. `complete:false` and `epistemic` remain separate fields and cannot be erased by a positive status. The result-boundary test executes the combined contradiction/hypothesis/incompleteness packet. `complete:null` is an unreported field, not a success. `runtime_status` always carries the original runtime status, including unsupported extensions.

#### DEFAULT with an exception and no-support control

There is **no general DEFAULT wire or default-rule compiler** in `SPEC`/`ReasoningRegistry`. The exercised limited case is a model `stated` proposition with `certainty hedged` ("Normally Ana likes this book"), lowered to a `fact … source assumption` consumed through `assume`: while uncontested, `Runtime` reports `supported`, `hypothetical:true`, projected `PLAUSIBLE`. If an explicit, session-recorded `not likes ana book` is visible at the same knowledge cutoff, the assumption is listed under `defeatedAssumptions`, and the result is `refuted`/`CONTRADICTED`; the assumption is not a second stored claim. With neither assumption nor supporting record, the same query is `unknown`/`UNKNOWN`. These three executions are in “DEFAULT proposal with explicit exception…”. A requested `theory dialect defeasible-default` returns `unsupported`/`UNSUPPORTED` rather than pretending that this narrow assumption rule implements arbitrary unordered defaults. No candidate rule is silently promoted to HARD.

## Controller algorithm contracts

The operations run over the oracle: `abduce`, `diagnose` and `plan` lower the typed facts, rules, hypotheses, actions and goal to knowledge wires (`reasoning/bridge/operations.mjs`) and ask the oracle's `abduce` and `plan` queries, `simulate` closes and reads the intervened world with the oracle (`reasoning/bridge/closure.mjs`: `closure` is the oracle's closure of typed facts, `evaluate` its reading of a typed query), and `associate`, `induce` and `analogize` score supplied traces (`reasoning/learning.mjs`; `lib/unify.mjs` is the one matcher). They share the oracle's budget (`js-reference/budget.mjs`; the runtime asks for `reasoning/bridge/packet.mjs:OPERATION_LIMITS`, never above the oracle's ceilings): `maxNodes`, `maxDepth`, `maxHypotheses` (the number of candidate hypotheses; more is `budget_exhausted`, never a shortened search), `maxCandidates` (each subset tried by abduction), `maxPlans`, `maxRounds`, `maxFacts`, `maxJoins`, `maxAssignments` and `timeoutMs` (reason `wall`). The budgets are cooperative checks, not preemption; an endpoint that accepts untrusted input must run the engine in a worker or process with its own time and memory limits. What the oracle does not decide is host work before the question and is reported in the packet: the observed target is removed from the premises, a candidate that repeats the target or contradicts an observed fact is `rejected`, missing-condition candidates are generated from the retrieved rules (`reasoning/abducibles.mjs`) and actions not valid at the instant asked are `ignored`.

- **Abduction** removes the observed target from the premises before searching, so "true because observed" is never an explanation. Hypotheses are explicit ground candidates built from constants already present; no new entity or cause is invented. Cost-ordered subsets are validated by Horn closure and only inclusion-minimal consistent explanations are kept. Cost is a search preference, not a probability, and depth or candidate limits propagate to `complete`. Nothing is asserted.
- **Diagnosis** ranks supplied ground test queries by how many explanation pairs each separates, a deterministic heuristic rather than Bayesian information gain. A simulated `unknown` outcome is not a measurement, and the runtime never executes a test.
- **Induction** reports opportunities, support, counterexamples, unknowns and conflicts separately over supplied traces; a missing consequent counts as a counterexample only in a trace marked `closed`. A pattern with high support is never a universal rule and is never published automatically ([DS013](specsLoader.html?spec=DS013-skill-systems.md)).
- **Association** ranks supplied traces lexically, relationally or by RecallMemory projection ([DS016](specsLoader.html?spec=DS016-recall-memory.md)); every score is a retrieval hint.
- **Analogy** uses injective constant mappings; transferred properties stay hypotheses.
- **Planning** is uniform-cost search over finite, polarity-explicit states; derived consequences are recomputed rather than copied, reaching the declared goal is reported separately from exhausting the search, and a plan is never executed. Repository retrieval treats goal atoms, action prerequisites and selected rule-body atoms as independent demands, preserving premises needed after a future state transition. An incomplete or inexact retrieved action model cannot support a definite `no_plan`; it reports `budget_exhausted`, `reason: partial_retrieval`.
- **Simulation** changes an isolated copy of the state (`whatif.source_memory_modified: false`). Counterfactual mode requires a rule module in which every rule is marked causal; otherwise it returns `not_expressible` with `reason causal_model_required`, because correlations are not interventions.
- **Optimization** reports `optimal` only for a completed search; an interrupted search gives `feasible_bound`, and several distinct optima leave an output port ambiguous.

### Extension and omission contract

`ReasoningRegistry.register(name, handler)` accepts trusted host code, never a sandbox for model-emitted code. A handler returns at least `status` and `complete` in the packet above, and also states its guarantee, proof or evidence, the actual route and the reason for any unsupported or incomplete result; semantic correctness is established by differential tests against the reference route. An interpreter may list exploration objects it did not use (a pattern, hypothesis or recomputed derived fact) under `ignored`, but never uses them as premises, and it never drops a negation, interval, source, output cardinality, hypothetical status or required theory in order to produce an answer: a required but unknown theory yields `unsupported`.

### The js-reference oracle

`reasoning/strategies/js-reference/` is the oracle and, since 2026-10-01, the `reference` route of the runtime (through `reasoning/bridge/`; the smoke harness `eval/smoke-reasoning/` column is `js-oracle`, `tests/reasoning/js-oracle.test.mjs` and `tests/reasoning/reasoning-bridge.test.mjs` pin it). It is the oracle of the strategies below: a deliberately naive, auditable implementation of the whole proposed core that every other strategy is shadow-checked against. It consumes the knowledge and query circuits as text, parsed, governed and desugared by `sop/knowledge/` (the single grammar source; `reasoning/strategies/js-reference/parse.mjs` re-exports it for the strategies) and implements: facts with status, speaker and validity; paraconsistent four-valued evidence (positive and negative evidence propagate independently, `both` is only a reported status); rules with atom, `not`, `absent` (negation as failure over a closed predicate, stratified, checked), `compare`, `compute`, `order`, `start_of`/`end_of` and `all`/`any` groups; arity 0 to 6; `aggregate`; `count` and `every` with the closed and complete-view rules (a count over an open predicate is a lower bound, `bound: at_least`; an `every` over an open domain is `unknown` with reason `open_domain`); `default` (exception, `priority`, `overrides`, strict contrary, blocking by fire) and `integrity` through the desugarer (a violation relation, never a hard assertion); finite-domain `constraint` by enumeration; `action`/`goal` planning (bounded uniform-cost search over polarity-explicit states); `abduce` (all inclusion-minimal explanations, over `hypothesis` wires or over the query's `candidate` lines with `necessary`); `effect` (each candidate classified against a ground claim, Q-LANG-10); `why_not` (minimal additions of base atoms plus blockers); snapshot time (`at`, `during` = throughout, `overlaps`, derived atoms by endpoint partitioning); `conditional` per row, verified by a second run, with the `nonmonotone` and `conditional_unknown` flags; `used` as one sufficient support set (`used_incomplete` when it rests on negation as failure) and the proof DAG; and honest budgets (`budget_exhausted` with a `reason`, a partial positive answer only for programs without negation as failure or aggregates, never a weakened negative). The packet also carries `sensitivity`, judged on the desugared program: the predicates a partial retrieval must hold completely for the answer to be valid, and the defaults involved. The strategy declares modes of work (`method`, `norm`, `procedure`, `amendment`, `conform`) not expressible and throws `NotExpressibleError` for a circuit that needs them; its `conform` capability is the lowering of `reasoning/strategies/conform/` (a trace with its norms and methods becomes core rules the oracle answers), which the smoke column `js-oracle` includes since the former column `conform-core` was merged into it. A request that names no strategy stays on the oracle; whether and how requests are routed to other strategies is stated in "Routing rules" below.

**Query forms of the host language.** The value-level fields of a `query` wire run in the oracle (`js-reference/forms.mjs`), ported from the retired reasoner with its decision semantics: `compare` (`LEFT WORD RIGHT` lines or an `all`/`any` block; a value is a number when it is one or a string that starts with one, `"2380 lei"`; an ordering over a non-number is `not_computable`, reason `value_not_numeric`; a yes/no question whose known values all fail a comparison is `refuted`), `except ?v VALUE`, `filter` (a typed host expression, trusted circuits only), `rank highest|lowest ?v` (ties stay), `limit` (`truncated`, never `count`), and `quantifier all|none|not_all|most|half|at_least N` for `mode every`. With a `quantifier` the universal ranges over the KNOWN members of the restriction, each supported, refuted or unknown, grouped by `select`, and the packet carries `members`, `counterexamples` and `undecided` with reason `known_members` (no open-domain `unknown`: that is the host question language, DS014 Q-LANG-2); without it `every` is the strict closed-domain universal of the proposal, and with `select` it is decided per group of the selected variables ("Which teams have only certified players?": the answers are the groups where the universal holds, closed and open rules per group; feature `every_grouped`, smoke case 90; the other strategies do not declare it yet and report it `not_expressible`). `order`, `measure` and the time-valued variables are not run by the oracle: the bridge cuts an interval question at the validity boundaries of the facts and rules it depends on, asks once per part, takes the validity of an answer from the facts it used, binds a time variable to that interval (its start, end or length in days under `measure`) and compares the starts of two conditions for `order`; a claim and its negation are `both` when they hold in the same part and `mixed_temporal` when only in different parts. Reading a result is not counted against the probe ceilings (the closure is), but the wall clock stops it: `budget_exhausted`, reason `wall`. `closeFacts` (the closure with its derivations, with `blocked` conclusions for counterfactual interventions) and the `detail`, `forms` and `queryWires` problem fields are the primitives the bridge uses; `conditional: false` skips the per-row verification runs of a host that reports assumptions itself.

**Query absence.** The typed runtime bridge preserves a query atom's `absent` mode separately from explicit negative evidence and carries reviewed closed declarations to the oracle. A closed predicate's missing positive tuple supports absence; a present positive tuple refutes it. An open predicate cannot establish absence and is rejected (`absent_needs_closed`), without adding a negative fact or mutating memory.

### Condition admission before closed-world conclusions

`askMemory` checks query conditions in both `where` and `scope`, including grouped alternatives, before slice execution. Positional atoms must have the predicate declaration's arity; an arity mismatch is `arity_mismatch`, not a negative answer. Named query matches retain DS014's omitted-role semantics: missing declared roles become existential variables, whereas an undeclared role is an admission error.

For a closed, directly stored relation, a constant in an entity position needs occurrence in that position or compatible lexicon-class evidence. The condition guard uses exact indexed single-position lookups in the caller's visible repository, including both fact polarities and supplied turn-local facts. Position typing uses the knowledge cutoff but not the query's validity window: being absent at an earlier time is not a type error. A bounded predicate sample provides observed values; only a complete sample establishes class exclusion. Integer/value positions use their declared types rather than an enumeration of observed numeric values. A relation defined by rules or aggregates takes its domain from that definition, not an empty direct-fact sample. Open membership is not an exhaustive position domain.

For a specifically declared class, an admitted turn-local fact in the same predicate and argument position supplies typing for a conversational entity without informative class metadata. This does not override a known incompatible class, promote the local evidence or add it to base memory.

Absence ranges over the declared entity universe, not only positive members. A registered generic entity satisfies an `entity` absence position when no narrower class is known; incompatible known classes and primitive-type mismatches are still misuse. This preserves genuine closed-world absence for known entities never positively listed. No class is inferred from an identifier's spelling.

A detected misuse returns `unknown`, `reason: condition_misuse`, empty rows and evidence, and `misuses`: the condition, predicate, one-based position, role, offending value, reason and bounded observed `values` with `values_complete`. A completed misuse decision is `complete: true`; an exhausted domain check is `complete: false` with detail `domain_check_incomplete`. `condition_guard` reports lookup/probe counts and incomplete samples. Checks are capped at 128 lookups, 2,048 probes and 16 returned examples per lookup, tightened by smaller caller lookup/probe limits. A partial sample never proves absence of a class. Well-typed missing tuples on a closed predicate still yield `refuted`; well-typed absence retains its existing supported/refuted semantics. Candidate typing lookups never promote facts or write memory.

The consumer regressions are `tests/formalizer/query-author-condition-misuse.test.mjs`: exact saved department-total circuits, real SQLite execution, legitimate negatives and absence, sparse class evidence, numeric types, local conditional evidence, bounds and author repair without answer-shape preview.


## Strategies

A **strategy** is an independently selectable way of answering a question over the knowledge wires of [DS004](specsLoader.html?spec=DS004-sop.md). The knowledge wires are standardized once: every strategy reads the same parsed, governed and desugared program (`sop/knowledge/`), and each lowers it to its own engine (a nested-loop evaluator, tabled Prolog, SMT, Datalog, SQL, ASP, a planner). A strategy declares what it supports; a question that needs more is `not_expressible`, never silently weakened. The strategies live in `reasoning/strategies/<id>/`, the oracle is `reasoning/strategies/js-reference/`, and the smoke harness `eval/smoke-reasoning/` runs them side by side ([DS010](specsLoader.html?spec=DS010-engine-and-solver-comparison.md)). `reference` (alias of `js-reference`) and the deprecated `advanced` route above are the runtime's names for the oracle and for the oracle with external backends.

**Pruned on 2026-10-01** (owner decisions in chat): the old `js-reference` route (the retired reasoner), `prolog-swi` (the old SWI adapter, superseded by `prolog-tabling`: 82 against 35 smoke passes) and `z3-lia` (the old Z3 adapter, superseded by `z3-smt-bounded`, which passes cases 06a to 06c and 60, and by its typed-constraint module for unbounded integers) were removed, with the `neural-assist` stub (no evidence for it). `datalog-soplab` is demoted to a reference engine under `eval/reference-engines/` (a second independent implementation for the differential tests; not a routing candidate, `--with-reference-engines` adds its column), `golog-swi` is FROZEN (code and tests kept, `--with-frozen`; it overlaps `htn-strips-planner` and `conform`) and `conform-core` is merged into the `js-oracle` column. The default smoke columns are `js-oracle`, `prolog-tabling`, `datalog-e10`, `datalog-souffle`, `asp-clingo`, `sql-sqlite`, `z3-smt-bounded`, `htn-strips-planner`, `vrc-compressed-planning`, `worlds-sopr`, `closure-template`, `dreaming-session` and the two `llm-agent` baselines.

### The strategy interface

A strategy is `{id, capabilities, available(), ask(program, query, options)}` with the optional calls `prepare`, `update`, `check` and `dream`. `capabilities` declares, beyond the feature list, the dimensions a router needs to choose between two strategies that support the same features:

| Dimension | Values | Why |
| --- | --- | --- |
| `features` | the words of the smoke cases' `requires` list: `facts select open_world classical_negation conflict rules recursion conjunction exists every count explain used why_not temporal interval throughout snapshot_derived time_vars whatif epistemic_status naf closed_world closed_derived compare_in_rules compute_in_rules aggregate default overrides strict_contrary versions integrity constraint optimize plan blocked_info method htn_choice on_failure norms_hard norms_soft temporal_norms procedures procedure_render amendment check_plan abduce abduce_waive zero_arity budget budget_probes retrieval` | a circuit that needs a feature the strategy lacks is `not_expressible` |
| `delivery` | `slice`, `source`, `both` | a slice engine needs the retrieved wires materialised; a source engine pulls from a fact source |
| `max_wires`, `max_arity`, `integer_range` | numbers | a slice larger than the engine's input limit is split or refused before the call |
| `guarantee` | `exact`, `bounded`, `approximate` | a bounded engine (horizon, depth, domain) can only say `budget_exhausted`, never a negative answer |
| `provides` | `explain`, `used`, `proof`, `why_not_predicates` | which parts of the packet the strategy fills itself; the host computes `used` and `conditional` for the rest |
| `determinism` | `deterministic`, `seeded` | the shadow comparison needs a fixed seed for the latter |
| `isolation` | yes, no | the strategy can run in a worker with wall and heap limits; its stop maps to `budget_exhausted` with reason `wall` |

Profiles are shorthand for feature sets: P0 Datalog core (facts, rules, recursion, select, exists, count), P1 adds classical negation, conflict, open world, every, explain, whatif, temporal, interval, P2 adds naf, closed_world, closed_derived, compare_in_rules, compute_in_rules, aggregate, default, overrides, strict_contrary, integrity, versions, P3 adds constraint, optimize, P4 adds plan, method, abduce, why_not, blocked_info, P5 adds the modes of work (htn_choice, on_failure, norms_hard, norms_soft, temporal_norms, procedures, procedure_render, amendment, check_plan, abduce_waive). A strategy may support any subset.

The calls: `prepare(theory, options)` returns a handle (indexing, compilation, "dreaming"; it may run offline, must not change answers and reports its own cost); `ask(problem, budget)` returns a result packet; `check(plan, theory)` evaluates a given plan or trace against the procedures and norms in force (the interface of `mode conform`); `update(handle, delta)` is incremental maintenance (additions are monotone and recompute what depends on a count, an aggregate, an `absent` or a plan; a retraction under negation as failure needs delete and re-derive or invalidation; `update` returns `stale` rather than a wrong handle); `dream(journal, budget)` is offline consolidation. The theory of `ask` is a materialised slice (a structured object, not re-parsed text) or a fact source the strategy pulls from (`lookup`, `rulesFor` with `complete`, `count`, `closed`). A simple engine implements only `ask`. Preparation never writes knowledge, and a read never hides a write ([DS005](specsLoader.html?spec=DS005-memory.md)).

### The result packet

```
{status, complete, bound?, conditional?: [ids], nonmonotone?, conditional_unknown?,
 rows?: [{..., conditional?: [ids], conditional_unknown?}], count?, witness?, objective?, plan?, hypotheses?, explain?, missing?,
 effects?: [{candidate, kind, baseline, with, effect, used, contradicts?}], necessary?: [ids],
 used: [{id, version}], used_incomplete?, proof?: DAG,
 compliance?: {hard, violated?, soft_violations?, deviations?, total_cost}, blocked_by?, blocked?: {step, requirement, norm},
 choices?, procedure?, relaxed?, contested?: [ids], obligations_triggered?, obligation_unscoped?: [ids], scope_unknown?: bool,
 guarantee: exact|bounded|approximate,
 budget: {limit, used, exhausted, reason, partial},
 retrieval: {complete, truncated, keyed, steps, wires, probes},
 strategy, route: {requested, chosen, reason, fallback: null},
 timings: {load, index, prepare, ask, replay}, ignored: [...], notes: [...]}
```

The statuses are `supported refuted both unknown` (relational), `entailed possible impossible inconsistent optimal feasible_bound` (numeric), `plan_found no_plan blocked` (planning), `compliant non_compliant` (conformance), `procedure_found`, `hypotheses`, `budget_exhausted`, and the preparation outcomes `approximate` (a bounded or learned answer without a guarantee), `stale` (a prepared artefact no longer matches the theory) and `no_model` (no certified encoding; not a negative answer). `not_expressible` and `unavailable` are reported by the router or the harness before a strategy runs; `unsupported` stays reserved for the explicit-backend rule of AGENTS.md. The fields that are not obvious:

- `used` is one sufficient support set ([DS004](specsLoader.html?spec=DS004-sop.md), item 9 of the shared semantics); it is mandatory for a `supported` or `refuted` answer with `complete: true`, because proof-use promotion is per claim.
- `proof` is a minimal DAG for the shadow comparison of explanations: nodes `{id, atom, kind: fact|rule|assumption|default, source, premises, binding}`. The shadow check compares the status of every node, never the shape of the DAG.
- `ignored` lists only the wires outside the query's dependency slice; it never lists an unsupported feature.
- `blocked` keeps the failing step, the unmet requirement and the norm, so that "no plan" is never the only information; `no_plan` is used only when nothing can be named, the search having completed over a closed, fully retrieved problem.
- `bound` is `at_least` for a count over an open predicate; `guarantee` says whether the answer is the semantics of the theory (`exact`), exact within a declared bound (`bounded`) or an estimate that is never used for a negative answer (`approximate`).
- `conditional` is per row and verified (DS004, item 6); the packet-level list is the union of the rows' lists.
- `abduce` and `why_not` explain one state: the facts valid at the query's `at` instant, or all facts without a time. Over `during` or `overlaps` they are `not_expressible` (2026-10-02, capability battery: the oracle and the solver strategies used to ignore the query's time and explained an observation false at that instant). `asp-clingo` refuses `abduce` and `why_not` over decimal numbers, because their closure is not run through the fixed-point rewriting.
- `inconsistent` (mode `abduce`) lists the explaining sets rejected because their closure contradicts an admitted fact: `{hypotheses, atoms, cost, contradicts}`, `contradicts` naming the admitted literal (or, when neither side is admitted, the atom). The oracle tests consistency for every candidate set; `asp-clingo` and `z3-smt-bounded` filter their inclusion-minimal sets with their own closure (exact for programs without negation as failure); `prolog-tabling` does not filter yet.
- `effects` (mode `effect`, Q-LANG-10, owner decision 2026-10-03): the packet is the answer to the ground claim with the query's candidates out of force (the baseline), and one row per `candidate $id`: `{candidate, kind: fact|rule, baseline, with, effect, used, contradicts?}`, `with` the status of the claim with that candidate in force and `effect` one of `establishes` (the claim becomes `supported`), `blocks` (a decided claim becomes `unknown`: a default's exception, a strict contrary, an absence), `contradicts` (it becomes `refuted` or `both`), `no_effect`, `inconsistent` (a supposed fact whose contrary holds with it in force, or a candidate that makes an atom other than the claim hold both ways where the baseline did not; `contradicts` names the literals, and the candidate is not counted). A run cut by its budget gives `effect: null` and the packet `complete: false`. The sensitivity is monotone only when every run is. On the chat path each row adds `described` (the statement's atom, or the rule's conditions and conclusion) for the renderer (`line_effect_*`).
- `necessary` (mode `abduce` over candidates): the candidates present in every explaining set (what an argument assumes). Over candidates `explanations[].hypotheses` are candidate ids, `atoms` the atoms of the candidate facts; the chat path adds `candidates` (described) to each explanation and rejected set.
- Candidates (`candidate $id`, modes `effect` and `abduce`): a supposed fact of the query circuit or a rule or default of the knowledge, in force only in the runs of that query (`selectInForce` includes it like a supposed governed wire, whatever its approval; otherwise it is left out, even when approved). The slice of every run holds everything the candidates reach. A candidate is never an assumption of the answer (no conditional runs over it) and nothing is stored or reinforced from a run. Only the oracle declares the features `effect` and `candidate`; the wire engines refuse them (`not_expressible`, query field `candidate` or mode `effect`), so the battery's L2 records them as honest refusals.
- `rules_used` (chat path, mode `explain`; `lib/query-author/runtime.mjs`): the rules and defaults of `used` with their text, `{id, kind, origin, conditions: [{atom} | {text}], exceptions?, conclusion}`, so the answer names the rules of the derivation and not only its facts (the renderer's `line_rule_used` and `line_default_used` replies).

### Budgets and partial answers

A strategy may stop early; it may never answer as if it had finished. The packet carries `complete` and a `budget` block. A claim that depends on completeness (`unknown`, `refuted` by failure, `no_plan`, a count, `every`, `absent`, an optimum) is `budget_exhausted` when cut off, with a `reason` (`rounds probes horizon depth domain wall cancelled numeric_range`). A positive existential answer found before the cut stays `supported` with `complete: false`, and its rows are a subset of the true rows. A `no_plan`, `unknown` or `refuted` produced because a bound of the engine was hit (a planning horizon, a search depth, a finite domain, a coordinate limit) is not a statement about the theory: it is `budget_exhausted` with `reason horizon`, `depth` or `domain`. A partial count is a lower bound (`bound at_least`). The comparator of the smoke harness fails a result that reads as `unknown`, `refuted`, `no_plan` or `optimal` while incomplete.

The budget keys are `maxNodes maxDepth maxHypotheses maxCandidates maxPlans maxRounds maxFacts maxJoins maxAssignments maxFanout timeoutMs`; each strategy declares which it honours, and a budget only tightens the host's ceilings. The host maps the message to `effort quick|normal|deep`, which scales the budget between host floors and ceilings; the model never sets a budget. `partial forbid` means no partial answer: give up cleanly. A subprocess strategy runs under a timeout and maps it to `budget_exhausted` with reason `wall`.

### The shadow gate

A strategy is accepted by running it in shadow next to the oracle `js-reference` on the smoke and targeted suites. The entry condition is zero disagreements on exactly decided cases, on status, rows and counts. **`used` is checked by replay, not by equality**: the comparator takes the strategy's `used` (unless `used_incomplete`), runs the oracle on those claims alone and requires the same status and rows, so two strategies that prove an answer through different sufficient sets both pass and a `used` that does not re-derive the answer fails. The native closure template of the router produces answers, so it passes the same gate before a router rule may use it. The shadow comparison also runs on metamorphic variants (renaming, permutation, irrelevant facts) and, separately, on the host linking: a paraphrase of the same question must link to the same circuit.

An accepted learned or prepared artefact (a dreamed plan, a skill, an advisory hint) is re-certified on load, replays its positive witnesses in the original rules, runs in shadow against the oracle on small tasks, and is revoked on any disagreement; a learned part may only choose among legal plans and never decides an answer.

### Routing rules

An explicitly requested strategy or backend is never substituted (AGENTS.md rule 8): an unavailable one returns `unsupported` naming it with `fallback: null`. Routing runs only when the caller asks for it (`reasoning auto`, or a default of `auto` for requests that name no strategy), and the choice and its reason are always reported: `route: {requested: "auto", chosen, rule, reason, features, alternatives, fallback: null, verification}`. `policy.reasoningStrategy` takes strategy ids and `auto`; `reference` is an alias of `js-reference` (as is `js-oracle`); the former `advanced` route was removed (see the Strategy contract).

**StrategyRouter v1** (`reasoning/router/`, preregistered as `router-v1`) is rule-based. It chooses by the features of the circuit, read from the same compiled program the engines read (`features.mjs`: facts and rules of the dependency slice of the query, recursion, nonlinear recursion, negation as failure, aggregates, defaults, integrity, `count`/`every`, time, modes of work, a caller budget), and by the size of the memory slice. The rules, in order, each reported as `route.rule`:

1. `proof_or_mode_of_work`: `explain`, `why_not`, `plan`, `abduce`, `effect`, a query with `candidate` lines, constraints, norms, methods and procedures stay on the oracle, which supplies their proof and modes of work. On the product path a model `query` in mode `explain`, `why_not`, `abduce` or `effect` (`PRODUCT_REASONING_MODES` in `sop/enums.mjs` for the last three) runs through `askMemory` and this rule to the oracle (`effect` and `abduce` over candidates: Q-LANG-10, the candidates and the session rules an `if` supposes reach the oracle as `candidate`/`if` lines, the session rules as `approval proposed` wires that are never stored); `why_not` answers the minimal sets of missing base facts (`missing`) and the `blockers`, `abduce` the minimal consistent explanations over the memory's `hypothesis` wires (the model does not write hypotheses; a statement of the observation itself is removed from the premises, since an observation is never its own explanation). A model query in `plan`, `conform` or `procedure` needs actions, traces or procedures the model does not write and stays `not_computable`. An explicitly requested engine that does not express the mode answers `unsupported/not_expressible`, never the oracle's answer. Value forms do not force this route: `compare`, `rank`, `except`, `filter` and `limit` are evaluated by the oracle's row evaluator after a qualified SQLite engine computes the closure and joins. `quantifier` still requires the oracle; interval `order` and `measure` belong to the typed temporal bridge and remain explicitly unsupported by wire engines, including the wire-level oracle. `caller_budget`: an execution budget (a `policy` wire or `budget` argument) stays on the oracle, which defines partial answers; an independent `verifyBudget` never affects routing.
2. `small`: fewer facts than the threshold of the circuit class stay on the oracle (exact, with provenance, no process start). The thresholds `small_facts` are `nonlinear` 100, `recursion` 300 and `other` 10,000 facts, set from the measured table of DS010 (the oracle exhausts its budget on a transitive closure of about 1,000 facts and on a dense nonlinear closure of 300 edges, and matches the engines on joins, negation and aggregates up to about 10^4).
3. `scale`: the first installed engine of the class order that expresses the circuit. Linear recursion goes to `sql-sqlite` (a recursive CTE, demand-driven by the bound argument), then `datalog-souffle`, then `asp-clingo`; everything else bulk (nonlinear recursion, joins, negation, aggregates) goes to `datalog-souffle`, then `sql-sqlite` (which also expresses time and any size), then `asp-clingo` (inside its limit of 5,000 wires). An engine is eligible only when it declares every required feature and none in its `notExpressible`, carries the exact decimals of the circuit (a circuit that needs `exact_arithmetic` must have a fixed-point scale that the engine can hold: the plan `features.fixed_point` of `solver-common/fixed-point.mjs`, scale at most 12 and the largest scaled constant inside the engine's integer range; `route.alternatives` gives the reason), is installed, and has passed the shadow gate (zero disagreements with the oracle on the smoke cases it expresses; observed 2026-10-01 for the three). `route.alternatives` lists every engine considered with the reason it was or was not eligible.
4. `oracle`: nothing eligible and installed, or the circuit does not compile: the oracle answers (or reports its budget honestly). An engine that throws `not_expressible` for an `auto` question, or answers `budget_exhausted` with `reason numeric_range` (a scaled value or a sum left its 32-bit or 64-bit integer range), falls back to the oracle and says so in `route.reason`: the caller named no engine, so this is routing and not substitution. A circuit even the oracle cannot express is `unsupported/not_expressible` with the missing features.

The oracle stays the verifier, replaying the original problem, not engine-produced facts. A routed answer is checked always up to `verify.always_facts` (20,000) facts, otherwise by deterministic sampling (`verify.sample`, 1 of 8 by question digest). `verify` is `auto`, `always`, `never` or `offline`; the last records `checked: false, outcome: deferred` for a later report pass. `routedAsk` and `askMemory` accept `verifyBudget` independently of execution `budget`, overriding verification configuration only. `verifyPacket({handle, query, packet, verifyBudget})` replays a saved answer without rerunning the engine; reports must retain the original admitted problem with the answer. Trusted replay has ceilings of 120 seconds, 200 million join probes, 2 million derived facts, 2 million fanout and 10,000 rounds; ordinary asks retain their ordinary ceilings, and policy wires still tighten either profile. Online verification defaults remain the ordinary profile with the router's 3-second / 3-million-probe limit. `route.verification` reports `checked`, `outcome` (`agreed`, `discrepancy`, `unverified`, `deferred`), milliseconds and actual oracle `budget`. A budget stop never certifies an answer. Packet comparison includes status, completeness, rows, count, count bound and truncation. On an automatic-route discrepancy the oracle answer is returned with `route.rule: discrepancy`; on an explicit-route discrepancy return `unsupported/verification_discrepancy` naming the requested backend with `fallback: null`, never substitute it.

`tools/eval/engines/router-timing.mjs` isolates each shape × size × engine in a process. `closure-rank` and `closure-count` cover 10^3 through 10^6 supplied facts using depth-two fanout trees whose reachable population grows with the input; ranking retains two top ties among all scored leaves. `negation-complete` supplies a complete declared-closed base and exact output count; `negation-open-count` changes only the output closedness and requires `bound: at_least`. These construction checks do not emulate partial repository retrieval. Reports include actual facts, reachable and candidate cardinalities, correctness, latency, engine choice, count bound and digest agreement with the oracle only where it completes. `--only`, `--engines`, `--sizes` filter cells explicitly; `--quick` omits 10^5 and 10^6; skipped, unsupported, incomplete and timed-out cells are not successes. `--verify-offline` performs deferred replay with `--verify-timeout-ms` (default 120000) separately from the engine latency, records actual verification budget and time, and reports verified correctness only after a successful oracle check.

The wire engines answer a status, rows and a count, so the router serves the knowledge-wire path (`askMemory`, `POST /v1/sessions/{id}/query`, which accepts `reasoning` and `verify`). On the typed path (the runtime `reason` step) every answer carries its proof, its validity intervals and the question forms, which only the oracle produces, so `reasoning auto` there reports the same `route` with `chosen: js-reference` and `rule: proof_or_mode_of_work`; an explicit `backend prolog` or `backend z3` together with `reasoning auto` is honoured through the strategy of that backend. The default for a request that names no strategy stays `reference` on the typed path and `auto` on the knowledge-wire path. A portfolio under a shared budget and a learned router come later and may only reorder strategies that already passed the capability filter and the shadow agreement; the planner, Golog and ASP routes for strict procedures and norms over a horizon, the native closure template for a transitive closure with a bound argument, and a prepared handle held by a strategy are not part of v1.

### Completeness under partial retrieval

The host retrieves a slice of the memory; a partial slice makes a missing fact look false, so the rules of [DS005](specsLoader.html?spec=DS005-memory.md) apply to every strategy: a positive answer derived without negation as failure, aggregates, counts or universal quantifiers stays valid when more wires are retrieved (it is judged on the desugared program, so a default conclusion is not such an answer); `absent`, an aggregate, `mode count`, `mode every`, `no_plan`, an optimum and any `unknown` or `refuted` obtained by failure are valid only over predicates declared `closed` and fully retrieved for the relevant keys, recursively for derived predicates; default conclusions need retrieval completeness for the keys of the strict contrary and of the exceptions; associative candidates never close a predicate; adaptive forgetting invalidates closedness unless the predicate is pinned or archived; every packet reports `retrieval`. The host, not a strategy, widens a retrieval, so that every strategy gets the same guard. The implementation is `reasoning/slice/` (retrieval from a static demand plan, the guard, the widening loop `answerOverSlice`) behind `linkKnowledge` and the `reason` step of the runtime, and `askMemory` for knowledge-wire query circuits ([DS005](specsLoader.html?spec=DS005-memory.md) "Closedness and completeness for the knowledge wires", Implementation): a count, a universal answer, a ranking or a failure-derived `unknown` over a slice that is not settled is answered `status: incomplete` with `reason: partial_retrieval`, never as a closed-world answer, and every packet reports its `retrieval`. A ranking (`rank highest|lowest ?v`, with `position N` or `top N`: superlatives and ordinals) names the best of all candidates, so it is judged like a count: over a slice that cannot be completed the answer is `incomplete` (`reason partial_retrieval`, the candidates stay visible as `partial_answers`), never the best of the part (the oracle reports `sensitivity.monotone false` for a ranked query; the typed guard withholds it).

A negated claim over a closed predicate (the chat path asks it as `not` or `absent`) that is `refuted` by a proof of the atom itself is the exception: the oracle reports `sensitivity.refutation_monotone` when the program has no negation as failure or closed-world form on the way, and the guard accepts that refutation over an unsettled slice (`R-P1 refutation`, logic book item 91). Query absence is nonmonotone even when all retrieved tuples are exact: later positive evidence can invalidate a missing tuple. A partial or inexact slice therefore withholds absence answers and any count depending on them, including numeric counts and `at_least` bounds; such a count is not a lower bound on the completed result.

### The strategies

`js-reference` (the oracle) implements the whole core in a deliberately naive way and declares the modes of work `not_expressible`. The other strategies are added under this heading, each in its own subsection, with the capabilities it declares, what it lowers the knowledge wires to and its known limits.

#### vrc-compressed-planning, worlds-sopr, dreaming-session and the closure template

Four components from the VRC and sop-r experiments, each in its own folder under `reasoning/strategies/` with the engine vendored unmodified under `vendor/` (the zips are gitignored). Smoke adapters are in `eval/smoke-reasoning/adapters/`, measurements in `eval/reports/current/<id>/bench.json`.

**`vrc-compressed-planning`** is exact-rational numeric planning with certified state compression. Its circuits are the numeric `action` of extension E2 (`sop/knowledge/numeric-action.mjs`, the one module that defines the syntax): `next VAR EXPR` (one per state variable, identity explicit), `guard EXPR WORD EXPR`, relational flags beside them, numeric state as facts `state ENTITY VAR VALUE` (the `rational` term type: an integer, a decimal or `n/d`), and a plan query with `observe ENTITY EXPR WORD NUMBER` and `horizon`. An EXPR is a polynomial with exact rational constants, parsed as data and never evaluated as code. The search is breadth first over (flags, rational state) with unit cost; a certified encoding E (found by the vendored closure search and re-checked as exact polynomial identities on import) merges states with equal encodings. It declares `plan`, `numeric_action`, `facts`, `zero_arity`, `budget`, `used`; limits: unit cost only (a non-unit cost is rejected, never ignored), ground actions (no parameters), at most 32 state coordinates, no rules, closed flags. A plan is replayed in the original laws before it is returned; a bound of the engine (horizon, node ceiling, rational size, wall clock) is `budget_exhausted` with its reason, never `no_plan`; `no_plan` only when the finite quotient was explored and the frontier emptied. VRC's own "not found within the bound" is therefore `budget_exhausted` here. A certified artifact is bound to a contract hash of the laws, guards and observable (not of the facts or the threshold), so one artifact serves a family of tasks; a changed law makes it `STALE`, a tampered or invalid one `REJECTED`, and the search then runs uncompressed. With `shadow` the uncompressed search is also run and a disagreement revokes the artifact. Measured (exact arithmetic, median of three, `bench.json`): energy world 68,726 to 6,313 states, 44x warm and 2.2x cold (learning counted); product world 144,799 to 264 states, about 1,700x warm and 5.5x cold; the guard-rich control certifies the identity encoding (111 to 111 states) and loses once learning is counted. The energy and product worlds were generated with the symmetry the encoder finds, so this is reuse of a designed structure, not evidence about external planning benchmarks. Shadow check: the oracle plans over the ground graph of the reachable original states (`eval/smoke-reasoning/lib/numeric-strips.mjs`), which checks the search and the cost but shares the exact arithmetic with the strategy.

**`worlds-sopr`** answers many what-if queries over one large base with sop-r's copy-on-write worlds: the core is lowered to three-term statements (arity 1 and 2 only, `x-unit` for arity 1), one engine holds the base and its lazy saturation, a world is forked in time proportional to the number of relations, the first query after a change saturates only the forward cone of the changed relations, pure additions on monotone paths continue incrementally and sibling worlds share their parent's saturation. The fact wires of the query circuit are the additions of the world, so the host's conditional lowering (leave-one-out, verification) runs as sibling worlds of one base. API: `prepare`, `ask`, `fork(handle, delta)` with `delta = {add, remove, set}`, `askMany`. Entry gate (`tests/engines/strategy-worlds-sopr.test.mjs`): sop-r's own 1,200-answer incremental test on the vendored engine, the same shape through the core (recursion, `absent`, `compare`, `compute`; additions, retractions and `set`; 150 worlds, eight probes, every packet equal to the oracle's) and a non-monotone case. Deletion and `set` are supported but not incremental: the cone and everything downstream of a retraction is recomputed (at 4,000 entities: 0.24 ms for an addition world, 3.6 ms for a retraction and 7.7 ms for a `set`, against 233 ms for the oracle at 1,000 entities where it already stops at its probe ceiling); `set` needs a predicate declared with `key 1`. Not expressible: classical negation, time, aggregates, explanations, `divided_by`, arity 0 and 3 or more, budget keys; the host computes `used` by deletion.

**`dreaming-session`** is a wrapper, not a strategy: it has no coverage of its own and inherits the wrapped strategy's capabilities. It keeps the records of proposal 5.6 (`records.mjs`): episodes (cost counters, never the content of the answer), skills (kind, scope, contract, certificate kind, evidence, status `candidate promoted rejected quarantined revoked advisory`), certificates, one frozen deployment plan per query family, advisory hints (an observed functional dependency, never deployed) and a negative cache keyed by kind, scope, learner version and budget. `dream` replays the journal of hot families, proposes join-order skills (a legal permutation of the positive atoms of a rule body), certifies each by shadow replay against the wrapped strategy on training and held-out tasks (same status, completeness, rows, count and bound), promotes the verified ones whose gain reaches 3 percent, and composes one plan (a skill that passed alone is deployed only if the composition costs less). `propose` offers any other candidate (for example a lemma) to the same gate. Acceptance rule: on every load the contract of the schema cone (rules and predicate declarations, not facts) must equal the skill's, otherwise the plan is retired and its skills quarantined; a stored artifact that no longer applies to a changed rule is never applied; with `shadow` (or `shadowEvery`) the reference runs too and any disagreement revokes the plan and returns the reference answer; a revoked skill is not promoted again except by explicit operator approval. A learned part only chooses among legal plans. Measured on a repeated family whose rule is written in the worst join order (`bench.json`): probes fall 10x to 52x, wall clock 2x to 6x (the wrapper re-parses the circuits on every call), the dream pass pays back after 9 to 32 queries, and on a well-ordered control the wrapper finds nothing and costs 1.7x wall. The gate is as strong as its replay tasks: an unsound shortcut that no replayed query exercises passes it. A sound doubling lemma for transitive closure is certified and rejected on cost, as all four lemma bundles of E10 were.

**The native closure template** is a router-rule component, not a strategy. It recognises a transitive-closure rule pair (base `P x y :- E x y`, and a right-linear, left-linear or non-linear step; `E` extensional, `P` defined by exactly these two rules, no negative facts or validity intervals) and, when an argument of a single-atom query is bound, answers `select`, `exists` and `count` with one breadth-first search and a witness path. It produces answers, so it passes the shadow gate like a strategy (120 random programs in `tests/engines/strategy-closure-template.test.mjs`, every shape and bound pattern, equal to the oracle, with `used` replayed). `matches(problem)` is the router rule; any other shape, both arguments free, time, suppositions or other modes are `not_expressible`, so it never partially applies. A `maxRounds` ceiling caps the BFS levels (an honest partial answer); `maxJoins` counts edges examined, so the oracle's probe-unit budget feature is not declared. Measured on the reach shapes (chain, tree, cycle, layered, disconnected, bound start): 55x to 1,100x faster warm than the oracle, which materialises the whole closure and stops at its probe ceiling on the larger chain and cycle; against the wired Datalog engines the call is several times faster (their time includes lowering). These ratios compare query-directed search with broad bottom-up evaluation, not two graph algorithms.

#### datalog-souffle, datalog-e10 and datalog-soplab

Three Datalog strategies that share one host front end, `reasoning/strategies/datalog-common/front.mjs`: governance, desugaring, `compileProgram`, the dependency slice, the oracle's own query reader (`evaluatePart`) over the evidence tables an engine returns, the packet, the budget and the host conditional. An engine only closes the sliced program (or answers a pushed-down query), so a disagreement with the oracle can come only from an engine or its lowering. None provides `used`, `proof` (soplab provides `explain`); the host computes `used` by deletion and verified replay. All three declare time, why_not, constraints and the modes of work `not_expressible`, and refuse a circuit they cannot run instead of weakening it. Smoke adapters: `datalog-souffle`, `datalog-e10`, `datalog-soplab` (the old read-only adapters on the unpacked zips remain as `zip-e10.mjs` and `zip-soplab.mjs`, labelled legacy and not registered). Cases 65 to 69 are theirs. Shadow gate: `tests/engines/strategy-datalog-differential.test.mjs` runs random stratified programs (facts of both polarities, recursion, `not`, `absent`, compare, arithmetic, aggregates; select, exists, count, every) against the oracle, with fixed seeds; 300 seeds gave about 20,000 answers and no disagreement, Soufflé with and without its magic-set transformation included.

**`datalog-souffle`** lowers to Soufflé 2.5 (private build, `SOUFFLE_BIN`): two relations per predicate (`p_<name>` positive evidence, `n_<name>` explicit negative), facts as `.facts` TSV files in a temporary directory (nullary facts inline), one clause per alternative, `absent` as stratified `!`, `compare` and `compute` as constraints and arithmetic, and each aggregate as a set relation of the distinct bindings of `over` with count, sum, min and max over exactly that set (set semantics, tested: equal salaries both count). Defaults and integrity arrive desugared. Select, exists and count are pushed into the program (rows, a clean-derivation relation for `both`, nullary refutation flags) and only the answer is read back; `every` reads the closure of the query predicates. The interpreter is the default; compile mode keeps a binary per program text (and Soufflé version) in `CHATSOP_SOUFFLE_CACHE` or the temporary directory and reuses it over new facts (about 6 s to build, then milliseconds). Integers are 32-bit (`limits.integer_range`): a larger one, a column mixing numbers and text, ordering over text, `collect` and an `order` or `start_of` leaf are `not_expressible`, and every `plus`, `minus`, `times` and `sum` carries a float guard whose overflow is `budget_exhausted`, reason `numeric_range`, never a wrapped number; a zero divisor makes the body false. A wall-clock timeout kills the subprocess: `budget_exhausted`, reason `wall`; `maxFacts` is checked before the run. Soufflé's magic-set option (`-m '*'`) is applied by option `magic` (`true`, or `auto` for programs without negation, aggregates and arithmetic). Provenance (`-t explain`) was tried: it prints an ASCII proof tree for one tuple per command on an instrumented run; it was not wired (one process per explained tuple, a layout to parse, no proof nodes for `absent` and aggregates), hence `provides: []`.

**`datalog-e10`** vendors eleven modules of `sop_reasoner_e10.zip` (sop-verified-reasoner 0.3.0) verbatim in `vendor/`, with a header naming the source. The core lowers to the E10 dialect (`FACT [NOT]`, `NONE`, `TEST`, queries with `OR` alternatives); E10 has no arithmetic terms and no aggregate, so `compute` and aggregates are `not_expressible`. Queries are pushed in (the `both` and refutation tests are extra queries, run only when the opposite polarity can carry evidence). Budgets map `maxJoins` to E10's `maxWork`, `maxFacts` to `maxDerived` and `timeoutMs` to `maxMs`; INCOMPLETE is `budget_exhausted` with a reason (`probes`, `facts`, `wall`) and a monotone select reports its partial rows as a subset. Demand rewriting (magic sets) is on by default and falls back when the cone has negation: it is the whole gain on a selective bound query (case 68: 1,136 ms against 25,427 ms at 10^5 facts) and a loss on dense nonlinear recursion with no bound argument (case 69: 1,853 ms against 936 ms at 100 nodes, 15 s against 8 s at 200), the regression the inventory records.

**`datalog-soplab`** (demoted on 2026-10-01 to a reference engine: `eval/reference-engines/datalog-soplab/`, not a product strategy and not a routing candidate, kept as a second independent implementation for `tests/engines/strategy-datalog-differential.test.mjs`) vendors nineteen modules of `soplab-v0.4.0.zip` (sop-reasoning-lab 0.4.0, MIT) in `vendor/`. The core lowers to its CNL (`claim`, `rule` with `NONE` and `TEST`, an `all` wire plus a `reduce` wire per grouped aggregate); `compute`, `collect`, ungrouped aggregates (soplab makes a group of zero rows, the oracle does not) and negative literals in actions are `not_expressible`. It also answers `explain` (the first derivation in its proof store) and `plan` (actions as transitions, cheapest plan; `no_plan` only when the state space was exhausted, else `budget_exhausted`, reason `nodes`). Budgets: `maxRounds` (a cut closure is partial and sound), `maxFacts` and `maxNodes`; soplab has no clock, so `timeoutMs` is not honoured. Finding of case `14a`: the engine's own `abduct()` returns the first cheapest explanation only (capabilities `nativeAbduce: cheapest_only`, kept as a test); the strategy enumerates all inclusion-minimal explanations over soplab closures and declares `abduce: all_minimal`.

Speed (`eval/reports/current/smoke-reasoning/datalog-speed.json`, regenerable, `bench/datalog.mjs`, wall time of `ask` on pre-parsed wires): at 10^6 facts of ring components Soufflé needs 6.4 s (3.3 s with magic sets), E10 7.5 s with demand and 65 s without, sql-sqlite 28.7 s; the naive oracle cannot finish 10^3 facts inside its probe ceiling, and soplab needs 4.2 s at 10^4. Soufflé does 10^6 salaries grouped in 3.7 s and a three-layer negation chain over 6 * 10^5 nodes in 4.1 s. Known limits: the grammar parser of `sop/knowledge/lexical.mjs` is quadratic in the number of wires (a duplicate-id scan: 10^4 wires 0.5 s, 5 * 10^4 wires 10.8 s), so large inputs reach a strategy as structured wires, not as text; Soufflé is a subprocess (about 15 ms of start-up per run); the compile-mode path was exercised once per program shape only.

#### asp-clingo and z3-smt-bounded

Two solver strategies in `reasoning/strategies/asp-clingo/` and `reasoning/strategies/z3-smt-bounded/`, over one shared host front end (`reasoning/strategies/solver-common/`: governance, desugaring, slicing, the query reader and the packet are the oracle's own modules, so a disagreement with the oracle can only come from the lowering or the solver). Both run the private binary (`tools/.solvers/clingo/bin/clingo` 5.8.2, `tools/.solvers/z3/bin/z3` 4.15.8, or `CLINGO_BIN`/`Z3_BIN`) as a subprocess with a time limit (`--time-limit` and a hard process timeout; `-T`); a stop is `budget_exhausted` with `reason wall`, an overflow of the range of the engine is `reason numeric_range`. Smoke adapters: `eval/smoke-reasoning/adapters/asp-clingo.mjs`, `z3-smt-bounded.mjs`. The existing `z3-lia` strategy is unchanged and separate.

**`asp-clingo`** lowers the desugared core to ASP: polarity as two relations (`pos_p`, `neg_p`, so a fact and its negation stay a model and never make the program inconsistent, and strong negation `-p` is not used), `absent` as `not`, `compare` and `compute` as arithmetic in the body (integer division truncates toward zero, an undefined operation drops the instance, which is the oracle's false), aggregates as `#count`, `#sum`, `#min`, `#max` with SET semantics over all the variables of the `over` group, defaults and integrity through the desugaring (the desugared program is the normative semantics, so the strategy agrees by construction on stratified programs), recursion by the stable model. Brave and cautious reasoning: a stratified program has ONE stable model, so there is nothing to choose between and the atoms of that model are the closure; were several models ever produced (an unstratified extension), `supported` would be cautious truth (true in every model), `unknown` truth in some model only, `refuted` the cautious negative relation and `both` both relations cautious. The program is refused if it is not stratified (`compileProgram`). Abduction is a choice rule over the hypotheses, the observation as a constraint, `#minimize` over the number chosen and an iteration that blocks every superset of an explanation found (each model is inclusion-minimal and none is missed; the result equals the oracle's). `why_not` is the same over fresh EDB atoms: the MINIMUM-cardinality sets (the oracle returns the inclusion-minimal sets of the nearest explanations; they agree whenever the nearest explanation is a smallest one), with the blocking atoms read off the model by the oracle's blocker scan (a diagnostic). The `constraint` wire is a choice per variable, integrity constraints over `holds_N` atoms and `#minimize`; ties are broken lexicographically with lower-priority terms, as in the oracle's enumeration. gringo integers are 32 bits and wrap silently, so a wide constant or a possible overflow is `not_expressible`, an overflow found by the witness rules of every `compute` is `numeric_range`, and the range of a sum is checked on the model.

**`z3-smt-bounded`** encodes NON-recursive programs over a finite domain: two Booleans per ground atom (one per polarity), the Clark completion of the ground non-recursive rules (the atoms are the possible ones, found by joining the positive bodies, so the domain is finite by construction), aggregates as bounded sums over the members of a group evaluated by Z3 at their stratum (everything below an aggregate is decided, becomes constant and is read by the next strata), `compare` and `compute` over constants while grounding, arithmetic constraints and optimisation with Z3's `minimize` (`opt.priority lex`, truncating `tdiv`, a validity conjunct per divisor), abduction and why_not as cardinality-minimal choices over Boolean literals. **Recursion is declared unsupported**: completion over a cycle characterises the supported models, not the least model, so a recursive slice is `not_expressible` (case `04b`, `probes/z3-04b-completion-recursion.smt2`, and `64`, `probes/z3-64-unfounded-loop.smt2`); a recursive rule outside the dependency slice of the question is not a reason to refuse. Integers are unbounded in Z3 but the packet carries safe integers: a larger value is `numeric_range`. Aggregates inside a planning problem are `not_expressible`.

**Planning with norms over a horizon (both).** A step holds one action instance or the plan has ended; the states are polarity-explicit literals (an open fluent's removed atom is recorded as negative evidence, a closed fluent's is absent, 4.2 item 8), re-closed under the rules at every step; frame axioms give the next state; the objective is the plan cost plus the cost of the soft violations, then fewer steps. Norms are VIOLATION atoms (`viol`, `viol_N`), never hard assertions inside the encoding: a hard norm is enforced by a "no violation" requirement; when that is unsatisfiable the requirement is LIFTED and the violations are minimised, which names the blockers (an unsat core cannot): stage A every hard norm enforced (`plan_found`, `compliance.hard ok`), stage B hard advisory norms relaxable with the fewest relaxations first (`plan_found`, `relaxed`, `compliance.hard relaxed`), stage C hard strict norms lifted and their violations minimised (`blocked`, `blocked_by`). A forbidden action instance executed while an equal-strength obligation on the same action is triggered marks BOTH norms (case `39b`, `61`). Qualifiers: `forbid always|before ~b|after ~b|at_most_once`, `oblige sometime|within N|always`, `permit ... overrides`, `standing`; an obligation instance is triggered only for a binding bound by the goal or by an executed action's parameter (`obligations_triggered`), a standing one for every binding (`obligation_unscoped`); a contested norm binds and is listed in `contested`. `abduce` with `waive $norm` hypotheses returns the inclusion-minimal sets of norms to waive. Unsat within the horizon is NEVER `no_plan`: it is `budget_exhausted` with `reason horizon`, unless it is proved complete: when every norm is Markov (`forbid ... always`, `permit`) and the plan has no `via`, a plan can be shortened to a loopless path, so no plan within H together with no loopless path of H actions means no plan at all (`no_plan`, case `11b`); the optimum is certified the same way or by the cost bound (a plan of more than H steps costs at least (H + 1) times the cheapest action), otherwise `guarantee bounded` and the note `optimality_bounded_by_horizon`. `oblige ... before|after ~b`, a norm `priority`, methods, procedures and conformance are `not_expressible` (the planners and `conform-core` have them).

**Declared and not declared.** Both declare `facts select open_world classical_negation conflict rules conjunction exists every count zero_arity naf closed_world closed_derived compute_in_rules compare_in_rules aggregate default overrides strict_contrary integrity versions whatif epistemic_status temporal interval throughout snapshot_derived used constraint optimize plan abduce why_not norms_hard norms_soft temporal_norms blocked_info abduce_waive binding_advisory norm_conflict`; `asp-clingo` adds `recursion`. Neither declares `explain` (no proofs: `provides` is empty, `used` is the host's deletion method plus a verifying replay), `time_vars`, `budget` and `budget_probes` (the only budget key honoured is `timeoutMs`, plus `maxDepth`, `maxHypotheses`, `maxCandidates`), `method`, `htn_choice`, `on_failure`, `procedures`, `procedure_render`, `amendment`, `check_plan`, `conform_*`. Ordering comparisons over time texts are not lowered by clingo (`not_expressible`); the oracle compares them by instant. Shadow result on the 131 smoke cases: `asp-clingo` passes the 88 it declares (43 not expressible), `z3-smt-bounded` the 74 it declares (57 not expressible), zero disagreements on exactly decided cases; the two agree with each other on the norm scenarios of `tests/engines/strategy-z3-smt-bounded.test.mjs`. Cases `60` to `64` were added for them (the cheapest assignment, a norm conflict with named blockers over a horizon, an arithmetic plus logic puzzle, abduction with all minimal explanations, an unfounded loop where stable and supported models differ).

#### conform-core and htn-strips-planner

The modes of work of proposal 8 (`method`, `norm`, `procedure`, `amendment`, `trace`) in two strategies that share one reading of the wires, `reasoning/strategies/modes/` (norm and method models, governance and the query context, the planning world, the run evaluator and the method checker). Smoke adapters: `eval/smoke-reasoning/adapters/conform-core.mjs`, `htn-strips-planner.mjs`.

**Definitions both use** (`modes/run-eval.mjs`, one function for the planner's monitors, `check` and `conform`). A run has steps 1..n and states 0..n; step i is performed in state i-1. An absent `binding` is `strict`, an absent `severity` is `hard`; a policy may only tighten. Every norm instance (a norm and a binding of its pattern variables) is violated at most once, at its first step. `forbid ~a`: an occurrence at step i whose `when` holds in state i-1 and that no override blocks (`before ~b`: only while no b happened at a step below i; `after ~b`: only once one has; `at_most_once`: from the second occurrence). `forbid ATOM`: the atom holds with `when` in some state, the initial one included. `oblige`: an instance is triggered at the first state k where `when` holds for a binding whose values are relevant (the goal's constants, or parameters of steps up to k+1, since the next step binds them; `standing` waives the test and the packet reports `obligation_unscoped`), then `sometime` needs an occurrence at a step after k (a state from k for an atom), `within N` one at a step in (k, k+N] (N days in a fully timestamped trace), `before ~b` an occurrence before the first later b, `after ~b` one after the last later b, `always` (an atom) that the atom holds in every state from k; an obligation unmet at the end of the run is a violation at the last step. A `permit`, an explicit `overrides` or a higher `priority` of an opposite norm blocks a `forbid` of an action where the overrider's `when` holds; only a `forbid` of an action can be overridden (anything else is `not_expressible`). An equal-strength pair (a hard forbid and a hard obligation of the same step, no override and no priority between them) is a conflict and is never a silent pick.

**`conform-core`** (since 2026-10-01 not a separate smoke column: the `js-oracle` column runs it) is the oracle with the `conform` capability, through the lowering of `conform/` (8.4 rule 3): a `trace` plus the norms and methods in force at the time of its steps become ONE core program (`predicate`, `fact` and `rule` wires only; the oracle itself is not rewritten, only wrapped) that derives `x_c_viol_<norm>` (violated), `x_c_dev_<method>` (deviation) and `x_c_compliant`. The state of the trace is lowered to step-indexed relations (`x_c_s_<p> i args`: static predicates in every state, fluents by inertia rules with the effects of the steps as ground tables, derived predicates by a guarded copy of each rule), the norms to the rules of the definitions above, a method to a chart of its steps over the steps of the instance's scope (`choose`, `optional`, `any_order`, `if/else`, `until ... max`, `pick`; `achieve` and sub-task steps, `if`/`until`/`pick` on variables the method does not bind first, more than four method variables, `at_most_once` over a state atom and aggregates in the cone of a condition are `not_expressible`). A step is judged against the wires in force at its own time (`at DATE`, else the query's `asof`, else now); leaving a strict method is non-compliance and lists the method in `compliance.deviations`, an advisory one is only listed, a violated hard advisory norm is `relaxed`. The answer carries `compliance {hard, violated, relaxed?, soft_violations, deviations, total_cost}`, `used` with versions, `violations`, `deviations` and `obligations_triggered`. Every other query is delegated to the oracle unchanged, and a theory holding modes-of-work wires is refused for them. The lowered text gives the same verdict on `prolog-tabling`, `datalog-souffle`, `sql-sqlite`, `asp-clingo` and `z3-smt-bounded` (`tests/engines/strategy-conform.test.mjs`); E10 and soplab refuse it honestly (no arithmetic).

**`htn-strips-planner`** is forward state-space search (uniform cost; heap) over polarity-explicit states (the closure of the rules is recomputed per state). `modes/` gives it the norms; `htn-strips-planner/decompose.mjs` resolves a method into a continuation that starts with a primitive step: `choose`, `pick`, `any_order`, `optional`, `if/else`, `until ATOM max N` (the cap reached with the condition false is a failed run, reported as `budget_exhausted` with `reason depth`), a sub-task step (a method that achieves it), `achieve` (blind search from primitives) and `on_failure` ($method, `replan`, `abort`). A strict method that applies to the goal may not be left: with no legal run the declared fallback runs, an advisory method falls back to primitives and the packet notes `method_fallback_to_primitives`, a strict method with no fallback is `blocked` with `blocked {step, requirement}`. Hard norms prune, soft ones add their cost (the objective `policy objective cost|violations|lexicographic`), `prefer ~a over ~b` breaks ties. With no legal plan the hard advisory norms are relaxed first (smallest set, then cheapest plan; `relaxed`, `compliance.hard relaxed`), then the strict ones are named: `blocked` with `blocked_by`, the union of the inclusion-minimal sets of norms whose waiver unblocks the plan plus the partner of a conflict (`blocked_by_not_minimal` when more than three are needed). `why_not` with `via ~action ...` asks about one step; `abduce` over `hypothesis` wires with `waive $norm` returns the minimal sets of waivers (`hypotheses [["waive n1"]]`); an amendment the query supposes puts its `members` in force and takes its `removes` out; `mode procedure` renders the method in force at `asof` without search; `check(plan)` and `mode conform` judge a plan or a trace with the same monitors. The plan-length horizon is `maxDepth` (host ceiling 20): a cut is `budget_exhausted` with `reason horizon`, never `no_plan`. States are deduplicated on the positive literals, the negative literals somebody reads, the continuation and the monitor summary, which is what makes open fluents that move (`removes at r a`) tractable: a 10 by 10 road grid plans in about 0.1 s, where the oracle's blind search gives up after 30 s.

**Declared and not declared.** Both declare `plan method htn_choice on_failure norms_hard norms_soft temporal_norms procedures procedure_render amendment check_plan blocked_info abduce_waive binding_advisory norm_conflict overrides conform_asof conform_deviation versions used zero_arity` (the planner adds `why_not` and `abduce` for planning questions only; `conform-core` adds the oracle's features). The planner does not declare the relational modes (`select`, `exists`, `count`, `every`, `explain`, a relational why_not or abduce), aggregates, defaults, integrity or time; `triggered_by` events of a method are parsed and not acted on; actions are compiled for one reference time per query (versions of an action in `used` come from that time). Shadow evidence: 300 generated road graphs and the smoke plans give the oracle's status and cost; 276 generated norm problems give the cost of an exhaustive search judged by the same monitors; the lowering and the monitors agree on 9,600 generated traces (`tests/engines/strategy-htn-strips-planner.test.mjs`, `tests/engines/strategy-conform.test.mjs`).

#### prolog-tabling and golog-swi

Two strategies in `reasoning/strategies/prolog-tabling/` and `reasoning/strategies/golog-swi/` on the private SWI-Prolog 9.0.4 (`SWIPL_BIN`, `tools/.solvers/swi/swipl`; each ask is one process with a temporary program, about 60 ms of start-up). They share the oracle's front end (parser, governance, desugaring, `compileProgram`, `planQuery`, the packet builders) and the Prolog runtime `prolog-tabling/runtime.pl`; the decisions about statuses stay in the oracle's definitions, the evaluation is Prolog.

**`prolog-tabling`** compiles the desugared core to one tabled Prolog program (`codegen.mjs`): two predicates per relation (`p_<rel>` positive evidence, `n_<rel>` explicit negative, so `both` is a reported status and never an explosion), every relation tabled (SLG resolution: left recursion, mutual recursion and cycles terminate), `absent` as `tnot`, `compare` and `compute` as arithmetic helpers (integers only, safe range, division truncating toward zero, an undefined operation makes the body false and notes `arithmetic_undefined`), aggregates as `findall` plus `sort` plus a fold (set semantics: the rows are the distinct bindings of all variables), `start_of` and `end_of` over the facts of the time view, an `any` group as several clauses, defaults and integrity by the shared desugaring. A query is a goal-directed tabled call (`taskgen.mjs`): only what the query depends on is evaluated (a 400-node chain answers `reach n0 ?t` in about 0.5 s where the naive oracle runs out of probes at 100). Time is the host partition: one run per part of an interval, combined by the oracle's `combineParts`. **Well-founded negation:** on the stratified programs the validator admits, the well-founded model equals the perfect model, so every `tnot` is decided. A program that is not stratified is refused before the strategy runs (`not_stratifiable`); the runtime still maps an UNDEFINED atom (`call_delays/2` with a delay) to `unknown` with reason `well_founded_undefined` and never to a row, a refutation or `both` (tested on a hand-built program).

*Proofs and `used`.* A second tabled variant of every derived predicate carries the derivation height (`proofs.mjs`, `min` mode: the round at which the oracle's naive evaluation derives the atom, and the depth of an explanation); a proof is built from minimal-height instances, so the node graph is acyclic, `explain` is the shortest derivation and `used` is the leaves and rules of one proof (checked by replay in the oracle). A proof is capped at 4000 nodes (a closure over a long chain has quadratically many): past it the answer says `used_incomplete` and no explanation (honest under-reporting). An aggregate has no per-group height (one above the largest height under it). *`why_not`* is an abductive meta-interpreter in Prolog over the completed evidence and the rule data (`runtime.pl wn_*`), not over the tabled predicates: the inclusion-minimal sets of base atoms whose addition makes the claim derivable plus the blockers (`absent_fails`, `contradicts`) with their supporting facts, the same definition as the oracle. *`abduce`* is a subset search over the hypothesis wires by increasing size, skipping supersets of an explanation found (all inclusion-minimal), with `abolish_all_tables` after every change of the hypotheses.

*Budgets.* `maxJoins` is `call_with_inference_limit` (`budget_exhausted`, reason `probes`, no partial rows). `maxRounds` is honoured without rounds by the height encoding: with a ceiling N every derived predicate carries the round height counted inside its stratum, the answer keeps exactly the atoms of rounds 1..N (a positive existential answer stays `supported` with `complete: false`, rows a subset of the true rows) and the run is `budget_exhausted` with reason `rounds` when an atom of round N+1 exists. `timeoutMs` is `budget_exhausted` with reason `wall` by killing the process; the proposal names `call_with_time_limit` with `abolish_all_tables`, but the alarm thread of `library(time)` deadlocks SWI-Prolog 9.0.4 at `halt` (measured: 1 run in about 1,700 printed its JSON and never exited, and none in 10,500 runs without the alarm), and a killed process leaves no incomplete table behind. Tables left incomplete by an inference-limit cut are abolished in Prolog before anything else runs. `call_with_depth_limit` is not used (meaningless on tabled predicates). Other ceilings are reported in `notes` as `budget_key_ignored:<key>`.

*Not covered (`not_expressible`):* `plan`, `method`, norms, procedures, `conform`, `constraint` wires, the query fields the host links. *Evidence:* every smoke case it declares agrees with the oracle on status, rows, counts, explanations and `conditional` (one difference: a probe cut returns no partial rows, the oracle returns a prefix; one `used_incomplete` over the aggregates of case 51), 600 random programs (facts, left and mutual recursion, negation, compare, compute, aggregates, defaults, five query modes) with zero disagreements, and the nine tabled programs exported by VRC give the same row counts when read back as circuits (`tests/engines/helpers-vrc-pl.mjs`). New cases 55 (left recursion over two cycles), 56 (mutual recursion with stratified negation), 57 (a deep explanation: the shortest derivation), 58 (`why_not` with blockers).

**`golog-swi`** (FROZEN since 2026-10-01: code and tests kept, not a default smoke column and not a routing candidate, because it overlaps `htn-strips-planner` and `conform`) is a small Golog interpreter (`golog-swi/golog.pl`) for the strict procedures of the modes of work. A method is a program: sequence, `choose` (nondeterministic choice, `prefer` reorders the branches), `optional`, `any_order`, `if` (a test on the state), `until ATOM max N` (a bounded loop; the cap reached with the test false is `budget_exhausted`, reason `depth`), `pick`, a primitive step (an action: its preconditions are tests on the state, its effects change it) and a sub-task (a call of the method that achieves it). The interpreter chooses only at the choice points and enumerates every legal run; the cheapest run that no hard norm rules out wins (the policy objective; ties by search order, so the first run found). The state is a polarity-explicit set of literals; the derived relations are the `prolog-tabling` program in state mode (`rt_st/3` facts, tables abolished at every state change). The norms are tests on the primitive actions of a COMPLETE run (`gl_eval`, the definitions of 8.2 with all temporal qualifiers, `permit`/`overrides`, severity and binding, day-based `within` for a timestamped trace): one function judges a plan and a recorded trace.

Modes: `plan` for a goal that is one task atom some approved method achieves (`on_failure $method` fallbacks, advisory hard norms relaxed and listed in `relaxed`, `blocked` with `blocked_by` or with the deepest unmet requirement, `choices`, `used` with versions: the norms listed are those matched by a step the engine could have taken at some state of the run), `why_not` with `via`, `abduce` over `waive` hypotheses, `procedure` (render, `asof`) and `conform` / `check(plan)` (the norms in force at the time of each step; a strict method is a program and a trace that is not one of its runs is a deviation, non-compliance; an advisory deviation is only listed). Not covered (`not_expressible`): blind planning (a goal no approved method achieves, an `achieve` step, `replan` or an advisory method with no legal run: the htn-strips-planner), relational modes, abduction over atom hypotheses, a forbid that outranks an obligation, rule versions that differ between the steps of a trace. The planner and `golog-swi` implement the same definitions independently (search with monitors against complete runs), and agree on every smoke case both decide (31 compared) and on 16 scenario programs (`tests/engines/golog-scenarios.mjs`: loops, `pick`, `any_order`, sub-tasks, `forbid before` and `at_most_once`, soft and hard obligations, conformance with deviation). New cases 59a (a trace takes the wrong branch of an `if` of a strict procedure) and 59b (the legal run).

#### sql-sqlite

The desugared core compiled to SQL and run by the built-in `node:sqlite` (`reasoning/strategies/sql-sqlite/`, smoke adapter `sql-sqlite`). It uses the oracle's own front end (governance, desugaring, `compileProgram`, the dependency slice, `planQuery`), so a disagreement with the oracle can only come from the SQL lowering. Relations are one table per predicate, arity and polarity (`"+p/2"` positive evidence, `"-p/2"` explicit negative evidence, columns `c0..`, a primary key on all of them, a derivation counter `rk`); `both` is never stored, it is P and N read together at query time (an `EXISTS` over the opposite relation). Integers are stored as INTEGER (bound as BigInt, because `node:sqlite` binds a JS number as REAL), text as TEXT, so an integer never equals a string; a NUL in text is `not_expressible`.

Lowering. Rules are **materialised per stratum** with `INSERT OR IGNORE ... SELECT`, not left as views: every derived relation is read several times (by rules, `absent`, aggregates, the conflict test of `both`, provenance), `absent` and aggregates need finished lower strata, and tables give the planner real row counts and indexes. Linear recursion over one relation is one **recursive CTE** (`UNION`, breadth first, the recursive table as the outer loop). **Nonlinear and mutual recursion are expressible**: a semi-naive loop in JS over prepared SQL statements (per alternative and per recursive atom one statement reading the previous round's delta, a `next` table, a commit per round, so the rounds are the oracle's rounds); a tightened `maxRounds` also makes a linear stratum run as that loop, because a CTE has no round counter. `absent` is `NOT EXISTS` over the finished stratum; `compare` is a plain operator when both sides are provably integers (or one side provably not a time) and the exact `cmp` function otherwise; `compute` is a guarded SQL expression (both operands integers, non-zero divisor, result a safe integer: division truncates toward zero, a zero divisor or an overflow makes the body false and sets the note `arithmetic_undefined`); `aggregate` is `GROUP BY` over the distinct bindings of all variables of `over` (count, sum, min, max; `collect` builds its sorted JSON array in JS; an empty group yields nothing); defaults and integrity arrive desugared. `count`, `exists`, `select` and `every` are SQL over the finished relations with the oracle's statuses (`bound at_least`, `open_domain`, counterexample refutes). Time is the oracle's partition: one database per part of the partition of `[S, E)` at the fact endpoints, combined by `combineParts`; `start_of`/`end_of` read a stored-facts table with the validity text. **Demand** (the cheap half of magic sets): a select, exists, count or explain query whose atoms on a recursive relation carry constants that the linear step keeps (left-linear `path ?x ?z :- path ?x ?y, edge ?y ?z`, `path a ?t`) seeds the CTE with those constants, if nothing else in the slice reads the relation; a right-linear step changes the position, so a bound first argument gives no demand and the closure is full.

Query value forms. SQLite returns complete join bindings, including variables omitted from `select`, with conflict flags. The oracle's `evaluateCandidates` and `applyRowForms` perform `filter`, `except`, numeric `compare` and `rank` before projection and deduplication, preserving numeric-string readings, ties, ordinal positions and top-N groups. `limit` cuts select rows only, never counts. A ranking is completeness-sensitive: a cut closure never exposes a partial winner as a complete answer. Form answers carry `used_incomplete` because a projected row alone does not certify the value-level decision or the global winner; no unverified support is promoted. Interval `measure` and `order` remain typed-runtime operations, not wire-level forms.

Provenance. `used` is one sufficient support set by backward chaining with SQL point queries over `rk` (a derivation whose positive premises all have a smaller `rk` is acyclic, so a cycle cannot justify itself); aggregates rest on all their member rows, both sides of a `both` answer are included, `start_of`/`end_of` name the particular stored fact whose validity was read; `used_incomplete` when the proof rests on `absent`, a count, an `every` or a closed refutation, or when the proof exceeds its bound (2,000 rows, 20,000 nodes). `explain` returns the proof DAG and `{depth, uses}` of the oracle. The conditional list is the host's job (`options.conditional` applies the oracle's own two-run rule).

Budget. Every join statement calls `tick()` (a SQL function): it counts a joined tuple against `maxJoins` and checks the clock, and throws the stop out of the running statement, so the statement timeout works inside SQLite (which rolls back that statement; a cut closure holds only complete statements). `maxFacts` caps the tuples written (a CTE through `LIMIT`), `maxRounds` the loop rounds, `timeoutMs` the wall time; a cut is `budget_exhausted` with `rounds`, `probes`, `facts` or `wall`, a partial positive answer only for a monotone select, exists or explain. The `maxJoins` unit is a joined tuple, never comparable with another strategy's probes. Declared `not_expressible`: `plan`, `why_not`, `abduce`, constraints and the modes of work; `isolation` is false.

**Bank mode** (`bank.mjs`, `askBank({bank, theory, query})`, opt-in, never chosen by the router): the same rules run directly against a SQLite memory bank file of DS018. The file is opened read-only; base relations are TEMP views over `atoms` (the columns keep the bank's JSON text, so constants and joins hit the bank's own composite indexes), derived relations are TEMP tables, facts written in the circuit go to temp tables; with the single-file memory a tuple is present at `asof` when a claim known by then is not cancelled by a retraction known by then and, with `at`, its validity (shortened by `end` events) contains the instant. Limits: arity 1 to 4, a point in time (no interval), no `start_of`/`end_of`; `used` names bank tuples by `atoms.id`. The tests check the file byte for byte before and after, that no file appears beside it, that writes through the connection fail, and the index plans.

Evidence. All 78 smoke cases the strategy declares (at the time of writing) agree with the oracle (the others are `not_expressible`); `tools/eval/engines/sql-sqlite-fuzz.mjs` compares 2,500 seeded circuits (joins, `not`, `absent`, `compute` with zero divisors, aggregates, linear, nonlinear and mutual recursion, intervals, `start_of`/`end_of`) in both recursion modes with `used` replayed in the oracle: 0 disagreements, one tolerated divergence (`every` with `both`: the oracle takes the conflict flag of the first binding of a member, which depends on fact order; sql-sqlite calls a member conflicted only when all its bindings are). Smoke cases 50 to 54 (generated by `tools/eval/engines/sql-sqlite-cases.mjs`): a 3,000-row three-way join, aggregates over a 2,500-row group with `compute`, linear recursion 110 rounds deep on a cycle, nonlinear closure, `absent` over a 6,400-row join; the tests run depth 1,000 by CTE and by loop. Speed (`tools/eval/engines/sql-sqlite-bench.mjs`, `eval/reports/current/sql-sqlite/bench.json`, wall time of `ask` on a pre-built handle, median of 2 runs, **taken on a machine at load average 13 to 26, so only the ratios mean anything**): at 3.2 * 10^4 facts of a three-way join sql-sqlite needs 0.18 s, E10 0.35 s, the oracle stops on its probe ceiling after 0.47 s; at 3.2 * 10^5 facts 2.2 s against E10 5.4 s; the closed-world policy join at 1.8 * 10^5 facts 2.2 s against E10 13.0 s; 4 * 10^5 salaries grouped 3.6 s (the oracle 10.3 s, E10 has no aggregate); nonlinear closure of a 120-edge chain 0.15 s against E10 0.95 s; bound closure on a 1,000-edge chain 10 ms against E10 28 ms (demand); mutual recursion on 240 nodes 14 ms against E10 7.5 ms (E10 wins on small recursive cases and on selective bound queries where its magic sets apply to right-linear shapes that sql-sqlite computes in full). Known limits: every ask builds a fresh database (about 1 to 2 ms plus the load); the planner has no statistics (no `ANALYZE`), so the recursive table is forced outer with CROSS JOIN and other join orders are SQLite's; right-linear bound closures and anything needing real magic sets are full closures; provenance of a very large answer is bounded and reported as `used_incomplete`.

#### Exact decimals in the engines

The owner asked (2026-10-02) why the engines run only integers. They do not: every engine that declares `exact_arithmetic` computes decimals exactly, never with binary floating point, and each one's `capabilities.exact` says how (`kind: fixed_point | rational`).

| engine | exact decimals | words | refuses (`not_expressible`, feature `exact_arithmetic`) | integer range |
| --- | --- | --- | --- | --- |
| `sql-sqlite` | fixed point | all twelve (`plus minus times divided_by whole_divided_by modulo power rounded_to rounded_up_to rounded_down_to minimum_with maximum_with`) | see below | 64-bit (final values within 2^53; intermediates up to 2^63) |
| `datalog-souffle` | fixed point | all twelve | see below | 32-bit; an overflow is `budget_exhausted`, `reason numeric_range`, never a wrapped number |
| `asp-clingo` | fixed point | all twelve | see below | 32-bit, as Soufflé |
| `prolog-tabling` | exact rationals (`1r10` literals, `rdiv`) | all twelve | none | unbounded (results within 2^53) |
| `z3-smt-bounded` | exact rationals (`Real` sort for aggregates, BigInt fractions while grounding) | all twelve | none | decimals unbounded in the Real sort |
| `js-reference` | the oracle: exact per operation, a decimal result rounded to 12 significant digits | all twelve | none | safe integers |
| `datalog-e10` | integers only | `plus minus times whole_divided_by` | decimals and the other words (feature missing) | |

**Fixed point** (`reasoning/strategies/solver-common/fixed-point.mjs`). Before lowering, the sliced program is rewritten into an integer program. `planFixedPoint` chooses ONE scale S per problem: the largest number of decimal places that any constant, stored value or computed value can need, found by a fixed point over the argument positions of the predicates (`plus`/`minus` keep the larger scale, `times` adds the scales, `power` multiplies by the constant exponent, `divided_by` a constant adds the places the quotient needs, `divided_by` a variable adds two places of headroom, the rounding words keep the scale of B, `minimum_with`/`maximum_with` keep the larger scale and become two alternatives of the body (a `compare` of the scaled values, then the kept one), the aggregates keep the scale of their field, `count` has scale 0). S above 12 is refused. Then `scaleProgram` multiplies every number of facts, rule constants, aggregate yields and query constants by 10^S and expands each `compute` word into the four integer words the engines already lower (`plus minus times whole_divided_by`) and comparisons: `times` is `A*B` then an exact whole division by 10^S (the 32-bit engines use `qA*B + (rA*B)/10^S` with `A = qA*10^S + rA`, so no intermediate exceeds the result by more than 10^S times an operand); `divided_by` is `A*10^S` whole-divided by B; `rounded_down_to` and `rounded_up_to` are floor and ceiling over the multiples of B by the positive remainder; `rounded_to` (half away from zero) splits the body into the alternatives `A >= 0` and `A < 0`; `power` is an unrolled exact product (exponent 0 to 8). A count aggregate is multiplied by 10^S by the engine (`scaleCount`). The values the engines return are divided by 10^S exactly (`fromScaled` goes through the decimal text, so `0.1 plus 0.2` is `0.3`). A division by a variable adds the helper rule `x_fx_inexact`, which fires when the quotient has more than S places: the engine then raises `not_expressible` and the oracle answers, so a quotient is never rounded silently. Refused: a quotient by a constant with a prime factor other than 2 and 5 (`10 divided_by 3`), a constant zero divisor, a variable or too large exponent (`power`), more than 12 places, a scaled constant outside the safe or 32-bit range, and decimals in the bank mode of `sql-sqlite` (JSON text of numbers). The packet notes `fixed_point_scale_S`. Proofs and explanations of `sql-sqlite` show decimals (the helper variables `?fx...` are not shown).

**Rationals.** `prolog-tabling` reads a decimal as the exact rational literal (`0.1` is `1r10`), computes with `is`, `rdiv`, `round`, `ceiling`, `floor` and `^`, and writes a terminating rational as the nearest double of its exact value; `z3-smt-bounded` grounds `compute` over BigInt fractions (`solver-common/exact-rational.mjs`) and evaluates aggregate sums, minima and maxima over decimals in the `Real` sort, reading Z3's `(/ 3.0 10.0)` back as a fraction. A quotient that does not terminate (`1 divided_by 3`) is rendered like the oracle (`0.333333333333`, 12 significant digits) and the note `rational_rounded_12_digits` says so; values pass between rules as rendered numbers in Z3's grounding, so a chain of such quotients can differ from Prolog's by that rounding (the oracle decides).

**Evidence** (2026-10-02). `tests/reasoning/exact-decimals-engines.test.mjs` (66 tests): per engine the sum of prices (0.1 + 0.2 = 0.3), mixed scales, comparisons, sum/min/max/count over decimals, division (constant, variable, refused), rounding of negatives and ties, power, `whole_divided_by`/`modulo` over decimals, the refusals, the 32-bit overflow, proofs, a seeded differential fuzz of 40 programs against the oracle, and the router's choice and fallbacks. Smoke cases 91 (exact sums), 92 (division, rounding, power), 93 (average with a variable divisor) and 94 (`minimum_with`/`maximum_with`): all six engines that declare `exact_arithmetic` pass with the oracle. Speed (`node tools/eval/engines/exact-decimals-bench.mjs`, `eval/reports/current/exact-decimals/timing.json`, sum/count/min/max plus a `times 0.07` rule over N two-decimal prices, one process per cell): at 10^5 facts `sql-sqlite` 0.8 s against the oracle 1.7 s and `prolog-tabling` 7.8 s; Soufflé and clingo answer up to 10^4 facts (105 and 214 ms against the oracle's 201) and report `numeric_range` at 10^5, where the scaled sum (about 3 * 10^9) leaves 32 bits, so the router hands that question to the oracle; Z3 is measured to 10^3 facts (115 ms), its s-expression reader overflowing the stack on a let chain of thousands of terms, with integers too.

#### llm-agent (a baseline, advisory)

`reasoning/strategies/llm-agent/` is not an engine: it asks a large language model, through a plain chat-completion call through Ploinky Workers (no tools; nothing of the repository is readable or writable), to work through the problem, so that evaluations show whether the engines beat bigger models (owner request 2026-10-01). Its capability declaration is `exact: false`, `bounded: false`, `verified: false`, `guarantee: advisory`: the smoke harness compares its answers with the oracle, but they are never ground truth, never promoted to evidence and never feed the knowledge.

- **Input.** `{theory: {knowledge}, query, source?}` in one of two presentations. `sop` gives the knowledge slice and the query circuit as SOP text with the engine's reasoning conventions (four statuses, `absent` against `not`, lower-bound counts, defaults, time, planning, budgets) and the language guide (`skills/sop-wire-authoring/authoring-guide.md`, sections 1 to 3). `nl` gives only the natural-language text of the case (`source.md`, optional per smoke case) with the same conventions in prose: the "big model reads the text" baseline. A prompt over `limits.max_chars` (90000) is `not_expressible`, as is `nl` without a text.
- **Output.** The model works through the problem in text and ends with `ANSWER_JSON:` and one JSON object in the shape of the result packet (status, rows, count, bound, plan, hypotheses, compliance and so on, and `used` and `conditional` ids for `sop`). `packet.mjs` parses it strictly: anything else is `status: error` with `reason: malformed_output`, never a repaired or guessed answer; a provider failure is `error` with `reason: provider`; a wall timeout is `budget_exhausted` with `reason: wall`; the paid-cost cap is `budget_exhausted` with `reason: cost`. The `direct` reply (JSON only) exists as an ablation: a non-reasoning model scores much lower without room to think.
- **Completion transport.** `options.backend: completion` selects `completion.mjs`, the one transport: an OpenAI-compatible endpoint (`endpoint`, optional `apiKey`, explicit `model`, `maxTokens`) without tools. Requests are bounded, temperature zero and internal thinking disabled; usage and latency are retained, local monetary cost is zero. Provider failure and malformed responses remain errors. Cache identity includes backend, endpoint and token ceiling. `reasoning/slice/render-english.mjs` renders knowledge or actual retrieved facts/rules as deterministic English evidence, preserving explicit negation, defaults/overrides, completeness declarations and inclusive-start/exclusive-end time; omitted repository facts, unsupported wires and conflicting duplicate identifiers fail closed.
- **Verify mode** (`options.verify`, `sop` only): the claimed `used` support is replayed in the js-oracle (the claims not in `used` are removed) and the packet carries `verified` and a per-row `row_verified`; `verified: null` means the oracle could not decide (a mode it does not express).
- **Model and cost.** `config/llm-agent.json`: the default is `Qwen3.8 27b` of the openference plan through Ploinky Workers, with no fallback model unless `fallbackModels` lists one. The cost and tokens of each call come from the response usage and are reported in `llm.cost`. Answers are cached by (model, presentation, reply mode, prompt text) in `state/llm-agent/cache` (gitignored), so smoke reruns are free.
- **Smoke.** The adapters `llm-agent-sop` and `llm-agent-nl` are registered and run only with `SMOKE_LLM=1`; they are `raw` (no conditional re-runs, closed-world policy or retrieval widening around them, because the model gives the final answer itself). `eval/smoke-reasoning/bench/llm-agent-report.mjs` writes the per-model agreement (`full` with wire ids, `core` without), cost, time and failure family to `eval/reports/current/llm-agent/summary.md`. Cases 80 to 84 are built where LLMs are expected to struggle (a long chain with a cut and blocked nodes, an exact count over closed against open predicates, a defaults priority ladder, a plan with soft tradeoffs, a derived fact throughout a period with gaps).
- **First measurement** (2026-10-01, regenerable): on 136 smoke cases the sop presentation agrees with the oracle on the answer content in 74% (Grok non-reasoning), 91% (Grok reasoning), and in 91% to 94% of the 47 cases with a text for GLM and for Grok reasoning on the nl presentation; the failures concentrate in planning with norms, `not` against `absent`, partly covered time and budget honesty. The smoke is small and the oracle defines the answer, so this is a first data point and not a result; the recommended harder families are in the report.

#### code-sandbox

The verifier of the programming path (`reasoning/strategies/code-sandbox/`, smoke adapter `code-sandbox`, cases 85 to 89; plan `experiments/proposal/programming-kb-plan.md`, milestone P0). It is not a reasoning engine and holds no knowledge: it declares only the feature `code_sandbox`, so every other strategy reports its cases as `not_expressible` and it reports every other case the same way. `ask({code, tests, inputs}, budget)` takes a `code` wire (DS004 "Programming wires", JavaScript) and its `test` wires (`inputs` are extra generated calls that must simply run) and answers:

- `verified`: every test passed. `guarantee bounded`, `exact false`, never `exact`: the program passed these tests, nothing more. A run with no test is `not_computable` (`reason no_tests`), never `verified`.
- `failed`: the failing tests, each with its call, the expected and actual value or the error.
- `budget_exhausted`: `reason wall` (a per-test CPU timeout, or the wall-clock guard of the whole run) or `reason memory` (the heap limit), with the test that hit it; `complete false`. It never reads as a negative answer.

It declares `provides: ['trace']` and `isolation: yes`, and never writes knowledge. The trace is a list of closed facts (`closed true` predicates, integers only, at most 50 per run): `run r1`, `in_elem r1 3`, `out_elem r1 2`, `test_result r1 t1 passed`, for `conform` and the Datalog strategies. **Isolation:** one worker thread per ask with an empty environment, a heap limit and a wall-clock guard owned by the parent, which terminates the worker; the program runs in a fresh `vm` context per test that holds only the ECMAScript built-ins (no `require`, `process`, `fetch`, timers or filesystem; `import()` fails) with a per-test CPU timeout; the expected value of a test is evaluated in a separate clean context and both values are compared by tag in the worker realm, so a program cannot change what it is compared with. `tests/code-sandbox.test.mjs` shows that `require`, `process`, `fetch`, a constructor escape, an infinite loop, an `Atomics.wait` and unbounded allocation are all contained and that the parent survives. Known limits: JavaScript only, synchronous code only (a promise is a failure), no hard CPU or memory accounting beyond the limits above.

The host loop that uses it is `probably_obsolete/paused/lib/programming/solve-instruction.mjs` (route `proposer`): the `llm-agent` presentation `code` proposes `task.sop` and `candidate.sop`, the host validates them, the sandbox runs the visible examples and the agent's tests, a failed round is repaired at most three times within `maxPaidUsd`, and every run leaves a `dreaming-session` episode (`DreamStore.addEpisode`: task, family, route, rounds, cost, status; never the instruction or the code) so that later dreaming can use it. Hidden tests live in `eval/suites/code-instructions-v1/` and are run by the evaluation harness after the packet is committed (`probably_obsolete/paused/eval/programming-kb/run-p0.mjs`).

Z3 guide: basic commands <https://microsoft.github.io/z3guide/docs/logic/basiccommands/>, satisfiability versus validity <https://microsoft.github.io/z3guide/docs/logic/propositional-logic/>, optimization <https://microsoft.github.io/z3guide/docs/optimization/intro/> and <https://microsoft.github.io/z3guide/docs/optimization/arithmeticaloptimization/>; the adapter checks optimality and projections separately. Forward state-space planning follows Poole and Mackworth, *Artificial Intelligence: Foundations of Computational Agents*, 3rd edition, chapter 6 (<https://artint.info/3e/html/ArtInt3e.Ch6.S2.html>); the code is this project's own. These sources describe external techniques, not results of ChatSOP.
