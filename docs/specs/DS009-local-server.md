# Local OpenAI-compatible server

## Scope and authority

`server/http.mjs` provides an HTTP façade, listening on all interfaces by default. Every chat turn runs through ChatSOPAdapter (`lib/adapter`, section "ChatSOPAdapter"), the backend the evaluations use too. In its default mode `stepwise` the conversational execution path is `Agent.turn`: the request parser (`server/query-parser.mjs`) asks the query author (`lib/query-author`) for a circuit from the user's message and the schema neighbourhood of the session's memory, with the session's formalization strategy (section "Request parser"); the validator admits it or sends bounded repair rounds ([DS014](specsLoader.html?spec=DS014-model-surface.md)); the KnowledgeLinker links its strings; the `Runtime` compiles the execution circuit, retrieves a slice under the completeness guard, and the StrategyRouter and a reasoning strategy execute it, with oracle verification of a routed answer ([DS006](specsLoader.html?spec=DS006-reasoning.md)); the answer is rendered in English from the result packet by fixed templates. The author writes only circuits (queries, constraints, `unclear` and `unparsed` reports, `stated` suppositions, labelled `assumed` lines and session definitions, which are stored in the session layer once valid, [DS022](specsLoader.html?spec=DS022-sessions-and-base-memories.md)); it cannot choose `remember`, claim documentary provenance, invoke tools or publish knowledge. A separately authenticated, explicitly supplied `chatSop.trustedSop` circuit may contain `fact`, `event` and `remember` wires only; it runs as a trusted user action in that user's session before the question. The receipt of a stored claim is returned as `chatSop.system_receipt` and can identify the target of a later correction. This is not model output or automatic ingestion. Trusted writes persist in the repository's private session; they are not committed to another user's state or published as base knowledge.

## Request parser

The request parser runs one of two step-by-step formalization strategies, chosen per session (`settings.formalizer`, `null` for the server default; [DS022](specsLoader.html?spec=DS022-sessions-and-base-memories.md) "Formalization strategies"): `LocalLLMStepByStep` (the default, method B) and `InternalReasoningStepByStep`. The system asks short questions and assembles the circuit; Ploinky Workers (the project's one model gateway, reached through `lib/pworker.mjs`) answers them on the tier ladder `queryParser.local.ladder` of `config/runtime.json` (shipped `tiny`, then `small`, then `good`), each question escalating to the next tier only when its answer cannot be read or the tier does not answer; a session's `formalizer_model` names the tier the ladder starts at. The one-shot strategy `LLMDirect` is archived (`probably_obsolete/one-shot-formalization/`, owner decision 2026-10-02); a session or caller that names it (or `CodingAgent`, `LocalLLMDirect`) runs the default step-by-step strategy, with `strategy_note` in the parse record. The configuration names Ploinky Workers tiers (`nano`, `micro`, `tiny`, `small`, `medium`, `good`, `best`), never a concrete model by default; Ploinky Workers reports what served a call in `x-pworker-model` and `x-pworker-tier`, and the formalization calls carry the purpose `formalize`, which Ploinky Workers serves with interactive priority. One formalization is made per turn; quality control is offline, from Ploinky Workers's request log and audit store. The parse record names the strategy, the tier ladder, the questions with each answer's tier (`dialog`), and the escalated questions (`tiers`). There is no fallback parser and no SymbolicLM, and a strategy is never replaced by another: a turn whose strategy this server cannot run, or whose first tier cannot run, answers 503 `parse_unavailable` with `chatSop.status: parse_unavailable` and the reason; when the questions ran and no valid circuit came back, it answers 422 `parse_failed` with `chatSop.status: rejected`. The server itself starts without any formalization model: `GET /v1/models` lists the façade model together with the availability of the formalizer (`chatsop.formalizer`), `GET /readyz` reports `ready` while the server can serve and the readiness key `formalizer` `{strategy, available, reason?, models, skipped?}`, and `GET /v1/status` reports every strategy (section "Server status"). Readiness of the first tier comes from Ploinky Workers's tier listing (a tier without a usable provider reports why). Identical requests are cached per memory version, strategy and ladder (`GET /v1/cache/stats`, `POST /v1/cache/clear`). The chat server itself loads no model weights and starts no model server: local models are Ploinky Workers providers, started and stopped by Ploinky Workers; the step-by-step model is always a Ploinky Workers tier, and an explicit `queryParser.local.endpoint` or `gguf` is refused (`invalid_strategy`).

### ChatSOPAdapter

`lib/adapter/index.mjs` (`createChatSOPAdapter`) answers one message in a mode: `stepwise` (the request parser and `Agent.turn` above), `routed` or `direct-verified` ([DS003](specsLoader.html?spec=DS003-main-behavior.md) "Translate local conversation into checked SOP answers"); further modes register with `registerMode`. The mode of a turn is the request's `adapter.mode`, else the session setting `adapter_mode`, else `config/runtime.json` `adapter.mode` (shipped `stepwise`). `adapter.tiers` names the Ploinky Workers tiers of the roles: `structure` (the structure role), `formalizer` (FOL v2), `compute` (path B, jsEval, engineCode; shipped `tiny`) and `direct` (the direct answer; shipped `tiny`); `adapter.routed` sets the second formalizations (`second`, shipped `["jsEval", "engineCode"]`), the engineCode languages (`engineCodeLanguages`, shipped `["js", "smt"]`), `fallbackToFol` (a compute problem that no compute path answers goes to FOL) and `earlyStop` (no further formalization once two agree, or once one verifies the direct answer). A request may override `tiers` and `routed` in `adapter.options`. The routed paths execute on a scratch memory of the engines (core-min, one discarded session per circuit), never on the session's repository. The answer packet `{object: 'chatsop.answer', mode, path, answer, verification, route, paths, circuits, proofs, timings, tiers}` is returned in the trace as `chatSop.adapter`; in the modes `routed` and `direct-verified` the reply body is chosen by the conversation layer from the turn facts `cv_turn_verification`, `cv_turn_answer_source` and `cv_turn_alternatives` (`config/knowledge/conversation-v1/0080-verification.sop`), and the turn's `formalizer_model` reads `adapter:<mode>`.

### Server status

`GET /v1/status` (bearer token or session cookie; `server/status.mjs`) returns `{object: 'status', ready, started_at, uptime_s, formalization, memories, reasoning, caches}`. `formalization` is `{default, strategies: [{id, label, available, reason?, backend, model, ladder?, endpoint?}]}`: both step-by-step strategies appear with whether they can run now and why not, the first tier (`model`), the tier ladder (`ladder`) and the endpoint (`pworker`). `ready` is true when the default strategy can run; `default_base` names the base memory new sessions fork (DS022 "Base memories"). `memories` lists the base memories `{id, name, strategy, facts, circuits, warm}`, where `warm` is `{ms, facts, layers}` after the start-up warming, `{skipped}` or `null`. `reasoning` is `{router: 'StrategyRouter v1', oracle: 'js-reference', engines: [{id, routable, available}]}` (installation probed once per process, read only). `caches` reports the request parser's circuit cache. The chat page's Settings tab shows it as the server status card.

### Warm memories

At start the base memories named by `server.warmMemories` (shipped `["world-v1"]`) and, always, the default base memory are decoded in the background (`server/warm-memories.mjs`), so the first question on them does not pay the decoding; `world-v1` (about 357k facts in 221 layers) takes about 12 s. The server is usable at once. `server.warmup: false` or `CHATSOP_WARMUP=0` disables it; the outcome appears in `GET /v1/status` `memories[].warm`.

### Answer language

The request parser reads a message in any language and writes English circuits; the runtime reasons in English and `sop/answer-text.mjs` always renders the answer deterministically in English, kept in the trace as `chatSop.english_text`. An optional last step (`server/answer-language.mjs`) phrases that answer in the language of the message. A model of `answerLanguage.providers` (default the Ploinky Workers tier `small`) works strictly from the English answer and a compact result packet (status, answers, count, facts used with their sources). It adds no fact: every number and every Wikidata id of the English answer must appear in its text, otherwise the next model is tried, and in the end the English answer is returned. `answerLanguage.mode` is `auto` (the default: applied when the message does not look English by the `looksEnglish` heuristic, never for English), `always` or `off`. For an English message `answerLanguage.natural` decides (`all`, the default: the reply composed from the conversation layer is the draft and the default model rewrites it as a natural chat reply under the same rules, keeping also the proper names of the draft; `conversation`: only replies with a conversation-layer part besides the answer; `off`); a failed natural phrasing shows the draft at once ([DS023](specsLoader.html?spec=DS023-courtesy-and-emotion.md) "Conversation layer"). The trace reports `chatSop.answer_language` `{mode, message_language, natural, applied, model, ms, tried, reason}`, `chatSop.reply` (the reply chosen by the JS oracle over the conversation layer: per part the situation, its priority, the number of variants, the derivation and the situations it outranked; the turn facts; the time) and `chatSop.near_miss` (the closest names of the memory for a turn without an answer). The request parser receives `messageLanguage` (`en` or `other`), so a local formalization strategy may translate a non-English message to English before a small model reads it.

Memory sizes shown to a chat user are knowledge files and SOP wires, never circuits: `GET /v1/status`, `GET /v1/memories`, `GET /v1/memories/{id}`, `GET /v1/sessions/{id}` and the review memory list add `knowledge_files`, `sop_wires` and `wires_by_type` (computed once per memory content by `BaseMemories.stats`, cached in `stats.json`); the `circuits` and `facts` counters stay, `facts` being the stored-fact index.

## Chat data, sessions and stored circuits

All chat data lives under one gitignored root, `chat_data/` (`chatData.root` in `config/runtime.json`, `CHATSOP_CHAT_DATA`), with `base_memories/`, `sessions/` and `tmp/`; a cleanup policy removes temporary folders older than `chatData.tmpTtlHours` (24) and sessions idle for `chatData.sessionTtlDays` (14) at start and every `chatData.cleanupIntervalMinutes` ([DS022](specsLoader.html?spec=DS022-sessions-and-base-memories.md)). A chat runs in a **session**: a working copy of a chosen **base memory** (a named, forkable knowledge store of any memory strategy, [DS005](specsLoader.html?spec=DS005-memory.md) and DS016 to DS021) cloned into the session folder; the chat request carries `session_id`, and one automatic session per user and conversation on the default base memory serves requests without one. The default base memory is `chatData.defaultBase`, the encyclopedic `world-v1`; when it is not loaded the minimal `default` (importing `core-min`) is used; every session is a fork of its base memory. Knowledge circuits written by the direct author (from attached files or instructions) are validated and stored in the session layer at once; an invalid circuit is refused and nothing is stored. There is no manual accept or reject of knowledge. The request parser keeps the parse record in the packet (`parse: {parser, model, rounds, cost_usd, ms, cache, ...}`) so the trace shows the models, rounds, time and cost.

## HTTP contract

`GET /docs` redirects to `/docs/`, which serves the repository documentation site statically (`docs/index.html`, the wiki, the wire help, the specification matrix and the DS files). Static serving needs no bearer token, is read-only, never lists a directory, refuses any path that resolves outside `docs/` (encoded traversal and NUL bytes included) and sets `no-cache` for HTML and a short cache for other assets. The chat API keeps its authentication.

For a signed-in session the server also serves a fixed allowlist of repository Markdown read-only as plain text (`REPO_MARKDOWN` in `server/http.mjs`), so the owner can read the skills and project files on the server. One shared menu (`server/pages/site-menu.mjs`, mirrored in `docs/partials/header.html` and checked by `node tools/site-menu.mjs --check`) links the server pages and the documentation. `node tools/check-links.mjs` crawls the served site (its own server on a temporary port with temporary state, signed in) and fails on any broken link or `#anchor`; `tests/docs/site-links.test.mjs` runs it in `npm test`.

Every `/v1/*` path requires a bearer token or the administrator session cookie.

| `GET /v1/models` | The façade model and the availability of the formalizer. |

The request fields `parser` and `language` do not exist: the circuit is written by the session's formalization strategy, and the answer language follows the message (section "Answer language"). Endpoints of the earlier tiny-model branch (`/v1/symbolic/*`, `/v1/understand`, `/v1/language/proofread`, `/v1/text-to-clean-english`, `/v1/emotion/detect`, `/v1/server/models`, `/v1/route`, `/v1/sessions/{id}/scope-answer`, `/v1/models/{id}/start`, the corpus audit page `/audit`) are not part of the product; the capability-API specification is archived at `probably_obsolete/tinyLLMExperiments/specs/DS030-capability-apis.md`. The reference with executable examples is `docs/api.html`.

`POST /v1/chat/completions` accepts one **new** `{role:'user',content:'...'}` message (any language), `model` (the façade id listed by `GET /v1/models`; any other value is refused with 400 `unknown_model`), optional `conversation_id` (default `default`), optional `session_id`, optional `stream`, optional `chatSop.trustedSop`, and optional `adapter` (`{mode: 'stepwise'|'routed'|'direct-verified', options?: {tiers?, routed?}}`; an unknown mode or option is refused with 400). Any other parameter is refused with 400. The server, not the client-supplied message list, owns conversation history; arbitrary prior roles, tools/function calling and unsupported generation parameters are refused. Supplying `user` is optional but must equal the authenticated principal. The default `CHATSOP_API_KEY` authenticates principal `local`; embedded integrations can pass separate named bearer credentials via `createServer({authTokens:{alice:'...',bob:'...'}})`. A shared token is a shared identity and cannot provide multi-user isolation. A circuit that is written but not admitted or cannot be executed answers 422 `model_output_rejected` with a partial `chatSop` (`status: rejected`, `rejection`, `model_sop`, `parse`); nothing is executed or written.

The normal completion is an OpenAI chat-completion envelope with `choices[0].message.content` (the answer: the deterministic English rendering, or its formulation in the message's language under section "Answer language") and `chatSop` containing `model_sop` (the circuit the formalizer wrote), the generated execution `circuit`, proof `provenance`, reasoner `backend`, reported `fallback`, `completeness`, authoritative `cnl`, `status`, clarification `pendingSop` and `required` when applicable, the rendered `user_statements`, `carried_statements`, `model_assumptions`, `assumption_policy` and `assumption_branch`, the `unclear` kind and the `understood_as` reading of a not-computable problem when present, `reply` and `near_miss` (section "Answer language"), the `parse` record (with `strategy`, `tried`, `rounds`, `repairs: [{round, problems: [codes]}]`, `vocabulary_dialog`, `retrieval`, `cost_usd`, `ms`, `cache`), `strategy`, `linking`, `retrieval` (the slice), `route`, `verification` (the oracle check of a routed answer, `route.verification`), `session_circuits` (session definitions written this turn, already stored in the session layer when valid), `session` (id, base memory, formalizer, adapter mode), `adapter` (the ChatSOPAdapter answer packet: mode, answering path, verification status and agreeing paths, route, every path that ran, circuits, proofs, timings, tiers), `latency_ms`, `formalization_ms` and `turn_ms` (the whole turn). Provenance is observed or conditional as recorded by the runtime; no fabricated confidence is implied. `stream:true` emits the **already validated complete result** in SSE chat-completion chunks and terminates with `data: [DONE]`; it does not stream unverified model tokens. If the client disconnects, no additional HTTP chunks are sent; an already started inference or write is not rolled back. Explicit `/v1/responses`, `/v1/embeddings`, `/v1/tools` and chat tools receive errors rather than mock behavior.

`GET /healthz` and its alias `GET /health` report process liveness (no authentication); `GET /readyz` reports readiness and the availability of the formalizer (503 while not ready).

### Browser pages

When the server has the administrator password store (`npm start`, `startServer`), browser pages are layered on the unchanged session-cookie authentication; they present it and never grant access themselves. Page modules live in `server/pages/` and their routing in `server/web.mjs`. All server pages and the documentation site share one top menu (Home, Chat, Eval, an Experiments dropdown, Admin, a Docs dropdown, then Logout, or Sign in on a signed-out page), defined once in `server/pages/site-menu.mjs` and styled by `docs/assets/site-menu.css`. The layout works at phone width. `GET /assets/sop-code.mjs` (public) serves the shared SOP highlighter (`server/pages/sop-code.mjs`), which the documentation pages use to link SOP blocks to the wire help; the chat trace and the evaluation browser use the same renderer. It links wire types and fields to their help pages and marks a type or field outside the parser contract "undocumented". The structural words `all`, `any`, `match`, `end` and the atom prefix `not`, read from `sop/conditions.mjs` and `sop/parser.mjs`, are grammar: they are rendered as syntax keywords linked to `docs/wire_typs/syntax.html#syntax-<word>` and never flagged (`tests/server/sop-code-syntax.test.mjs`).

- `GET /` is a public home page. It states whether the visitor is signed in, whether the administrator password is set and whether the formalizer is available, and links to `/chat`, `/eval`, `/experiments`, `/admin` and `/docs/`; the shared menu also reaches `/review` (*Knowledge*).
- `GET /login?next=<path>` shows the first-run "choose the administrator password" form while no password exists, and the sign-in form afterwards; a request that already carries a valid session is redirected to `next`. `POST /login` (form-encoded `password`, `confirm` for the first run, `next`) calls the existing `Auth.setup`/`Auth.login`, so the minimum length (8), the throttle (ten failures within a minute) and the scrypt verification are unchanged. Success sets the HttpOnly `SameSite=Strict` session cookie and answers 303 to `next`. `next` is accepted only as a same-origin relative path (a single leading `/`, no scheme, authority, backslash or control characters); anything else becomes `/`. A post whose `Origin` differs from `Host` or that the browser marks `Sec-Fetch-Site: cross-site` is refused with 403. Failures re-render the form with a plain message: mismatched passwords or a too-short password (400), a setup attempt after a password exists (409), a wrong password (401), throttling (429).
- `POST /logout` ends the session, clears the cookie and answers 303 to `/login` (same cross-site refusal).
- A signed-out `GET /chat`, `/review`, `/eval`, `/eval/guide`, `/admin`, `/experiments` or any `/experiments/…` page that asks for HTML (`Accept: text/html`) and carries no `Authorization` header answers 303 to `/login?next=<requested path>`. Every other unauthenticated request keeps the JSON 401 (`unauthorized`) or 403 (`setup_required`) answer, including `/v1/*`, `/readyz`, `/eval/api/*`, `/experiments/api/*` and its alias `/project/api/*`.
- `GET /eval` (authenticated) is the read-only evaluation browser (`probably_obsolete/tinyLLMExperiments/server/eval-browser.mjs`, three-pane layout through `probably_obsolete/tinyLLMExperiments/server/pages/three-pane.mjs`): the sealed suites under `eval/suites/**` and the files under `eval/predictions`, `eval/registry`, `eval/reports/current` and `eval/reports/history` (the last marked historical). For each row it shows the message, the gold target, the evaluator steps with `file:line` citations, the expected result and world, and any prediction with its line diff and recorded outcome. `GET /eval/guide` explains splits, the sealed-test guard, admission, canonical versus execution comparison, the metrics and qualified runs, citing code lines resolved when served.
- `GET /experiments` (authenticated; the menu's "Experiments" dropdown: Index, Topics, Reports, Timeline & live status, Open questions) is the living project history, rendered on the server by `server/pages/history.mjs` from `server/history.mjs`. Every list on these pages is newest first, and nothing shown is ever replaced: records accumulate across project phases.
  - `/experiments` (index): a current-status header (the phase recorded in `status/tasks.json`, the tasks and experiments in progress, the open questions of `questions.md`, the latest journal activity and a count of the computed checks), every task and experiment newest first, and every topic with its note count and latest entry.
  - `/experiments/<id>`: one page per task record of `status/tasks.json` or experiment record of `status/experiments.json` (DS007). The page keeps two sides apart: **Owner** (what the owner asked, why, the owner's decisions and corrections, then a newest-first stack of the related owner decisions from the journal and decision notes) and **Agents / analysis** (what was analysed, tried and run including failed attempts, what was obtained, the conclusions, open follow-ups and evidence links, then a newest-first stack of the related agent notes and journal events). Experiment records are shown in full: hypothesis, the preregistration record rendered, deviations, datasets and hashes, models, results, conclusions and reports. Notes and events are related to a task through its `match` phrases and experiment ids.
  - `/experiments/topics` and `/experiments/topic/<id>`: the topics of `status/topics.json` and one topic's full note stack (`status/notes/<id>.jsonl`), newest first, with browser-side filters by kind and author (`?kind=`, `?author=`) and supersede chains shown both ways ("superseded by …", "supersedes …"); a superseded note stays visible, dimmed.
  - `/experiments/reports[?dir=…]` and `/experiments/report?path=…`: a read-only, newest-first browser of `eval/reports/current/**` and `eval/reports/history/**` (the latter marked historical). Markdown is rendered, JSON is tabulated when simple and pretty-printed otherwise, JSONL, log and text files are shown as text, and a file over 2 MB shows only its first 96 KB. Paths are repository-relative and must resolve, after symlinks, inside one of the two roots; absolute paths, `..`, NUL and backslashes are refused with 400. Cache directories (`cache*`) and test leftovers are listed but not expanded.
  - `/experiments/timeline` polls `GET /experiments/api/status` every 15 s and on focus: the computed checks, the append-only journal `status/journal.jsonl` newest first with an area filter, `status/experiments.json` and `questions.md`.
  - `/experiments/questions`: `questions.md` rendered.
  - JSON APIs for the same data: `/experiments/api/status`, `/experiments/api/tasks`, `/experiments/api/topics`, `/experiments/api/notes[?topic=&kind=&author=]` and `/experiments/api/report?path=…|?dir=…` (same path rules). `/project/api/*` answers the same endpoints as an alias; every other `/project` or `/project/…` browser path answers 301 to the same path under `/experiments`.
  - Agents write the journal with `node tools/journal.mjs` (`lib/journal.mjs`), topic notes with `node tools/notes.mjs` (`lib/notes.mjs`) and task records in `status/tasks.json` (`lib/tasks.mjs`); the schemas are in [DS007-experiment-preregistration.md](specsLoader.html?spec=DS007-experiment-preregistration.md) ("Tasks and topic notes"). The journal and the notes are append-only; neither is product documentation nor, by itself, evidence of a result: entries point at their evidence.
- `GET /chat` (authenticated) serves the browser chat, a sidebar of vertical tabs (Chat, Settings, Base Memory; the open tab is remembered per browser, icon rail below 760 px). *Chat*: a header with the session and its base memory, *New session* (forks the default base memory, marked "(default)", or another one picked from `GET /v1/memories`), *Commit*, the message list (newest at the bottom, a "new messages" pill once the user scrolled up) and the composer (attach button, Enter sends, Shift+Enter adds a line). It posts one user message per turn to `/v1/chat/completions` through same-origin fetch with the session cookie and renders each answer in plain English with a collapsible trace panel built from `chatSop` and ordered as the pipeline: **Formalization** (strategy, a note when an archived strategy was asked for, model, tier ladder, number of questions, escalated questions, cache, latency, cost), **Vocabulary** (the size of the schema neighbourhood and the vocabulary dialog), **Session definitions and assumptions** (each session definition, user statements, carried statements, model assumptions and policy), **Linking**, **Retrieval** (complete or not, the bounds), **Route and verification**, **Answer formulation** (whether the answer was phrased in the message's language, by which model, with the English rendering), **Latency**, then the circuit the author wrote, the execution circuit, provenance, reinforcement, the `unclear` kind, the not-computable reading and a pending clarification. Status codes are explained in plain words: 401/403 sign in again, 503 `parse_unavailable` (the first tier of the ladder could not run, or the strategy is not available on this server, with the reason), 422 circuit refused (`parse_failed` or `model_output_rejected`; the trace shows what was written and why), 409 conversation busy, 429 server busy, 504 time limit, 413 message too long. The browser keeps only a local display copy of the transcript; the server owns conversation context. *Settings*: the formalization strategy selector of the session (from `GET /v1/status`; a strategy that cannot run is disabled with its reason), the first-tier select (element `formalizer-model`, over the tier ladder from `GET /v1/status`), the answer mode select (element `adapter-mode`: server default, step by step, routed, direct verified; saved as the session setting `adapter_mode`), the authoring options and a server status card (`GET /v1/status`). *Base Memory*: a table (name, strategy, size, created, parent) with View, Fork, Add knowledge (validation problems shown), Start session and Create memory ("Built on: encyclopedic / minimal / empty"); the default base memory is marked "(default)". The page is `server/pages/chat.mjs` with `chat/style.mjs` and `chat-product.mjs`; `probably_obsolete/tinyLLMExperiments/tools/ui/chat-ui-shots.mjs` checks it in a browser at 1280 and 390 px, light and dark.
- `GET /review` (authenticated; menu *Knowledge*) is the read-only knowledge browser of [DS022](specsLoader.html?spec=DS022-sessions-and-base-memories.md) "Knowledge browser" (`server/review.mjs`, `server/pages/review.mjs`, `lib/review/`). Its state is in the URL (`?memory=<id>` or `?session=<id>`, then `view=memory&layer=…`, `q=…`, `entity=…`, `predicate=…` or `rule=…`), so the chat trace links entity and relation names to their cards. It has no accept, reject or approve control.
- `GET /admin` keeps server status and token mint/revoke and links to the chat; signing in and the first-run password happen on `/login`.

## Starting it

```sh
# local, documentation + chat API; a formalization model (a Ploinky Workers tier) is needed only to answer chat turns
CHATSOP_API_KEY=<token at least 16 chars> node server/http.mjs            # 0.0.0.0:9999, all interfaces

# loopback only
CHATSOP_HOST=127.0.0.1 npm start
```

The launcher prints the home URL first (`http://<host>:<port>/`); the documentation site is available immediately at `/docs/`, the browser chat at `/chat`, the evaluation browser at `/eval`, and the project history, journal and status at `/experiments`. `CHATSOP_PORT`, `CHATSOP_CONFIG` and `CHATSOP_CHAT_DATA` start a private server on another port with its own configuration and chat data root, without touching the main one. Without an available formalization model the server starts, `GET /readyz` and `GET /v1/status` report it unavailable, and chat requests return 503 `parse_unavailable`.

## Locality, limits, persistence and errors

The default listener is `0.0.0.0:9999`, all IPv4 interfaces (`CHATSOP_HOST`, `CHATSOP_PORT`); set `CHATSOP_HOST=127.0.0.1` to restrict it to loopback. Because the default is reachable from the network, the unauthenticated documentation path, the home page and the first-run password setup on `/login` are exposed to that network, and anything beyond a trusted network still needs external transport security and access controls. Authentication is either the administrator password chosen on the first visit to `/login` (stored only as a scrypt hash in `state/auth.json`, handed to the browser as an HttpOnly session cookie) or a bearer token: `CHATSOP_API_KEY` from the environment, or a token minted on the admin page and stored as a SHA-256 digest. Environment tokens must be unique per principal and at least 16 characters. `limits.maxRequestBytes` (default 65536), `maxContextBytes` (4800), `maxConcurrent` (4) and `timeoutMs` (180000, three minutes, enough for a turn with repair rounds and a vocabulary dialog) can be supplied through `config.server.limits` or `createServer({limits})`. Request byte and message-context oversize return 413; overload returns 429; same-session concurrent calls return 409. On timeout the façade returns 504 while the in-flight operation retains its concurrency slot until settled. Do not retry a timed-out trusted write without checking the session receipt/state. Errors have generic messages and must not echo request content, private claim details, coding-agent output bodies or bearer keys.

Repository sessions are keyed by base, authenticated principal and `conversation_id`. Agent conversational context is stored alongside the repository in a private per-conversation state file; context is reloaded after restart, while repository writes survive independently. Keep the repository and conversation directory inaccessible to other local accounts, and do not expose this API publicly without an independent security review. The HTTP tests use a deterministic completion endpoint to prove wire and process behavior without a real model; benchmark results are measured under [DS012](specsLoader.html?spec=DS012-evaluation-metrics.md), not by this server.
