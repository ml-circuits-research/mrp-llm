## Introduction

Owner decision of 2026-10-01: a chat does not write into one shared database. It runs in a **session** whose folder holds a clone of a chosen **base memory**; knowledge created during the conversation lands in the session layer, and a user can commit it, explicitly, to a fork of a base memory. Instruction or source files, rules, procedures and other knowledge can be sent to the **direct author** (a chain model with the wire-authoring skill, no tools) that writes SOP circuits in a temporary folder. The direct author runs only when the user attaches files or asks for authoring through `POST /v1/author`; its circuits are validated and, with a session, stored in the session layer at once. There is no manual accept or reject of knowledge anywhere (AGENTS.md direction 8, owner correction of 2026-10-02): errors are corrected systematically through tests and interactions.

The circuit-authoring boundary of [DS000](specsLoader.html?spec=DS000-vision.md) and [DS014](specsLoader.html?spec=DS014-model-surface.md) is unchanged: the formalizer sees the user's message and the vocabulary of the memory and writes circuits, never answers and never facts. The rules of AGENTS.md directions 4, 5 and 7 hold: asserted statements are turn-local evidence kept in the session's conversation context; knowledge accumulates only through explicit approval; a read hides no write. [DS009](specsLoader.html?spec=DS009-local-server.md) describes the server; the memory strategies are [DS005](specsLoader.html?spec=DS005-memory.md) and DS016 to DS021.

## Core Content

**English-only base memories (owner decision of 2026-10-01).** Every base memory, the seed memories (`core-min`, `core-en`, `demo`) and `world-v1` included, holds English knowledge only: lexemes are `language en`, labels and aliases are `en`, and the validator rejects any other language tag (`non_english_knowledge`). The formalizer reads a message in any language and writes the circuit in English terms of the memory vocabulary, and answers are English, so no session depends on the language of its user. Import layers are snapshots, so a changed seed is renewed in a chat data root with `node tools/refresh-seed-memories.mjs --apply` (dry run by default; memories with circuits of their own are never deleted), and `world-v1` is rebuilt with `node tools/world-kb/build.mjs` and `node tools/world-kb/load.mjs --replace --with-core-en` (which also imports `commonsense-v1` unless `--without-commonsense` is given).

**The common-sense layer `commonsense-v1` (2026-10-02).** A seed memory (`config/knowledge/commonsense-v1/`, imports `core-min` and `core-en`) that the encyclopedic base imports, so a chat starts with common sense rather than learning it from interactions; a blank memory is for tests and specialised tasks. It holds: about 2,000 classes of common nouns with their WordNet 3.0 hypernyms (`is_a`), one-line descriptions and part/substance meronyms; typical uses, abilities, places, properties and parts of those nouns from the CC BY 4.0 edges of ConceptNet 5.7 (`used_for`, `capable_of`, `typical_property`, `found_at`, `typically_has`, `part_of`, `made_of_material`; class-level facts: a class symbol in the subject stands for a typical member); and authored rules, defaults and integrity constraints for class disjointness, lifetimes (`older_than`, `younger_than`, `contemporary_of` with a certain "no" when one died before the other was born, `lived_before`, `outlived`, ages), family (`male_child_of`, `female_child_of`, siblings by gender, `uncle_of`, `aunt_of`, `nibling_of`, in-laws, cousins, relatives), geography (`on_continent`, `in_country`, same country or continent) and units (`dimension_of`, `base_amount` in a fine base unit per dimension, `converts_to`). Every wire names its source; the generated files are rebuilt by `node tools/commonsense/build.mjs` from the gitignored caches and carry their licence notices (DS011). Like every knowledge layer it has no manual approval step: it is used once the validator and the automated checks pass (`node tools/commonsense/check.mjs [--world]`, `tests/sop/commonsense-layer.test.mjs`, the sampled integrity check `tools/commonsense/integrity.mjs`), and errors are corrected through tests and interactions. The chat path uses its positive rules (with comparisons and computations); its defaults and integrity constraints serve the knowledge-wire path (`POST /v1/sessions/{id}/query`).

### Chat data root

One folder holds all chat data: `chat_data/` at the project root, gitignored, configured by `chatData.root` in `config/runtime.json` (relative to the project) and overridden by `CHATSOP_CHAT_DATA`. `lib/chat-data/index.mjs` owns it.

| Path | Content |
| --- | --- |
| `chat_data/base_memories/<id>/` | one base memory (below) |
| `chat_data/sessions/<id>/` | one session (below) |
| `chat_data/tmp/` | temporary folders not tied to a session |

Folder identifiers are lowercase letters, digits, `_` and `-` (1 to 64 characters), so a request value never names a path.

**Cleanup policy.** `chatData.tmpTtlHours` (default 24): a temporary folder whose newest file is older goes. `chatData.sessionTtlDays` (default 14): a session whose `last_active_at` is older is abandoned and goes, unless its `session.json` says `kept: true`. Base memories are never removed by the policy. The server runs the cleanup at start and every `chatData.cleanupIntervalMinutes`; `node tools/chat-data.mjs cleanup [--dry-run]` runs it by hand.

**Legacy storage.** Earlier versions kept chats and the memory repository under `state/` (`index.json`, `snapshots/`, `shards/`, `sessions/`, `http-conversations/`). The owner allowed dropping them. `node tools/chat-data.mjs drop-legacy [--dry-run]` removes exactly those paths and keeps `state/auth.json`, `state/cache/` and `state/formalizer-logs/`; it is run with the server stopped.

### Base memories

A base memory is a named, forkable knowledge store (`lib/chat-data/memories.mjs`):

| File | Content |
| --- | --- |
| `manifest.json` | `id`, `name`, `parent` (id, name, strategy, circuits count, fork time, or null), `strategy`, `created_at`, `description`, counters |
| `repo/` | a memory repository ([DS021](specsLoader.html?spec=DS021-memory-retention-and-generations.md)) with one base named `main`, built for the manifest's strategy |
| `circuits/NNNN-<name>.sop` | the validated knowledge circuits in the order they were added: the source of truth the repository is derived from |
| `provenance.jsonl` | one record per addition, import or fork: `approved_by`, `approved_at`, `reason`, `source`, the circuit's SHA-256, the wire count and what was ingested |

**Default base and kinds (owner decision of 2026-10-02).** The encyclopedic memory is the default, empty or minimal memories serve specialised tasks, and every session is a fork. `chatData.defaultBase` names the base memory that sessions naming none fork from; its documented value is the encyclopedic `world-v1` (`ENCYCLOPEDIC_BASE`, a Wikidata subset that imports `core-min`, `core-en` and the common-sense layer `commonsense-v1`, built by `tools/world-kb`), which gives every session common sense and basic knowledge. When `world-v1` is not loaded, the minimal memory `default` (importing `core-min`) is created and used instead, so no chat starts without a vocabulary (`ensureDefaultBase`). `GET /v1/memories` returns `default_base` and `kinds`. `POST /v1/memories` accepts `kind`:
- `encyclopedic`: a copy-on-write fork of `world-v1`; 409 `not_available` when it is not loaded.
- `minimal`: imports `core-min`; the default when neither `kind` nor `imports` is given.
- `empty`: no imports.

`kind` and `imports` are exclusive. The start-up warmup always includes the default base, and `GET /v1/status` reports `default_base`.

**Strategy.** The default is `sqlite` (owner decision of 2026-10-01: the exact, completeness-capable strategy; `memory.engine` in `config/runtime.json`, `DEFAULT_STRATEGY` in `lib/chat-data/memories.mjs`): a base memory created without a strategy, the `default` base memory and therefore the sessions cloned from it use it. `ensureDefaultBase` re-creates an EMPTY `default` base memory of another strategy at start and leaves one that holds circuits alone. The product offers SQLite base memories only (owner decision of 2026-10-01, hygiene cleanup): `/v1/memories` and the Base Memory tab accept no other strategy and refuse one with 400. The other engines of [DS005](specsLoader.html?spec=DS005-memory.md) (`recall-memory`, `holo-memory`, `scan`, `hybrid`, and `exact: true` for the sidecar of [DS019](specsLoader.html?spec=DS019-exact-reference-memory.md)) stay in `memory/` for research and comparison. The repository's memory configuration is the runtime `memory` block with the engine set.

**What the repository holds.** The `fact` wires of a circuit are ingested into the memory strategy (a fact without `valid` is stored with `valid timeless` and counted in `facts_defaulted_valid`; a fact the store cannot lower is listed in `facts_skipped` and stays in its circuit). Every other knowledge wire (rules, defaults, norms, aggregates, methods) lives as a circuit; `theory()` concatenates the circuits for the exact engines (`reasoning/strategies/js-reference`), which read the whole theory.

**Adding knowledge is open to every authenticated user** (owner decision of 2026-10-01, Q-PROD-1: there is no administrator role; every user may create, fork, extend and delete base memories, commit sessions and use the authoring path; authentication itself, a bearer token or a signed-in session, is unchanged). `addKnowledge` validates the circuits with the knowledge validator of `sop/knowledge/` (authoring mode) together with the circuits already stored (duplicate ids, arity, closedness), rejects `jsEval`, any model-surface wire, any `query` wire and any governance field (`approval`, `approved_by`, `approved_at`: the server's record is the provenance), and writes nothing when anything fails (answer 422 with `problems`). On success it stores the circuit, ingests its facts and appends the provenance record with the acting user (`approved_by`: the authenticated user identity, with `approved_at`). There is no implicit write path.

**Fork.** A fork copies the circuits and the provenance, records the parent in its manifest and adds a `fork` provenance record. With the same strategy the repository is cloned by `cloneRepository`: the `snapshots/<sha256>.json` and `shards/<sha256>.json` files are content-addressed, written once through a temporary file and a rename and never modified in place, so they are hard-linked (copy-on-write, no data copy); every other file is copied, so parent and child never share a mutable inode. Isolation guarantee, for every strategy: a write to the child (or to a session clone) never changes the parent's files, and a write to the parent after the fork never reaches the child (`tests/memory/memory-isolation.test.mjs`, which compares the parent's repository files byte for byte). The SQLite strategy keeps no mutable database file in a repository (its bank is a private in-memory SQL database rebuilt from the snapshot rows, DS018), so there is no `-wal` or `-shm` file to share; should a native `.sqlite` file ever appear in a repository folder it is copied through `VACUUM INTO` and its `-wal`/`-shm` files are never linked or copied. With another strategy the repository is rebuilt by replaying the circuits into the new engine (`method: replay`).

### Imports

A base memory may be created with `imports`: base memories whose circuits form its lower layers (`POST /v1/memories` `imports`, `create({imports})`). The manifest records `imports` as the flat, ordered list of `{id, hash}` (each imported memory's own imports first, then the memory itself), and the circuits of every layer are snapshotted under `imports/<id>/`. The theory, the validation of every addition and the lexicon of the memory are computed over its layers: the imports in order, then its own circuits. An import is a snapshot: a later change of the imported memory never reaches the importer; importing again is an explicit act. A fork keeps the imports of its parent. The seed memories `core-min` and `demo` ship in `config/knowledge/` (`lib/knowledge-seeds.mjs`, created at the first start of a chat data root); the `default` memory imports `core-min`, so no chat starts without a vocabulary.

### Composing a base memory

Owner request of 2026-10-02: a base memory is composed from prepared collections chosen with checkboxes. The **base-memory composer** (`lib/chat-data/composer.mjs`; `GET` and `POST /v1/memory-composer`, `docs/api.html` section 5; the "Base memory composer" card of `/admin`) lists every base memory of the chat data root as a layer (the seeds of `config/knowledge` first: core vocabulary, `commonsense-v1`, `world-v1` when loaded, the conversation layer and its collections) with what `seed.json` says about it: `role` (`knowledge`, or `conversation` for a layer of the chat's phrasing), an exclusive `group`, `licence`, `provenance` and `counts`, and whether the stored seed is stale. Building uses the ordinary import path (`create` with `imports`, the layers snapshotted in order and their facts ingested) and records `composition: {layers, at, validated}` in the manifest. The chosen layers are validated together (duplicate ids, arities) unless they exceed 8 MB of circuits (an encyclopedic layer was validated when it was built); at most one layer of a `group` is accepted. A memory is refreshed (deleted and built again) only when it is not a seed and holds no circuits of its own; a seed is renewed by `tools/refresh-seed-memories.mjs`, and a memory with its own knowledge is forked instead (409). Sessions are clones, so a rebuilt memory reaches the sessions started after it.

**The chat's reply memory.** The conversation layer of the chat ([DS023](specsLoader.html?spec=DS023-courtesy-and-emotion.md) "Conversation layer") is the set of conversation layers of one base memory, `conversation.memory` of the runtime configuration (`conversation-default`; without the setting, the seed `conversation-v1` alone). When that memory is missing at start it is composed from `conversation.layers`: `conversation-v1` and the small-talk collections `smalltalk-core-v1`, `smalltalk-empathy-v1`, `smalltalk-self-v1`, `smalltalk-playful-v1` and `smalltalk-professional-v1`. The reply memory also declares the **message acts** the formalizer may name (`cv_act` and its group, description, examples; [DS023](specsLoader.html?spec=DS023-courtesy-and-emotion.md) "The pragmatic wire"), so the formalizer's act questions and the parser's check of a `pragmatic` kind read the same layers; a harness without chat data loads the configured layers with `useConfiguredReplyLayer` (`lib/conversation/index.mjs`). Its conversation layers (not `core-min`, which `conversation-v1` imports) are read by `setReplyLayer`; rebuilding it in the composer reloads the reply layer at once (`reply_layer` in the answer), and the composer, not the configuration, is then the authority until it is deleted. A conversation seed whose snapshot differs from `config/knowledge` is reported at start.

**Small-talk collections** (`config/knowledge/smalltalk-*-v1/`, generated by `tools/smalltalk/build.mjs`; each imports `conversation-v1` and loads alone or with the others). `smalltalk-core-v1` (greetings, farewells, thanks, apologies, how-are-you, weather, weekend, hobbies and sport chat, compliments, acknowledgements, clarification and repair, small talk that leads back to help), `smalltalk-empathy-v1` (frustration, sadness, joy, grief, loneliness, stress, fear, anger, disappointment, embarrassment, tiredness, pride, excitement, nostalgia, surprise, and a crisis reply that points to emergency help without naming numbers or organizations), `smalltalk-self-v1` (who the assistant is, what it can do and knows, no feelings, not human, no internet, no memory beyond the conversation and its base memory, how it works; opinion and advice requests framed honestly; off-topic tasks, manipulation, paradoxes, impossible premises, nonsense hypotheticals, offensive messages, possible irony), `smalltalk-playful-v1` (jokes, riddles, laughter, teasing, and a playful variant `<situation>_playful` of the light situations) and `smalltalk-professional-v1` (group `register`: a formal variant `<situation>_formal` of every situation). The register variants are derived by the collections' rules (`stf_r_formal`, `stp_r_playful` from `st_formal_variant`, `st_playful_variant`) only while the conversation's register is theirs (`cv_register`, from the user's `formal` or `playful` instruction, P-2.2), one priority above the base; without a register the neutral and warm variants answer. Each collection adds `reply` variants to situations of `conversation-v1` and new situations triggered through the layer's own data (`cv_courtesy_situation`, `cv_opening_situation`, `cv_situation_priority`, and rules for the variants that name the memory's topics), declares the message acts that trigger them (`0005-acts.sop`, from the taxonomy's `acts`; `seed.json` lists them under `acts`), and orders its ties with the other act-selected situations (`cv_situation_outranks`, from the taxonomy's `tie_rank` and order). The texts are generated by the job `jobs/smalltalk-replies` (LLM job runner; the worker tier writes variants per situation and register, the auditor tier reviews every item and reports only problems: robotic phrasing, false claims about the system, wrong tone, unsafe advice, duplicates; the decider tier decides retries and escalations), then the knowledge validator, a structural check of slots and lengths, and a deterministic diversity filter (near duplicates by word-set and bigram overlap, also against the replies of `conversation-v1`; distinct-1 and distinct-2 per situation recorded in `seed.json`). The taxonomy (`tools/smalltalk/taxonomy.json`) is the project's own design informed by the label sets of DailyDialog, EmpatheticDialogues, MultiWOZ, Wizard of Wikipedia and Cornell Movie-Dialogs as ideas only ([DS011](specsLoader.html?spec=DS011-source-rights.md), inspired-by, structure only: no corpus text). `node tools/smalltalk/build.mjs check` validates every collection alone and all together and reports slot misuse and unordered priority ties (`build.mjs acts` rewrites only the act declarations); `tests/conversation/smalltalk-collections.test.mjs` and `tests/memory/memory-composer.test.mjs` cover the collections and the composer.

### Lexicon of a memory

Every session links against the lexicon of its own base memory, never a global one (owner decision of 2026-10-01; the global `config/ontology.sop` is retired). The lexicon is compiled from the layered circuits of the memory (`Lexicon.fromCircuits`, DS004 "Lexicon wires": the `predicate`, `lexeme` and `entity` wires and the `is_a` facts) and cached by the hash of those circuits (`chat_data/cache/lexicon/`, a cache that is safe to delete). `BaseMemories.lexicon(id)` gives it for a memory. A session copies the layered circuits of its base into `base_circuits/` when it is created, so its lexicon is `base_circuits/` followed by the circuits stored in the session layer (`Sessions.lexicon(id)`); a circuit stored in the session is visible to the open agent at once (`SessionRuntimes.open` notices changed session circuits and refreshes the lexicon and the repository view), and nothing the base memory later gains reaches the session. The code paths without sessions (CLI, tests, examples) use `demoLexicon()`.

### Sessions

A session is one chat's working copy of a base memory (`lib/chat-data/sessions.mjs`, `server/session-runtime.mjs`):

| Path in `chat_data/sessions/<id>/` | Content |
| --- | --- |
| `session.json` | `id`, `user`, `name`, `base` (id, name, strategy, circuit count at the clone), `settings`, `kept`, `committed_to`, `created_at`, `last_active_at` |
| `repo/` | the base memory's repository, cloned (content-addressed files hard-linked, anything else copied), plus the facts of the circuits stored in the session |
| `base_circuits/` | a copy of the base memory's circuits at the time of the clone: a session is self-contained |
| `circuits/` | circuits stored during the conversation (the session layer), each validated first |
| `requests/<request>/` | one temporary folder per authoring request: `TASK.md`, `skill/`, `input/`, the model's conversation, `status.json`, `result.json` |
| `agent/` | the chat agent's conversation context and last answer (`server/session-store.mjs`) |
| `provenance.jsonl`, `transcript.jsonl` | the stored circuits (kind `add`, origin) and the turns |

**What goes where.** Asserted statements stay turn-local evidence in `agent/` (AGENTS.md direction 5); they are not committed. Persistent circuits written by the direct author go through `Sessions.addCircuit`: it validates the circuit with the base and session circuits and stores it in the session layer at once (provenance kind `add`, with its origin); an invalid circuit is refused and nothing is stored. Definitions the query author writes while formalizing a chat turn take the same path when a chat session exists, and are also reported with `session_circuits: {origin: coding_agent, scope: turn, text}`. Committing a session to a base memory stays a separate act. Labelled assumptions follow DS014 report/branch semantics and are never persisted.

**Queries reason over base plus session.** The chat agent's repository session sits on the session repository, whose base head holds the cloned base plus the stored circuits' facts (`Repository.rebase` moves an open agent onto a new head after a circuit is stored). `GET /v1/sessions/{id}/theory` returns the base circuits followed by the session circuits, and `POST /v1/sessions/{id}/query` runs a query circuit over them on a slice, with the engine chosen by the StrategyRouter ([DS006](specsLoader.html?spec=DS006-reasoning.md) "Routing rules": body `reasoning` `auto` by default or one strategy id run exactly, `verify` `auto|always|never`; the answer's `route` names the choice, the rule and the verification against the oracle): `askMemory` (`reasoning/slice/wire.mjs`, [DS005](specsLoader.html?spec=DS005-memory.md)) takes the rules of the session's theory that can reach the query, retrieves the facts they and the query can use from the session repository by keyed lookups, and answers with `answer.retrieval` and `answer.route` (the slice's size, predicates, bounds, whether it is complete and why not). The whole theory never goes to the engine, and an answer that needs a complete slice (a count, a universal question, `absent`, a default conclusion, an aggregate) over a slice that cannot be proven complete is `status: incomplete`, `reason: partial_retrieval`.

**Commit to a fork.** Open to every authenticated user: a new base memory made as a fork of the base memory's current state plus the session's circuits, validated on top, with provenance (`kind: commit`, source `session:<id>`); the strategy is `sqlite`, the only one the product offers. The base memory the session started from never changes. A session without circuits of its own has nothing to commit (409).

**The chat request** carries `session_id` (`POST /v1/chat/completions`); the answer's `chatSop.session` names the session and its base, and the turn is appended to `transcript.jsonl`. Without `session_id` one automatic session per user and conversation is used, forked from the default base memory. `base` in `POST /v1/sessions` is optional and defaults to the default base memory as well. A session is visible to the user who started it and to an administrator. Without a chat data root (embedding the server in tests) the earlier single-repository path is unchanged.

### The direct author

Knowledge authoring runs without tools and without any agent CLI. `lib/ingest/direct-author.mjs` (`directAuthor`) holds one chat-completion conversation with a model of the chain, called through Ploinky Workers (`lib/pworker.mjs`) by tier name or `<provider>/<model>` (section "Model chain"); the shared checks (`checkFiles`, `vocabularyOf`, `validateAuthored`, `LIMITS`) live in `lib/authoring/circuits.mjs`.

- **The authoring path.** `POST /v1/author {session?, files?, instructions?, model?, wait?}` creates `chat_data/sessions/<id>/requests/<request>/` (or a folder under `chat_data/tmp/`), writes `TASK.md` (from the skill [`sop-wire-authoring`](../../skills/sop-wire-authoring/SKILL.md)), `skill/`, `input/` (the attached UTF-8 text files and the vocabulary already in the theory) and runs the direct author. The system message holds the fence, the skill and its guide; the user message holds the instructions and the attached files; the model answers with `knowledge.sop`, `queries.sop` and `report.md` in delimited blocks. The model is the request `model`, else the configured authoring tier `ingest.tier` (shipped `small`); the session's `formalizer_model` names the first tier of the step-by-step questions and does not choose the knowledge author. The server validates `knowledge.sop` and `queries.sop` with the knowledge validator of `sop/knowledge/` together with the circuits of the theory, and the validator's problems go back into the same conversation as patch rounds (only the wires that change or are added, plus a `remove` block of ids) for at most three rounds. The answer carries the circuits, the validation, the usage (tokens, cost), the time, `model` (the chain id that wrote them), `cost_class` (`subscription` for the openference plan, otherwise `paid_api`) and, with a session, the file stored in the session layer (`added`); an invalid result stores nothing. A failed or timed-out run is a result (`status` `failed` or `invalid`, with a reason), not an error; 429 `author_busy` is the only refusal (a chain with no reachable model returns a failed result with the reason). `wait: false` answers 202 and `GET /v1/sessions/{id}/requests/{request}` reports the phase and, when finished, the result.
- **Fence.** The model has no tools, no shell and no file access: it receives text and returns text, and nothing it writes is trusted until the validator admits it. No secret is ever put in a prompt. Calls carry a Ploinky Workers purpose (`ingest`, or the purpose of the task that runs the ingestion) so Ploinky Workers's request log and audit store can be reviewed offline.

### Ingesting documents into a base memory

Owner decision of 2026-10-02: besides sessions, documents, books and other material are added to base memories, and sessions are then made from those memories. Learning means adding facts, relations, rules and procedures to a base memory, never training a model, and there are base memories for different types of tasks (a task-type base memory: an HR policy memory, a planetary-science memory, ...). The path is `lib/ingest/`, `tools/ingest-documents.mjs` and the endpoints below; it reuses the direct author of section "The direct author".

1. **Rights first.** Every document carries `source.rights` `cleared`, `permissive-attribution` or `owner-provided` ([DS011](specsLoader.html?spec=DS011-source-rights.md)); any other value is refused (`rights_required`) before a model runs. The URL, licence and attribution are kept with the provenance.
2. **Chunking** (`lib/ingest/chunk.mjs`) follows the document's own structure: Markdown headings open sections, consecutive sections are packed while a chunk stays under the bound (default 7,000 bytes), and a larger section is cut at blank lines, so a paragraph or a table is never cut. Each chunk records its heading path, its line range and its SHA-256.
3. **Writing.** A model compiles each chunk with the skill [`sop-wire-authoring`](../../skills/sop-wire-authoring/SKILL.md) (no agent session per chunk). The **direct author** (`lib/ingest/direct-author.mjs`, the only author) holds one chat-completion conversation per chunk with a model named by tier through Ploinky Workers (default tier `small`, `ingest.tier`, thinking off; `reasoning low|medium|xhigh` is passed as `reasoning_effort`; one answer holds at most 5,000 tokens so that it finishes within the call's time limit, a cut answer (`length`, or an answer that ended early upstream: `stop` without usage) keeps its complete wires and is continued, and repairs are patches by wire id): the system message holds the fence of the authoring task, the skill and its guide; the user message holds the chunk's instructions and the attached files as `input/<name>`; the model answers with `knowledge.sop`, `queries.sop` and `report.md` in delimited blocks. Each chunk's instructions give its coordinates, an id prefix (`d<doc>c<chunk>_`) so ids stay unique, the memory's vocabulary together with the circuits merged before the chunk started, and the entity symbols already in use (`known-symbols.txt`), so the same thing gets the same name across passages. Facts carry `quote` (words copied from the passage) and `source` (document and section); eligibility tests, definitions and procedures become rules or defaults over declared predicates, grouped in a `procedure` bundle with a description of the question form they answer. Up to three chunks are drafted at once (Ploinky Workers's rate and plan limits pace the calls) and **merged in document order**: a predicate that a chunk merged earlier declared with the same `args` is kept once, and a chunk that was valid alone but no longer validates with the chunks merged before it continues its own conversation with the validator's problems (bounded by the same repair rounds).
4. **Checks in the repair loop.** The knowledge validator (with the memory's layers and the earlier chunks) and the quote check (`lib/ingest/checks.mjs`: every `quote` must be a contiguous passage of the chunk after typographic and whitespace normalisation) run inside the bounded repair rounds of the author (option `check`; at most three repairs: the problems go back into the chunk's conversation). After the last round, a wire whose quote is still not in the passage is rejected, not stored.
5. **Conflicts with the memory.** A ground fact written by the agent that duplicates a stored one, contradicts it (`not p a` against `p a`) or breaks a declared functional key (`key N`) is held back and reported: memory wins, and nothing is overwritten silently.
6. **Report.** The ingestion (`chat_data/base_memories/<id>/ingestions/<ingestion>/ingestion.json` and `report.md`) lists per chunk what was extracted (wires by type), rejected (quotes not in the source), held back (conflicts), uncertain (reported or hedged facts, defaults, advisory norms and methods, wires without a source sentence), the validator's problems and warnings, and what the author reports as not expressed, with rounds, time and cost.
7. **Storing.** There is no manual acceptance: every validated chunk is stored in the base memory at once through `addKnowledge` (validated again with the memory's current layers) with the provenance `source: {kind: document, ingestion, document, title, document_sha256, url, licence, rights, chunk, lines, section, chunk_sha256}` and the acting user as `approved_by`. The record status is `stored`, `nothing_new` or `failed`; the chunk status is `stored` or `store_failed` (a chunk that no longer validates is not stored). Wrong knowledge is corrected through tests and interactions, not by a review step.
8. **Idempotent re-ingestion.** A chunk whose SHA-256 is already in the memory's provenance is skipped (`already_ingested`) before any model runs: ingesting the same document again adds nothing, and an edited document adds only its changed chunks (a changed chunk whose facts duplicate stored ones is held back by step 5).
9. **Sessions from it.** A session is started on the memory like on any base memory (`POST /v1/sessions {base}`); the session clones its circuits and repository, and the query author links against its lexicon.

**Ingestion v2** (owner decision of 2026-10-03; `lib/ingest/v2/`, the task template `ingest-document` with `version: v2`, target a base memory or a session) replaces the free-form authoring of step 3 by the structure-and-formalizer roles; steps 1, 2, 5, 7 and 8 are unchanged, and v1 stays the template's default until v2 measures better on eval-ingest-v1.

1. **Units.** Each chunk (default 3,000 bytes) is cut into sentences and table rows; a unit keeps its line and its quote, the exact characters of the document.
2. **Structure pass** (`config/ingest/structure-doc-v1.md`, tier `small`): per chunk, the entities with every mention, the relations as predicates with argument kinds and a reading, the values, and the sentences the passage presents as hedged, reported or supposed. Mentions and values must be copied from the passage (one re-ask).
3. **Canonical vocabulary** (`vocabulary.mjs`), deterministic: names that fold to the same symbol, and capitalised mentions that are another entry's name, are one entity (label: the fullest name; aliases: the other names); lowercase mentions stay local hints; one predicate per name and arity. Conflicts (one name with several kinds, a short name inside a longer one, predicates of the same arity that share a word) go to one call (`config/ingest/vocabulary-merge-v1.md`, tier `medium`). An alias two entities claim is dropped and escalated. Day dates are the integers YYYYMMDD (`dates.mjs`, through the runtime's time reader). The shared document relations of `config/knowledge/analysis-core-v1/0002-vocabulary.sop` (`amount`, `unit_of`, `component_of`, `share_of` in percent, `lower_limit`, `upper_limit`, `starts_on`, `ends_on`, `precedes`, ...; library-only relations excluded) join every document's vocabulary and are declared exactly as that file declares them; a relation the structure role marks `one_value` is declared with `key 1`.
4. **FOL per sentence**: the formalizer's FOL role (`fol-v2`, tier `medium` with reasoning, a chunk that cannot be read falls back to `small`) with the canonical vocabulary and the passage's dates as its inventory (`config/ingest/fol-inventory-v1.md`).
5. **Converter** (`to-knowledge.mjs`): the formalizer's reader and clausifier, then knowledge wires with `quote` and `source` (document, section, line). Function terms (arithmetic, the date functions `months_between`, `years_between`, `add_months`, `add_years`, a relation used as a function) become `compute` conditions; a ground statement `Eq(name, number)` names a value for the whole document; `P(x, true|false)` is `P x` or `not P x`. A rule whose conclusion the document denies by a strict rule becomes a `default` (the exception wins); facts of hedged, reported or supposed sentences keep that `status`, their rules are defaults. A predicate is `closed` when its facts all come from table rows, or it is defined only by strict rules over closed predicates.
6. **Repair and alignment.** One repair round per chunk with the converter's findings over the whole document: refused formulas, statements made of a group's name that facts give to members, and rule conditions on values no fact takes; the repair also sees the relations the facts use with their values. A condition that no fact states and no rule concludes is asked once (`config/ingest/align-v1.md`) for a definition through the relations that have facts, with the document's words that justify it as the quote.
7. **Checks before storing**: the quote check, the contradiction check against the memory and the chunks before (memory wins), and the knowledge validator, which drops each wire it refuses (bounded rounds). The vocabulary layer (`ingest-v2-<doc>-vocabulary`) is stored first, then one circuit per chunk, each with its provenance. Everything unresolved is a line of the run's `escalations.jsonl`; the run folder also holds `summary.md` (at most 10 lines), `ingestion.json`, `structure.jsonl`, `vocabulary-<n>.json`, `fol.jsonl`, `align.jsonl` and `knowledge/*.sop`.

| Endpoint | Effect |
| --- | --- |
| `POST /v1/memories/{id}/ingest` | `{documents: [{name, text, title?, source: {rights, url?, licence?}}], model?, purpose?, author?, wait?}`: ingests the documents (200 with the record and the report; `wait: false` answers 202 with the status URL). `author` is `direct` (the only author; the retired `omp` is refused with 400); `model` is a Ploinky Workers tier or a concrete model of a Ploinky Workers provider. 400 `rights_required`, 429 `ingest_busy` |
| `GET /v1/memories/{id}/ingestions`, `GET /v1/memories/{id}/ingestions/{ingestion}` | the ingestions of a memory; one ingestion with its chunks and report |

The command line is `node tools/ingest-documents.mjs create-memory|ingest|label-entities|report|list` (`draft` is an alias of `ingest`; options `--author direct`, `--model`, `--reasoning off|low|medium|xhigh`, `--concurrency N`; header of the file). The record and the report name the author, the model and the reasoning setting; each chunk folder keeps `TASK.md` (the prompt), `transcript.json` (the conversation) and `result.json` (rounds, time, tokens). Long material (a book) is ingested as several documents or as one document of many chunks; the model sees one chunk at a time plus the vocabulary, never the whole book.

### Mining common sense from the problem books

Owner request of 2026-10-02: the owner's school problem books (`datasets_sources/books/`, 7,000 problems up to grade 8, extracted to `datasets_sources/books/eval/items.jsonl`) show which common sense the default base memory lacks; the knowledge is mined from the failures automatically. Facts and general rules are taken, never book text ([DS011](specsLoader.html?spec=DS011-source-rights.md)). The layer **`commonsense-books-v1`** (`config/knowledge/commonsense-books-v1/`, a seed memory that imports `core-min`, `core-en` and `commonsense-v1`) holds what is admitted; `tools/world-kb/load.mjs --with-core-en` imports it into `world-v1` after `commonsense-v1` (`--without-books-commonsense` omits it), so it reaches the chat's default base at the next rebuild of `world-v1`. The ShareAlike layer **`conceptnet-bysa-v1`** (ConceptNet 5.7 edges licensed CC BY-SA 4.0, owner decision of 2026-10-02, [DS011](specsLoader.html?spec=DS011-source-rights.md)) is imported the same way (`--without-bysa` omits it); it stays marked CC BY-SA 4.0 with an attribution README, and the licence passes to `world-v1` and what derives from it.

`node tools/knowledge-mining/mine.mjs --n N` runs unattended, in stages that each leave their file in `eval/reports/current/knowledge-mining/run-<stamp>/`:

1. **Baseline.** `N` unseen problems (stratified sample of `tools/eval/books/sample.mjs`, then marked seen) run through the product chat turn (`tools/eval/books/system.mjs`, strategy LocalLLMStepByStep on one named tier) over a private fork of `world-v1` plus the admitted layer (`tools/knowledge-mining/trial.mjs`, child processes). Scoring uses the rules of `tools/eval/books/score.mjs` and a judge (the default model) for what a rule cannot decide.
2. **Proposal.** For each problem answered wrong, unknown or with no valid circuit, the default model (Qwen3.8 27b on the openference plan through Ploinky Workers, tier `small`, which falls back to DeepSeek) gets the problem, the failure trace (status, the circuit, the runtime's problems; never the gold answer) and the general vocabulary (predicates and the entities whose labels occur in the problem), and writes the GENERAL knowledge problems of that kind need (facts, rules, units and conversion factors, formulas, part-whole and typical relations), or an explicit "none". It uses the direct author of document ingestion (`lib/ingest/direct-author.mjs`): the knowledge validator and a check against the problem's own names run inside its bounded repair rounds.
3. **Deterministic checks** (`tools/knowledge-mining/checks.mjs`): a candidate is dropped when it repeats a wire of the memory (canonical key), names the problem's own people or places (capitalised tokens of the problem that are not labels of the general vocabulary), or copies book text (a shared 8-gram with any book item, or a distinctive 4-gram shared with its problem, the measure of `tools/datasets/no-copy.mjs`); a fact that contradicts the memory (`not p a` against `p a`, or another number for the same atom) is escalated; a declared entity whose English label the memory already has is merged into the existing entity.
4. **Bulk review** of truth and generality by DeepSeek flash through `/u/openrouter` (`lib/llm-review`, kind `config/review/commonsense-wires/`): a confirmed problem is repaired once (validated, re-reviewed) or the wire is dropped and escalated.
5. **Admission.** The surviving wires of a problem form a group with ids prefixed by the problem, validated with the layers and stamped with provenance on every wire (book, problem, proposing model, reviewing model, date; a predicate declaration in a comment line above it). The group is admitted only when the problem rerun with it is correct, a control rerun without it is not (the fix is the knowledge, not chance), and the fixed regression set (`tools/knowledge-mining/regression-set.json`: problems answered correctly in a baseline, which only grows) loses no answer; a loss confirmed by a control rerun withdraws the group whose removal restores it (or every new group). Admitted groups are appended to `config/knowledge/commonsense-books-v1/0100-mined.sop`. There is no manual step; unresolved conflicts go to `escalations.jsonl` and at most ten lines of `summary.md`.

The run records the cost of every call by client name in Ploinky Workers's request log (`knowledge-mining-trial`, `-author`, `-review`, `-judge`: USD of the paid upstream and openference plan credits). A changed layer reaches a chat data root through `node tools/refresh-seed-memories.mjs --apply` and a rebuild of `world-v1`.

### Large inputs through the job runner

Owner decisions of 2026-10-02: every LLM batch job (ingestion, labelling, knowledge mining, bulk review, calibrations, data generation) is a declarative job spec run by deterministic code, and the same runner is the product's way to process large inputs; no model or agent controls the loop. The runner is part of Ploinky Workers (`Ploinky-Worker/lib/jobs/`, manual `Ploinky-Worker/README.md`; Node built-ins only, no import from ChatSOP), and every job, task and TaskLambda call runs as an operation of the Ploinky Workers server; ChatSOP's part is its configuration layer `the Ploinky user configuration (~/.pworker/config.json)` (section `runner`: run folders under `state/llm-jobs/`, the template folder, roles and task limits; section `lambdas`, old name `skills`: project TaskLambdas and the job folders offered as TaskLambdas) and the job library `jobs/` (jobs, templates, job plugins and the project TaskLambdas of `jobs/lambdas/`); every call of a TaskLambda, a job run or a task is a TaskLambdaCall with its own audited folder (Ploinky Workers's calls root).

1. **Two uses.** Building a base memory from documents, books or sources (ingestion and knowledge extraction), and a session that receives a large attachment with instructions ("extract the prices and answer ...", "learn this handbook").
2. **Task folder.** A task (instructions, attachments, target: a base memory id, a session id, or none) gets its own folder `state/llm-jobs/tasks/<task-id>/` (created exclusively, immutable per run, removed after `tasks.keepDays`).
3. **Planning.** One call to the planner role (the `good` tier) chooses one template of `jobs/templates/` (`ingest-document`, `extract-table`, `label-entities`, `bulk-review`) and fills its parameters; the plan is validated deterministically (known template, target allowed, parameters inside the template's schema, ladder inside its allowed tiers, budget inside the template's and the configuration's limits) with one repair round, then refused. The model never writes code or prompts; a caller that knows the template skips planning.
4. **Execution.** A prompt template runs as a job: the attachments cut into chunks, a tier ladder (each item starts at the tier learned for its task kind and climbs while it fails the checks and repair rounds), staged stop rules, the decider on failures, an audit sample. An adapter template wraps an existing pipeline: `ingest-document` calls the direct ingestion of "Ingesting documents into a base memory" unchanged, its model calls tagged with the task's purpose and run id.
5. **Storage.** Results enter the target through the existing store path with no manual approval: the ingestion stores validated chunks with provenance; the sink plugin `jobs/plugins/sop-sink.mjs` adds validated circuits to a base memory (`addKnowledge`) or a session layer (`addCircuit`); records of `extract-table` and `label-entities` stay in the run folder and are returned to the caller.
6. **Summary.** At most 10 lines return to the caller (the library call `task` of `lib/pworker.mjs`, the command `pworker task`); the full records stay in the task folder. The chat turn's attachments and `POST /v1/memories/{id}/ingest` still call the direct ingestion themselves; routing them through a Ploinky Workers task is tracked in `TODO.md`.

Model tiers are configuration, never code: jobs name tiers or roles (planner and decider `good`, auditor `medium`, worker `small`, short questions `tiny`); Ploinky Workers serves the tiers and enforces per-run budgets, the purpose policy and the priority classes (work that can wait runs as `background`, on spare capacity only). Every run writes only its own folder; a summary that enters the repository goes to a dated, run-named path.

### Procedure library

Owner request of 2026-10-02: procedures written by the formalizer or the direct author become reusable, also by small models. A **procedure** is a `procedure` bundle wire ([DS004](specsLoader.html?spec=DS004-sop.md) "Procedures") stored in a base memory: `members` names the predicates, rules, defaults and aggregates that solve one question form, and `description` states that form in words ("Answers: how many days of annual leave does a person get?"). Sources of procedures: the rules a document ingestion grouped into a bundle, and session definitions the query author wrote for a turn that a user stores with `POST /v1/memories/{id}/procedures {id, description, definitions, reason?}` (`procedureCircuit` adds the bundle wire; the circuit is validated with the memory's layers and recorded with provenance `source: {kind: procedure}` like any knowledge).

**Retrieval.** `lib/query-author/procedures.mjs` builds the library of the stored circuits (cached by their text) and matches the message against each description by IDF-weighted content stems; a procedure is offered only when the message shares at least two stems with its description and one of them names its head predicate (the message asks what the procedure concludes). The query author's context (`buildContext`) then puts the head predicates first among the candidate predicates and adds a "Procedures in memory" section with the member wires as SOP, within the same vocabulary byte budget (at most a third of it). `parse.retrieval.procedures` reports the offered procedures. The author queries the head predicate instead of re-deriving the rule; nothing is executed or approved by the retrieval, and a procedure is in force exactly when its members are.

### Analysis procedures

Owner request of 2026-10-03: analysis PROCEDURES are defined as rules in a base memory and applied by the reasoners to the wires a document left in a session or a base memory: contradiction detection in a scientific document, a book or a manual, illogical or wrong statements, KPIs and indicators, and quality evaluations by predefined rules. The analyzer is `lib/analysis/`; it calls no model.

1. **Representation.** An analysis procedure is a `procedure` wire ([DS004](specsLoader.html?spec=DS004-sop.md) "Procedures") whose `scope` carries the tag `analysis`, with a `description`, `members` and `report` lines (atom patterns, proposal P-8 of `experiments/proposal/wire-type-proposals.md`). Its **findings** are the violations of its `integrity` members (`violation ID WITNESS`, with the integrity wire's `message` and `severity`); its **measures** are the rows of its `report` lines (KPIs as `compute`/`aggregate` rules, rubric scores as rules plus weight facts summed by an aggregate); its **parameters** are member facts `analysis_parameter NAME VALUE`, which a run may override by name (`unknown_parameter`, `invalid_parameter` otherwise). A procedure is exactly its members: the analyzer runs those wires and nothing else of the memory, so a helper rule two procedures share is a member of both, and a member that reads a predicate only non-member rules derive is reported as `member_dependency_missing` (`memberLint`). An owner adds a domain procedure as data, in any layer or session, with no code.
2. **The document layer.** The circuits whose provenance says `kind: document` (ingestion v1 and v2 write it; for a session, its own provenance and that of its base memory and the base's layers, matched by the circuit's SHA-256), or the circuits named by `documents` (a circuit name, the document name or the document SHA-256 of the provenance). Without a document layer the answer is `no_document_layer` (422). A document wire that takes the id of a procedure member is `id_collision`. Each piece of evidence is a document wire with `document` (the provenance), `location` (the wire's `source`, else the provenance's line range) and the exact `quote`.
3. **The document view** (`lib/analysis/view.mjs`). Checks over statements in general ("an atom asserted and denied", "two values for one key") need the statements as data. The document layer is closed under the run's rules (the members, defaults desugared, integrity left out) by the oracle's saturation, and every literal whose derivation uses a document wire becomes a fact of the closed view predicates of `analysis-core-v1`: `asserted_atom TEXT`, `denied_atom TEXT` and, for a predicate declared `key N` and a fact without a validity interval, `keyed_value "P KEY" "REST"`. TEXT is the canonical SOP text of the literal: structure, not understanding. Each view fact keeps the document wires and rules of its support set, so a finding over the view is reported with the document's words.
4. **Execution** (`analyzeSession(source, procedures, options)`). The theory of a run is the declarations the members and the document use, the members (with parameter overrides), the document wires and the view. Each query of each selected procedure (the violations of every integrity member, every report line) runs through the StrategyRouter (`reasoning` `auto`, or one engine id run exactly: a query that engine cannot express is listed in `routes.unsupported` and announced in the report, never answered by another engine); every row is explained by the oracle (`mode explain`): its `proof`, its support set and from it the evidence, the `rules` applied and the `view` atoms. A finding found by two selected procedures is reported once with both; so is a measure.
5. **The report.** The packet `{object: chatsop.analysis}` holds `documents`, `procedures` (with the parameters in force), `findings`, `measures`, `counts`, `view`, `routes`, `lint` and `text`. Every sentence of `text` is a `line_*` reply wire of the conversation layer (`config/knowledge/conversation-v1/0080-analysis-lines.sop`, [DS023](specsLoader.html?spec=DS023-courtesy-and-emotion.md)): a finding uses `line_finding_<integrity id>` when the layer phrases that rule, else `line_finding` with the rule's message, then one `line_finding_evidence` per distinct quote; a measure uses `line_report_<predicate>` (slots: the variables of the report line), else `line_report_row`. The code holds no phrasing. A conversation layer in use that lacks these lines (a stored copy older than the shipped layer, renewed by `tools/refresh-seed-memories.mjs`) leaves `text` null with `render_error`; the analysis itself stands.
6. **The starter library** `analysis-core-v1` (`config/knowledge/analysis-core-v1/`, a seed memory importing `core-min`): the view predicates; a document-analysis vocabulary (`amount` with `key 1`, `unit_of`, `component_of`, `breakdown_complete`, `share_of`, `lower_limit`, `upper_limit`, `measure_of`, `plausible_min`, `plausible_max`, `starts_on`, `ends_on`, `precedes`, `born_in_year`, `age_years`, `as_of_year`, `claim_rests_on`, `premise_stated`, `disjoint_classes`, `period_amount`, `period_follows`, `ratio_definition`, `analysis_parameter`; dates are the integer YYYYMMDD of ingestion v2; the relations the procedures count or test for absence are closed, because a document is a closed record); and six procedures: `analysis_contradictions`, `analysis_numeric_consistency` (totals and parts, complete breakdowns, shares, units, stated limits, plausible ranges), `analysis_temporal_consistency` (an end before its start, a stated order against the dates, ages), `analysis_claim_support` (a claim resting on a premise the document does not state), `analysis_kpis` (shares, growth, averages, ratios defined as data; no value over a zero denominator or mixed units) and `analysis_quality_rubric` (`document_quality_v1`, six weighted criteria).
7. **Entry points.** `analyzeSession` and `listProcedures` (`lib/analysis/index.mjs`); the ChatSOPAdapter mode `analysis` (`lib/analysis/adapter.mjs`, registered through the adapter's `registerMode` when the server starts; the request options carry `analysis: {source, procedures?, parameters?, documents?, reasoning?}`); the task template `analyze-document` (ingestion v2 into a base memory, a session or a new session on `analysis-core-v1`, then the analysis of each document's circuits, `analysis.json` and `report.md` in the task folder); and the HTTP routes `POST /v1/sessions/{id}/analyze`, `POST /v1/memories/{id}/analyze` (body `{procedures?, parameters?, documents?, reasoning?, verify?, proofs?}`), `GET /v1/sessions/{id}/analysis-procedures` and `GET /v1/memories/{id}/analysis-procedures` (`server/analysis.mjs`, read only).
8. **Evaluation.** The test set `eval/analysis-v1/` (our own documents with planted issues and the KPI values to compute, `truth.json`) and `tools/eval/analysis/run.mjs`: level (a) over hand-written SOP of each document, the procedures in isolation; level (b) end to end through the `analyze-document` template. The results are recorded in `eval/analysis-v1/README.md`.

### Formalization strategies

The request parser obtains the circuit of a message by one of two **step-by-step formalization strategies** (owner decisions of 2026-10-02), the default of the chat: the system asks short questions and assembles the circuit itself; a model only answers the questions. A Symbolic Model may select instead one of the MRP strategies `DirectSOP`, `SchemaGuidedLLM` or `Ensemble` in its formalize slot (DS025, DS028 "Routed formalizers"), which run through the same request parser. The strategy is a session setting; everything after the circuit (admission, KnowledgeLinker, slice retrieval, StrategyRouter, oracle verification, completeness guard, rendering) is shared and does not depend on it. One-shot formalization, where a model writes the whole circuit with repair rounds (`LLMDirect`), is archived in `probably_obsolete/one-shot-formalization/` (last measurements: commonsense 27/32; books 15/100 one-shot against 27/100 step by step on `tiny`): larger tiers answer the same protocol questions, so tiers are compared like with like, and the protocol learns to ask the questions small models can answer.

| Strategy | What writes the circuit | Transport |
| --- | --- | --- |
| `LLMDirect`, `CodingAgent`, `LocalLLMDirect` (archived names) | nothing of their own: a session or caller that names them runs the server's default step-by-step strategy, and the parse record carries `strategy_note` | — |
| `LocalLLMStepByStep` (server default) | the symbolic system asks short questions (numbered choices, short lists) and assembles the circuit itself | the Ploinky Workers tier ladder (section "Tier ladder"); `lib/query-author/step-by-step/` (section "LocalLLMStepByStep") |
| `InternalReasoningStepByStep` | the same kind of short questions, but the questioning protocol is a base memory of wires and the JS oracle plans each next question | the Ploinky Workers tier ladder; `lib/formalize/internal-reasoning/` (section "InternalReasoningStepByStep") |

**Session setting.** `settings.formalizer` is `null` (the server default) or one of `LocalLLMStepByStep`, `InternalReasoningStepByStep`, `DirectSOP`, `SchemaGuidedLLM`, `Ensemble`; the archived `LLMDirect` (and the earlier names `CodingAgent`, `LocalLLMDirect`, stored as `LLMDirect`) is still accepted and runs the default step-by-step strategy with a `strategy_note` in the trace (`lib/chat-data/sessions.mjs`, `resolveStrategy` in `lib/formalize/strategies.mjs`). It is set by `POST /v1/sessions/{id}/settings {formalizer_model?, formalizer?, adapter_mode?}` or in the `settings` of `POST /v1/sessions` (`adapter_mode`: section "Answer modes of a session"). `formalizer_model` (it replaces `omp_model`, still accepted on input) names the first tier of the ladder for the session's questions: a tier on the ladder starts it there and the ladder continues upward; another tier is the only rung. A turn whose strategy the server cannot run is refused when it starts with 503 `parse_unavailable` naming the strategy (`server/status.mjs` `strategyRequest`), never silently replaced by another; `GET /v1/status` (DS009) lists each strategy with `available`, the `reason` when it cannot run, its backend, its `ladder` and endpoint. The parse record and `chatSop.strategy` name the strategy that wrote the circuit.

**Configuration.** `queryParser.strategy` is the server default (`LocalLLMStepByStep` shipped, method `B`; the environment variable `CHATSOP_FORMALIZER` overrides it); a session's `formalizer` overrides both for its turns. `queryParser.local` configures who answers the questions of both step-by-step strategies: always Ploinky Workers tiers (`local.tier`, and `local.ladder`, section "Tier ladder"), with `maxTokens` and `thinking` (false: `enable_thinking` off); the product starts no llama-server, and an explicit `endpoint` or `gguf` is refused (`invalid_strategy`): a local GGUF is configured as a Ploinky Workers provider and tier. The local 27B model never runs. The registry is `lib/formalize/strategies.mjs` (`FORMALIZATION_STRATEGIES`, `DEFAULT_STRATEGY`, `ARCHIVED_STRATEGIES`, `resolveStrategy`, `ladderOf`, `localStrategy`, `localReadiness`); `queryParser.strategies()` reports a step-by-step strategy as available when Ploinky Workers lists the first tier of its ladder as usable, without starting anything.

**Tier ladder.** `queryParser.local.ladder` lists the Ploinky Workers tiers that answer the questions, smallest first (shipped: `tiny`, `small`, `good`; an entry is a tier name or `{tier, extraBody}`, and `good` is asked with reasoning disabled); without a ladder, `local.tier` alone answers. Every question goes to the first tier. When its answer cannot be read twice (the reader's check) or the tier does not answer, the failed exchange is taken out of the conversation and the same question goes to the next tier with the same history; the next question starts again at the first tier (`createOracle` in `lib/query-author/step-by-step/index.mjs`). Larger tiers never write a circuit; they answer the same questions. The parse record carries `ladder`, `steps`, `dialog` (each answer with its `tier`, a superseded one marked `escalated`) and, when more than one tier answered, `tiers: {answered: {tier: count}, escalated: [{question, tier}]}`. Evaluations run one tier at a time (`--tier`) so tiers are compared on the same protocol.

**Local models.** Local models are Ploinky Workers providers (`the Ploinky user configuration (~/.pworker/config.json)`): Ploinky Workers starts each llama.cpp `llama-server` at boot or at its first request (full GPU offload, flash attention, a configured number of slots with a context per slot, prompt cache reuse), shares it between all clients, stops an on-demand one after its idle time, and refuses a start while a training or parse GPU lock file exists (the request falls back down its tier chain). Prompts put the byte-identical stable prefix first (LocalLLMStepByStep: its rules and the list of answer kinds; InternalReasoningStepByStep: the prefix rendered from the protocol memory) and everything variable last (the request, the candidates and neighbourhood, the step answers), so the server's prompt cache reuses the prefix. How to choose a formalization model is described in [docs/runtime.html](runtime.html#local-formalizer).

**LocalLLMStepByStep.** Owner decision of 2026-10-02: the small model is an oracle that classifies and points; it never writes SOP or JSON. One growing conversation per request; the symbolic system decides every next question from the previous answers and the memory:

1. **Kind** (numbered choice; the list precedes the request so it is part of the cached prefix): yes/no, reachability through a chain of steps, names, a stored value, a count, the highest, the lowest, a numeric puzzle, nothing. The model's answer stands: no word list or pattern over the question second-guesses it (AGENTS.md "No hardcoded understanding"; the former `cueKinds` check was removed on 2026-10-02).
2. **Names**: the entity hints of the message are linked symbolically; an ambiguous name is a numbered choice among its candidates; when nothing links, the model lists the names and each line is linked.
3. **Statements**: the schema neighbourhood (`collectNeighbourhood`, with the memory's repository) rendered as numbered English sentences with letters for the places ("A is assigned to B"), the memory's derived relations first and marked, a stored example or "its words are in the request" when true; the model answers with numbers or 0 (none fits: `unclear relation_not_in_memory`).
4. **Places**: for each chosen statement a lettered choice among the linked names, the request's numbers (only for a number place), "the thing the request asks for", "the value to compare" (highest/lowest) and "anything"; automatic when only one reading exists. Type errors (a name in a number place) and a missing asked place are asked once more; when every place holds a name, a numbered choice decides whether the request is a yes/no question. A count whose asked place is a stored number becomes a value lookup (a derived count relation).
5. **Truth** (yes/no only): true, explicitly false, or absent; absence is offered only for a statement the memory declares closed. **Time**: when the message has a date, the dates are read from the message (asked only when unreadable); one date gives `at`, two give a numbered choice between `during` and `overlaps`.
6. **Puzzle**: unknowns with ranges ("x: 0 to 10"), one arithmetic line per condition (read into SOP words with the usual precedence; parentheses and undeclared names are refused), the goal (possible, min, max, prove) and its expression or claim.
7. **Reachability**: the step statement, the statement the chain must avoid (or none), start and end; the system writes two labelled session definitions (an allowed step, a `default` with `except` when something is avoided, and a recursive chain) and queries the chain. When no statement links two things the kind is asked again without reachability.
8. **Assembly and confirmation**: per-form templates write the model-surface SOP (`assemble.mjs`), the same validator as every author checks it, and a validator report that a name of the request is unused leads to a numbered question for the statement and the place that name belongs to. A deterministic English paraphrase of the circuit is shown with "Is this what the request asks? yes/no"; on "no" the model names the doubtful part and that step and the steps after it are asked again, at most once.

Answers are read robustly (`answers.mjs`: the first option number, number lists, lettered lines, yes/no, ISO and month-name dates, arithmetic lines); an unreadable answer is asked once more and then the strategy stops with `failed` and the reason, never a guess. The result has the common step-by-step shape (status, sop, validation, unclear, usage) plus `steps` (per step: name, answer, ms, input and output tokens, cached and evaluated prompt tokens). Development measurement: `eval/reports/current/omp-tasks/t10-stepbystep.md`.

**The generic question protocol (methods B, D; default B).** Owner decision of 2026-10-02: the question protocol above is method A; `queryParser.local.method` (`A`, `B`, `D`, `B-yesno`; `STEP_BY_STEP_METHODS`) selects the protocol, and the shipped default is `B`, adopted on the measurement of experiment `eval-stepbystep-protocol-v1`. Methods `C` and `B-cue`, which took the aspects from a regular-expression cue table, were removed with that table on 2026-10-02 (owner rule "No hardcoded understanding": the model understands, the system asks and assembles). The generic protocol (`protocol.mjs`, every question template and choice list in `questions.mjs`, circuit writer `circuit.mjs`, session definitions `definitions.mjs`) keeps method A's system message and puts the 13 answer kinds (yes/no, reachability, names, a value, a count, highest, lowest, a numeric puzzle, all/none/most of a group, when/since/until/how long, why, a stated fact, nothing) and the first 8 aspects (a number limit, a choice between named options, an exclusion, a date, a supposition, a two-sided comparison, a second question, a reason) in the byte-identical cached first-turn prefix (`PROTOCOL_PREFIX`); the checklist question adds three more (something that does not hold, a chain of links, the fewest links), kept out of the prefix because a longer prefix list shifted Qwen3-4B's kind answers. Every question is a numbered choice with "0. none", a number list, lettered lines or a part of the request copied verbatim (kept only when it is a verbatim part of the message); at most 16 questions are asked (`MAX_QUESTIONS`; optional re-asks and the confirmation are skipped when the budget is spent). The system reads only structure from the message: its standalone numbers, its written dates (date normalisation) and the memory's names in it. The steps:

1. **Kind** (Q1; 15 kinds, among them `problem` (item 12) and, last but one, `self`: a request about the assistant or its memory, answered by one numbered question (who it is, what it can do, what it knows about, how much its memory holds, one random fact, several facts or examples) and a fixed circuit over the self layer `assistant-v1`; a random fact or examples sample one of the relations with the most facts with `order random` and `limit`, [DS023](specsLoader.html?spec=DS023-courtesy-and-emotion.md) "Conversation layer"), then the **message acts** (`firstQuestion`, P-2.1): the acts are data of the reply memory (DS023 "The pragmatic wire"), asked coarse first and then fine so that no menu lists every act. The coarse question repeats the message with one lettered yes/no line per act group (courtesy, small talk, hard feelings, upset, good feelings, about the assistant, play, off limits, the conversation itself) and a last line "a question, or a request to look something up"; for every ticked group the fine question lists its acts (description and example) as a numbered list; an act that copies a part of the message (the user's name) is followed by a copy question. When Q1 said "nothing to look up" and the last line says there is a question while no ticked act can be the whole request, the kind is asked once more without "nothing"; when Q1 asks for a lookup or about the assistant while a ticked act can be the whole request (`cv_act_standalone`: how are you, a joke, grief, a question about the assistant's feelings), one question asks whether the message also asks about the world, and "no" makes it a message of acts only; the self question then offers "none of these" too. The texts of these questions are protocol data (`formalizer-protocol-v1/0070-acts.sop`). The acts become `pragmatic` wires. "Hello!" costs three short questions.
2. **Aspects**: the model's checklist; an aspect with nothing in the request to build it from (a limit without a number, options without two names) is dropped. The details are asked: the limit each standalone number sets (more than, less than, at least, at most, exactly, none), the option names and the excluded names among the linked names (multi-select), the supposition and the second question copied verbatim (B).
3. **Parts** (D): the model copies the parts of the request, the main question first; each other part gets the clause-role question (supposition, stated fact, time bound, second question, same question, nothing) and, for a supposition or a time bound, its link (if or unless; before, after or when). A supposition becomes `stated` with `certainty supposed` and `if`/`unless $s` on the query; a second question its own query; a part that cannot be formalized an `unparsed` span.
4. **Statements**: the neighbourhood ranked by lexical overlap with the clause (words in more than half of the neighbourhood's statements are ignored: the memory's own vocabulary decides, not a stop list), 8 shown with "show other statements"; when the oracle answers none while exactly one statement shares a content word with the request, that statement is asked once. A relation of the memory whose whole label is in the request ("older than", "outlive", "part of") among the best lexical candidates joins the list even when the bounded neighbourhood filled up with the relations around the named things (commonsense guard, 2026-10-03).
5. **Places**, typed and pre-filled by the memory: each place lists only the choices that fit it (names and entity unknowns in a name place, numbers and value unknowns in a number place) and a name fits a place only when its class fits and, by **observed role fit**, when the memory records it in that place or records it together with the things that fill that place; a name recorded in exactly one place of the statement is placed without a question, and the asked unknown fills the one place left of the first statement; one name or unknown never fills two places of a statement; a choice that does not fit is asked again for that place alone. A word of the request that names exactly one class of the memory ("a city", "a hand") is offered as a choice for the places too (not as a name of the request), so "A is a B" and "A part of B" can hold it where the role fit allows (commonsense guard, 2026-10-03). Unknowns: X (the asked thing), M (each member of a group), V (the ranked or compared value), W (a limited value, its own unknown per statement), P and Q (other shared unknowns); "anything" is a fresh unknown.
6. **Connectivity**: the statements of one question must share an unknown; the possible joins are listed and, when one join is supported by the recorded fillers, made without a question. **Coverage**: a content word of the request that only one unchosen statement names is offered once (at most two).
7. **Truth and negation** (when the checklist ticks "something that does not hold"): yes/no truth (absence only for closed statements); for a list or count question the statement that does not hold is asked (negated, absent when closed).
8. **Aspect handlers**: limits (`compare`; the limited value pre-filled when one place fits or the words next to the number name its statement; a count per group as an `aggregate` session definition), options (`compare any`), exclusions (`except`), two-sided comparisons (the first two linked names; the kind asked: same, smaller/earlier, larger/later, both, how many more; the statement used once per name in the same place, a shared unknown or `compare ?a above|below ?b`; "how many more" a difference of two per-group counts with `compute … minus`), a yes/no question whose two names fill the same place of one statement used twice with a shared unknown ("born on the same day") while the checklist ticked no comparison gets the comparison question once, structure deciding when to ask ("Was Newton older than Einstein?"; also after a validator re-ask added the second statement), quantified groups (`mode every`, the restriction holds the group's name, the quantifier asked; with a single statement the question is a yes/no question), chains (a recursive session definition, `closed` when the step statement is; confirmed by one question), fewest links (bounded layers ranked lowest), reachability (a derived reachability relation of the memory asked first; otherwise method A's chain, start and end asked, the avoided statement named by the copied supposition's words when exactly one statement fits), puzzles (method A's questions), time (`at`/`during`/`overlaps` from the written dates; since when, until when or how long asked for "when"; a declared `time` place is reused).
9. **Re-asks** driven by the validator (unused name, asked place, class mismatch, absence on an open statement), at most two rounds.
10. **Confirmation by forced contrast** (B, D): the paraphrase of the circuit against the paraphrase of one alternative with one oracle-decided slot changed (a derived statement alone, a statement with the same role structure, swapped places when the recorded facts allow it, the truth, the kind, the quantifier, the avoided statement), in an order fixed by the request's hash, plus "neither"; the chosen alternative replaces the circuit when it validates, "neither" redoes one part once. B-yesno keeps method A's yes/no confirmation.
11. **No invalid circuit**: when the answers cannot be assembled into a valid circuit after the re-asks, or no question of the circuit holds any name, number or comparison although the request names something, the strategy answers `unclear` with kind `relation_not_in_memory` and keeps the rejected circuit and the problem codes in its report (`fallback`).
12. **Problem mode** (owner 2026-10-02, DS014 "Problems that state their own data"; `problem.mjs`): the kind `problem` (a result worked out from numbers, things, facts or rules the request itself gives), or a "yes" to one question asked after any other kind ("Does the request itself give the numbers, facts or rules that its answer must be worked out from?"), starts the problem questions: what it asks (computed numbers, the best of several options by a computed number, a yes/no deduction, none); for numbers, every given value as a `name = number` line (a number the message does not write is dropped; a percentage written as a fraction is stated as written and divided by 100 in a rule), the formulas of the asked values as `name = arithmetic` lines (+ - * / ^, parentheses, `round(x, 0.01)`, `ceil`, `floor`; a comparison makes a yes/no check whose rules derive the yes or the explicit no), which values the question asks for, and for a choice the option each computed value belongs to (copied names) and lowest or highest; for a deduction the facts as `thing | property` lines, the rules as `if p and not q then r` lines and the asked `thing | property`. The system writes one session predicate per value or property, `stated` wires for the data, one rule per formula with `compute` lines, and the queries (`rank` over an `option_score` for a choice). An unreadable answer drops the problem questions and the request continues through the general protocol with its first kind. The problem questions are protocol data, not code: `config/knowledge/formalizer-protocol-v1/0060-problem.sop` holds the kinds of problem and their texts, the questions of each kind in order (`fp_problem_step`), the structural conditions of a step (`fp_problem_step_when`: options found, no direction, several formulas), the steps whose unreadable answer ends problem mode (`fp_problem_required`, `fp_problem_exit_kind`), the first kinds after which the own-data question is asked (`fp_own_data_kind`), the fallback kind and every text; the learned-rules layer `config/knowledge/formalizer-learned-v1/` (seed `"chat": false`) follows it and may add hints (`fp_hint`) and invented examples (`fp_example`) to a question or replace its text (the last text wins). Both step-by-step strategies read the two layers through `lib/formalize/protocol-data.mjs`; InternalReasoningStepByStep plans the same questions as the actions `ask_own_data` and `ask_problem` (kind `problem`, choice 13 of `ask_kind`). The layers change only through the formalization improver's regression gate (`eval/formalization-regression`, `jobs/formalization-improve`). Archived on 2026-10-03 (owner decision to rebuild the formalization infrastructure): the stage-A semantic decomposition of problem mode (`0070-decomposition.sop` and `decompose.mjs`, never routed by default), the research layers `formalizer-six-paths-v1` and `formalizer-methods-v1` with their harnesses, and the dual-formalization tooling with its cross-family and tiny-only verifiers; `probably_obsolete/formalization-experiments-2026-10/README.md` lists them with their final numbers.

Measurement after the removal of the cue table (2026-10-02, Qwen3-4B Q4, method B, 24 known-form rows (3 per family F2-F9) and the first 10 natural rows, against the same rows of the earlier `final-B` run): known forms 21 of 24 correct before and after (1 wrong after, 0 before), natural 7 of 10 after and 6 before; questions per request 7.3 against 5.6 on known forms (the acts question and the explicit limit, option and measure questions). ### InternalReasoningStepByStep

Owner decision of 2026-10-02: the step-by-step questions leave the code and become wires of a base memory, and reasoning drives the questioning (plan: `experiments/proposal/internal-reasoning-step-by-step.md`). LocalLLMStepByStep is unchanged; this strategy asks the same Ploinky Workers tier ladder, with its own stable prompt prefix.

**The protocol memory** `config/knowledge/formalizer-protocol-v1/` (seed `"chat": false`: `seedIds()` and the chat roots leave it out, the strategy reads it with `seedCircuits`; every wire id and predicate carries the namespace `fp_`, the code names them without it) uses existing wire types only:

| File | Content |
| --- | --- |
| `0001-vocabulary.sop` | about 200 closed predicates: static protocol data, observations, slots, control |
| `0010-slots.sop` | when a slot is `needed` (by the kind, the aspects, the statements chosen), `settled` (an answer, a default, a value) or `open_slot`; `circuit_complete ← settled kind, absent any_open, absent any_violation`; `formalized ← circuit_complete, assembled, confirmed` |
| `0020-questions.sop` | per question: `question_text` (placeholders `{{name}}`), `answer_format`, `establishes`, `asserts`, `choice`/`choice_text` or `choices_from` (an option source computed from structure and memory data), `zero_choice`, `priority`, `auto_single`; the cached prefix (`protocol_text`, `prefix_section`, `prefix_title`), the plan and question budgets, notes for re-asks, `kind_dependent` and `statement_dependent` answers |
| `0030-actions.sop` | one `askable` rule and one `action` per question (`requires askable Q ?a`, `adds answered Q ?a`, `cost` = model calls; re-asks cost 2; `assemble` is the system's own step, cost 0; the effects a question has besides its answer: `reasked`, `removes assembly_failed`, `removes assembled`) and the `goal` `formalized` |
| `0040-defaults.sop` | early exits: a single candidate links a mention, exactly two names are the options, a name recorded in exactly one place of a used statement goes there, one name and one place in a yes/no question, the asked unknown in a one-place statement, affirmed without a negation, a clause's single statement and single name, the avoided statement named by the supposition's words, confirmed without a contrast |
| `0050-integrity.sop` | the asked unknown in no place, a name in a number place, a number or V in a name place, a superlative without its value, no statement at all, a quantified question without group and scope; a violation blocks the goal and enables a re-ask |

**Control.** Every decision the code adds the request's facts (observations from structure and memory data: mentions and candidates, standalone numbers, readable dates, the statements of the schema neighbourhood with their places and shapes, lexeme hits of the memory's vocabulary, observed role fit, coverage words, validator problems; and the slots established so far) to the prepared protocol and asks the JS oracle (`lib/formalize/internal-reasoning/reasoner.mjs`): one closure that the code reads (open slots, violations, askable questions, the values the defaults derived) and `mode plan` to `formalized` with a policy (maxDepth 12, maxNodes 400, timeoutMs 150). The first action of the cheapest plan is the next question; a plan of no step means the goal holds; `no_plan` before any question means no route (no statement and no number: `unclear relation_not_in_memory`, no model call), later it means the answers cannot be completed into a circuit (the honest fallback). The plan is a receding horizon: answers are unknown when planning, so it is computed again after each answer. The derivation of the chosen `askable` atom (from the oracle's proof) is the trace's reason for the question. When the plan budget is exhausted the greedy choice decides (the askable question of lowest `priority`); `control: 'greedy'` (`queryParser.local.reasoningControl`) is the ablation.

**Questions and answers.** The question texts are byte-identical to the generic protocol's (method B) where the questions coincide, and the cached prefix is the same text. Each `answer_format` has a structural handler (`handlers.mjs`): numbered choices from static choices or an option source, lettered places (an option written out instead of its number is accepted), copied parts, names, dates, arithmetic lines, the forced contrast; a numbered question with one option and `auto_single` is not asked. The answer is asserted as slot facts (`asserts`), then `answered Q ARG` and the action's declared effects. The contrast "neither" asks which part is wrong (the kind, the statements, the places) and that slot is asked again; a quantified question whose statements do not split into group and scope, or "nothing to look up" for a message whose acts line says it asks, asks the kind again.

**Assembly.** `program.mjs` maps the established slots (read from the closure) to the program of `lib/query-author/step-by-step/circuit.mjs` (read-only) and its session definitions (`definitions.mjs`: chains, counts per group, differences, fewest links); `validateQuery` is the only gate. Its problems become facts (`validator_problem`, `repair_target`) that enable the re-ask actions for at most two rounds; an absence on an open statement is negated structurally.

**Result.** The common result shape of the step-by-step strategies (status, sop, validation, unclear, usage, steps) plus `trace` (per decision: control, open slots, violations, askable questions, the plan and its cost, the chosen question, the derivation, the model's answer, the facts established, engine ms), `explanation` (the trace as English lines), `defaults` (the questions the defaults avoided) and a `report` (questions, decisions, avoided questions, engine ms per decision, contrast, fallback).

**Protocol as data.** `node tools/formalizer-protocol/check.mjs` lints the memory (validator, compiled by the oracle, every question complete with a handler and an askable rule, every slot and value read, a dry run without a model from every kind reaches `formalized`); `node tools/formalizer-protocol/replay.mjs --run DIR` formalizes recorded runs again with the recorded answers and reports the first question that changed. A new question type is a question's facts, an `askable` rule and an action; a new format needs a handler.

**Measurement** (experiment `eval-internal-reasoning-stepbystep-v1`, Qwen3-4B Q4, the 89 rows of `eval-stepbystep-protocol-v1`, B as in the checkout on 2026-10-02): `eval/reports/current/internal-reasoning/summary.md`.

### Answer modes of a session (ChatSOPAdapter)

Every turn of a session runs through ChatSOPAdapter (`lib/adapter`, owner decision 2026-10-03), the backend the evaluations use too. **Session setting.** `settings.adapter_mode` is `null` (the server default `config/runtime.json` `adapter.mode`, shipped `stepwise`) or one of `stepwise`, `routed`, `direct-verified`; it is set by `POST /v1/sessions/{id}/settings {adapter_mode}`, in the `settings` of `POST /v1/sessions`, or on the chat page (Settings, "Answer mode"); a single request may name another mode in its `adapter` field (DS009 "ChatSOPAdapter"). In `stepwise` the formalization strategy of section "Formalization strategies" writes the circuit and the session's agent executes it in the session's own memory and conversation context. In `routed` and `direct-verified` a message is a self-contained problem: the structure role routes it, path B, jsEval, engineCode or FOL v2 formalize it, the engines execute each circuit on a scratch memory, two formalizations that agree verify the answer, and a direct model answer is verified, contradicted or reported unverified ([DS003](specsLoader.html?spec=DS003-main-behavior.md)); nothing of the problem enters the session layer and the session's statements are not used. The transcript entry of a turn records `adapter_mode`, and the reply states the verification status through the conversation layer.

### The query author in the chat turn

A chat turn starts by giving the user's message (any language) to the formalizer, which returns the circuit of [DS014](specsLoader.html?spec=DS014-model-surface.md). There is **one request parser** with two step-by-step formalization strategies (owner decisions of 2026-10-02, section "Formalization strategies"); the earlier SymbolicLM parser is frozen history (`probably_obsolete/tinyLLMExperiments/`) and the one-shot author LLMDirect is archived (`probably_obsolete/one-shot-formalization/`). Shared library `lib/query-author/` (retrieval, vocabulary, validator, step-by-step protocol), orchestration `server/query-parser.mjs`.

**Tiers.** The tiers are Ploinky Workers configuration (`the Ploinky user configuration (~/.pworker/config.json)`), never code: `nano` the local Qwen3-0.6B (on demand), `micro` the local Qwen3-4B (on demand; alias `supertiny`), `tiny` the local Qwen3.6-35B-A3B MoE (always on, falling back to DeepSeek v4 flash), `small` the openference Qwen3.8 27b (falling back to DeepSeek v4 flash), `medium` and `good` the openference DeepSeek-V4-Flash (falling back to OpenRouter; `good` under a duration cap), and `best` is served by `tiny` until a stronger model is configured. Readiness comes from Ploinky Workers's tier listing for the first tier of the ladder; a first tier that is not reachable is `parse_unavailable` (503) with the reason, a run whose questions could not be answered or read on any tier is `parse_unavailable` too, and a run that ended with an invalid circuit is `parse_failed` (422). Every call carries the purpose `formalize` (interactive priority). Quality control is offline: Ploinky Workers's request log and audit store are reviewed in batch; a turn makes one formalization and no model vote. Whatever produced the circuit, **the shared symbolic path runs after it**: admission, KnowledgeLinker, slice retrieval, StrategyRouter, oracle verification, completeness guard, rendering. The packet and `chatSop` carry `parse: {parser, strategy, strategy_note?, model, ladder, tiers?, steps, dialog, backend, cost_usd, cache_read_tokens?, ms, cache, mode, retrieval, unlinked?, closest?}`.

**One-shot authoring (archived).** The one-shot author (its guide `skills/coding-agent-query/`, the context builder with a 24,000-byte vocabulary budget, the validate-and-repair loop `authorQuery` with a bounded vocabulary dialog and an answer-shape self-check, the completion backend and the constrained-decoding experiments) is kept for history in `probably_obsolete/one-shot-formalization/`; nothing in the product calls it.



**What it writes.** The result is a set of circuits (`circuits: [{file, role, text, origin: coding_agent}]`): queries and optional session `predicate`, `rule`, `default` definitions, labelled `assumed` propositions, numeric constraints and uncertainty markers. User suppositions use `stated certainty supposed`; assertions and raw `fact` wires are forbidden. Existing predicates are preferred; a new term needs a declaration and a definition over existing predicates, or a short clarification if equally plausible definitions exist. Labelled model knowledge is the last preference and remains conditional. A declaration may mark a new predicate `closed true`, but cannot replace a declaration of memory. Entity strings are names from the message or listed ids. DS014 owns the proposition language; DS004 owns the definition syntax.

**Validate, execute and self-check.** The shared author admission validates model wires and their vocabulary, while the knowledge validator checks the definition layer together with the base and session circuits. Unknown body predicates, duplicate ids, unsafe variables, arity conflicts and stratification errors reject the output. Strong unused mentions, dropped explicit quantifiers and comparisons are errors; a step-by-step strategy re-asks the doubtful question for at most its bounded rounds. `lib/query-author/runtime.mjs` retains the declarative compiler and scheduler but delegates generated query solves to `askMemory`/`routedAsk`, using the base and session circuits plus only this turn's definitions, evidence and conditional facts. Defaults, aggregates, rules and closedness therefore use the same Theory as harness execution. Used steps carry `origins` (memory, definition by the formalizer, assumption by the formalizer); defeated assumptions carry `session_conflicts` with `reason: memory_wins`. A request-local execution callback permits one additional circuit-only answer-shape self-check: status, cardinality and a deterministic circuit reading, never answer values. Its revision passes the same admission and executes once; invalid revisions are reported. `parse.self_check` records the outcome.

**Declaration and condition-use guards.** Admission checks declared roles on direct chat circuits and in the shared author validator; phrase-linked role mismatches are errors, not repair advice. Positional rule/default atoms are checked against declarations by the knowledge validator. Named query matches may omit roles as existential variables (DS014); omission is not a positional arity error. When accepted circuits or a repository/session are available, `validateQuery` also uses the indexed condition-domain check of DS006 before accepting a circuit. Names resolve exactly; phrase mode reuses the declarative compiler's linking semantics. Confirmed `condition_misuse` is repair feedback with the condition, position and bounded observed values, and makes the step-by-step strategy re-ask the place of the condition. This requires no execution preview and works with `selfCheck: false`. The execution guard independently protects cached or directly submitted circuits. The author never automatically swaps or drops a condition, and a refusal after the bounded rounds remains a refusal.


**Failure is honest.** There is no fallback parser. When the first tier of the ladder is not available, or no tier could answer a question, the turn fails with `parse_unavailable` (503); when the questions ran and no valid circuit came back it fails with `parse_failed` (422); a busy agent (`queryParser.maxConcurrent`) is reported the same way; `unclear no_request` (not a question: statements and courtesy) is answered from the circuit without a query. Both errors carry the `parse` record.

**Latency and cost.** Identical requests are cached by normalized message, accepted memory version, conversation evidence, model, guide version, self-check setting and `queryParser.runTag`; fragments also require identical previous-query context. A cache hit has cost zero and executes against the current memory, without a new author round. The initial preview used by self-check performs no proof-use reinforcement or draft write. Only the final admitted turn may perform policy-authorized proof-use reinforcement and store its definitions. Request folders are removed after authoring unless `queryParser.keepFolders`.

### The chat page

The page keeps one session per conversation (the id is remembered in the browser; a missing session is started again on the last base memory). Its three vertical tabs (DS009 "Browser pages") offer: in Chat, a header with the session and *New session* on a chosen base memory, file attachment, a plain-English answer with a trace panel under each message ordered as the pipeline (formalization: strategy, model, models tried, repair rounds with problem codes, cache, latency, cost; vocabulary: schema neighbourhood size and vocabulary dialog; session definitions and assumptions; linking; retrieval: complete or not, bounds; route and verification; circuits), the authoring progress, the validation, report and cost of what it stored, and the commit dialog; in Settings, the formalization strategy selector (an unavailable strategy disabled with its reason), the first-tier select (element `formalizer-model`) over the tier ladder from `GET /v1/status`, and a server status card; in Base Memory, a table of the memories with View (provenance and stored facts), Fork with a chosen strategy, Add knowledge (validated), Start session and Create, open to every signed-in user. The contract the page is built from, with every endpoint and example, is `eval/reports/current/product/ui-contract.md`.

### Chat feedback

Every answered turn of a session is numbered: the chat answer carries `chatSop.turn` and `chatSop.trace_id` (the completion id), and the assistant entry of the session transcript is the turn record (`turn`, `trace_id`, `message`, `text`, `status`, `strategy`, `model`, `model_sop`, `circuit`, `reasoning_strategy`, `backend`; `GET /v1/sessions/{id}/turns/{turn}`). The chat page shows thumbs up and thumbs down under each numbered answer. Thumbs up records a vote at once; thumbs down opens a dialog where the user picks exactly one cause and may add a comment (at most 2000 characters). The causes are `not_understood` (did not understand the request), `wrong_answer` (the reasoning or the facts are wrong), `missing_knowledge` (it should know this), `unnecessary_question` (asked back although the request was clear) and `bad_wording` (correct, but phrased badly, robotic or rude); their labels are page chrome.

`POST /v1/feedback {session, turn, vote: up|down, cause?, comment?}` (server/feedback.mjs) is authorised like the other chat APIs and only for a session visible to the caller. The server joins the vote to the turn record and appends it to `state/feedback/chat-feedback.jsonl` (append-only, gitignored). A down vote is routed deterministically by its cause, once per turn and cause:

| Cause | Destination |
| --- | --- |
| `not_understood` | the formalization error inbox, `reportFormalizationError({source: 'chat-feedback', kind: 'wrong'})` with the authored circuit |
| `unnecessary_question` | the formalization error inbox, kind `unclear` |
| `missing_knowledge` | the knowledge-gap queue `query-gaps.jsonl` of the chat data root (the file the request parser's gap log writes) |
| `bad_wording` | `state/feedback/reply-layer.jsonl`, material for the conversation-layer wires |
| `wrong_answer` | `state/feedback/answer-wrong.jsonl` |

`GET /v1/feedback` (the administrator session only) lists the recent votes grouped by cause; the admin page shows them as a table linking each vote to its turn record. `GET /v1/feedback/stats` counts votes and causes over the latest vote of each turn and user. Feedback is evidence for the offline improvement loops; it never changes a base memory or the protocol by itself.

### Knowledge browser

Owner requests of 2026-10-02: "where can I review world-v1 and core-en" and "search by keywords and see what the current memory knows". The page `/review` and the API `GET /v1/knowledge/*` (`server/review.mjs`, `server/pages/review.mjs`, `lib/review/`) show what a base memory or a chat session knows. They are read only: no route writes knowledge, any method other than `GET` answers 405, and there is no accept, reject or approve step (AGENTS.md direction 8, owner correction of 2026-10-02: errors are corrected systematically through tests and interactions). Every authenticated caller may browse (the server has one administrator identity and no read-only role); a session target must be visible to the caller.

**Targets and layers** (`lib/review/target.mjs`). A target is a base memory (`memory=<id>`) or a chat session (`session=<id>`). A base memory is its import layers in order (the snapshots under `imports/`; a layer whose id is a seed of `config/knowledge/` is marked `seed`), then its own circuits, with the own circuit files that a document ingestion stored (provenance `source.kind: document`) split into one layer per ingestion. A session is its base memory's layers (from `base_circuits/`) followed by the session layer (`circuits/`). Each layer's circuits are parsed once per fingerprint (circuit file names, sizes and modification times) into a summary: wires by type, files, facts per predicate, the vocabulary and theory wires, and a token index of the text values of facts. A fact or an entity is attributed to the first layer that holds it; the largest layer is not indexed and is the default (world-v1: about 357k facts).

**Risk views** (`lib/review/items.mjs`). The items of a layer are its predicate, lexeme, rule, default, aggregate, integrity, procedure, method and norm wires, its class entities, one group per predicate of its facts and one group per class of its plain entities (never one row per fact). A flag marks a likely problem; the risk of an item is the highest weight of each of its flag codes plus 2 for every repeated flag, and a view lists the most risk first. Flags: `no_description` (30), `form_no_evidence` (30: a form with no count in the mined corpus and no Wikidata label or alias of a property its lexeme or predicate cites), `shared_form` (30, or 15 when a `restrict` or `weight` tells the claimants apart: another predicate with the same number of roles claims the form; a role-set variant with another frame length is listed but not flagged), `undeclared` (30), `rule` (15, 5 for a generated projection rule), `converse_frame` (15), `flipped_mapping` and `merged_mapping` (15, world-v1 mapping rows), `review_dropped` (10: the core-en build dropped forms of the predicate), `no_lexeme` (10), `partial_rule` (5), `class` (5), `curated_values` (0). Evidence (`lib/review/evidence.mjs`, absent evidence reported as absent): `eval/reports/current/core-en/mined.json` (counts and example messages), `dropped.json` (forms dropped with the cross-review verdict), `datasets_sources/core-en/wikidata-properties.json`, and the world-v1 mapping of `tools/world-kb/mapping.mjs` with `datasets_sources/world-kb/build-stats.json`.

**Effect, not syntax** (`lib/review/examples.mjs`). A lexeme form is shown as a generated sentence and the atom it maps to, through the lexeme's frame and the predicate's role order ("Beta Labs employs Ana" → `works_at ana beta_labs`); fillers are the labels of one real fact of the predicate when the memory has one, else placeholder names by role class. The predicates the memory's lexicon links the phrase to are listed with it. A fact is rendered through the first English, non-converse lexeme of its predicate. A rule is shown with up to two derivations over the memory's own facts (a bounded join of keyed lookups; conditions other than plain relations are named as not checked by the preview) or, when no stored facts match, one hypothetical derivation over placeholder names, labelled as such. Generated sentences illustrate the vocabulary; they are never knowledge.

**Search and cards** (`lib/review/index.mjs`). Search reads the compiled lexicon's token index (labels, aliases, lexeme forms and ids of entities and predicates; every word must match, the last also as a prefix), the predicate descriptions, the rule wires and the per-layer text index; results are grouped (`entities`, `classes`, `predicates`, `rules`, `facts`), ranked and paged. An entity card gives the label, aliases, classes closed over `is_a`, description, every stored fact in both directions grouped by predicate (keyed lookups of the memory strategy per declared predicate and admissible position, at most 50 per lookup) with its source and layer, and the rules whose bodies use those predicates. Derive asks the oracle (`askMemory`, at most 12 select queries over the heads of those rules with the entity in each admissible position, then `mode explain` for at most 8 derived facts) and returns each derived fact that is not stored with its proof tree and the layer of each stored premise. A predicate card gives roles, description, closedness, readings, the lexemes with per-form evidence and flags, generated sentences, fact counts per layer, example facts, the rules that conclude or use it, the dropped forms and the mapping rows. A rule card gives the SOP, a deterministic English reading and the example derivation. The chat trace links the linked entity and relation symbols and the relations of the schema neighbourhood and of the retrieval slice to these cards over the turn's session.

### Configuration

`config/runtime.json`: `chatData` (`root`, `tmpTtlHours`, `sessionTtlDays`, `cleanupIntervalMinutes`, `defaultBase`, shipped `world-v1`), `answerLanguage` (`mode` `auto|always|off`, `models`, `timeoutSeconds`, `thinking`; DS009 "Answer language") and `ingest` (`author` `direct`, `tier`, `reasoning`, `concurrency`), `llmProviders` (`openference`, `openrouter`, `local`: per Ploinky Workers provider its default model and request settings, no endpoint) and `queryParser` (`strategy`, `local` with `tier`, `ladder`, `method`, `maxTokens`, `thinking`; `timeoutSeconds`, `maxConcurrent`, `cacheEntries`). `CHATSOP_CHAT_DATA` overrides the root.
