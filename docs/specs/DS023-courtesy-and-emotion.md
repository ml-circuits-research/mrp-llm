## Introduction

Owner decisions of 2026-10-01 and 2026-10-02. A message does more than ask or state: it greets, thanks, apologises, says goodbye, asks politely, or shows a feeling (frustration, confusion, urgency, joy, sadness, fear, disappointment, anger). The reply should answer that too: "Hello!" gets a greeting back and no computation, a frustrated question gets an apology for the trouble with its answer.

Owner rule of 2026-10-02 ("No hardcoded understanding", AGENTS.md): understanding a message, including its courtesy and its emotion, is the formalizer's work in the same step that writes the query. The earlier **EmotionDetectionSystem** (a lexicon and regular-expression pre-step in `Agent.turn`, English and Romanian) read the message with hand-written word lists before the formalizer; it is archived under `probably_obsolete/paused/lib/emotion-detection/` (with its configuration, tools and tests) and is used only as a reference number in the evaluation below. This specification had the file name "emotion-detection" until 2026-10-02 (`docs/specs/aliases.json`).

## Core Content

### The `pragmatic` wire

A model-language wire ([DS014](specsLoader.html?spec=DS014-model-surface.md) `MODEL_TYPES`; help page [docs/wire_typs/pragmatic.html](wire_typs/pragmatic.html)): `kind` (a **message act declared by the reply memory**, below), `basis` (`llm` for every formalizer; `lexicon`, `pattern` and `classifier` remain valid for archived experiments), optional `score` (0 to 1, default 1), optional `span` (a verbatim part of the message; admission rejects a span that is not in it with `pragmatic_span_not_in_message`), optional `near $id` (another, non-pragmatic wire of the same output) and optional `source` (the strategy id). `unclear` stays the only wire of its output except for pragmatic wires ("Thanks!" may be `unclear kind no_request` with a `thanks` wire).

**Message acts are memory data** (P-2.1, owner request of 2026-10-03). The kinds are not a list in code: a layer of the reply memory declares them with facts, read by `messageActs` (`sop/message-acts.mjs`):

| Fact | Meaning |
|---|---|
| `cv_act_group GROUP "line"` | a group of acts, asked as one line of the coarse question (groups in file order; a group without a line is not asked) |
| `cv_act KIND GROUP` | an act and its group |
| `cv_act_description KIND "line"` | the act as one line of the fine question |
| `cv_act_example KIND "message"` | a short example message (never an evaluation message) |
| `cv_act_standalone KIND` | the act can be the whole request (how are you, tell me a joke, grief) |
| `cv_act_span KIND "what"` | the protocol copies this part of the message verbatim as the wire's `span` |
| `cv_act_sets_slot KIND SLOT` | the span fills this conversation slot from this turn on (`introduction` sets `user_name`) |

`conversation-v1/0005-acts.sop` declares nine groups (courtesy, small talk, hard feelings, upset, good feelings, about the assistant, play, off limits, the conversation itself) and the 22 earlier kinds plus `introduction`; each small-talk collection declares the acts its situations answer (`0005-acts.sop`, written by `tools/smalltalk/build.mjs` from the taxonomy's `acts`): 41 more, such as `how_are_you`, `ask_joke`, `grief`, `crisis`, `ask_feelings`, `manipulation` and `false_premise`. The parser (`sop/parser.mjs`) admits a kind only when the reply memory in use declares it (`pragmatic_kind_form`, `pragmatic_kind_unknown`); a new act is a few facts in a layer and needs no code change.

A signal is the system's perception of the message: never a fact about the world, never evidence, never stored and never carried to a later turn.

### Compilation and rendering

`sop/declarative.mjs` `compileDeclarative` splits the pragmatic wires from the authored program (`pragmaticOf`, `sop/pragmatic-text.mjs`) and compiles the rest unchanged; they are never linked, executed or used as evidence. `runDeclarative` then:

1. **Courtesy only.** A program of pragmatic wires only, or `unclear kind no_request` with pragmatic wires, is answered by `courtesyResult`: `status: courtesy`, a reply chosen from the conversation layer (below), no computation and no memory change.
2. **With a request.** Every packet of the turn carries `packet.pragmatic` (`{id, kind, score, span, near, source, basis}` per wire) and the result carries `pragmaticSop`.

The formalizer receives the whole message: nothing is stripped before it. The reply is English like every answer; the output edge (`server/answer-language.mjs`) phrases it in the language of the message.

### Conversation layer

Owner rules of 2026-10-02: no user-facing text in code, and the choice of a reply is a judgment made by the reasoning engine, not by if/else code. Every sentence the chat says is a **`reply` wire** (knowledge grammar, [DS004](specsLoader.html?spec=DS004-sop.md); help page [docs/wire_typs/reply.html](wire_typs/reply.html)) of the seed memory **`conversation-v1`** (`config/knowledge/conversation-v1/`, stored as a base memory and visible in `/review`; it imports `core-min` and is not imported by the knowledge memories, since its predicates describe the dialogue, not the world): `situation` (a symbol), `part` (`opening`, `body`, `closing`, or `line`, a sentence of the answer renderer), `language` (English, the knowledge language) and `text` with `{{slot}}` placeholders. Several reply wires of one situation are variants.

1. **Facts of the turn.** `lib/conversation/index.mjs` `turnFacts` maps the result packet to facts, structure only: `cv_turn_status`, `cv_turn_unclear`, `cv_turn_signal` (pragmatic kinds of score 0.5 or more), `cv_turn_language`, `cv_turn_computed` (a rendered answer exists), `cv_turn_answered` (rows, a yes or no, or a count), `cv_turn_candidate` / `cv_turn_candidate_exact` / `cv_turn_candidate_described` / `cv_turn_candidate_relations` (the near-miss search), `cv_turn_topics` and `cv_turn_readings`.
2. **Rules and priorities.** The layer's rules (`0010-situations.sop`) derive `cv_applies SITUATION` (an answer outranks small talk; a near name replaces a dry "no answer"; frustration opens with an apology; a closing signal closes with a goodbye; urgency gives the `short` style); the reply wires become the facts `cv_reply_for`, `cv_reply_part` and `cv_reply_language`, and the generic rule derives `cv_applicable_reply ?r`. `cv_situation_priority` (`0020-data.sop`) orders the situations.
3. **Choice.** The JS oracle evaluates the layer in process (prepared once per layer version, the turn facts added; about 2 ms a turn). Per part, the applicable situation with the highest priority wins; one of its variants is picked with a choice seeded by the turn time; the derivation of each chosen situation ("why this reply") and the situations it outranked go to `packet.reply` (`{opening, body, closing, style, facts, ms, layer}`) and the chat trace.
4. **Composition.** Code fills the slots from the packet (`answer`, `mention`, `candidate`, `candidate_description`, `relations`, `topics`, `readings`, and from the conversation `user_name` and `time_of_day`) and joins opening, body and closing (`composeReply`). The slots the turn can fill are turn facts (`cv_turn_slot`) and the slots each reply names are facts (`cv_reply_slot`, read from its text); the rule `cv_r_unfillable` makes a reply that names a slot the turn cannot fill not applicable, so a personal variant is left out when the name or the time is unknown and the turn never fails for it (P-2.3). A missing layer or situation is a configuration error (`reply_layer_missing`, `reply_missing`), never a built-in sentence.
5. **Ties** (P-2.4). Between applicable situations of one part with the same priority, `cv_situation_outranks A B` decides (data, and rules: a register variant ties as its base does); a tie the data leaves open falls to the situation id in alphabetical order and is reported in the record (`tie`). `tools/smalltalk/build.mjs check` and `tests/conversation/smalltalk-collections.test.mjs` fail on an unordered tie between situations that one message can select (act-selected situations and register variants); the build writes the ordering facts from the taxonomy's `tie_rank` and order.

The answer renderer (`sop/answer-text.mjs`), the host notices (`sop/declarative.mjs`) and the status sentences (`sop/cnl.mjs`) take their sentences from the `line` replies (`line_answer_one`, `line_yes`, `line_sources_used`, `line_status_unknown`, ...) chosen from the structure of the packet; the English inflection of relation phrases (`conjugate`) stays in code as grammar. A sample of one relation (`order random`, DS004 "Sampling") is rendered as one fact sentence per row. The server reads the stored `conversation-v1` at start (`setReplyLayer`) and warns when it differs from the shipped files (`node tools/refresh-seed-memories.mjs --only conversation-v1 --apply`); without chat data the shipped files are the layer.

**Near misses** (`lib/near-miss.mjs`). A turn without an answer (an open answer, `relation_not_in_memory`, `no_request` excluded) gets the closest entities of the memory to the names of the message: the unresolved mentions, or the name-like spans of the message matched against the memory's own name index; accent and case folding, doubled letters collapsed, a Damerau-Levenshtein distance bounded by the name length and one-word matches of longer labels (an algorithm, no word lists). Each candidate brings its description and the relations around it (bounded indexed lookups, about 16 ms per candidate). The packet records `near_miss`; the layer turns it into "Did you mean Socrates (…)?" or, for an exact name the memory knows, a closing that lists what it knows about it.

**Self layer** (`config/knowledge/assistant-v1/`, imported by `world-v1`). Questions about the assistant are ordinary questions about the entity `chatsop` ("ChatSOP"): `description`, `can_do`, `knows_about` (derived by a rule from `entity_count`), `entity_count`, `relation_fact_count`, `memory_size` and `memory_layer`. The statistics are generated from the memory's own lexicon and manifest by `tools/assistant/memory-statistics.mjs` when the memory is built (`tools/world-kb/load.mjs` runs it); the `topics` slot of the replies is computed live from the same lexicon (`lib/assistant/statistics.mjs` `topicsOf`).

**Natural phrasing.** The reply composed from the layer is the draft. The answer-formulation step (`server/answer-language.mjs`, setting `answerLanguage.natural`, default `all`) rewrites an English draft as a natural chat reply with the default model (Qwen3.8 27b of the openference plan, Ploinky Workers tier `small`) under the same rules as a translation: no new fact, every number, source id and proper name of the draft kept, otherwise the draft is shown; a failed call shows the draft at once (no other fallback for this optional step). A non-English message is phrased in its language as before.

### Behaviour layer

Owner decision of 2026-10-02 (`experiments/proposal/behaviour-layer.md`): more dynamism, following the user's instructions symbolically, preoccupations that surface when their occasion comes; every reply is still decided by the reasoner over the conversation layer, and code only maps facts in and fills text out.

- **Reply parts.** A reply is joined from `prefix` (a user instruction), `opening` (tone), `body` (the answer or the main reply), `aside` (a drive's remark), `follow_up` (a drive's question), `closing` and `suffix` (a user instruction); per part the applicable situation of the highest priority wins.
- **Time facts.** The conversation's behaviour state (`lib/conversation/behaviour.mjs`, `context.behaviour`, caller-owned and saved with the conversation by `server/session-store.mjs`) counts the turns and records when each situation was last used, and when each reaction kind (`cv_reaction_kind`, for example all greeting situations are the kind `greeting`) was. Each turn adds `cv_turn_number N`, `cv_turns_since X N` and `cv_seconds_since X S`; a drive never used counts the turns since the start of the conversation.
- **User instructions.** The formalizer writes an `instruction` wire ([DS014](specsLoader.html?spec=DS014-model-surface.md); "From now on always start your answers with «I'm here:»" is `do set`, `kind prefix`, `text "I'm here:"`; "stop starting with I'm here" is `do cancel`, `kind prefix`; "what are my instructions?" is `do list`). The runtime applies it to the behaviour state (`sop/declarative.mjs`: one active instruction per kind; `short` and `detailed` exclude each other; the history keeps when each was set and withdrawn) and the outcome becomes facts (`cv_turn_instruction_set`, `cv_turn_instruction_cancelled`, `cv_turn_instruction_missing`, `cv_turn_instructions_listed`, `cv_turn_instructions_none`) and slots (`instruction`, `instructions`, phrased by the `line_instruction_*` replies). Every active instruction joins the layer as data of the conversation (origin user): a prefix or suffix is a `reply` wire of its own situation `user_uiN` with the user's words, a rule that makes it applicable on every turn and a priority of 100; a style is a rule deriving `cv_style short` (the first line of the answer) or `cv_style detailed` (which also blocks the short style of urgency). The reasoner follows an instruction because it derives it; withdrawing it removes the wires.
- **Drives.** A drive (`cv_drive D`, `cv_drive_cooldown D N`) fires when `cv_drive_ready` (its turns since last use reach the cooldown) and `cv_drive_occasion` (its own rules) both hold: `aside_fact` (cooldown 3; an answered turn whose answer has another stored fact, slot `aside_fact`, and a user who is not frustrated, angry or in a hurry), `check_helped` (cooldown 2; a computed turn after frustration, confusion, disappointment or anger: "Did that help?") and `offer_more` (cooldown 5; an answered turn: what else the assistant can do). Firing records the reaction, which restarts the cooldown.
- **Register** (P-2.2, 2026-10-03). The instruction kinds `formal` and `playful` (they exclude each other) choose the register of the conversation: the layer derives `cv_register KIND` from `cv_instruction_active KIND` and `cv_register_kind KIND` (`0090-personal.sop`), and the register collections derive their variant situations (`<situation>_formal` of `smalltalk-professional-v1`, `<situation>_playful` of `smalltalk-playful-v1`, one priority above the base) only while it holds. Without a register the neutral and warm variants answer. A deployment that always wants one register adds a layer with a rule `when cv_turn_language ?l` `then cv_register formal`.
- **Personalisation** (P-2.3). The act `introduction` copies the name the user gives; the behaviour state keeps it (`slots.user_name`, `personalFacts` in `lib/conversation/behaviour.mjs`), and every later turn gets `cv_turn_user_name` and the slot `user_name`. The part of the day of the turn's clock (the server clock, by `cv_day_part_starts` data: morning 5, afternoon 12, evening 18, night 22) gives `cv_turn_time_of_day PART` and the slot `time_of_day`. Situations of `0090-personal.sop`: `courtesy_introduction_named` / `courtesy_introduction`, `courtesy_greeting_named`, `open_greeting_named`, `courtesy_closing_named`, `close_goodbye_named` and `courtesy_greeting_first_timed` (the first greeting names the part of the day; never "good night" as a greeting, `cv_greeting_day_part`).
- **Decision rules over time.** A greeting within the hour of the last one is answered as a return (`courtesy_greeting_again`, `open_greeting_again`, from `cv_seconds_since greeting`); the first greeting of a conversation introduces the assistant and its topics (`courtesy_greeting_first`, from `cv_turn_number 1`).
- **Trace.** `packet.reply` names, per part, the situation, its priority, the derivation (for example `cv_applies aside_fact ← rule cv_r_drive_fires`, `cv_drive_ready aside_fact ← rule cv_r_drive_ready`, `cv_turns_since aside_fact 3 ← turn fact`) and what it outranked; `packet.behaviour` lists the active instructions and the changes of the turn.

### How each strategy writes them

- **LLMDirect** (archived 2026-10-02, `probably_obsolete/one-shot-formalization/`) wrote the same pragmatic wires from its author guide; the validator accepts the wires (`AUTHOR_TYPES`) and a message of pragmatic wires only is not `no_query`.
- **Instructions.** LocalLLMStepByStep has the answer kind `instruction` (one numbered question: start or end every answer with some words, short or detailed answers, a formal or a playful tone, stop one, list them; the words are copied verbatim from the message; which one to stop is a second numbered question). InternalReasoningStepByStep does not ask for instructions yet (its protocol memory is ir-agent's; the wire and the runtime are shared).
- **LocalLLMStepByStep** (generic protocol, [DS022](specsLoader.html?spec=DS022-sessions-and-base-memories.md) "LocalLLMStepByStep"): after the kind question, `firstQuestion` asks the message acts **coarse first, then fine**, so that no menu lists every act: the coarse question repeats the message and has one lettered yes/no line per act group of the reply memory and a last line for "a question, or a request to look something up"; for every group the model ticks, the fine question lists that group's acts (description and example) as a numbered list, several answers allowed. An act with `cv_act_span` is followed by a copy question (the user's name), kept only when it is a verbatim part of the message. When the kind says "nothing to look up" but the last line says there is a question and no ticked act can be the whole request, the kind is asked once more without "nothing"; when the kind asks for a lookup but a ticked act can be the whole request, the model is asked whether the message also asks about the world, and "no" makes it a message of acts only. For the kind `self` with such an act, the self question offers "0. none of these: something else about the assistant", which leaves the message to the act's reply. The question texts are protocol data (`config/knowledge/formalizer-protocol-v1/0070-acts.sop`); the circuit writer emits one `pragmatic` wire per act (`source local_llm_step_by_step`, `basis llm`, with `span` when copied). "Hello!" costs three short questions (kind "nothing", the coarse acts, the courtesy group). Method A (the first protocol) writes no pragmatic wires.

### Use by the reasoner

The wires regulate the reply only (the opening, closing and style chosen by the conversation layer). The advice mapping of the archived component (urgency: shorter answer and a faster strategy; frustration or confusion: re-check the previous interpretation; a hedge as a supposition; a possible irony asks for confirmation) is not applied by the product; a reasoner use beyond the tone needs a preregistered end-to-end comparison first.

### Evaluation (eval-pragmatics-v1)

Set: `eval/pragmatics-v1/messages.jsonl`, the 300 messages of the archived experiment emotion-detection-v1 (30 each from `bad_english`, `neuro_english`, `symbolic_english`, 29 from `new_cases`, 181 handwritten; English, Romanian and mixed) with the labels of its two judges (Grok and GLM): a kind is positive when both listed it, negative when neither did, disputed kinds are left out of that message. Runner: `node tools/eval/conversation/pragmatics/run.mjs --arm stepbystep|coding|lexicon` and `--report` (records and summary in `eval/reports/current/pragmatics/`). Micro precision and recall over the 14 kinds the step-by-step question can name ("core"), 2026-10-02:

| Arm | Messages | Core precision | Core recall |
|---|---|---|---|
| LocalLLMStepByStep, Qwen3-4B Q4 (acts and emotion questions) | 250 held out (the first 50 were used to word the questions) | 45.2% | 82.5% |
| same | all 300 | 48.0% | 83.1% |
| CodingAgent guide, Claude Haiku as a proxy (GLM quota exhausted) | first 50 | 100% | 100% |
| archived lexicon EmotionDetectionSystem (reference only) | 300 | 93.9% | 86.6% |

Reading. The lexicon number is optimistic: its word lists were written and corrected on these very messages by the author of the handwritten ones. The guide arm is the guide's pragmatic section followed by an LLM, not the full CodingAgent run (which writes the query too); the zai/glm-5.3 arm through omp is still to run (`--arm coding`). Qwen3-4B finds most courtesy and feelings but over-reports them (a plain question read as curiosity or fear; "pls" read as a goodbye); its p50 latency for the acts questions is about 0.5 s on the GPU. Questions were worded on the first 50 messages only; the held-out 250 give the honest number.

### Status and gaps

Implemented and tested (`tests/conversation/pragmatic-turn.test.mjs`, `tests/conversation/conversation-layer.test.mjs`, `tests/conversation/behaviour-layer.test.mjs`, `tests/sop/near-miss.test.mjs`, `tests/formalizer/local-llm-step-by-step-protocol.test.mjs`, `tests/docs/wire-help.test.mjs`). Small talk with the acts as memory data (2026-10-03, `eval/smalltalk-v1`, 40 messages, the product ladder with `tiny` = Qwen3.6-35B-A3B, blind judge tier `medium`, rubric of 2026-10-02): mean reply score 3.60 before (the formalizer could name only the 22 closed kinds) and 4.21 after, paired difference +0.61 (95% paired bootstrap [0.31, 0.93]; 26 better, 12 worse); the arm that adds the message's label as an oracle signal scores 4.19, so the formalizer now reaches it (`eval/reports/history/smalltalk-acts-2026-10-03/report.md`). Live check on a private port: "Hello, how are you?" (`greeting`, `how_are_you`, situation `smalltalk_how_are_you`), "Tell me a joke" (`ask_joke`, `playful_joke`), "I feel sad today" (`sadness`, `courtesy_sadness`), "Is a whale a mammal?" (answered). Observed: the optional natural-phrasing step rewrote the honest how-are-you draft ("I don't experience emotions or days") as "I'm doing well", a claim about the assistant the draft did not make; that step needs the same honesty rule as the reply layer. Open: the CodingAgent arm with zai/glm-5.3 on the 300 messages; better step-by-step precision (the acts question over-reports feelings); whether pragmatic signals improve answers beyond the tone (no preregistered comparison yet).
