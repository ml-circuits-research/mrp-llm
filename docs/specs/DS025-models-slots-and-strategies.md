## Introduction

MRP-LLM builds small neurosymbolic language models. What a user or an API client talks to is a **Model**: a knowledge base (a base memory, DS022) together with the configuration that says how every stage of the pipeline runs on it. The pipeline is a fixed sequence of **slots**; every slot has a fixed contract and several interchangeable **strategies**. Design questions that have no single right answer ("where does a reflex end and reasoning begin", "how much round-trip checking is worth one more model call", "who commits knowledge learned in a conversation", "which sparse autoencoder") are not decided globally: each is a slot with documented strategies and parameters, chosen per Model, with a default. The code lives in `lib/mrp/` (`strategies.mjs`, `models.mjs`, `pipeline.mjs`, `similarity.mjs`), the HTTP routes in `server/mrp-routes.mjs`, the page in `server/pages/models.mjs`.

## Core Content

### Symbolic Model and tier

Two different things are called "model" around MRP-LLM, and the product keeps them apart by name. A **Symbolic Model** is what MRP-LLM exposes: the `model` of the API, the choice in the chat, a base memory plus one strategy per slot; this specification calls it a Model for short. A **tier** is the name a strategy uses for a language model (`tiny`, `small`, `fast`, …); Ploinky Workers maps every tier to an ordered chain of real provider models (for example `fast` → `deepseek/deepseek-flash`, then `zai/glm-5.3-flash`) (DS027). A Symbolic Model never names a real provider model; it names tiers, and the mapping is changed in one place for every Symbolic Model. `GET /v1/mrp/tiers` (read only, every authenticated user) returns every tier with its configured chain and what the running proxy serves now; the chat's *Symbolic Models* tab and the `/models` page show, next to every tier a Symbolic Model uses, the real model behind it.

### Model

A Model has an id (lowercase letters, digits, `-`, `_`; at most 64 characters), a name, a description, a base memory (`base`), an output language (`language.output`: `auto` or a language code), one entry per slot (`slots.<slot> = {strategy, params}`), a FAQ for the reflex slot (`faq: [{id, q, a, variants?}]`) and `allowOverrides`. It is stored as `<chat data root>/models/<id>/model.json`; what the Model learns while it runs (reflex statistics, the learned reflex boundary, the review queue) is stored in `state.json` next to it and is never mixed with the configuration. The knowledge of a Model is one or several base memories (`memories`, chosen with checkboxes on the chat's *Symbolic Models* tab and on `/models`): one memory is used directly as `base`; several are composed into the base memory `sm-<model id>`, which imports them all through the base-memory composer (DS022 "Composing a base memory") and is rebuilt when the choice changes. Memories whose definitions conflict (for example two layers that define the same predicate id) are refused with the validator's problems and nothing changes. Deleting a Model never deletes its base memories. A Model is what `model` names in `POST /v1/chat/completions` and what `GET /v1/models` lists (`owned_by: mrp-llm`, with `mrp.base`, `mrp.language`, `mrp.default`). The server's default model (`mrp.defaultModel` of `config/runtime.json`, else the first model) answers requests that name no Model. The MRP layer is on when the runtime configuration has an `mrp` section; without it the server runs the bare symbolic core.

### Slots

The slots, in pipeline order, are `normalize`, `reflex`, `affect`, `formalize`, `admit`, `link`, `memory`, `retrieve`, `reason`, `verify`, `roundtrip`, `render`, `voice`, `commit` and `discover`. `GET /v1/mrp/strategies` returns each slot with its title, contract, default strategy and strategies; with `?check=1` it adds whether each strategy can run on this server and why not. The slots `formalize` to `render` are the symbolic core inherited from ChatSOP (DS002, DS006, DS009); `normalize`, `reflex`, `affect`, `roundtrip`, `voice` and `commit` run around it in `lib/mrp/pipeline.mjs`; `memory` applies when a base memory is created for a Model; `discover` proposes value schemas offline (DS028).

### Strategies

Every strategy has a slot, an id, a title, a summary, a statement of when to use it, a cost (`none` or the model calls it makes) and typed parameters (`tier`, `number` with bounds, `enum`, `boolean`) with defaults. Parameters are checked when a Model is saved; an unknown parameter, a value out of range or an unknown strategy is refused with a 400 error. A strategy `runs` either on this server or as an `external` strategy that needs components outside the Node runtime (a Python package, a parser, a trained model, a strategy service); an external strategy states its requirement. A strategy that calls a model names a Ploinky tier (DS027) and is available when the proxy serves that tier.

### No silent substitution

A turn whose Model names an external strategy in any slot is refused with 503 `strategy_unavailable` and the requirement; it is never run with another strategy. A server strategy whose tier fails degrades in its documented way and says so in the trace: `normalize` keeps the original message, `reflex` with a judge does not fire, `affect` records nothing, `roundtrip` records that it could not run, `voice` keeps the English answer. The formalizer keeps its own contract (DS009): `parse_unavailable` when no tier can run, `parse_failed` when no valid circuit came back.

### The catalog

`normalize`: `translate-llm` (default: one call detects the language, translates to English, fixes spelling, with `formalize` makes casual wording explicit and, with `context` (default 4 previous turns), rewrites the message so it is self-contained: pronouns and ellipsis resolved, values and facts the user stated in earlier turns restated, never the assistant's answers), `translate-if-foreign` (a cheap check skips English messages), `proofread-llm`, `passthrough`. `reflex`: `faq-fixed` (default for models with a FAQ), `faq-margin`, `faq-feedback`, `faq-llm-judge`, `off`. `affect`: `formalizer-pragmatic` (default, DS023), `llm-label`, `off`. `formalize`: `LocalLLMStepByStep` (default), `InternalReasoningStepByStep`, `Routed`, `DirectVerified`, and the external `SchemaGuidedLLM`, `DependencyScaffold`, `FrameGuided`, `SpladeRouted`, `SaeRouted`, `CNL-ACE`, `Ensemble`, `FineTunedSOP`. `admit`: `validate-repair`. `link`: `knowledge-linker`, external `schema-linker`. `memory`: `sqlite`, and the server-wide engines `hybrid`, `recall-memory`, `holo-memory`, `scan` (selected by `memory.engine` of the runtime configuration, DS005) and the external `splade-index`, `dense-index`. `retrieve`: `slice`, external `splade-slice`, `graph-walk`, `hybrid-rerank`. `reason`: `strategy-router`. `verify`: `oracle-js`, external `cross-engine`. `roundtrip`: `on-doubt` (default), `off`, `lexical-always`, `lexical-sampled`, `llm-judge`, external `embedding`. `render`: `answer-text`. `voice`: `natural-rephrase` (default), `translate-only`, `english-only`. `commit`: `manual` (default), `review-queue`, `auto-validated`, `never`. `discover`: `manual`, and the external `splade-stats`, `llm-consolidate`, `frame-seed`, `sae-llm-activations`, `sae-sentence-embeddings`, `sae-pretrained-dictionary`. `lib/mrp/strategies.mjs` holds each strategy's full description and parameters and is the source of truth for this list.

### Effective configuration and overrides

The configuration of a turn is computed in layers: the catalog defaults, then the Model's slots, then the session's settings (`slots`, `language`; `POST /v1/sessions/{id}/settings`), then the request's `metadata` (`{slots, language}` in `POST /v1/chat/completions`). A later layer that names a strategy replaces the earlier strategy and its parameters; a later layer that gives only parameters tunes the current strategy. Session and request layers apply only when the Model has `allowOverrides`; otherwise they are ignored and the trace says which layers were refused. `GET /v1/mrp/models/{id}/effective` returns the Model's own effective configuration.

### The turn

For a chat turn the server resolves the Model (the session's Model when `session_id` is given, else the request's `model` when it names a Model, else the default Model). A request without `session_id` uses one automatic session per user, conversation and Model, on the Model's base memory; `POST /v1/sessions` with `settings.model` starts a session on the Model's base memory unless a base is named. The chat's *New session* dialog chooses a Symbolic Model, not a base memory: the knowledge comes with the model. The turn then runs `normalize`, `reflex` (a reflex answer ends the turn: it goes through `voice` and is recorded in the transcript with `status: reflex`), `affect`, the symbolic core on the English text (the formalize strategy chooses the ChatSOPAdapter mode: `Routed` runs `routed`, `DirectVerified` runs `direct-verified`, the step-by-step strategies run `stepwise` with the strategy's tier as the first rung); the session's own formalization settings (`formalizer`, `formalizer_model`, `adapter_mode`, the *Settings* tab of the chat) override the formalize slot when the Model allows overrides, `roundtrip`, `voice` and `commit`. The response carries `mrp` (and `chatSop.mrp`): the Model, the original message, the English text, the detected and output languages, the reflex hit, the affect, the round-trip result, the effective slots, the overrides and a trace entry per slot with strategy, duration and outcome. The deterministic English answer stays in `chatSop.english_text`.

### Reflex boundary

The boundary between an instant reflex answer and full reasoning is a setting. The FAQ is matched in English after normalization, so one English entry serves every input language. `lib/mrp/similarity.mjs` scores a message against every question and variant (token cosine with idf over the FAQ, light stemming, a short list of English function words); an entry scores as its best question. `faq-fixed` fires at a fixed threshold (default 0.6). `faq-margin` also requires the best entry to lead the second by a margin. `faq-feedback` starts at a threshold and learns it from votes on reflex answers (`POST /v1/feedback` on a reflex turn, or `POST /v1/mrp/models/{id}/reflex-feedback`): a down vote raises the boundary to just above the voted score, by at most one `step`; an up vote on an answer whose score was within two steps of the boundary lowers it by half a step; the boundary stays within `[min, max]` and is stored in `state.json`. `faq-llm-judge` uses a low threshold to select a candidate and a small model to confirm that the message asks the same thing. `off` never fires.

### Round-trip check

Whether to restate a formalization in English and compare it with the message is a setting, because its value depends on the cost of a misread question in the Model's domain. `off` never checks. `on-doubt` (default) checks only when the circuit holds `unclear`, `unparsed` or `assumed` lines or a formalization question escalated to a larger tier. `lexical-always` checks every formalized turn and `lexical-sampled` a random share (`rate`); both compare the restatement with the normalized message by token cosine against `threshold`. `llm-judge` asks a model whether the two ask the same thing. `onMismatch` is `note` (recorded in the trace) or `warn` (the answer also tells the user how the message was understood and asks to rephrase if that was not meant). The check never changes the computed answer.

### Commit policy

What happens to definitions and assumptions the validator admitted into a session during a turn is a setting. `manual`: they stay in the session and a user commits the session into a new base memory (`POST /v1/sessions/{id}/commit`). `review-queue`: they are queued on the Model; an administrator approves (they are written to the Model's base memory through the knowledge validator, with provenance naming the approver and the session) or rejects each item on `/models` or with `POST /v1/mrp/models/{id}/review/{item}/approve|reject`. `auto-validated`: they are written to the Model's base memory at once through the same validator, with provenance `auto-validated:<user>`; a circuit the validator refuses is reported in the turn's `mrp.commit` and nothing is written. `never`: sessions of the Model never change a base memory and explicit commits are refused with 403 `commit_refused`.

### Profiles

A profile is a ready-made Model configuration in `config/profiles/<id>.json` (`GET /v1/mrp/profiles`). The shipped profiles are `general`, `acme-demo`, `support-bot`, `rigorous-judge`, `companion-edge` and `research-bench`. Profiles with `createOnFirstStart` become Models when the server starts with no Model and their base memory exists. `POST /v1/mrp/models` with `profile` starts from it; with `createBase: true` it also creates the named base memory (minimal, importing `core-min`) on the engine of the `memory` slot.

### Administration

The chat has a *Symbolic Models* tab (below *Base Memory*): it lists the Symbolic Models with, for each, every slot that calls a language model, its tier and the real model behind it; it switches the chat to a Symbolic Model, changes the tiers of a Symbolic Model's slots (`PUT /v1/mrp/models/{id}` with `slots`), creates a Symbolic Model from a profile on a base memory, and shows the tier table of Ploinky Workers. Strategies, FAQ, overrides and the review queue are edited on `/models`.

`GET/POST /v1/mrp/models`, `GET/PUT/DELETE /v1/mrp/models/{id}`, `GET /v1/mrp/models/{id}/review` and the page `/models` manage Models for every authenticated user, like base memories (DS022). The page edits the general fields, one strategy and its parameters per slot (external strategies are listed with their requirement and cannot be selected), the FAQ with variants, and shows what the Model learned and its review queue.
