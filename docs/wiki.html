Overview / Concepts and execution flow

What the ChatSOP components do

ChatSOP separates understanding a question from answering it. A language model proposes a structured problem in SOP. Ordinary program code checks that proposal, retrieves permitted knowledge, and runs a solver. Another code step turns the result into text. An optional language model can then improve the wording. The model's fluent answer is not used as the proof.

Follow one question through the system

Suppose the user asks: “In which country does Maria work?” The permitted knowledge contains two facts—Maria works at Acme, and Acme is located in France—and an approved rule connecting those relations. The identifiers and relation names below are illustrative; the runtime must actually supply them before a model can use them.

  1. The conversational agent prepares the request. It reads the user's text and selects the permitted session. The request parser gives the session's formalization strategy the message, the authoring guide and the schema neighbourhood of the session's memory (the relations around the entities the message names, with roles and a few examples). It never receives answers, other sessions or the whole memory. The runtime, not the model, chooses whose knowledge is visible and links the model's strings to it afterwards.
  2. The author returns SOP, not “France.” It writes the question as a match block with a relation from the neighbourhood (or a quoted phrase), role subject "Maria" and role location ?country, and requests ?country. The runtime then links the relation to its predicate (for example works_in_country) and “Maria” to a known person; if either cannot be linked safely, the runtime asks the user instead of guessing an identifier.
  3. The agent and runtime validate the proposal. They check allowed symbols, field syntax, references, variable types, declared roles, the domains of conditions and permitted operations, and send problems back for bounded repair rounds. An invalid or unauthorized circuit is not made safe by a confident model response.
  4. The runtime executes the solve operation. For a knowledge query, it invokes the linker. The linker finds the approved rule whose conclusion answers the requested relation and asks the retrieval layer for the required facts.
  5. Retrieval reads the permitted repository view. It returns Maria's employment fact and Acme's location fact, with source/time information and completeness indicators. Retrieval chooses candidates; it does not itself prove the answer.
  6. The reasoner applies the rule and matches the query. It produces an answer assigning France to ?country, references to the supporting evidence, a status, and a completeness flag. With missing facts it must not invent France; with conflicting facts it must expose the conflict.
  7. The CNL renderer turns that result into text. It reports what follows from the admitted knowledge, including uncertainty or limits. The optional verbalizer may make the wording more natural without changing the result.
  8. The agent returns the answer and inspection data. The local interface can expose the generated SOP, evidence, and execution trace, rather than only a final sentence.

The numeric route is shorter. A constraint such as finding integers whose sum is five goes from validated variables and conditions to the numeric solver; it does not need to retrieve employment facts or domain rules. A model stated supplies turn-local evidence or a supposition without recording it. In a trusted full circuit, fact constructs a sourced value without storing it, and solve.data can use explicit local facts temporarily without recording them.

Two current authoring layers: the model may author only stated, assumed, unclear, query, constraint or unparsed, written as context-free strings, one finite clause per wire: a quoted relation phrase (the lemma of the message's words, in the message's language or English), roles from a closed inventory with names as written in the message and other values normalized, ?variables in questions, temporal expressions as stated, link keyword lines (because $s2, if $s1, …) between clauses, and unparsed spans for what it could not formalize. The runtime translates content words with its dictionary. A stated proposition is what the message puts forward (with the user's certainty); an assumed one is what the model added. Neither has a source, quotation, or write field, and neither is automatically remembered; the runtime links the strings to its lexicon and asks when something is unknown or ambiguous. Approved runtime operations build an inspectable execution circuit for identity lookup, reasoning, rendering and, when needed, clarification. A trusted tool may separately use remember to record an authorized sourced fact/event in the selected session. That recording neither proves truth nor publishes globally; session commit is a separate runtime action.

An asserted statement is compiled to a turn-local fact … source user used as evidence for this turn only, and carried in caller-owned conversation context; a supposition, hedge or reported claim is supplied to solve.assume and conclusions depending on it are hypothetical; a model assumption is only reported unless runtime policy branches it into a separate hypothetical solve. None of them is stored or reinforced.

@context stated
  relation "works at"
  role subject "Maria"
  role object "Acme"
  polarity affirmed
  certainty supposed
@question query
  mode exists
  where match
    relation "works at"
    role subject "Maria"
    role object "Acme"
    polarity affirmed
  end

The model states the condition and the question here, not how to store or solve them. The runtime may answer hypothetically under @context; inspecting the resulting execution circuit shows the generated assumption, solve, and rendering operations. This example does not authorize or perform a repository write.

SOP: the language passed between translation and execution

Name. SOP comes from Standard Operating Procedure. The language is properly called SOP Lang (shortened to SOP throughout this documentation): an attempt to formalize standard operating procedures, and the facts, questions and constraints they depend on, as inspectable, executable text rather than prose.

SOP is a text language for stating user statements and assumptions, sourced facts, questions, numeric constraints, and operations over them. It is not the language model and it is not the solver. A model can author only declarative statements, assumptions, questions and constraints, as strings; the runtime links them, compiles an inspectable execution circuit and generates clarification requests when required. A person or a model can write trusted full circuits; the runtime checks and executes them. JSON may transport SOP or represent parsed objects, but does not replace the authored SOP language.

A header @question query declares a named, typed wire. A wire is a named piece of the circuit, not a separate operating-system process. $question consumes its produced value; ~definition refers to an approved definition; ?country is a logical unknown within a problem. Relations use [not ]predicate term1 term2 ... with one to four whitespace-separated terms in runtime circuits and on the model surface (the knowledge language below allows zero to six), for example where works_at maria ?organization. Parentheses and comma separators are not SOP atom syntax; JSON double-quoted terms preserve embedded spaces, punctuation, and escapes. all, any, and end preserve the grouping of conditions. See wire help for executable examples and the field contract of each type.

pack groups values for trusted program or runtime plumbing; resolve performs actual identity lookup; the runtime generates it for the strings a model wrote (the model never sees identifiers). Neither is model-authored. The runtime generates a clarify wire when a relation, identity or date cannot be linked uniquely or a required downstream scalar is missing/nonunique; it suspends dependent work pending a user response. Lack of evidence for an otherwise valid query does not automatically request clarification. A model-authored clarify wire is rejected.

Model constraint declarations express integer variables and domains, comparisons, a requested claim or optimization objective, and supported selected results. The runtime chooses the solver. In the trusted reference language, template and procedure currently use the same approved parameterized-circuit mechanism; policy sets runtime execution limits. theory carries a foreign-dialect body, but required theories have no registered compiler today and cannot run. None of these reference types becomes a required small-model lesson merely because its field grammar is documented.

Knowledge wires. Besides the runtime circuits and the model surface, SOP has an authoring surface: the knowledge wires (predicate, fact, rule, default, integrity, aggregate, action, method, norm, procedure, argument, trace, and the runtime-composed amendment) that the direct author or the owner writes from a source text and the runtime stores as reviewed knowledge. Their grammar, parser, validator, governance and desugarer are one module, sop/knowledge/, and the manual is the section "Knowledge wires" of DS004. The two surfaces meet only through the roles of a predicate declaration and the runtime linking: the model writes strings, the knowledge is written in symbols, and the model never sees an identifier. SOP Lang is still being discovered, so it has no version numbers; every change is documented in the specifications and the wire help in the same step.

One match can be represented by a structure of related variable assignments; several matches can be represented by an array of such structures. For example, [{person: "maria", country: "france"}, {person: "ana", country: "romania"}] preserves two person/country pairs. This is the intuition, not a universal wire return format. A question declares what to find; solving and an explicit output mode determine what is exported. Current rows outputs remain arrays even with one row, whereas one requests a unique scalar. Engines must document supported result forms, limits, and completeness; they must not silently change what the declared condition means.

Query author: translating the input into circuits

This is a role. Formerly called the formalizer, it is played by the session's formalization strategy through lib/query-author: step by step (LocalLLMStepByStep by default, or InternalReasoningStepByStep): the system asks short questions about the user's message and the schema neighbourhood of the memory, Ploinky Workers tiers answer them, and the system assembles only circuits: queries, constraints, unclear and unparsed markers, and session definitions or assumptions marked assumed. It never answers and never states a fact. A statement of the user is not a sourced fact or an instruction to store it. For “Who works at Acme?” the formalizer assembles the employment query, not a guessed employee. If the identity is ambiguous, the runtime asks the user.

The validator admits only what the circuit surface allows (DS014) and repairs in bounded rounds. When no model of the model chain is available the answer is parse_unavailable; there is no fallback parser. The earlier small-model formalizers (SymbolicLM, FormalizerLLM) are frozen. The query author formulates the problem; the reasoner solves it.

Agent: who coordinates and authorizes the turn?

Here, the conversational agent is the application code (server/agent.mjs) that asks the query author for circuits, validates them, builds and checks an inspectable execution circuit through approved metaprograms, invokes the runtime and returns the answer. It is not a language model. The CLI's chat command uses this coordinator. Its inputs include the user text, session and policy; its output includes the answer, generated SOP, result packet and execution trace. The authored circuit and the generated execution circuit have different authorship and authority.

The runtime and its operator supply identity, permissions, knowledge, schemas and execution limits and choose the user's session; approved metaprograms arrange resolve, pack, solve, cnl or a grounded clarify as needed, rather than ask the formalizer to emit them. Explicit remember remains a trusted tool operation for authorized sourced facts and events, not a consequence of statements or assumptions. The runtime must not guess an intended identity or promote hypotheses, quotations or inferences to stored claims. A circuit cannot grant itself publication rights by writing a field in SOP.

The direct author is a different use of “agent” from the turn coordinator: a chain model, called through Ploinky Workers without tools, that writes knowledge circuits. Its changes still need validation and the applicable review.

Runtime: executing the circuit in dependency order

The runtime is ordinary interpreter code. The conversational agent or a direct program caller gives it SOP, a clock, schemas, repository/session access, and policy. It parses declarations, checks references and types, waits for required wire values, and runs the corresponding operations. For example, a solve using $question must wait until that query value exists; a consumer of an exported answer must wait until the answer is justified.

It calls the linker and reasoner for knowledge questions, the numeric solver for constraints, the repository for authorized writes, and the CNL renderer for explicit rendering operations. It returns values, execution traces, and the states of requested outputs. A blocked or ambiguous value is not silently replaced by the first available candidate.

The current implementation is in sop/runtime.mjs, with parsing in sop/parser.mjs and typed problem construction in sop/lower.mjs. Approved template/procedure expansion and system-side restricted expression evaluation are distinct capabilities; their existence does not require the formalizer to generate code.

Linker: finding facts and rules worth solving with

The runtime calls the linker with a query, approved definitions, and access to the permitted memory view. The linker works backward from the requested relation: which rule concludes it, and what facts would that rule need? In the Maria example, it selects the rule connecting employment and organization location, then requests those two kinds of facts.

Its output contains selected facts and rules, the original question, and retrieval diagnostics. It does not answer the question merely by selecting candidates. It must not invent a rule because two relation names sound similar, nor join unrelated queries merely because both use ?x.

The current linker uses rule-head matching, backward goal expansion, and bounded retrieval through a strategy registry. Those are program algorithms, not a separate language-model call. Choosing exact or associative retrieval changes how facts are found, not the intended meaning of the query. Prolog and Z3 do not independently search the repository for missing domain knowledge.

Base memory: a named, forkable knowledge store

A base memory is a named store of reviewed knowledge of one memory strategy (the product uses SQLite; RecallMemory, HoloMemory, scan and hybrid are research engines) with the validated circuits it was built from and a provenance log. It lives under chat_data/base_memories/<id>/. A fork copies it (copy-on-write when the strategy is the same, a replay of the circuits when it changes). Knowledge enters a base memory only through a validated add recorded with its provenance (the acting user); nothing enters it implicitly and there is no manual accept or reject step. The shipped base memories are world-v1 (a Wikidata subset, about 357k facts in 221 layers, warmed at server start, over the common-sense layer), commonsense-v1 (common nouns and their classes from WordNet, typical uses, places and abilities from ConceptNet, rules for classes, lifetimes, family, geography and units), core-en (English vocabulary drafts, not approved), core-min, demo and default; all hold English knowledge. A new session forks the default base memory (chatData.defaultBase), which is the encyclopedic world-v1; when world-v1 is not loaded, the minimal default (which imports core-min) is used instead. A memory for a specialised task is created minimal (it imports core-min) or empty; an encyclopedic memory is a copy-on-write fork of world-v1. See DS022.

Session: a chat's own copy of a base memory

A session is created from a base memory, clones it into its own folder and holds what the conversation adds: the circuits stored in the session layer (each validated first), the transcript and the temporary request folders. Asserted statements stay turn-local. A session can be committed to a fork of its base memory by a user; the base memory it started from never changes. Abandoned sessions are removed by the cleanup policy. See DS022.

Direct author: writer of SOP circuits

The direct author is a model reached through Ploinky Workers (the authoring tier ingest.tier, shipped small) called as a plain chat completion, with no tools, no shell and no files. With the skill sop-wire-authoring it writes knowledge circuits from attached files (POST /v1/author, lib/ingest/direct-author.mjs), which the validator repairs for a bounded number of rounds and which, with a session, join the session layer at once when valid. It does not formalize chat messages (the chat's formalizer is step by step); it never answers and never states facts. See DS022.

Repository: persistent knowledge, ownership, and history

The repository stores reviewed facts and rules, private user knowledge, session changes, and their history. For example, a user can submit the claim “Maria works at Acme” for recording through remember in a private session, query it there, and later commit or discard that change. Other users must not silently inherit the private claim. Recording does not prove the claim true.

The runtime or runtime calls repository operations to admit a sourced claim, record a correction, open a knowledge view, commit a session, or discard its changes. The repository returns claim identifiers, receipts, and authorized views. The linker and retrieval layer read those views when assembling a problem.

It distinguishes valid time—when Maria is said to work there—from knowledge time—when the system learned or corrected that claim. A historical question may need either or both. Snapshots and forks preserve earlier or separate views. The repository manages this history and ownership; the memory engine beneath it handles a particular storage/search representation. Neither component proves that an asserted claim is true in the world.

Memory engine: how stored facts are searched

The memory engine is the implementation used to retain and retrieve facts. The retrieval layer asks for a pattern such as works_at maria ?organization within an authorized time/session view. It gets candidate facts plus information about probes, limits, and completeness. The reasoner, not the memory score, decides what follows from the retrieved facts.

Reasoner, backend, and strategy: how the problem is solved

The reasoner receives a typed problem and its admitted inputs from the runtime. For a relational query, those inputs are facts and approved rules. For a numeric problem, they are variable domains, requirements, a claim, and possibly an objective. It returns a status, answers or assignments, evidence where supported, and whether the computation was complete.

A backend is a concrete implementation that performs the calculation. A reasoning strategy selects the route and applies the runtime's limits. These are not names for additional language models.

Beside these routes, the knowledge wires of DS004 are answered by strategies (reasoning/strategies/<id>/): each reads the same parsed, governed and desugared program and lowers it to its own engine (a nested-loop evaluator, tabled Prolog, SMT, Datalog, SQL, ASP, a planner). A strategy declares its capabilities, and a question that needs a feature it lacks is not_expressible, never silently weakened. The simple, auditable js-reference strategy is the oracle: another strategy is accepted by agreeing with it on the cases it declares (the shadow gate). Every result carries its status, complete, used (one sufficient support set), per-row conditional and a budget block; a budget cut is budget_exhausted with a reason, never unknown or no_plan. An explicit external backend (prolog, z3) runs its own strategy or answers unsupported with the backend named and fallback: null; a JavaScript answer never stands in for it (the former advanced route, which could report such a fallback, was removed on 2026-10-01). Unsupported operations, exhausted budgets, and incomplete retrieval must remain visible. A satisfiable numeric assignment means “possible under these requirements,” not “necessarily true.” Missing relational support is not explicit negation, and contradictory facts must not make every conclusion provable.

Engines must document their supported semantics and result contracts: which variables are returned, scalar versus row projections, duplicate handling, ordering, limits, completeness, and ambiguity. Different implementations should preserve the meaning of the shared declared problem. They may reject unsupported features, but must not silently reinterpret them. See variable/result intuition for the structure-versus-array distinction.

CNL: turning the result into readable text

CNL means controlled natural language. Here it is a deterministic code step: it receives a computed result packet and renders its status, answers, time, and available supporting information. It does not call a model to decide the answer. If no admitted fact establishes the answer, its text must report that lack of support rather than turn it into “false.”

In a trusted full circuit, cnl explicitly consumes a real operation result. The runtime rejects a literal imitation of a result packet. For model-origin declarative input, the runtime constructs and checks that rendering operation rather than asking the model to author it.

Why keep rendering in the runtime? CNL reports computed status and evidence, not a new proposition in the user's question. The formalizer specifies the conditional problem; approved runtime code determines and renders its result without asking it to repeat boilerplate execution wires.

CNL is not entity resolution. resolve looks up which approved entity a name denotes. If “Maria” names several people, an identity-dependent query needs disambiguation. Adding a renderer cannot repair that missing identity.

Verbalizer: optionally improving the wording (not in the product)

The verbalizer is a language-model role at the end of a turn. Today the chat returns the deterministic CNL text (sop/answer-text.mjs); the direction is that a Ploinky Workers tier may later formulate the final answer from the checked result packet. As a design, it receives the checked CNL answer and the result information and returns a more natural formulation. Without it, the agent returns the deterministic text.

For example, it can turn a terse supported-employment result into “According to the available records, Maria works at Acme.” It must not change the employer, drop the qualification, invent a date, or turn an unknown answer into a negative one. This is a fidelity requirement, not a new proof supplied by the rewriting model. The formalizer translates input language into a problem; the verbalizer rewrites an already computed answer into prose.

Semantic case: one meaning used to evaluate translation

A semantic case is evaluation data, not a running component. It groups an intended input meaning, a reviewed SOP target, source information, linguistic variants, and expectations in specified test situations under a stable identifier such as semantic_case_id. “Who works at Acme?” and “Which people are employed by Acme?” may be two phrasings of one case. “Who does not work at Acme?” is a different meaning, not an equivalent paraphrase.

Benchmark-building code keeps equivalent phrasings of one case together when splitting development and sealed test data, so a near-duplicate is never credited as unseen; development and test rows are never duplicated, and the leakage guard eval/leakage.mjs keeps the sealed suites out of every generator.

Two measurements must remain separate. Running the reviewed target SOP against test knowledge checks the program and system behavior. Running the model on the natural-language variants and judging its generated SOP checks translation. Passing the first does not establish the second. Case files, JSONL rows, and reports are different representations of this evaluation material, not additional query languages.

GC: deleting storage that no live view needs

Garbage collection is repository maintenance code. As sessions, corrections, snapshots, and forks accumulate, some stored objects become unreferenced. GC starts from the approved bases and existing user/session/fork views, determines which snapshot or shard objects remain reachable, and identifies the rest as removal candidates.

The operator can inspect a dry run before using gc --apply. For example, an old snapshot must stay if a historical session still references it, even when a newer snapshot exists. GC does not decide that a fact is false and does not remove a private session merely because it is old. Its purpose is reclaiming proven-unused storage without breaking a view someone can still open.

Glossary: data, evaluation and learning terms

These short definitions fix the meaning of terms used across the specifications and dataset tooling. The linked DS files are the normative source.

MRP (Meta Rational Pragmatics)
The thesis behind MRP-LLM: language has no fixed semantics but has a rational pragmatic meta-level; for a given domain, a well chosen interpreter knows what it is sensitive to, what it extracts and what reasoning it applies to what it extracted. MRP-LLM makes that interpreter explicit (a formalize strategy and the value schemas it uses), replaceable (strategies per slot) and measurable (the benchmark of every slot). See DS000 and DS028.
Symbolic Model
What MRP-LLM exposes and what a user or API client talks to (called Model for short in the specifications): a base memory plus one strategy with parameters per pipeline slot, an output language, a FAQ for the reflex slot and whether sessions and requests may override slots. It is named by model in POST /v1/chat/completions, listed by GET /v1/models, stored under chat_data/models/<id>/ (configuration in model.json, what it learned in state.json) and edited on /models. A Symbolic Model is not a language model: the language models it uses are Ploinky tiers named by its strategies, and Ploinky Workers maps every tier to real provider models (for example fast → deepseek/deepseek-flash). The chat's Symbolic Models tab and /models show the real model behind every tier a Symbolic Model uses. Deleting a Model keeps its base memory. See DS025.
Slot
One stage of the MRP-LLM pipeline with a fixed contract: normalize, reflex, affect, formalize, admit, link, memory, retrieve, reason, verify, roundtrip, render, voice, commit, discover. Each slot has several strategies and a default; a Model chooses one per slot. The slots from formalize to render are the symbolic core; the others run around it in lib/mrp/pipeline.mjs. See DS025.
Strategy
One interchangeable way of doing a slot, with typed parameters, a cost and a statement of when to use it (catalog: lib/mrp/strategies.mjs, GET /v1/mrp/strategies). A server strategy runs in this Node server; an external strategy needs components outside it and is listed with its requirement. A strategy that cannot run is reported, never replaced by another one.
Profile
A ready-made Model configuration in config/profiles/<id>.json (general, acme-demo, support-bot, rigorous-judge, companion-edge, research-bench). A new Model starts from a profile; profiles marked createOnFirstStart become Models when the server starts without any.
Reflex
An instant answer from a Model's FAQ that ends the turn before formalization. The boundary between a reflex and full reasoning is a strategy of the reflex slot: a fixed threshold, a threshold with a margin over the second-best entry, a threshold learned from users' votes, or a candidate confirmed by a small model. FAQ entries are English and are matched after normalization.
Round-trip check
The roundtrip slot: a model restates the circuit in English and the restatement is compared with the normalized message (token cosine or a model's judgement) to catch a circuit that answers another question. How often it runs (never, on doubt, sampled, always) is a strategy, because its worth depends on the cost of a misread question in the Model's domain.
Commit policy
The commit slot: what happens to definitions the validator admitted into a session: kept in the session until a user commits it (manual), queued for an administrator's review on /models (review-queue), written to the Model's base memory after the validator (auto-validated), or never written.
Normalize and voice
The two language edges of a turn (DS026): normalize turns the message into clean English and detects its language; voice phrases the deterministic English answer in the output language and must keep every number and source id. Everything between them is English.
Compact surface
The key=value form of SOP Lang (@order entity name="Order 17" kind=order), accepted next to the canonical field lines and rewritten to them before any reader sees the circuit (sop/compact.mjs, DS024). A compact pair carries one term.
Tier
The name a strategy uses for a language model (nano, micro, tiny, small, medium, good, best, fast, …). Ploinky Workers maps it to an ordered chain of provider and model with fallbacks; what each tier really uses is shown by GET /v1/mrp/tiers, the chat's Symbolic Models tab and /models; the mapping and the API keys are configured on /models → Model gateway (DS027).
Surface
One natural-language phrasing of a semantic case (a question or request, in one language). Several surfaces (English, Romanian, mixed, with or without typing noise) share a semantic_case_id and always stay in the same split.
Gold
The reference answer recorded for a row: its declarative SOP target together with the expected, executed result. A gold is produced by the builder and executed against the real runtime; it is a reference for evaluation, not a human-reviewed truth unless an audit verdict says so.
Oracle
The independent procedure that decides the expected result of a case without trusting the SOP target under test, for example a handwritten computation over the case's finite world. A target that merely executes is not its own oracle.
Sealed test
The held-out split stored only under eval/suites/<corpus>/test.jsonl. It is never used to build or tune the system, and connected case groups never cross into it from development data (DS012).
Epistemic status
What the system can claim about an answer, kept separate from whether a computation ran: supported, refuted, both (conflicting evidence) or unknown, qualified by complete and hypothetical. Lack of support is unknown, never an implicit negation (DS006).
Stated
A model proposition that surely comes from the user's message, written as strings with the user's certainty (asserted, hedged, supposed) and an optional reported speaker. An asserted statement is turn-local evidence carried in caller-owned conversation context; the others are used conditionally. Never stored or reinforced (DS014).
Assumed
A proposition that the formalizer added (a presupposition, a closure, a default, world knowledge). Reported in model_assumptions and ignored by the primary answer; runtime policy branch runs it in a separate hypothetical solve. Not carried across turns.
Basis
The optional, purely descriptive label of an assumption: closure, default, disambiguation, implicature or world. It never affects trust, admission or reasoning; its accuracy is measured separately under a preregistered keep/drop criterion.
Question forms
The one formalization of each question word in the model language (DS014): mode every with a scope for "all/every/no", role time ?t with select ?t for "when" and measure start|end|duration for "since when / until when / how long", mode count over ?t for "how many times", the location role for "where", the instrument role for "how", and mode explain for "why".
Question types
The eighteen labels the corpora put on a message (yes_no, wh, count, universal, when, since_when, until_when, how_long, how_many_times, where, why, how, claim_check, multi, numeric, none, unclear, ambiguous); each maps to one question form. See Question types.
Not computable
The runtime answer status: not_computable for a formalized problem that no engine can compute yet: "I understood the question as …; I cannot compute this kind of answer yet", with the formalization shown. It replaces a model refusal. unsupported is reserved for an explicitly requested backend that is unavailable in a trusted circuit (AGENTS rule 8).
Unclear
The only-wire model output for an unintelligible message (gibberish), one with neither a statement nor a question (no_request), or a visible ambiguity with no preferable reading (ambiguous, with 2–4 reading paraphrases); the runtime replies from a fixed table and lists the readings. Distinct from the runtime-generated clarify. When one reading is preferable, the model states it with assumed (basis disambiguation) instead.

EmotionDetectionSystem
The former lexicon and pattern component that read courtesy and emotion from the raw message before the author (probably_obsolete/paused/lib/emotion-detection/), archived on 2026-10-02: the formalizer now writes them as pragmatic wires in the same understanding step (DS023). Kept only as a reference arm of the evaluation eval-pragmatics-v1.
conversation layer
The seed memory conversation-v1: the reply wires that hold every sentence the chat says (situation, part, text with {{slot}} placeholders, several variants), the situation priorities and the rules that derive which replies apply to a turn from the facts of its result packet. The JS oracle chooses the reply; code only maps the packet to facts and fills slots (DS023 "Conversation layer").
reply wire
A knowledge wire with situation, part (opening, body, closing, line), language and text: one phrasing of the assistant, data for the renderer and never evidence.
behaviour layer
The part of the conversation layer that makes replies dynamic: the user's standing instructions (the instruction wire, kept in the conversation and turned into reply wires and rules of origin user), drives (preoccupations with an occasion and a cooldown that surface by themselves) and decision rules over the time since the last reaction of a kind. All of it is decided by the JS oracle (DS023 "Behaviour layer").
instruction wire
The model-surface wire for what the user asks about the answers from now on: do set|cancel|list, kind prefix|suffix|short|detailed and the verbatim text of a prefix or suffix; never a fact.
drive
A preoccupation of the assistant in the behaviour layer (cv_drive): it fires when its occasion holds and its cooldown, counted in turns since its last use, has passed; firing restarts the cooldown.
self layer
The seed memory assistant-v1, imported by world-v1: the assistant as the entity chatsop ("ChatSOP", "you"), what it can do, and the statistics of its memory generated from the memory itself (entities per class, facts per relation, totals, layers).
near miss
The closest entities of the memory to a name of a message that has no answer (accent and case folding, bounded edit distance, one-word matches of longer labels; no word lists), with their descriptions and the relations around them; the conversation layer turns them into a suggestion instead of a dry refusal (lib/near-miss.mjs).
pragmatic signal
An advisory signal about how a message is said (greeting, thanks, urgency, frustration, confusion and the other kinds of sop/enums.mjs PRAGMATIC_KINDS), with a score, a verbatim span, a source and a basis. It is carried as a pragmatic wire and as the packet field pragmatic; it regulates the courtesy and tone of the answer and is never a fact, evidence or knowledge.
The datasets bad_english, symbolic_english, neuro_english, natural

Linking
The deterministic step after the formalizer: relation phrase and role set to a lexicon predicate, quoted values to typed entities, temporal expressions to intervals; unknown or ambiguous links become a runtime clarify.
Request parser (query parser)
The entry point of a chat turn (server/query-parser.mjs): it runs the session's formalization strategy through lib/query-author and returns admitted circuits with a parse record (strategy, model, models tried, rounds, repairs, vocabulary dialog, cost, time, cache). Non-English input is handled here, at the edge; the core is English-only. The same symbolic path follows whatever wrote the circuit (KnowledgeLinker, slice retrieval, StrategyRouter, oracle verification, completeness guard, rendering). The former localQuery (SymbolicLM) is frozen history. See DS022.
Formalization strategy
How the request parser obtains the circuit of a message, step by step: LocalLLMStepByStep (the default) or InternalReasoningStepByStep; the one-shot LLMDirect is archived. It is a session setting (formalizer, null for the server default); GET /v1/status lists each strategy with its availability and reason. A turn whose strategy cannot run is refused with parse_unavailable, never silently replaced.
LLMDirect
The archived one-shot formalization strategy (owner decision 2026-10-02): a model wrote the whole circuit as chat-completion text, with validator repair rounds. Its code, guide and tests are in probably_obsolete/one-shot-formalization/ (last measured: commonsense 27/32; books 15/100 against 27/100 step by step on tiny). A session or caller that names it, or the earlier names CodingAgent and LocalLLMDirect, runs the default step-by-step strategy with a strategy_note in the trace. See the direct author for knowledge authoring.
LocalLLMStepByStep
A formalization strategy: the symbolic system asks a small local model short questions (numbered choices, short lists, yes/no, arithmetic lines) and assembles the circuit itself from per-form templates; the model never writes SOP or JSON (lib/query-author/step-by-step/, DS022 "LocalLLMStepByStep"). See running a local formalizer.
Schema neighbourhood
The bounded vocabulary the author receives (lib/query-author/neighbourhood.mjs): the entities the message names, resolved without guessing namesakes, and the predicates used around them (one hop, two on expansion) with declared roles and classes, fact counts, at most two examples in SOP and English, related rules and closedness, within a 24,000-byte budget. The examples explain meaning and argument order; they are not answers or evidence.
Vocabulary dialog
Extra rounds of the archived one-shot author in which the neighbourhood was widened and the author asked again; archived with LLMDirect in probably_obsolete/one-shot-formalization/. The step-by-step strategies re-ask the doubtful question instead.
Repair round
A bounded further round after the validator found problems. In the step-by-step strategies the doubtful question is asked again; the direct author of knowledge circuits gets the problem codes back (at most three rounds). A circuit still invalid after the last round is reported (unclear or parse_failed), never replaced by a guess.
Condition misuse and the time guards
Admission guards on the meaning of a circuit. condition_misuse (reasoning/slice/condition-misuse.mjs, used by lib/query-author/condition-use.mjs): a constant in a position where the memory's indexed domain never holds it, or a wrong arity or type, reported with the condition, the position and a bounded list of observed values. time_not_a_point: at or asof given a range. time_range_needs_quantifier: a range as role time, which must become during (throughout) or overlaps (at some time within). All are repair feedback; the author never has a condition swapped or dropped for it.
Session definition
A predicate with a rule or default over existing relations that the author writes when the memory lacks a term. It is used for its turn only, labelled in the answer (origin: definition by the author), reported as session_circuits and, once the validator admits it, stored in the session layer at once, so it is available to later turns; an invalid one is refused. The memory always wins over a conflicting definition or assumption.
Completeness guard
reasoning/slice/guard.mjs: decides what may be said over a retrieved slice. A proof or counterexample stays valid over a partial slice; a count, a universal answer, a ranking or an unknown needs a complete slice and is otherwise widened or answered status: incomplete, reason: partial_retrieval.
Answer formulation
The optional last step of a chat turn (server/answer-language.mjs). When the message does not look English, a model called through Ploinky Workers phrases the deterministic English answer in the message's language. It works strictly from the English answer and a compact result packet, and every number and source id must survive. Otherwise the English answer is returned, and it is always kept in the trace as english_text. Settings: answerLanguage (mode auto|always|off, providers, natural).
Oracle verification
The check of an answer computed by a routed engine against the js-reference oracle, reported as route.verification (and chatSop.verification); a disagreement returns the oracle's answer with the discrepancy.
Analysis procedure
A procedure wire tagged analysis: rules, integrity constraints, aggregates and parameter facts in a base memory that the reasoners apply to the document layer of a session or a base memory (contradictions, numeric and temporal consistency, unsupported claims, KPIs, rubrics). Each finding carries the rule that fired, the oracle proof and the document's own quotes. See Analysis procedures and DS022.
KnowledgeLinker
The deterministic step after the formalizer that links the names and phrases of a circuit to the predicates of the chosen base memory (see linking); it does not parse language. The forms it matches are knowledge of the memory, not code: the predicate, lexeme and entity wires of the session's base memory and of the memories it imports (the memory's lexicon, one per session; it reports what it bound as linking). It reads a relation phrase by the memory's predicate ids, labels and lexeme forms and by the reviewed relation lexicon; the plain copula (be, be a, be in) it reads with the six closed copula readings class, occupation, attribute, identity, location and describe ("Who is Ana?"), looking up which predicates the base memory declares for each (reading NAME, describe_rank N on a predicate wire). The code names no predicate; with no declared reading it asks a precise question and never answers "unknown relation be". See DS014, "KnowledgeLinker: the copula and the relation lexicon".
Relation lexicon
Reviewed language data of the KnowledgeLinker (config/relation-lexicon.json): copula verb forms, articles, locative phrases, occupation nouns, attribute adjectives (English and Romanian) and the relations a base memory maps to its own predicates. It is the review: a phrase it does not cover stays unknown and the user is asked.
Frame normalization
Frozen history (owner decision of 2026-10-01): part of the tiny-model branch archived in probably_obsolete/tinyLLMExperiments/; not part of the product.
Role inventory
The closed, context-free argument names of model propositions: subject, object, recipient, location, source, destination, instrument, time, topic. Lexicon predicates map their positions to them with role NAME TYPE.
Knowledge wire
A wire of the authoring surface of SOP (predicate fact rule default integrity aggregate action method norm procedure argument trace, and the runtime-composed amendment), written from a source text and validated by sop/knowledge/. Never model output: the model-origin compiler rejects it. See the manual.
Closed predicate
A predicate declared closed true: the retained view holds every fact of the relation, so absent, counts, sums and every are meaningful. Declared only with the source sentence that says the list is exhaustive, accepted by runtime review over an archived or pinned view, never inferred.
Two negations
not p a is explicit evidence that p a is false (the source says so); absent p a means "no record of it" and is allowed only over a closed predicate. Absence of evidence is unknown, never false.
both
The reported status of an atom with positive and negative evidence. The two evidences propagate independently (a paraconsistent, monotone reading), so a contradiction stays local and nothing unrelated becomes derivable.
Default and override
A default is a defeasible rule ("usually"): it is blocked by an exception, by a strict contrary, or by the firing of a default it is overridden by (overrides). Two defaults of equal strength with contrary heads give both.
Norm
A norm forbids, obliges or permits an action or a state, with at most one temporal qualifier (always before after within sometime at_most_once), a severity (hard or soft) and a binding (strict by default, or advisory).
Method and procedure
A method is the manual's own ordered procedure for a task, with the choice points the engine may optimise; a procedure is a named bundle of wires. A procedure has no approval or version of its own: its members carry them.
Mode of work
The sum of approved methods, norms and procedures: the system acts by them, optimises within them, keeps them named, versioned and addressable, and lets an amendment be negotiated with the user. All of it is knowledge written from a source and approved by the runtime, never model output.
Governance
The fields version supersedes approval approved_by approved_at retired_at scope of the governed wires (rule, default, integrity, action, method, norm). The runtime writes the approval fields; only approved (and contested, flagged) wires bind; proposed and rejected wires bind only when a query supposes them; asof selects the version known at a date.
Amendment
A proposed change to a procedure or wire, composed by the runtime from the user's words, evaluated as a what-if (if $amendment) and accepted or rejected by a runtime write recorded in the journal.
conditional and used
conditional, per row, lists the assumptions (reported, hedged or supposed facts, proposed wires) a row rests on, verified by a second run. used is one sufficient support set of claims, with their versions, that re-derives the answer.
budget_exhausted
The status of an answer cut off by a budget (reason rounds probes horizon depth domain wall cancelled numeric_range). It never reads as unknown, refuted, no_plan or optimal.
not_expressible
The harness or router answer for a question that needs a feature the strategy does not declare. Distinct from unsupported, which stays reserved for an explicit backend request that cannot be honoured.
Circuit
A set of typed SOP wires that the runtime executes in dependency order. A user or coding-agent circuit is what a person or the query author wrote (queries, constraints, markers, assumed definitions); the execution circuit is generated by the runtime (resolve, solve, render). See DS004.
Memory vocabulary
The predicates (id, roles, phrases, gloss) and entity hints of a session's memory that lib/query-author retrieves for a message and gives to the author, together with the schema neighbourhood, so that it writes predicate ids and names that exist. It contains no answers, gold, sealed tests or other sessions.
Ploinky Workers
The one model gateway of the project (Ploinky-Worker/, manual Ploinky-Worker/README.md): one server per machine (pworker serve, OpenAI/Anthropic-compatible on http://127.0.0.1:18080) that routes every model request by tier, applies rate, plan and budget limits and the priority classes, caches responses (modes use, strict, record, off), keeps the request log and the audit store, starts and stops the local model servers, falls back down a tier's chain, and runs batch jobs, tasks and TaskLambdas, each call in an audited folder. No component calls a model API directly: code uses the library (pworker({purpose}) of lib/pworker.mjs), command lines, Claude subagents and external tools use the CLI (pworker run|call|job|task|chat|stats|models); a client starts the server when none runs. Configuration layers: Ploinky-Worker/config.default.json, ~/.pworker/config.json, then ChatSOP's the Ploinky user configuration (~/.pworker/config.json); keys live in ~/.pworker/keys/. Ploinky Workers knows nothing about circuits: SOP-aware work enters as job folders, task templates and project TaskLambdas.
TaskLambda and TaskLambdaCall
A TaskLambda (owner, 2026-10-03) is a content-hashed executable unit of Ploinky Workers: code, a typed parameter schema, an optional check, metadata (name, description, origin: built-in, project, job folder, task template or model-written) and a required effects declaration (pure, or writes-workdir, model-calls, runs-scripts, runs-jobs, writes-external; network is refused). Built-in TaskLambdas are chat, json, job, task, write-lambda and agent; ChatSOP's project TaskLambdas are the modules of jobs/lambdas/ (the Ploinky user configuration (~/.pworker/config.json)), every job folder and task template is one too, and the agent of pworker run writes model-written ones that run in a sandbox and are cached beside their work folder (.pworker/lambdas). Every invocation is a TaskLambdaCall with its own folder under Ploinky Workers's calls root (~/.pworker/calls/<day>/<lambda>-<id>/: call.json, output.json, effects.jsonl, models.jsonl, log.txt, child calls under calls/); a job run has one child call per item. A pure TaskLambda called again with the same hash, parameters and unchanged inputs returns its recorded output (reused_from); a call with effects is never replayed, only audited. pworker call <name>, pworker lambdas, pworker calls list|tree|show|search|prune. Not to be confused with Agent Skills (instructions under .agents/skills/) or with the task procedures under skills/.
Priority class
The class of a Ploinky Workers request: interactive (a person waiting: the purposes chat, formalize, answer-*) goes first in every queue and falls back down its tier chain instead of waiting long; normal waits its turn; background (recurring work such as regressions) runs only when nothing else waits and, on a plan provider, within 70% of every rate and plan window, and is held, never refused. Every request also carries a purpose, which budgets and the daily allowance for untagged requests are counted by.
Tier and tier ladder
A tier is the name a client gives Ploinky Workers instead of a model: a chain of models where the first usable entry serves and the rest is its fallback. ChatSOP's tiers are nano (local Qwen3-0.6B, on demand), micro (local Qwen3-4B, on demand; supertiny is an alias), tiny (local Qwen3.6-35B-A3B MoE, always on), small (openference Qwen3.8 27b), medium and good (openference DeepSeek-V4-Flash), each cloud tier falling back to OpenRouter, and best (served by tiny until a stronger model is configured); with no provider key only the local tiers serve. The formalizer's tier ladder (queryParser.local.ladder, shipped tiny, small, good) answers the step-by-step questions: each question goes to the first tier and escalates to the next only when its answer cannot be read or the tier does not answer; the next question starts again at the first tier.
StrategyRouter
reasoning/router/ (StrategyRouter v1): chooses the js-reference oracle or an engine (sql-sqlite, datalog-souffle, asp-clingo) from the features of the circuit (recursion, negation, aggregates, time, modes of work) and the size of the slice, reports the choice, the rule and the alternatives in route, and checks a routed answer against the oracle (DS006).
parse_unavailable
The honest answer (503) of a chat turn when no model of the session's formalization strategy can run. When models ran but no valid circuit came back after the last repair round the answer is parse_failed (422); a written circuit that cannot be admitted or executed is model_output_rejected (422). There is no fallback parser and nothing is guessed.
Benchmark
The validation procedure of the project: symbolic reasoning against small LLMs reading the same evidence as text, over task families such as multi-hop, counting, closed-world negation, transitive closure, constraints, temporal reasoning and rule chaining, reported as accuracy, wrong versus honest unknown, and scaling curves with a paired bootstrap (experiments/proposal/symbolic-vs-llm-benchmark.md; to be built).
Oracle and shadow gate
The oracle is the js-reference strategy, a deliberately naive implementation of the whole core; a strategy is accepted by agreeing with it, with zero disagreements, on every case it declares. used is checked by replaying it alone in the oracle.
Reinforcement
Proof-use promotion of an admitted, metadata-verified observed fact. It happens only in a real, non-hypothetical proof, only when runtime policy (policy.reinforce !== false) and the memory retention setting (reinforceOnUse) both allow it, and the reason packet reports it. A read or retrieval alone never reinforces anything (DS006).
Ingestion
Turning source material into sourced SOP facts or candidate rules: extract passages, quote them exactly, draft facts, probe candidate rules, and publish only after independent owner approval (DS008). Drafts are not runtime knowledge.
Knowledge accumulation
Material ingestion accumulates reviewed knowledge in the repository from quoted sources after approval; it changes no model. There is no model training in this project.
