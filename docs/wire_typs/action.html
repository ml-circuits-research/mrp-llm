All wire types

action

An action describes a symbolic state transition for planning; it does not operate a physical device. Only trusted or reviewed ingestion can author actions in the current runtime, although a trusted system/tool circuit can use an approved action handle.

SOP syntax: @id type, exactly two leading spaces on each field line, $id for a computed value, ~id for a declaration handle, and ?x for a local logic variable or an output name. Atoms use [not ]predicate term1 [term2 [term3 [term4]]] with one to four whitespace-separated terms; lowercase predicate names, canonical symbols, JSON-quoted strings or safe integers. Parenthesized predicate(arg, …) and comma-separated arguments are not executable syntax.

Fields and inputs

KeywordCardinalityAccepted value, default and effect
paramsAt most once; optionalWhitespace-separated distinct ?variable names; default empty. Each must occur in a requires atom.
requiresRepeatable; requiredOne to any repeated predicate atoms describing preconditions. Their variables bind parameters and effects; an action needs at least one precondition.
addsRepeatable; optionalRepeatable effect atoms inserted into a hypothetical plan state. At least one adds or removes is required.
removesRepeatable; optionalRepeatable effect atoms removed from a hypothetical plan state; insertion also removes explicit opposing polarity.
costAt most once; optionalFinite nonnegative number, default 1; used in lowest-cost state search.
sourceAt most once; optionalPlain/quoted provenance text, default provided.
validAt most once; optionaltimeless (default) or start exclusive-end using ISO date/UTC timestamp, beginning/open; applies to whether the action can be used at planning time.

Pass ~action or $action (or a packed $array) to plan actions, or include actions in plan data if actions is omitted. Supplying a nonempty explicit actions set overrides action declarations from data.

Result and limits

The declaration produces a typed action with preconditions, effects, parameters, cost and validity. plan grounds variables against a candidate state and returns steps labelled planned-not-executed; no actuation or repository write happens.

Variables in params, adds and removes must occur in preconditions. The planning state is finite and search bounded by host or tighter policy; a missing plan under incomplete search is not proof of impossibility.

Executable examples

Move between connected places

@move action
  params ?robot ?from ?to
  requires located_in ?robot ?from
  requires connected ?from ?to
  removes located_in ?robot ?from
  adds located_in ?robot ?to
  cost 1

Planning can instantiate all three parameters from the two preconditions; the resulting step changes only a hypothetical state.

Release a reservation

@release action
  params ?item
  requires reserved ?item
  removes reserved ?item
  adds available ?item
  valid 2026-01-01 open

The transition can be considered on or after the start date and never performs an external release.

Invalid or unsafe use

@unsafe action
  requires ready machine
  adds ready ?other

The parser accepts both atoms, but lowering rejects ?other because effects must be range-restricted by preconditions.

Knowledge language: action

In the knowledge language an action is a primitive STRIPS step with preconditions and effects, governed like a method. The tables and examples of this section are about the knowledge form, written from a source and checked by sop/knowledge/; the sections above describe the host-circuit form. Anchors of this section's fields start with kfield-. The language manual is the section "Knowledge wires" of DS004.

Other field names are rejected (unknown_field). The table is generated from sop/knowledge/grammar.mjs.

FieldCardinalityAccepted values and behavior
paramsAt most once; optionalThe ?variables of the action; every parameter must occur in a requires (unsafe_action).
requiresRepeatable; requiredPreconditions: atoms, possibly negative. Without evidence a precondition is unsatisfied (unknown is not true); over a closed predicate requires not p means p is absent.
addsRepeatable; optionalAtoms made true; their variables must be parameters.
removesRepeatable; optionalAtoms made false. An action needs adds, removes, next or guard (action_needs_effect).
nextRepeatable; optionalNumeric effect (extension E2): next VAR EXPR, one line per state variable, identity written explicitly (next a ?a). EXPR is a polynomial in the state variables ?v with exact rational constants (+ - * ^, parentheses, division by a nonzero constant); it is parsed as data, never run as code. Problems: bad_next, duplicate_next, missing_next, unknown_state_variable.

What it is for

An action is one step a manual names, with what it needs and what it changes. Methods and norms refer to it as ~lock_db ?s (the term count must match params). A planner reaches a goal by actions alone, or by a method's steps; an action that took part in a plan is listed in used with its version.

Examples

@server predicate
  args subject:entity
@locked predicate
  args subject:entity

@lock_db action
  params ?s
  requires server ?s
  adds locked ?s
  cost 1

Invalid: an action with no effect

@server predicate
  args subject:entity
@noop action
  params ?s
  requires server ?s

Numeric action (extension E2)

A numeric action carries exact-rational arithmetic as in the VRC planner. The numeric state lives in ground facts of the reserved relation state (entity, variable, value), declared with the argument type rational (an integer, a decimal or n/d). The relational part is optional in spirit: requires may be a zero-arity flag, and the effect may be numeric only. Only a strategy that declares the feature numeric_action answers such a question; every other strategy of the smoke harness answers not_expressible; the query below is executed by vrc-compressed-planning.

@ready predicate
  args none
@state predicate
  args subject:entity topic:entity object:rational
@m0 fact
  holds ready
@sq fact
  holds state demo q 0
@sa fact
  holds state demo a 2
@scale action
  requires ready
  guard ?a at_least 1
  next q ?q + ?a * ?a
  next a 3/2 * ?a

One step adds the square of a to q and multiplies a by one and a half; the guard keeps a at one or more.

@q query
  mode plan
  observe demo ?q at_least 20
  horizon 6

The plan query needs no where: observe names the entity, the expression and the threshold. See observe and horizon.

Invalid: a guard without a comparison word

@ready predicate
  args none
@bad action
  requires ready
  guard ?a plus 1
  next a ?a

Common mistakes

  1. A parameter that no requires mentions.
  2. An effect variable that is not a parameter.
  3. Writing the approval fields: the host writes them.
