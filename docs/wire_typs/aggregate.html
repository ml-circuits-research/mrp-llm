aggregate

Defines a derived relation by grouping: the number, the sum, the minimum, the maximum or the list of the values of a group of conditions. "The payroll of each department", "how many employees each team has".

Status and author: Knowledge wire, written by a model or the owner from a source. Core, not sugar: an aggregate sits in a lower stratum than the rules that consume its result. A model-origin program cannot author it.

Accepted fields

Single means at most once, repeatable means zero or more, and required means at least once. Other field names are rejected (unknown_field). The table is generated from the grammar in sop/knowledge/grammar.mjs.

FieldCardinalityAccepted values and behavior
overRepeatable; requiredThe grouped conditions, a condition group. The rows are the distinct bindings of ALL variables that occur in it.
groupAt most once; optionalThe ?variables the result is grouped by; they must be bound by over.
countAt most once; optional?field as ?out, or as ?out to count the rows. Exactly one of count, sum, min, max, collect (aggregate_one_function).
sumAt most once; optional?field as ?out over integers; the field must be bound by over (aggregate_field, unsafe_variable).
minAt most once; optional?field as ?out.
maxAt most once; optional?field as ?out.
collectAt most once; optional?field as ?out: the set of the values.
yieldsAt most once; requiredThe derived atom over the group variables and the output variable; no other variable may occur (unsafe_head).

What it is for and how to write it

Declare the relation the aggregate yields (dept_payroll) with its roles and types, write the over group on the base relation, name the grouping variables and one function, and yield the result. The relation under over should be declared closed true only if the source says the list is exhaustive ("the table lists the salary of every employee"): over an open relation the result is a lower bound.

What the engine does

It computes the distinct bindings of every variable of over and groups them, so two employees with the same salary count twice, because the employee variable is in over although it is not in group. The yielded atoms are ordinary derived facts that rules and questions can use. An aggregate may not occur in a cycle of the dependency graph (not_stratifiable), so recursive aggregation is not expressible; shortest-path and path-counting questions on cyclic graphs are planning or closure questions. Over an open relation the validator warns aggregate_needs_closed and a count is reported as a lower bound (bound at_least).

Examples

@salary predicate
  args subject:entity topic:entity object:integer
  closed true
  description "HR handbook 2.1: 'the table lists the salary of every employee'"
@dept_payroll predicate
  args subject:entity object:integer

@s1 fact
  holds salary ann dev 100
@s2 fact
  holds salary bob dev 120
@s3 fact
  holds salary di ops 80

@payroll aggregate
  over salary ?p ?d ?s
  group ?d
  sum ?s as ?total
  yields dept_payroll ?d ?total
@q query
  where dept_payroll ?d ?t
  select ?d ?t

The development department pays 220 and operations 80.

The same aggregate over an open relation

@salary predicate
  args subject:entity topic:entity object:integer
  description "HR handbook 2.1: 'the table lists the salary of every employee'"
@dept_payroll predicate
  args subject:entity object:integer

@s1 fact
  holds salary ann dev 100
@s2 fact
  holds salary bob dev 120
@s3 fact
  holds salary di ops 80

@payroll aggregate
  over salary ?p ?d ?s
  group ?d
  sum ?s as ?total
  yields dept_payroll ?d ?total

The validator warns aggregate_needs_closed: the source did not say that the table is complete, so the totals are lower bounds.

Invalid: two functions in one aggregate

@salary predicate
  args subject:entity topic:entity object:integer
  closed true
@total predicate
  args subject:entity object:integer
@bad aggregate
  over salary ?p ?d ?s
  group ?d
  sum ?s as ?t
  count as ?n
  yields total ?d ?t

Common mistakes

  1. Counting without declaring the relation closed when the source says the list is complete (or declaring it closed when it does not).
  2. Expecting a set of people to collapse when they have equal values: the person variable is part of the row.
  3. Yielding a variable that is neither grouped nor the output (unsafe_head).
  4. Using an aggregate inside a recursive definition (not_stratifiable).
