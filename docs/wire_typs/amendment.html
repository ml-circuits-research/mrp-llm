amendment

A proposed change to a procedure or to a wire: new wires that supersede versions in force, removals, the reason and the review state. "Allow hard resets when a ticket is open" becomes a proposed norm version plus an amendment that carries it.

Status and author: Host wire. The host composes it from the user's words (the user says the sentence; the host writes the proposed norm version, the amendment and the argument); it is not authored by the formalizer, which never emits it. Acceptance is a host write recorded in the project journal.

Accepted fields

Single means at most once, repeatable means zero or more, and required means at least once. Other field names are rejected (unknown_field). The table is generated from the grammar in sop/knowledge/grammar.mjs.

FieldCardinalityAccepted values and behavior
ofAt most once; requiredThe $procedure_or_wire the amendment changes.
proposed_byAt most once; requireduser or agent.
membersRepeatable; optionalThe proposed wires ($id list): new versions that supersede, or additions, each with approval proposed or contested (amendment_member_not_proposed).
removesRepeatable; optionalWires the amendment would retire ($id list). An amendment proposes members or removes something (amendment_empty).
reasonAt most once; optionalThe user's reason, quoted.
approvalAt most once; optionalproposed, approved or rejected (the same words as the wires' approval).
evaluatedAt most once; optionalA link or note pointing to the what-if comparison the host ran.

What it is for and how to write it

An author normally does not write an amendment. The host writes it in the negotiation loop: a user objects ("why can't I hard-reset r7?", answered blocked_by $no_hard_reset_in_hours); the host asks, through mode abduce with waive hypotheses, which norms would have to be relaxed; the user's words become a proposed norm version, an amendment and an argument; the engine evaluates it as a what-if (if $amendment); the host shows the delta (plan cost, violations, blocked steps) and the user accepts or rejects.

What the engine does

A proposed or rejected wire binds only when a query supposes it with if $id; the answer is then conditional on it, and a proposed successor displaces the version it supersedes for that query. if $amendment supposes all its members at once. Accepting makes the proposed wires approved with approved_by and approved_at and the superseded versions superseded; rejecting records the amendment and its arguments so that the proposal is not re-litigated blindly. Before approval the host may replay the procedure's own smoke cases under the amendment and show which previously passing cases change.

Examples

@router predicate
  args subject:entity
@business_hours predicate
  args none
@ticket_open predicate
  args subject:entity
  closed true
@act action
  params ?r
  requires router ?r
  adds router ?r

@no_hard_reset_in_hours norm
  forbid ~act ?r
  when business_hours
  version 1
  approval approved
  approved_by "ops lead"
  approved_at 2026-01-15
@relax_hours norm
  forbid ~act ?r
  when business_hours
  when absent ticket_open ?r
  version 2
  supersedes $no_hard_reset_in_hours
  approval proposed
@a1 argument
  for $relax_hours
  claim "an open ticket already implies on-call awareness"
  source "incident review 2026-09"
@am1 amendment
  of $no_hard_reset_in_hours
  proposed_by user
  members $relax_hours
  reason "allow a hard reset when a ticket is open"
  approval proposed

The proposed version 2 supersedes version 1 and is used only by a question that supposes it: if $am1 or if $relax_hours.

Common mistakes

  1. Listing as members a wire that is already approved.
  2. An amendment with neither members nor removes.
  3. Writing approval accepted: the vocabulary is proposed, approved, rejected.
  4. Treating an argument as evidence of a fact: it is evidence for a negotiation only.
