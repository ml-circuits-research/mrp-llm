Wire index · stated · unclear · query · unparsed · model/host roles

assumed

An assumed wire states one proposition that the model adds during intent detection: something it takes for granted about the user's intent or the situation that the message does not say. It belongs to the model language; there is one wire type with no subtypes. Like stated it is written context-free, as strings: a relation phrase, roles from the closed inventory with quoted values, polarity and optional temporal expressions. The model uses it whenever a message is vague or has several readings and it picks one (basis disambiguation), when the wording presupposes something (implicature), when it treats a list as complete (closure), or when it applies a typical case (default) or general knowledge (world). An assumption may even restate the queried proposition; that is allowed, but not over-generated. It is never a fact, never stored, never carried to a later turn (the model restates it if needed) and never rendered with fact wording. The normative contract is DS014.

By default (host policy modelAssumptions: 'report') the reasoner ignores model assumptions: the primary answer is computed without them and each one is listed in packet.model_assumptions with treatment: "reported"; the host links it only for the report and an unlinkable assumption never blocks the turn. Only under modelAssumptions: 'branch' does the host link and resolve the assumptions like statements (an ambiguous entity then becomes a host question, so an assumption never chooses an identity) and add a second, hypothetical solve that supplies them as fact … source assumption through solve.assume; that branch is reported separately in packet.assumption_branch and never replaces the primary answer.

Validation and reports

An assumed equal to a stated of the same turn (same folded relation phrase, role values, polarity and validity text) is redundant and rejected (assumed_duplicates_stated). One contrary to a statement is accepted; under branch it is defeated by the user's evidence and reported with defeated: true. At most policy.maxModelAssumptions (default 8) are accepted; more reject the turn (too_many_assumptions) instead of truncating it. Each entry of model_assumptions carries the authored strings, the linked predicate (or null), the atom, validity, basis (or unspecified), treatment, used_in_proof and defeated (both null when reported only) and a host-rendered sentence The model assumed: ….

A closure assumption next to a user statement

@s1 stated
  relation "be a member of"
  role subject "Ana"
  role object "Alpha Lab"
  polarity affirmed
  certainty asserted

@s2 stated
  relation "be a member of"
  role subject "Ana"
  role object "Gamma Lab"
  polarity affirmed
  certainty asserted

@a1 assumed
  relation "be a member of"
  role subject "Ana"
  role object "Beta Lab"
  polarity negated
  basis closure

@q query
  where match
    relation "be a member of"
    role subject "Ana"
    role object "Beta Lab"
    polarity affirmed
  end

"Ana is a member of Alpha Lab and of Gamma Lab. Is she a member of Beta Lab?" Treating the two memberships as the complete list is the model's addition. Under report the answer is unknown (open world) and a1 is listed. Under branch the separate branch is refuted and hypothetical, while the primary answer stays unknown.

An implicature with an open start

@a1 assumed
  relation "works at"
  role subject "Maria"
  role object "Alpha Lab"
  polarity affirmed
  basis implicature

@q query
  where match
    relation "works at"
    role subject "Maria"
    role object "Alpha Lab"
    polarity affirmed
  end

"Is Maria still working at Alpha Lab?" presupposes an earlier employment that the user did not assert. The assumption has no valid line, because the message names no time, and it restates the queried proposition, which is allowed.

A chosen reading

EN “Ana manages Irina. Does she live in Cluj?”

@s1 stated
  relation "manage"
  role subject "Ana"
  role object "Irina"
  polarity affirmed
  certainty asserted

@a1 assumed
  relation "refer to"
  role subject "she"
  role object "Ana"
  polarity affirmed
  basis disambiguation

@q query
  where match
    relation "live in"
    role subject "Ana"
    role location "Cluj"
    polarity affirmed
  end

relation "refer to" (and "mean" for a word sense) is the fixed phrase of the disambiguation convention. The pronoun is read as the subject of the preceding sentence (the convention); the choice is visible as an assumption and the query names Ana. With two parallel clauses and no preferable reading the model writes unclear kind ambiguous instead. More cases: How the model writes.

An assumed clause with a link

EN “Is Maria still at Alpha Lab, now that the Delta Project is over?”

@s1 stated
  relation "be over"
  role subject "the Delta Project"
  polarity affirmed
  certainty asserted

@a1 assumed
  relation "work at"
  role subject "Maria"
  role object "Alpha Lab"
  polarity affirmed
  basis implicature
  before $s1

@q query
  where match
    relation "work at"
    role subject "Maria"
    role object "Alpha Lab"
    polarity affirmed
  end

"still" presupposes that Maria worked there before the project ended: the presupposition is the model's addition, so it is assumed, and the order of the two clauses is its before $s1 line. A link on an assumption is recorded in clause_links as not_checked, like any link on a statement.
