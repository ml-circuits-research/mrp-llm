clarify

The symbolic host can generate clarify when a relation phrase, a name or a temporal expression written by the model cannot be linked uniquely to its lexicon (reason: unresolved_link), when a required identity cannot be resolved uniquely (reason: unresolved_dependency), or when a downstream required scalar is missing or nonunique. The questions use the lexicon's labels in the answer language, never identifiers. Model-authored declarative input is limited to stated/assumed/unclear/query/constraint and cannot write this wire. The host suspends dependent work and asks the user rather than guessing. Missing factual support for an otherwise well-formed query is not a clarification trigger. The wire returns an explicit clarification packet; it does not insert a guessed identity into a SOP question, retrieve evidence or mutate the repository.

Supported field

Field / multiplicityValue and semantics
text — exactly one, requiredA question or instruction for the user, plain or JSON double-quoted because this field consumes the rest of the line. For example, text Which Maria Ionescu? and text "Which Maria Ionescu?" are both accepted; canonical generated/training text always uses the latter form, including a one-word message. Preserve proper-name spelling and encode embedded double quotes and backslashes with a JSON string encoder; single and smart quotes are not string delimiters. See quoted text syntax. Runtime calls unquote: quoted text is decoded, unquoted text is passed through literally. The parser checks that the field exists but does not enforce nonempty text or that it ends with a question mark. $id or ?name inside quoted text remains ordinary text, not a reference or variable: text is excluded from graph dependencies, so use actual language rather than a putative injected value. The UI/host decides how to present the question.

Packet, not an answer

Runtime returns {status:'clarify', text, complete:false}, records the wire value and recognizes the object as a genuine result packet. A cnl consumer renders its text as the leading message and indicates incompleteness. Clarification is appropriate before attempting resolve against unknown or ambiguous names; it is not automatic repair of an unresolved dependency. As with other packets, merely producing it does not guarantee that the conversational host will ask a follow-up: the consumer must display or use the result.

Current syntax examples

Standalone clarification for ambiguous locations:

@which_station clarify
  text "Do you mean the North Station or the South Station?"

The value is incomplete and requests an identity choice. The next circuit carries the same request through deterministic rendering; no fact or answer is asserted:

@which_period clarify
  text "What date or interval should the query use?"

@display cnl
  result $which_period
  language en

This source is rejected by the parser: an empty clarify declaration has no required text field. A present-but-empty text line is different: it may parse, but would provide no useful clarification.

@missing_question clarify
