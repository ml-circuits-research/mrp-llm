cnl

A cnl wire renders a genuine runtime result into controlled natural language. This is deterministic explanation of a checked result, not a query, second inference stage, or authorization to manufacture evidence. In a model-authored declarative turn the host generates rendering; the model cannot author a cnl wire or invent a result packet. A CLI user can inspect the rendering and the attached packet; a verbalizer is a separate optional agent stage. The rendering is shared by trusted and model-origin circuits; in a model-origin turn the host also renders the conditions a hypothetical answer rests on, the separately reported assumption branch, the fixed unclear replies and the "cannot compute this kind of answer yet" reply for an understood problem without an engine.

Fields

Field / multiplicityAccepted value and behavior
result — exactly one, required$id value reference to a runtime-produced result packet. The runtime checks its object identity against packets produced by reason/solve, clarify, remember, or supported operation handlers; a copied object with status/answers is rejected. No ~id definition handle or arbitrary quoted JSON is accepted here.
language — zero or one, default enThe core renders English only (owner decision of 2026-10-01, DS014 "English-only core"): a cnl wire renders the English message table whatever language says, and the returned value records language: "en". Another answer language (the chat API language field or an explicit request in the message such as "answer in Romanian") is produced by translating the finished English text at the output edge (TranslatorService), not by this wire.

Rendering and boundaries

The resulting value contains {kind:'cnl', language, text, packet}. Text starts with a localized status message (or the clarify.text question). Count packets include a count; answer rows emit ANSWER with variable/value pairs and, for interval queries, VALID [start, end). Bound output projections emit VALUE; proof facts emit EVIDENCE with atom, source or derivation, plus validity when appropriate. Other packets can emit objective, hypothesis, pattern, candidate, analogy, plan, suggested test, intervention or actual engine/fallback lines. complete:false appends an incomplete warning; hypothetical packets are marked. The formatter does not infer a negative answer from unknown status or convert candidate evidence into proof. Repository writes are not made by rendering.

Current syntax examples

Local evidence and a genuine solve result; expected rendering describes a supported answer with its source, subject to the reasoning result:

@record fact
  holds located book_a shelf_b
  valid timeless
  source "catalog item 41"

@request query
  where located book_a ?place
  select ?place
  mode select

@check solve
  query $request
  data $record
  output ?place one

@report cnl
  result $check
  language en

Clarification also produces a genuine packet. Here the rendering conveys the request for a missing distinction, not a fabricated answer:

@need_detail clarify
  text "Which of the two rooms do you mean?"

@question_to_user cnl
  result $need_detail
  language en

This parses, but value creates a plain object, not a runtime-produced result packet, so CNL rejects it:

@forgery value
  data {status: "supported", answers: []}

@unsafe cnl
  result $forgery
  language en
