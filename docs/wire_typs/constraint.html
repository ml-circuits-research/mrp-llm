constraint

Declares an integer arithmetic question over specified variables and requirements. A host-generated or trusted solve/reason wire evaluates it; declaration alone proves nothing. The model may request scalar variables using select.

Status and author: A formalizer may propose this wire under host policy; it is not by itself a memory write.

Accepted fields

Single means at most once, repeatable means zero or more, and required means at least once at parse time. Other field names are rejected.

FieldCardinalityAccepted values and current behavior
varrepeatable; optional?name int or ?name int min max. Name matches lowercase letter then lowercase letters/digits/underscore; distinct declarations. Bounds are safe integers (literal or scalar $wire values), inclusive with min ≤ max. The JS solver requires finite bounds.
selectAt most once; optional; default no requested scalar projectionWhitespace-separated ?var names declared by var. The model requests a checked scalar value from a numeric result; the host projects selected variables only when supported and unambiguous, rather than inventing assignments. An unresolved requested value produces host clarification even when the claim itself is entailed. Query projections feeding a later constraint are likewise generated as checked one-value outputs.
requirerepeatable; optionalA comparison in words, TERM COMPARATOR TERM, or a native all/any/end block of them, over declared integer variables, integer constants and resolved $wire integer references. Comparators: above, below, at_least, at_most, equal, not_equal; between terms: plus, minus, times, divided_by. Repeated require fields are conjunctive restrictions on feasible assignments. require ?v equal 2380 times 19, with only numbers on the right, makes the host compute ?v itself.
claimsingle; required unless select asks for result valuesA comparison in words or a native all/any/end block over the same variables; tested against feasible assignments for prove/possible, and treated as a feasibility condition for optimize. A computation or a selected finite assignment may omit claim. Repeated simultaneous conditions belong in require, never repeated claim fields or independently solved constraint wires.
tasksingle; required in model output (constraint_task_required); optional in trusted circuits, default proveOne of prove (all feasible models), possible (some feasible model), optimize (best objective among feasible models satisfying claim). Any other value fails lowering with constraint task must be prove, possible or optimize. The default is not neutral: an omitted task silently means prove, and prove and possible give opposite readings of the same claim. Always write task explicitly.
unitsingle; optional, default scalarUnquoted unit label carried in the problem/result for presentation; no automatic conversion or dimensional checking.
objectivesingle; required if optimize; forbidden otherwiseInteger arithmetic expression defining value to minimize/maximize.
directionsingle; optional, default minmin or max; any other value fails lowering with objective direction must be min or max. It is meaningful only for optimize. For prove and possible a valid direction is accepted and has no effect; this is a known gap, not a feature, so do not write it outside optimize.

Execution and result

Words, not operators. A model-authored constraint writes every comparison and arithmetic step in words (DS014 "Words, not operators"); the model admission rejects an operator symbol with operator_not_words. The host maps above below at_least at_most equal not_equal to > < >= <= == != and plus minus times divided_by to + - * /. Quantities are integers scaled by the model when needed (19% of 2380 is 2380 times 19 hundredths); divided_by and decimal numbers are answered not_computable. Trusted circuits may still write the operator spelling. Portable Boolean syntax supports !, &&, ||, == === != !== < <= > >=; integer expressions support constants, declared ?x, unary minus, + -, and multiplication only with a constant operand. No arbitrary JavaScript, division, remainder, function calls, string comparisons or non-linear variable products. $wire must resolve to a safe integer. The parser first accepts expression-shaped fields; lowerConstraint enforces the smaller numeric grammar.

Reasoning strategy reference uses JS finite enumeration, bounded by maxAssignments (default 100,000). advanced selects Z3 if available, otherwise JS finite fallback; an explicit non-JS backend (such as z3) on the evaluating solve/reason wire without a reasoning field implicitly selects the advanced strategy; write reasoning advanced explicitly so the route is visible. A requested backend is never substituted: if it is unavailable the result is unsupported with that backend named, and an explicit external backend with reasoning reference returns unsupported with code reference_backend_mismatch. solve can project declared variables via output ports; reason alone has no output fields. For prove: entailed/refuted/unknown/inconsistent; for possible: possible/impossible/unknown/inconsistent; optimization returns optimal, feasible_bound or inconsistent, subject to completeness. Neither SAT nor a witness alone means universal entailment. Constraint and solve do not write memory.

Current SOP examples

Finite feasibility and projection

@deadline constraint
  var ?arrival int 0 100
  require ?arrival equal 42
  claim ?arrival at_most 45
  task possible
  unit minute
  select ?arrival

The model submits this declaration alone. With a complete finite search, the host-generated circuit establishes possible and projects the unique arrival value 42.

Nested alternatives without parenthesized Boolean formulas

@pairs constraint
  var ?xx int 0 3
  var ?yy int 0 3
  require any
    ?xx plus ?yy equal 3
    all
      ?xx equal 3
      ?yy equal 3
    end
  end
  claim ?xx plus ?yy at_most 3
  task possible

@result solve
  constraint $pairs
  output ?solutions rows

The finite backend exports one array containing {xx: 0, yy: 3}, {xx: 1, yy: 2}, {xx: 2, yy: 1}, {xx: 3, yy: 0}, and {xx: 3, yy: 3}. These are correlated assignments satisfying require. The last row does not satisfy claim: possible/prove checks claim separately rather than filtering the exported base models. Merely declaring the variables does not produce $xx or $yy. The explicit rows output produces $solutions; Z3 does not currently support this projection. See group syntax and result-shape intuition.

Objective among models satisfying claim

@slots constraint
  var ?slot int 0 8
  require ?slot at_least 3
  claim ?slot at_most 6
  task optimize
  objective ?slot
  direction max

@choice solve
  constraint $slots
  output ?slot one

The feasible objective candidates are 3–6, so a complete search has optimum 6 and a unique slot projection.

Arithmetic: a computed value ("What is 19% of 2380 lei?")

@vat constraint
  var ?vat_hundredths int
  require ?vat_hundredths equal 2380 times 19
  select ?vat_hundredths
  task possible
  unit hundredths_of_lei

The model scales the percentage to integers (hundredths) and writes the arithmetic in words; it computes nothing. The host fixes ?vat_hundredths to 45220 and projects it; the answer is 452.20 lei. The same message in English ("What is 19% of 2380 lei?") gives the same target.

One named assignment, simultaneous requirements

"Let x be Ana's assignment and y be Bogdan's assignment. Both are integers from 0 to 6. Is there an assignment where x plus y equals 5, twice x plus y equals 7, and x is less than y? Give x and y if possible." The names label the declared unknowns, not string operands or separate participant queries.

@assignment constraint
  var ?x int 0 6
  var ?y int 0 6
  require ?x plus ?y equal 5
  require 2 times ?x plus ?y equal 7
  require ?x below ?y
  task possible
  select ?x ?y

The requirements hold together for the unique witness x = 2, y = 3. The author writes the original domains and conditions, never calculates this witness or narrows domains to an answer.

Division is not computed

@share constraint
  var ?each int
  require ?each equal 900 divided_by 4
  select ?each
  task possible

"Split 900 lei between 4 people": the model writes the division literally, which is valid model output. The host compiler recognizes divided_by (or a decimal number) and answers not_computable before any lowering; a trusted circuit that tries to lower it fails as shown, because division and decimals are outside the integer profile.

Invalid: an operator symbol in model output

@limit constraint
  var ?x int 0 10
  claim ?x >= 3
  task possible

A model writes claim ?x at_least 3, never >=.

Invalid or unsafe example

@bad constraint
  var ?a int 0 10
  var ?b int 0 10
  require ?a times ?b equal 6
  claim ?a above 0
  task prove

This parses (the words become ?a * ?b == 6) but fails numeric lowering: multiplication of two variables is not in the portable linear profile.

Knowledge language: constraint

In the knowledge language a constraint states a finite integer problem in words; the same wire is used on the model surface, where the model writes it from a message. The tables and examples of this section are about the knowledge form, written from a source and checked by sop/knowledge/; the sections above describe the host-circuit form. Anchors of this section's fields start with kfield-. The language manual is the section "Knowledge wires" of DS004.

Other field names are rejected (unknown_field). The table is generated from sop/knowledge/grammar.mjs.

FieldCardinalityAccepted values and behavior
varRepeatable; optional?x int [MIN MAX], repeatable; every variable of an expression must be declared (undeclared_variable).
requireRepeatable; optionalA comparison A [WORD A]... WORD B over declared variables and integers: comparators above below at_least at_most equal not_equal, arithmetic plus minus times divided_by.
claimAt most once; optionalThe comparison to prove; required for task prove.
objectiveAt most once; optionalAn arithmetic expression to optimise; required with direction for task optimize.
directionAt most once; optionalmin or max.
taskAt most once; optionalprove (default), possible or optimize.
selectAt most once; optionalThe ?variables to report.
unitAt most once; optionalText: the unit of the result.

What it is for and what comes back

Use a constraint for the arithmetic of a manual (totals, thresholds, tariffs, durations) that compute, compare and the aggregates cannot hold as a rule. The results are entailed, possible, impossible, inconsistent, optimal and feasible_bound. A mixed relational and numeric problem is a two-stage circuit: a query feeds a constraint through $q.

Examples

@c constraint
  var ?x int 0 20
  var ?y int 0 20
  require ?x plus ?y equal 10
  require ?x minus ?y equal 2
  claim ?x equal 6
  task prove
  select ?x ?y

Invalid: an undeclared variable

@c constraint
  var ?x int 0 20
  require ?x plus ?z equal 10
  claim ?x equal 6
  task prove
