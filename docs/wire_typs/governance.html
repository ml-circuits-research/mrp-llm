Governance and modes of work

Which version of a rule, action, method or norm binds, who writes the fields that say so, and how a change is negotiated. A "mode of work" is the sum of approved methods, norms and procedures: the system acts by them, optimises within them, and lets an amendment be negotiated with the user.

The governance fields

The governed wires are rule, default, integrity, action, method and norm. Fields: version, supersedes, approval (proposed approved contested rejected superseded retired), approved_by, approved_at, retired_at, scope, source, quote. The field is approval, not status, because fact.status already means observed|reported|hedged|supposed.

Who writes what

  • The host writes the approval fields. In memory every governed wire carries approval approved, approved_by and approved_at; a wire from a store older than the fields is read as approved at its known_at. An author never writes them: a submitted wire without them is proposed until the host approves it.
  • Authoring mode. node eval/smoke-reasoning/validator.mjs --authoring FILE... ignores the three fields with the warning governance_ignored and leaves approval_incomplete to ingestion.
  • approved_at is required for every norm and every strict method, so that an asof question about a prohibition is always answerable.

What binds

  • Only approved wires bind, and so do contested ones, flagged: a disputed wire keeps binding until the host rules, otherwise an objection could switch a prohibition off. The packet lists them in contested.
  • Proposed and rejected wires are used like supposed facts: they enter a query only when it supposes them (if $id), the answer is conditional on them, and a proposed successor displaces the version it supersedes for that query ("what would the plan be if this amendment were approved").
  • Superseded and retired wires bind only for an asof date inside their period. A wire is in force from its approved_at until its successor's approved_at (or its retired_at).
  • scope. A scoped wire binds when its tags intersect the query context; an unscoped wire always binds; with no context scope established, scoped norms bind anyway and the packet sets scope_unknown: true: a restriction is never dropped for lack of context. policy procedures selects methods and the rendered set; it does not switch norms off.

The negotiation loop

  1. A user objects: "why can't I hard-reset r7?" The answer is blocked_by $no_hard_reset_in_hours.
  2. The host asks, through mode abduce with waive hypotheses, which norms would have to be relaxed, and offers them as the negotiable items.
  3. The user's words become a proposed norm version, an amendment and an argument, composed by the runtime; the formalizer never emits them.
  4. The engine evaluates the amendment as a what-if (if $amendment); the host shows the delta (plan cost, violations, blocked steps).
  5. The user accepts or rejects. Acceptance is a host write recorded in the project journal with provenance; rejection keeps the amendment and its arguments so that the proposal is not re-litigated blindly. Who may approve is a host policy.

Example: versions and an amendment

@a predicate
  args subject:entity
@act action
  params ?x
  requires a ?x
  adds a ?x
@n1 norm
  forbid ~act ?x
  version 1
  approval superseded
  approved_by "ops lead"
  approved_at 2025-03-01
@n2 norm
  forbid ~act ?x
  when a ?x
  version 2
  supersedes $n1
  approval approved
  approved_by "ops lead"
  approved_at 2026-01-15
