All wire types

induce

Induction evaluates proposed rule-shaped regularities on explicitly supplied cases, or generates bounded one-condition candidates with a shared variable. Results remain candidate patterns and are not approved rules. Trusted system/tool circuits can use this operation; model-authored declarative input cannot invoke it directly.

SOP syntax: @id type, exactly two leading spaces on each field line, $id for a computed value, ~id for a declaration handle, and ?x for a local logic variable or an output name. Atoms use [not ]predicate term1 [term2 [term3 [term4]]] with one to four whitespace-separated terms; lowercase predicate names, canonical symbols, JSON-quoted strings or safe integers. Parenthesized predicate(arg, …) and comma-separated arguments are not executable syntax.

Fields and inputs

KeywordCardinalityAccepted value, default and effect
dataAt most once; requiredOne $trace, ~trace or packed $array of training traces. Required; every item must be a trace.
candidatesAt most once; optionalOne $pattern, ~pattern or packed $array of patterns. Omitted or empty means generate bounded one-condition shared-variable patterns from training traces.
holdoutAt most once; optionalOne $trace, ~trace or packed $array of validation traces. Optional, default empty; IDs must not overlap training IDs.
reasoningAt most once; optionalA strategy name (plain token), default host policy.reasoningStrategy (reference by default). Built-ins: reference (the js-reference oracle; js-reference and js-oracle are the same route) and the deprecated advanced (the oracle plus optional external backends for deduction and numeric constraints). The host may restrict allowed strategies.
policyAt most once; optionalOne $policy value or ~policy declaration handle. It must lower to a policy object; each specified positive integer budget caps the corresponding host budget by min(host, wire). No policy reference means host limits alone.
outputRepeatable; optionalRepeatable ?name [one|many|rows|count|status] declaration, default one. Each output becomes a deferred $name value if bound; names must be unique and cannot collide with explicit wires. status binds result status even for incomplete results. Other modes require completeness; unusable/unselected modes become blocked, not arbitrary first answers.
afterRepeatable; optionalRepeatable $wire value-dependency reference. Orders execution after that producer; it does not alter inputs, proofs or output. A ~definition handle is graph-checked but is not a value-ordering dependency.

Induction uses only trace features, never repository facts as implicit cases. For each matching condition assignment it checks explicit conclusion, explicit contrary evidence, or missing conclusion; missing counts as a counterexample only for closed true reviewed traces.

Result and limits

Returns status approximate (unknown when no pattern is found) with guarantee approximate and ranked patterns with training support/opportunities/counterexamples, optional holdout metrics and provenance requiring reviewed semantic validation (each pattern stays status candidate), generator and generator_truncated. Output one/many/rows projects patterns, count unsupported, status projects approximate or unknown. No fact or rule is installed.

All operations use bounded search (host defaults include maxNodes 5000, maxDepth 8, maxCandidates 512, timeoutMs 3000); a ~policy can only tighten configured limits. The result records completeness and epistemic status relative to supplied finite inputs and the visible memory view, never calibrated truth probability. No operation here writes to the repository; after is only scheduling. At most the bounded candidate set is evaluated. Training and holdout IDs must be disjoint; closed traces are barred to model-origin authorship. Support is a ratio over observed condition opportunities, not proof or a calibrated probability.

Executable examples

Evaluate supplied candidate

@a trace
  feature alert motor1
  feature inspect motor1
@b trace
  feature alert motor2
  feature not inspect motor2
@p pattern
  when alert ?x
  then inspect ?x
@train pack
  items $a $b
@result induce
  data $train
  candidates ~p

One matching trace supports the conclusion and the other explicitly contradicts it; induction reports counts and keeps the candidate unapproved.

Separate holdout

@training trace
  feature signal device1
  feature inspect device1
@validation trace
  feature signal device2
  feature inspect device2
@p pattern
  when signal ?x
  then inspect ?x
@result induce
  data ~training
  holdout ~validation
  candidates ~p

The two distinct trace IDs prevent training/holdout leakage; evaluation reports separate metrics.

Invalid or unsafe use

@same trace
  feature signal device1
@p pattern
  when signal ?x
  then inspect ?x
@bad induce
  data ~same
  holdout ~same
  candidates ~p

The parser accepts the references, but induction rejects overlapping training and holdout trace IDs.
