jsEval

Evaluates a restricted JavaScript-shaped expression for controlled coding-agent composition. This is not a JavaScript script runner, and it cannot read files, call the network or execute arbitrary functions.

Status and author: Host-controlled system surface, always available to trusted and host circuits (there is no host policy switch for it). Since 2026-10-03 (proposal P-6, owner decision) the formalizer may also write jsEval wires on one route only, the jsEval route: a problem whose goal asks for a value or a choice computed from given data. Everywhere else model-surface admission still rejects jsEval (MODEL_TYPES in sop/declarative.mjs). The expression sandbox limits maxExprOps and maxExprBytes always apply.

Accepted fields

Single means at most once, repeatable means zero or more, and required means at least once at parse time. Other field names are rejected.

FieldCardinalityAccepted values and current behavior
exprAt most once; requiredRestricted JavaScript-like expression, e.g. only($rows).name; interpreter reads completed $id values and rejects unavailable globals/statements.

Execution and result

Allowed literals are double-quoted JSON strings, finite numbers, booleans, null, arrays, and object literals with safe keys. Operators: unary !/-, + - * / %, comparisons < <= > >= for same-type numbers/strings, strict-equivalent == === != !==, short-circuit && || ??, and ?:. Numeric arithmetic requires numbers; string + joins strings. Dot/bracket lookups require own properties (or length for arrays/strings). Calls: String(x), Number(x), only(array) for exactly one element; numeric Math.abs/min/max/floor/ceil/round/pow; string trim/toLowerCase/toUpperCase/normalize/slice/substring/includes/startsWith/endsWith/replaceAll/split, and array slice/join. Methods enforce argument types; no regular expressions.

Bounded functional operations (since 2026-10-03, proposal P-6): range(n) (the integers 0 to n-1) and range(a, b) (a to b-1); sum(array) (0 for an empty array), count(array), count(array, x => test), min(array) and max(array) over numbers (an empty array fails); the array methods map(x => …) and filter(x => …) (the function may take the index as a second parameter), reduce((acc, x) => …, start) (without a start it begins with the first item; an empty array then fails), sort((a, b) => …) (a comparator is required and must return a number; the sort is stable and returns a new array, the input is never changed) and includes(value) for a number, text or yes/no value. A function is a pure arrow with an expression body only (x => x * 2, (a, b) => a - b, at most three parameters, no block, no statement). It exists only as the argument of map, filter, reduce, sort or count: it has no name and cannot be stored, returned, put in an array or object, or called directly, so there is no recursion. A parameter may not take a callable name (Math, range, …) or a forbidden key. Every call of a function body and every whole-array step is charged to the same operation budget, and range is charged per item. Recursion, graphs, paths and search are not expressions: they belong to SOP rules and constraint, where the engines solve them.

eval, Function, imports, globals, arbitrary object methods and keys __proto__, prototype, constructor, caller, callee, arguments are forbidden; a data value shaped like a function is never taken for one. Limits: source 16,384 characters, 4,096 tokens, 2,048 AST nodes, depth 64, at most 32 call arguments, default 10,000 evaluated operations, 65,536 bytes serialized output/string budget, and 4,096 array items. Host policy may lower operation/output budgets. Nonfinite results fail. The produced value is ordinary data without proof or world write.

Current SOP examples

Numeric composition

@start value
  data 770

@travel value
  data 70

@arrival jsEval
  expr $start + $travel

The interpreted result is 840. This expression has no side effect.

Safe object projection and unique selection

@rows value
  data [{name:"Ana", score:4}]

@selected jsEval
  expr only($rows).name.toUpperCase()

The result is the string ANA. With zero or two elements, only fails instead of choosing a row.

Counting and summing with a test

@weights value
  data [12, 7, 9]

@limit value
  data 8

@shipping jsEval
  expr count($weights, w => w > $limit) * 2

@heavy jsEval
  expr sum($weights.filter(w => w > $limit))

Two boxes weigh more than 8, so shipping is 4; heavy is 21.

A choice computed from data: map, reduce, sort

@options value
  data [{name:"bus", fare:12, trips:3}, {name:"train", fare:15, trips:2}]

@costs jsEval
  expr $options.map(o => ({name: o.name, total: o.fare * o.trips}))

@cheapest jsEval
  expr $costs.reduce((best, o) => o.total < best.total ? o : best).name

@ranked jsEval
  expr $costs.sort((a, b) => a.total - b.total).map(o => o.name).join(", ")

The bus costs 36 and the train 30: cheapest is train and ranked is train, bus.

A bounded range

@total jsEval
  expr sum(range(1, 11).filter(n => n % 3 == 0))

3 + 6 + 9 = 18.

Invalid or unsafe examples

@unsafe jsEval
  expr process.env.SECRET

Although this text parses as a property lookup, process is an unavailable global at evaluation; no host access is granted.

@loop jsEval
  expr [1, 2].map(x => { return x * 2 })

A function body is one expression; a block of statements is rejected by the expression parser.

@self jsEval
  expr (f => f(f))(1)

A function cannot be called directly, so it cannot call itself: there is no recursion.

@grid jsEval
  expr range(4096).map(i => range(4096))

Every function call and every array step is charged: the nested ranges exhaust the operation budget.

The jsEval route of the formalizer

Since 2026-10-03 (proposal P-6, DS014 "The jsEval route"). Routing (deterministic, lib/formalize/structure/route.mjs): a problem goes to this route when the structure role marked a goal span inside a question unit and at least one registry number lies inside a quantity span; everything else (puzzles, deductions and rule questions without data) stays on the FOL route. Authoring: the model (role prompt config/prompts/js-v1.md, served by Ploinky Workers) writes only jsEval wires over the problem's registry numbers $v1…$vn (a percentage is its fraction); the runtime states those numbers from the message, never the model. Admission (lib/formalize/js-program.mjs admitJsProgram): only jsEval wires with one expr (js_route_type, js_extra_field); new names, never vK (js_redefines_registry, js_duplicate_name); a wire reads only registry values and earlier wires, so there is no cycle (js_unknown_reference); no ?variable; a text literal is copied from the problem (js_text_not_in_message); an answer depends on the problem's numbers through the dataflow (js_answer_not_from_data); the interpreter evaluates every wire within its budgets (js_runtime_error); a violation is asked once more. Lowering: each admitted program is lowered where it can be: arrays of fixed shape (literals, a range of a literal bound, records with fixed fields) are unrolled through map, filter, reduce, sum, count, min, max and includes into the arithmetic of the expression path and from there into compute/compare rules that every engine executes with a proof. What has no fixed shape (a range over data, sort, text methods, a list answer of data-dependent length) stays jsEval and is executed by the oracle; the other engines answer not_expressible for it.

For example, the model's

@weights jsEval
  expr [$v6, $v7, $v8]
@answer jsEval
  expr count($weights, w => w > $v9) * $v10

is lowered to the rule answer = (((v6 > v9) ? 1 : 0) + ((v7 > v9) ? 1 : 0) + ((v8 > v9) ? 1 : 0)) * v10, i.e. one session rule per branch with compare and compute conditions over the stated registry values.

Where jsEval sits in the knowledge language

jsEval is a trusted escape hatch for what the core condition leaves cannot express (string handling, calendar arithmetic, a lookup the runtime owns), and the turn-local computation of the jsEval route. It is not a knowledge wire and not in the grammar of the knowledge language (the manual). The logic engines (Prolog, Z3, Datalog, ASP, SQL) cannot see inside an expression, so a rule or aggregate whose truth depends on one is not_expressible for them unless the runtime exposes it as a provider that feeds facts back; the oracle may evaluate it in-process, and the jsEval route lowers what it can to compute/compare first. A model that compiles a source never writes jsEval: an expression is code, its effects cannot be read off the wire and no engine can check it, so one that arrives from a source is not accepted into memory; a reviewed step may admit one, stored with its source sentence and version like any governed wire. Arithmetic of manuals (totals, thresholds, tariffs, durations) is written with compute, compare, the aggregate wire and constraint; what they cannot express (rounding rules, percentages with fractions, date arithmetic, string operations) is reported as "not expressed".
