How the model writes

Archived author guide. The one-shot author LLMDirect, which wrote whole circuits from a guide, was archived on 2026-10-02 (owner decision): formalization is step by step, the system asks short questions and assembles the circuit, and the answering model never writes SOP. Its guide is kept for history in probably_obsolete/one-shot-formalization/skills/coding-agent-query/. The grammar below is still the circuit surface that the step-by-step assembly produces and the validator admits.

This page explains the lower-level proposition grammar: stated, assumed, unclear, query, constraint and unparsed. The examples exercise that grammar through the trusted runtime; assertion examples are not permission for the current query author to state facts. Its stricter contract is queries, user suppositions, labelled assumptions and optional turn-local definitions: see Session circuits and answer-shape self-check and DS014. Question types lists the question forms. Every executable example is checked by tests/docs/wire-help.test.mjs.

1. What the model receives and writes

The query author's input is the user's message and retrieved memory vocabulary. Predicate ids with their roles and entity hints are allowed; answers, gold, sealed cases and other sessions are not. Names stay as written or use listed ids. After execution, one bounded circuit-only self-check sees status, result cardinality and the deterministic circuit reading, never answer values. Identity, time normalization and executable policy remain decisions of the KnowledgeLinker and runtime, not facts invented by the author.

Output: SOP wires, one keyword per line, with quoted strings. Keywords and normalized content words are English (see content words). A proposition has a relation, one to four role lines and a polarity; clause connections use link lines. The KnowledgeLinker links relation phrases and roles to predicates and values to entities. The runtime normalizes time, chooses an authorized reasoning strategy and emits clarify when a required value is unknown or ambiguous. The author never chooses an identity, an engine or an answer.

Use the full declared vocabulary before rebuilding a derivation or reporting a missing relation. Aggregate result values are selected, not counted again; defaults already include their exceptions; integrity relations keep their declared constraint and witness roles. Predicate metadata includes reviewed closed status without facts. In a query only, polarity absent asks about missing positive evidence on a closed predicate; polarity negated asks about explicit negative evidence. Open-predicate absence is refused. See closed-list absence and shared numeric assignments.

A proper name (person, organization, place, title) is written as in the message (with its diacritics, case ending or typo) in quotes; any other value is the message's word, normalized; a question slot is a ?variable. The relation is the phrase as meant, normalized to its lemma ("work at" for "works at", "worked at", "wroks at").

Content words: English, normalized

The core is English-only: the formalizer reads a message in any language and writes English content words. It normalizes the words it copies; the KnowledgeLinker links them to its English knowledge, retrying English synonyms from its reviewed dictionary (config/dictionary/).

  • Relation phrases are English lemmas: the base form ("work at", "live in", "be employed by"). A modal stays inside the relation ("be allowed to sign").
  • Common nouns and descriptions keep the message's determiners and definiteness, lower case: "the gym" → "the gym", "my brother" → "the user's brother". An obvious typo is repaired only when the intended word is unambiguous.
  • Proper names stay exactly as written, diacritics and typos included ("Ayşe Şahin", "Pitești", "Kovács & Asociații"), because the host links them to its entities.
  • Dates and times are copied as written ("12 March 2020", "now", "March 2024"); the host normalizes them.
  • The first person is "the user" and "the user's brother"; the host links "the user" to the caller's entity when the conversation supplies one.
  • Keywords are English in every language: relation, role subject, polarity, the link keywords because, if, … and the fixed disambiguation phrases relation "mean" and relation "refer to".

The host tries the phrase as written first; a phrase that does not link is retried with its English synonyms, and the lexicon picks (packet translations). After the synonyms, a reviewable frame and synonym list (sop/frames.mjs, config/dictionary/frames-*.tsv) may normalize the output as host work: a synonym becomes the frame's relation, a role name the frame does not declare is renamed when only one declared role is free, and a relation/object boundary is shifted when that names a frame ("get" + "the flu shot" → "get the flu shot"). The model writes what the message says; it never needs the list. The answer language is a separate concern of the output edge: the answer is English, and it is translated into Romanian when the caller or the message asks for it.

2. Step by step

  1. Is there anything to formalize? Unintelligible text → unclear kind gibberish. No statement and no question ("ok", "thanks", "write a poem") → unclear kind no_request. Otherwise continue; an odd, contradictory or seemingly irrelevant message is still formalized as written.
  2. Split the message into clauses. Each finite clause is one wire: an assertion, supposition or reported claim is a stated; a question is a query (or a constraint for a numeric problem). A subordinate clause is its own wire, and the main clause names it with one link line (because $s2, if $s1, …). Remarks about the user's own situation or purpose ("I have a meeting tomorrow", "I ask because my boss wants to know") are not part of the problem and are left out.
  3. Choose the question form from the question word, without rewriting it: see Question types.
  4. Write each proposition: relation as meant, values as written, content words in English, normalized, polarity always explicit (negated only for an explicit "not" or "no"), valid only when the message gives a time, and certainty on every stated.
  5. Make every interpretation visible. Whatever the model adds — a chosen reading, a presupposition, a closed list, a typical default — is an assumed proposition. If two readings are equally good, write only unclear kind ambiguous with the readings.
  6. Say what you could not formalize. A part of the message the model cannot write (jargon, an idiom, a garbled fragment, "that one") is copied verbatim into an unparsed wire; the role it would fill gets a placeholder ?variable.
  7. Stop. The model does not answer, does not judge whether the question can be answered, and never refuses.

3. Worked examples

EN “Maria has worked at Acme since 2021. Who else works there?”

@s1 stated
  relation "work at"
  role subject "Maria"
  role object "Acme"
  polarity affirmed
  valid from "2021"
  certainty asserted

@q query
  select ?who
  where match
    relation "work at"
    role subject ?who
    role object "Acme"
    polarity affirmed
  end
  except ?who "Maria"

"there" has one antecedent and is written as "Acme". "else" excludes Maria with except, whose value is written as in the message; the host resolves it like a role value. The model writes words, never operators.

4. Typos, missing diacritics and informal writing

Messages are often misspelled, written without diacritics in names, or in chat style (the input edge has already corrected the spelling of the words that are not names). The model normalizes the relation (it is the meaning, written as a lemma) but copies names as written (they are what the user typed). The host then matches names after case and accent folding, so "Brasov" finds "Brașov"; it never resolves an identity by similarity, so a misspelled name that matches nothing becomes a question to the user rather than a guess. For a stated value, the agent guard accepts small typos when it checks that the value occurs in the message (up to one edit for tokens of four to seven characters, two beyond, and short inflections).

EN “does Maira wrok at acme??”

@q query
  where match
    relation "work at"
    role subject "Maira"
    role object "acme"
    polarity affirmed
  end

"wrok" becomes the relation "work at"; "Maira" and "acme" stay as written. If the host knows a "Maria" but no "Maira", it asks.

No diacritics and no capitals in the message. The relations are normalized lemmas; the names stay exactly as typed ("ana", "brasov"). "I think" makes the statement hedged. "now" is a time expression the message gives, copied as written into at; the host normalizes it against its clock.

5. stated or assumed?

The rule. stated only when the model is sure the claim comes from the user's message. Anything the model adds, infers, completes or presupposes is assumed. When in doubt, assumed.

stated has a certainty: asserted (the user says it), hedged ("I think", "probably") or supposed ("suppose", "if"); reported speech ("Ion says that …") adds speaker "Ion". Every value of a stated must come from the message: a name as written, or the message's own words, normalized. assumed has no certainty and an optional, purely descriptive basis: closure, default, disambiguation, implicature or world. An assumption may even restate the queried proposition (a presupposition or a closure often does); it is reported, and by default never used to compute the answer.

MessageFormalizationWhy

"I think the door is open."stated certainty hedgedThe user said it, with a hedge.
"Suppose Maria works at Acme. Would she be paid?"stated certainty supposed + queryThe answer is conditional on the supposition.
"If Maria works at Acme, is she paid?"stated certainty supposed + query with if $s1The condition belongs to this question only.
"Ion says that Maria left."stated with speaker "Ion"Attributed to Ion, used only conditionally.
"Tweety is a bird. Can Tweety fly?"stated + optional assumed basis default + query"Birds fly" is general knowledge, not the user's claim.

EN “Room A and room B are booked. Is room C free?”

@s1 stated
  relation "be booked"
  role subject "Room A"
  polarity affirmed
  certainty asserted

@s2 stated
  relation "be booked"
  role subject "room B"
  polarity affirmed
  certainty asserted

@a1 assumed
  relation "be booked"
  role subject "room C"
  polarity negated
  basis closure

@q query
  where match
    relation "be free"
    role subject "room C"
    polarity affirmed
  end

Each booked room is its own proposition, and each value keeps the words of the message ("Room A" with its capital). The closure is the model's addition and is reported, not used, by default.

EN “Ion says that Maria left Acme in March 2024. Did she?”

@s1 stated
  relation "leave"
  role subject "Maria"
  role source "Acme"
  polarity affirmed
  valid on "March 2024"
  certainty asserted
  speaker "Ion"

@q query
  where match
    relation "leave"
    role subject "Maria"
    role source "Acme"
    polarity affirmed
  end
  during "March 2024"

The time is copied as written ("March 2024"), never converted by the model; the host normalizes it.

6. Vague messages and several readings

When a word, a pronoun or a scope has several readings and one is preferable, the model formalizes that reading and records the choice as an assumed with basis disambiguation (relation "refer to" for a pronoun, relation "mean" for a word sense; the values are the message's words), so the reader of the packet can see it. When none is preferable, the only output is unclear kind ambiguous with two to four reading lines, and the host asks the user to choose. A phrasing that is ambiguous in a way the model may resolve (for example "what for", which reads as "why" or as "for what") is formalized with one plausible reading; evaluation accepts every plausible reading (a row's sop_target plus its sop_targets_accepted), so no reading is dropped and the model never refuses.

EN “Ana manages Irina. Does she live in Cluj?”

@s1 stated
  relation "manage"
  role subject "Ana"
  role object "Irina"
  polarity affirmed
  certainty asserted

@a1 assumed
  relation "refer to"
  role subject "she"
  role object "Ana"
  polarity affirmed
  basis disambiguation

@q query
  where match
    relation "live in"
    role subject "Ana"
    role location "Cluj"
    polarity affirmed
  end

The query keeps the user's verb as its lemma ("made" → "make") and the title as written; the assumption states the chosen sense ("make" as "write"). The host still links the verb and asks when its lexicon finds it ambiguous.

EN “Is the court free on Saturday?”

@u unclear
  kind ambiguous
  reading "the tennis court is free on Saturday"
  reading "the law court has no hearing on Saturday"

Words, not operators

The model writes words, never symbols or parentheses (owner decisions Q-LANG-1 to Q-LANG-7, DS014 "Words, not operators"). It does not compute, compare or choose: it writes the literal approximation, and the host computes what it can or answers not_computable.

EN “Which of the Elm Street residents are over 80, not counting Walter?”

@q query
  select ?who
  compare ?age above 80
  except ?who "Walter"
  where all
    match
      relation "live on"
      role subject ?who
      role location "Elm Street"
      polarity affirmed
    end
    match
      relation "be aged"
      role subject ?who
      role object ?age
      polarity affirmed
    end
  end

EN “Did most of the neighbors sign the petition?”

@q query
  mode every
  quantifier most
  where match
    relation "be a neighbor of"
    role subject ?n
    role object "the user"
    polarity affirmed
  end
  scope match
    relation "sign"
    role subject ?n
    role object "the petition"
    polarity affirmed
  end

A question about the order of two events compares their times with order; a question limited by a dated clause ("who worked there before Maria arrived on 1 March?") uses a before link instead.

EN “and Priya?”

@q query
  fragment follow_up
  where match
    role subject "Priya"
  end

EN “Is the away match in Voluntari or in Otopeni?”

@q query
  where match
    relation "take place in"
    role subject "the away match"
    role location "Voluntari"
    polarity affirmed
  end

@q2 query
  where match
    relation "take place in"
    role subject "the away match"
    role location "Otopeni"
    polarity affirmed
  end

The first person is "the user"; the modal stays in the relation; "X or Y?" is one yes/no question per option; an advice question ("Should I negotiate?", relation "should negotiate") is formalized literally and answered not_computable.

7. One clause, one wire

Every finite clause of the message is one short wire; a whole clause is never packed into a string. A subordinate or result clause is related to its main clause by one keyword line on the main wire, KEYWORD $id, where $id is the wire of the clause the conjunction introduces. The keywords are English in every language; at most three link lines per wire, never inside a match block (syntax and host effects).

KeywordEnglish conjunctionsThe linked clauseWhat the host does

soso, therefore — written on the result clause, pointing at its causestated or assumedreports it
ififstated, certainty supposedon a query: the supposition applies to that query only; on a statement: the statement is conditional, reported only
unlessunlessstated, certainty supposed, written affirmedas if, negated by the host
althoughalthough, even thoughstated or assumedreports it
so_thatso that, in order tostated, certainty supposedreports it

afterafterstated or assumedon a query, with a dated clause: the period starts at that time
whenwhenstated or assumedon a query, with a dated clause: the period is that time
whilewhilestated or assumedas when

"I ask because …" explains the user's asking: it is a remark, not a link. A clause used as an argument ("is that fair", "Ana regrets that …") is a role value $s; a question about the answers of an earlier question is a role value $q. At most one $id role value per wire.

EN “Maria joined the Delta Project, so she works at Alpha Lab now.”

@s1 stated
  relation "be a member of project"
  role subject "Maria"
  role object "Delta Project"
  polarity affirmed
  certainty asserted

@s2 stated
  relation "work at"
  role subject "Maria"
  role object "Alpha Lab"
  polarity affirmed
  certainty asserted
  so $s1

so is the one keyword on the result side: the effect s2 points at its cause.

EN “If Maria works at Alpha Lab, is she on the Delta Project?”

@s1 stated
  relation "work at"
  role subject "Maria"
  role object "Alpha Lab"
  polarity affirmed
  certainty supposed

@q query
  where match
    relation "be a member of project"
    role subject "Maria"
    role object "Delta Project"
    polarity affirmed
  end
  if $s1

The condition is a supposition, and the question names it: the host uses it for this question only.

EN “Unless Maria left Alpha Lab, who works there?”

@s1 stated
  relation "leave"
  role subject "Maria"
  role source "Alpha Lab"
  polarity affirmed
  certainty supposed

@q query
  select ?who
  where match
    relation "work at"
    role subject ?who
    role object "Alpha Lab"
    polarity affirmed
  end
  unless $s1

The clause is written as the message words it ("Maria left", affirmed); unless tells the host to suppose its negation.

A purpose is not asserted to happen: s2 is supposed.

The clause is dated, so the host looks for answers from 1 March 2026 on (effect: "from"). The date is copied as written.

EN “Who is on the Delta Project, and where do they work?”

@q query
  select ?p
  where match
    relation "be a member of project"
    role subject ?p
    role object "Delta Project"
    polarity affirmed
  end

@q2 query
  select ?c
  where match
    relation "work at"
    role subject $q
    role object ?c
    polarity affirmed
  end

The second question is about the answers of the first: role subject $q. The first query selects exactly one variable.

The complement clause is its own wire and the argument of "regreta". The host reports the statement; it computes nothing over a proposition used as an argument.

"Because of" a thing and "because" as a question

"Because of" followed by a thing or a person is a role of the relation, not a link: role topic for "because of" / "din cauza", role source for "from" / "de la". A proposed reason that the user asks about is itself the question; the model does not decide whether it explains the observation.

EN “Aurelia resigned. She quit because of Shirin, right?”

@s1 stated
  relation "resign"
  role subject "Aurelia"
  polarity affirmed
  certainty asserted

@q query
  where match
    relation "quit because of"
    role subject "Aurelia"
    role topic "Shirin"
    polarity affirmed
  end

EN “Jack stays home. Is that because he went to the book fair?”

@s1 stated
  relation "stay home"
  role subject "Jack"
  polarity affirmed
  certainty asserted

@q query
  where match
    relation "go to"
    role subject "Jack"
    role destination "the book fair"
    polarity affirmed
  end

The host checks the asked proposition and, with mode explain questions, reports the derivation it found.

8. Say what you could not formalize

When the model cannot write a part of the message — jargon, an idiom, a garbled fragment, a reference to something said earlier ("he", "that one") — it formalizes the rest and copies that part verbatim into an unparsed wire: span "…", optionally near $id (the wire it belongs to) and hint (subject, object, time, location, value, relation, reference, other). The role it would fill holds a fresh placeholder ?variable, also in stated and assumed. The model never invents a value or a name; the host repairs what it can (dates, numbers, conversation references, names, English synonyms) and asks one question per span it cannot.

EN “Maria works at the new place near the station.”

@s1 stated
  relation "work at"
  role subject "Maria"
  role object ?place
  polarity affirmed
  certainty asserted

@u1 unparsed
  span "the new place near the station"
  near $s1
  hint object

The span pairs with the placeholder of the statement (near $s1, hint object). The host first tries to repair it (a name, a date, a conversation reference); otherwise it asks one question: Who or what do you mean by "the new place near the station"?

9. What the query author never writes

  • Unlisted memory identities. Names stay as written or use listed entity ids. Predicates use retrieved vocabulary or declarations validated in this output; a definition cannot replace a memory declaration.
  • Unlabelled knowledge. No asserted fact, date or identity inferred from a clock or from the model's knowledge. Added propositions are labelled assumed, stay conditional and cannot become repository writes.
  • Answer formulation. The message may be in any language; circuit keywords and normalized relation words are English. The author writes circuits, never a translated or reasoned answer.
  • Reasoning or answers. No conclusion, no status, no advice and no silently substituted circuit. Optional predicate, rule and default definitions are validated as a turn-local layer, not executable policy.
  • Plumbing. No fact, remember, resolve, solve, cnl, clarify, jsEval or runtime-only fields such as span on a query.
@p premise
  holds works_at maria acme

An atom of identifiers is not the model language. Write stated with strings.

@s1 stated
  relation "work at"
  role subject maria
  role object "Acme"
  polarity affirmed
  certainty asserted

A bare identifier; the value must be the mention in quotes.

@q query
  where works_at ?who acme
  select ?who

An atom condition belongs to trusted circuits; the model writes a match block.

@f fact
  holds works_at maria acme
  valid timeless
  source user

The model never writes facts; an asserted stated is turn-local evidence.

EN “If Maria works at Alpha Lab, who works there?”

@s1 stated
  relation "work at"
  role subject "Maria"
  role object "Alpha Lab"
  polarity affirmed
  certainty supposed

@q query
  select ?who
  where match
    relation "work at"
    role subject ?who
    role object "Alpha Lab"
    polarity affirmed
    if $s1
  end

A link line belongs to the wire, after the end of the match block.

$q stands for one answer value; the first query selects two. Here the second question is about the places (?c): write that variable's condition into the second query instead.

A placeholder without its unparsed span: add @u1 unparsed with span "ceva gen «blorf»", near $s1 and hint object.

One more rejection happens after parsing, in the agent guard: a stated value that does not occur in the message is rejected with stated_value_not_in_message, and an unparsed span that is not a verbatim part of the message with unparsed_span_not_in_message.
