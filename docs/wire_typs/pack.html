pack

pack groups already constructed values or approved declaration handles into an array. A trusted SOP circuit uses it when an operation needs several facts, assumption facts or events, for example solve data or remember inputs. Grouping does not establish truth, install a rule, or publish a claim. This is system/tool collection plumbing, not a model-authored declaration.

Complete field grammar

Field / multiplicityAccepted values and semantics
items — one or more lines, requiredEach line is split into whitespace-separated tokens by words() (quoted substrings count as one token but are not accepted as inputs). Each token must be $id referring to a produced value or ~id referring to a declared definition. $id follows value dependencies, so a future port can be consumed when materialized; ~id is a handle, not a value dependency. Only ~rule, supported research declarations and template/procedure handles can be read by the current readObject; despite the declarative appearance of fact, ~fact is not handled here: use $fact. ~solve and arbitrary literals also fail at runtime. Multiple items lines retain source order; nested arrays from pack values are recursively flattened. No count, type, or homogeneity check occurs in pack itself; its consumer checks acceptable item kinds.

Consumer contracts

Runtime returns a flat array. solve.data on the relational path requires only fact/rule items in its linker; numeric solve.constraint does not accept data. remember.input accepts facts, events, or approved library definitions with host permission. solve.assume accepts fact items (typically source assumption) and marks them conditional. A pack that combines kinds can be valid at construction and rejected by a later consumer; do not treat pack as a typed proof or a mutable ~ accumulator. Even when the same data also feeds a solve, session recording requires a separate authorized remember operation.

Current syntax examples

Two facts of the same relation can feed one local query. The expected binding collection contains shelf_a and shelf_b, subject to normal completeness checks:

@book_one fact
  holds located book_a shelf_a
  valid timeless

@book_two fact
  holds located book_b shelf_b
  valid timeless

@catalog pack
  items $book_one $book_two

@question query
  where located ?book ?shelf
  select ?shelf
  mode select

@answer solve
  query $question
  data $catalog
  output ?shelf many

A second application groups facts for an authorized session write, rather than using them as local solve data. The remember operation requires a session and write permission:

@north fact
  holds accessible entrance_north
  valid timeless

@south fact
  holds accessible entrance_south
  valid timeless

@entries pack
  items $north
  items $south

@store remember
  input $entries
  scope session

The following parses because items is initially an untyped string. It fails at runtime with Expected approved declarative definition ~need_detail: ~need_detail names a clarify operation, not a supported declaration handle.

@need_detail clarify
  text "Which item?"

@bad pack
  items ~need_detail
