All wire types

plan

Planning searches deterministic symbolic state transitions for a state satisfying an explicit goal. Plans describe hypothetical steps, not executable physical commands. Trusted system/tool circuits may request planning with approved actions. Model-authored declarative input cannot invoke planning or define actions directly.

SOP syntax: @id type, exactly two leading spaces on each field line, $id for a computed value, ~id for a declaration handle, and ?x for a local logic variable or an output name. Atoms use [not ]predicate term1 [term2 [term3 [term4]]] with one to four whitespace-separated terms; lowercase predicate names, canonical symbols, JSON-quoted strings or safe integers. Parenthesized predicate(arg, …) and comma-separated arguments are not executable syntax.

Fields and inputs

KeywordCardinalityAccepted value, default and effect
dataAt most once; optionalOne $value, ~declaration or packed $array. Facts/rules form the initial model; actions inside data are used only when actions is absent or empty. Constraint objects cannot be silently dropped.
memoryAt most once; optionalOne optional $link retrieval result. Without it and with repository/session, the runtime links facts/rules against goal atoms plus action preconditions; otherwise it uses local data.
actionsAt most once; optionalOne $action, ~action or packed $array of action declarations. If nonempty, these actions replace action objects from data. Default empty (then data actions are used).
goalAt most once; requiredExactly one $goal or ~goal yielding a goal declaration. Required by parser and runtime. Goal atoms must be expressible by current whitespace-separated atom syntax.
reasoningAt most once; optionalA strategy name (plain token), default host policy.reasoningStrategy (reference by default). Built-ins: reference (the js-reference oracle; js-reference and js-oracle are the same route) and the deprecated advanced (the oracle plus optional external backends for deduction and numeric constraints). The host may restrict allowed strategies.
policyAt most once; optionalOne $policy value or ~policy declaration handle. It must lower to a policy object; each specified positive integer budget caps the corresponding host budget by min(host, wire). No policy reference means host limits alone.
outputRepeatable; optionalRepeatable ?name [one|many|rows|count|status] declaration, default one. Each output becomes a deferred $name value if bound; names must be unique and cannot collide with explicit wires. status binds result status even for incomplete results. Other modes require completeness; unusable/unselected modes become blocked, not arbitrary first answers.
afterRepeatable; optionalRepeatable $wire value-dependency reference. Orders execution after that producer; it does not alter inputs, proofs or output. A ~definition handle is graph-checked but is not a value-ordering dependency.

At run time a retrieval query is constructed from goal atoms and available action preconditions, at the current time. A returned memory view is filtered by this query; explicit memory must already be a retrieval. Rules are approved definitions; a model can reference approved ~action and ~rule, but cannot define them in model-authored declarative code.

Result and limits

The result is the oracle's packet: status plan_found with plan ({steps: count, cost, names, sequence: [{action, args, binding, adds, removes, cost}]}, the cheapest plan), used (the actions of the plan), no_plan (the whole finite state space was explored) or budget_exhausted (reason horizon or nodes; never no_plan); guarantee exact, or bounded when the horizon cut some branch. A plan is never executed. Output one/many/rows projects plan as one record, count unsupported, status projects status.

All operations use bounded search (host defaults include maxNodes 5000, maxDepth 8, maxCandidates 512, timeoutMs 3000); a ~policy can only tighten configured limits. The result records completeness and epistemic status relative to supplied finite inputs and the visible memory view, never calibrated truth probability. No operation here writes to the repository; after is only scheduling. The search is uniform cost over polarity-explicit states (an open fluent that is removed becomes negative evidence, a closed fluent's is absent), re-closes the rules in every state, leaves out the actions that are not valid at the instant asked (reported in ignored) and obeys maxDepth as the horizon. no_plan requires the whole bounded search and is relative to the supplied model. One plan is returned: the cheapest.

Executable examples

Move a robot to a dock

@start fact
  holds located_in robot7 bay
  valid timeless
@road fact
  holds connected bay dock
  valid timeless
@facts pack
  items $start $road
@move action
  params ?robot ?from ?to
  requires located_in ?robot ?from
  requires connected ?from ?to
  removes located_in ?robot ?from
  adds located_in ?robot ?to
@destination goal
  where located_in robot7 dock
@route plan
  data $facts
  actions ~move
  goal ~destination

Run as trusted code or use a reviewed ~move action. The planner can return a symbolic move step and does not command the robot.

Goal already reached

@charged fact
  holds charged robot7
  valid timeless
@ready goal
  where charged robot7
@route plan
  data $charged
  goal ~ready

The initial state itself satisfies the goal; a valid plan may contain zero steps.

Valid, but not a proof of impossibility

@ready goal
  where available robot7
@move action
  requires located_in ?robot bay
  adds available ?robot
@stuck plan
  goal ~ready
  actions ~move

This runs and reports no_plan, but without a matching initial located_in fact the action is not applicable. Do not present a missing plan as proof that a physical route is impossible.

Invalid: goal is not a goal declaration

@move action
  requires located_in ?robot bay
  adds available ?robot
@bad plan
  goal ~move
  actions ~move

The parser accepts the handle, but the runtime rejects it with Plan needs goal: goal must name a goal declaration, not an action.
