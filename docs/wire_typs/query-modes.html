Query modes

The eleven question forms of the knowledge language. Five are older (select exists count explain every); six are reasoning modes (why_not plan abduce conform procedure effect), all declarative question forms, never operations. The small model may write them as the mode of a query (DS014); the host supplies via, trace and policy.

The modes

ModeAsksAnswer
mode selectwhich bindings of select satisfy whererows, each with its own conditional list
mode existsdoes where holdsupported, refuted, both or unknown
mode counthow many distinct bindingscount; a lower bound (bound at_least) over an open relation
mode everydoes scope hold for every member of the where restrictionsupported, refuted with a counterexample, or unknown over an open domain
mode explainwhy does the claim holdthe status plus the derivation (the rules and facts used)
mode why_notwhat would make the claim derivable, or what blocks itthe minimal sets of base atoms to add plus the blocking atoms; on a planning goal, blocked with blocked_by
mode planhow is the goal reachedplan_found with the plan, its used versions, compliance and choices; or blocked, no_plan, budget_exhausted
mode abducewhat could explain the observationall inclusion-minimal explanations (atoms, or waive $norm); limit bounds the list
mode conformdoes a performed trace comply with the procedures and norms in forcecompliant or non_compliant with violations, deviations and total cost
mode procedurewhat is the approved procedure for the taskthe method as written, its version, the norms in force (no planning)
mode effectwhat does each candidate (candidate $id: a supposed fact or a rule not in force) do to a ground claimthe claim's status without the candidates plus effects: per candidate establishes, blocks, contradicts, no_effect or inconsistent

Rules of the fields

The validator checks the mode against the fields: mode every needs scope and no other mode takes one; mode conform needs trace (and needs no where) and no other mode takes trace; via is only for plan, why_not and abduce; at most one of at, during, overlaps; every selected variable occurs in where; order random (a random sample with limit, see query) is only for select (order_random_mode); candidate lines (1 to 8, candidate_limit) only for effect and abduce (candidate_needs_mode), each naming a fact with status supposed or a rule/default (candidate_target) that is not also supposed with if (candidate_also_if); mode effect needs a ground claim and a candidate (effect_needs_ground_claim). A query belongs in a query circuit, never in a knowledge circuit.

why_not, plan, abduce, conform, procedure in detail

  • why_not is abduction over a restricted hypothesis space, not an unsat core: if the claim does not hold, its theory plus the negated claim is satisfiable and an unsat core explains only entailed claims. It returns the base atoms, in the vocabulary of the slice and respecting the predicate types, whose addition would make the claim derivable. With via ~hard_reset r7 on a goal it answers blocked when a plan would exist if the named norms or unmet requirements were waived, and no_plan when none exists even then.
  • plan returns the cheapest legal execution that satisfies the norms in force; with via the plan must contain the given steps. The packet carries plan, used: [{id, version}], compliance: {hard, soft_violations, total_cost} and choices for what the engine optimised.
  • abduce over atom hypotheses returns every inclusion-minimal consistent set of hypothesis wires that makes the observation hold: a set whose consequences contradict an admitted fact (it would derive tool_marks yard against the fact not tool_marks yard) is no explanation and is listed under inconsistent with the literals it contradicts; when every explaining set is inconsistent the answer is unknown with reason no_consistent_explanation. An observation that already holds is explained by the empty set. With waive hypotheses it returns the minimal sets of norms whose relaxation unblocks a plan.
  • conform judges a trace against the versions in force at the time of each step (at on a step, asof for the others); leaving a strict method is non-compliance and is listed in deviations, under binding advisory it is only reported.
  • procedure renders the approved method as of asof.

These modes need strategies that declare plan, method, norms_hard, abduce_waive, check_plan and the like; the oracle js-reference expresses abduce over atoms, why_not over base atoms and plan over actions, and declares the norm and method features not_expressible. A question no strategy declares is understood and answered not_computable, never answered as a plain select.

In the chat (DS006 "Routing rules", R1): a model query in mode explain, why_not or abduce is answered by the oracle. explain names the rules it used with their text (the packet field rules_used), why_not names the missing facts ("It would follow if …") and the blockers, and abduce names the consistent explanations among the memory's hypothesis wires, or among the question's own candidates, and the rejected ones (the model writes no hypotheses; the stated observation itself is not a premise); effect says what the claim is without the options and what each option does to it (candidates). plan, conform and procedure need actions, traces or procedures the model does not write and are answered not_computable. An explicitly requested engine that does not express a mode answers not_expressible.

Consistent abduction: a closed incident note

The gate was found open, the padlock lies closed, and there are no tool marks. Forced entry would open the gate and leave tool marks; a key would open it without marks.

@gate_open predicate
  args subject:entity
@padlock_closed predicate
  args subject:entity
@tool_marks predicate
  args subject:entity
@forced_entry predicate
  args subject:entity
@key_entry predicate
  args subject:entity
@f1 fact
  holds padlock_closed yard
@f2 fact
  holds not tool_marks yard
@r_forced_open rule
  when forced_entry ?s
  then gate_open ?s
@r_forced_marks rule
  when forced_entry ?s
  then tool_marks ?s
@r_key_open rule
  when key_entry ?s
  then gate_open ?s
@h_forced hypothesis
  holds forced_entry yard
@h_key hypothesis
  holds key_entry yard
@q query
  mode abduce
  where gate_open yard

The answer is hypotheses with the one explanation [h_key]; h_forced is listed under inconsistent with contradicts [not tool_marks yard]. The chat renders it as "A possible explanation: … key entry …" and "Rejected: … forced entry …, because it would contradict what is known (…)".

@q query
  mode why_not
  where gate_open yard

The gate's opening is not derivable from the facts alone: the answer is unknown with missing naming the base facts whose addition would derive it (forced_entry yard or key_entry yard).

Candidates: mode effect and abduce over candidates (Q-LANG-10)

A candidate $id line names a supposed fact of the query circuit or a rule or default of the knowledge (any approval; the chat hands a session rule named by candidate or if to the engines as approval proposed). It is in force only in the runs of this query. mode effect answers the claim without the candidates and then with each one; mode abduce with candidates looks for the minimal consistent sets of candidates that make the claim derivable and reports necessary, the candidates every set needs. Every run is hypothetical and never stored; strict knowledge beats defaults; a candidate contradicted by what is known is inconsistent. Only the oracle runs candidates: every other engine answers not_expressible. The examples below are invented SOP programs for three items of the logic book (proposal P-1), never its text.

Affirming the consequent (logic book item 171). The card says: if it rained at the market, the pavement there is wet. The pavement is wet. Sam concludes that it rained. The converse of the card's rule is a candidate the card does not contain.

@rained predicate
  args subject:entity
@pavement_wet predicate
  args subject:entity
@f1 fact
  holds pavement_wet market
@r_card rule
  when rained ?m
  then pavement_wet ?m
@r_converse rule
  when pavement_wet ?m
  then rained ?m
  approval proposed
@q_sam query
  mode effect
  where rained market
  candidate $r_converse

The claim does not follow from the card (unknown: it is not forced); with the converse it would (establishes). The chat says "Without any of the options, it does not follow from what is known." and "With the rule "r_converse" (if …, then …), it would follow.": Sam is right only with a rule the card does not state. The same rule supposed for one question only:

@q_if query
  mode exists
  where rained market
  if $r_converse

A rule that does not apply (logic book item 91). Rule One: an apprentice at the grinder wears the face shield. Sam is an apprentice at the grinder. Tess claims Sam may skip the shield because the depot is dark.

@apprentice predicate
  args subject:entity
@at_grinder predicate
  args subject:entity
@dark predicate
  args subject:entity
@wears_shield predicate
  args subject:entity
@f1 fact
  holds apprentice sam
@f2 fact
  holds at_grinder sam
@r_one rule
  when apprentice ?x
  when at_grinder ?x
  then wears_shield ?x

The darkness of the depot has no effect on Rule One: Sam still wears the shield.

Every class over a default. Birds fly unless injured. An injury blocks the default; a strict rule "birds do not fly" contradicts the claim; a supposed "Tweety is not a bird" is contradicted by the facts.

@bird predicate
  args subject:entity
@flies predicate
  args subject:entity
@injured predicate
  args subject:entity
@f1 fact
  holds bird tweety
@d_flies default
  when bird ?x
  then flies ?x
  except injured ?x
@r_never rule
  when bird ?x
  then not flies ?x
  approval proposed
@s_injured fact
  holds injured tweety
  status supposed

@s_not_bird fact
  holds not bird tweety
  status supposed

@s_pet fact
  holds injured polly
  status supposed

@q query
  mode effect
  where flies tweety
  candidate $s_injured
  candidate $r_never
  candidate $s_not_bird
  candidate $s_pet

Affirming the consequent, from FOL. The card's rule, the observation, and two options: Sam's converse rule and Tess's truck.

FORALLx (Rained(x) IMPLIES Wet(x))

The converter writes this circuit (each predicate carries its name in words as label en, so an answer reads "wet", not "f wet"):

@f_wet predicate
  args subject:entity
  label en "wet"
  closed true

@f_rained predicate
  args subject:entity
  label en "rained"
  closed true

@f_truck predicate
  args subject:entity
  label en "truck"
  closed true

@fs1 stated
  certainty asserted
  relation "f_wet"
  role subject "market"
  polarity affirmed

@fr1 rule
  when f_rained ?x
  then f_wet ?x

@opt_sam rule
  when f_wet ?x
  then f_rained ?x

@opt_tess stated
  certainty supposed
  relation "f_truck"
  role subject "market"
  polarity affirmed

@q query
  mode effect
  candidate $opt_sam
  candidate $opt_tess
  where match
    relation "f_rained"
    role subject "market"
    polarity affirmed
  end

Answer: the claim does not follow (status refuted without the options, a closed predicate); opt_sam establishes it, opt_tess has no_effect: "Without any of the options, what is known says it is false. With the rule "opt_sam" (if … wet …, then … rained …), it would follow." These circuits, and the other forms of the table, are executed through a chat turn by tests/routed/fol-v3.test.mjs.
