resolve

Authoring boundary: This is a real host lexicon lookup in an inspectable execution circuit. The small model cannot author resolve or decide which ambiguous identity to use; the symbolic host can supply a reviewed canonical ID or generate a clarification when necessary.

resolve searches a host-reviewed lexicon for an exact or accent-folded surface form. It helps a formalizer avoid guessing the identity of an entity; it does not create an entity, infer a new synonym, or turn an ambiguous mention into a fact. The host must supply a lexicon; the source program alone cannot define a trusted vocabulary.

All supported fields

Field / multiplicityGrammar and matching
text — exactly one, requiredNonempty text, plain or JSON double-quoted. This whole-line field accepts both text Maria Ionescu and text "Maria Ionescu"; canonical generated/training output always uses the double-quoted form, even for a single-word name. It is decoded by unquote, bounded to 1,600 UTF-8 bytes at lookup, and searched as a whole surface form, not as free-text inference. $other inside text is literal text: text does not create a value dependency. Normalization uses NFC, Romanian lowercase, cedilla replacements, collapsed whitespace; exact normalized matches are preferred, otherwise accent-folded matches.
language — exactly one, requiredTwo or three lowercase ASCII letters, e.g. en or ro. Lookup uses entries labeled in this language plus identifier aliases marked und. auto is a candidate-search feature, not an accepted resolve language.
kind — exactly one, requiredOne of entity (classes are entities of kind class) or predicate. Filters the lexicon entry kind before deciding whether the match is unique. A resolved predicate ID is not a dynamic predicate name inside atom syntax.
type — zero or oneNonempty text, only allowed for kind entity. Exact entity-type filter, such as organization, as declared in the entity kind of the session's base memory; no subtype inference. If supplied with predicate, parsing rejects the field combination.
domain — zero or oneNonempty text matching the lexicon entry's domain exactly. Narrows candidates; it does not define a domain or change a predicate's argument types.

Results and dependency behavior

The lexicon computes a version digest and records provenance with each resolution. Exactly one filtered match produces bound with canonical id, match method, type/domain and lexicon version. No match gives unknown; multiple give ambiguous with sorted candidates. Runtime records these statuses in outputs/trace. Only bound creates a usable $id value; a dependent wire is marked blocked if resolution is unknown or ambiguous, not silently assigned the first candidate. The checkResolvedTerms guard accepts a resolved value inside an atom only when its source is an entity, bound and compatible with the schema's argument position (not an integer/value position). Directly supply canonical predicate spellings in authored atoms; consider clarify if an identity remains ambiguous.

Current syntax examples

Keep a person’s spelling intact: Maria Ionescu is a surface mention, while maria_ionescu would be a separate canonical entity ID chosen by the reviewed base memory. Quotation marks delimit text; they do not resolve identity. text "?person" and text "$person" are inert text in this field, not variables or references. Encode embedded double quotes and backslashes with a JSON string encoder; single and smart quotes are not delimiters. See quoted text syntax.

Both examples require a host lexicon with the indicated reviewed entries; without it, resolve raises resolve requires a host-reviewed lexicon. First, assume room_a is a reviewed entity labeled “Room A” in English, with type room, and a schema allows occupied room:

@place resolve
  text "Room A"
  language en
  kind entity
  type room

@observation fact
  holds occupied $place
  valid timeless
  source "operator note"

A unique approved match supplies room_a as an atom argument; this declaration alone does not write memory. Second, assume an approved entity lab_alpha has alias “Alpha Lab” in domain work:

@employer resolve
  text "Alpha Lab"
  language en
  kind entity
  type organization
  domain work

@question query
  where works_at ana $employer
  mode exists

This produces a query value only if the entity is bound; a separate solve and admitted evidence would be required for an answer. Likewise, if a reviewed maria_ionescu entity has the exact English label “Maria Ionescu”, use the approved lookup before using her identity as an atom argument:

@person resolve
  text "Maria Ionescu"
  language en
  kind entity
  type person

@employment query
  where works_at $person lab_alpha
  mode exists

The canonical emitted lookup is quoted; the bare text Maria Ionescu is also accepted in this whole-line field. By contrast, where works_at "Maria Ionescu" lab_alpha is a quoted atom string, not a lookup of maria_ionescu; it must not be silently converted into an approved entity ID.

The following parses but fails at resolution/atom consumption: selecting a predicate entry cannot supply an entity argument.

@relation resolve
  text "works at"
  language en
  kind predicate

@bad query
  where works_at ana $relation
  mode exists
