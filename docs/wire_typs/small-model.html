Small-model language

The query author writes proposition circuits (stated suppositions, assumed, unclear, query, constraint, unparsed) and optional turn-local predicate, rule and default session definitions. Every circuit has origin coding_agent. It never writes an assertion, a raw fact, a backend choice, policy or an answer. The normative contract is DS014.

Who writes this language today. Since 2026-10-01 only the formalizer (step by step since 2026-10-02: the system asks short questions and assembles the circuit; the one-shot LLMDirect is archived) writes it, and the validator admits only what the circuit surface allows. The small-model formalizers (SymbolicLM and the fine-tuned models this page was first written for) are frozen in probably_obsolete/tinyLLMExperiments/.

The author sees the message and the memory vocabulary only. Its context is the user's message and the retrieved vocabulary of the session's memory (predicates by id with their roles, and hints for names): never answers, gold, sealed tests, other sessions or a clock. It writes strings for names: a quoted relation phrase, roles from a closed inventory (subject, object, recipient, location, source, destination, instrument, time, topic) with names as written in the message, ?variables in questions, and temporal expressions as written. Content words (relation phrases, common nouns) are English, normalized to a lemma ("work at", "the gym"); the core is English-only, so the formalizer reads a message in any language and writes English content words, and the keywords are English. One clause of the message is one wire, related to its main clause by a link keyword (because $s2, if $s1, before $s1, …); a role value may name another wire ($s, $q). The host retries an English synonym from its dictionary (config/dictionary/) when a phrase does not link. After the model, the host links the strings to its reviewed lexicon (relation phrase and role set to a predicate, values to entities, temporal expressions to intervals), compiles an inspectable execution circuit and asks the user with a host clarify when something is unknown or ambiguous.

Start with How the model writes (the model's point of view, with executed examples, typos and the stated/assumed boundary) and Question types (one formalization per question type).

Session circuits and answer-shape self-check

Prefer existing vocabulary, then a definition over existing predicates, then a short clarification for equally plausible meanings, and only then a labelled assumption. The knowledge validator checks definitions against the memory: declarations cannot replace memory ids, and every predicate reference must already exist or be declared in this output. Fresh definitions are used in this turn and, once valid, are stored in the session layer at once for later turns; an invalid definition is refused. A base memory is never changed by a chat turn.

For a memory whose works_at relation is already declared, coworkers can be defined by a shared employer. The complete declaration example below includes that memory vocabulary solely so the wire-help validator can execute it:

@works_at predicate
  args subject:entity object:entity
@coworker predicate
  args subject:entity object:entity
@coworker_at_work rule
  when works_at ?a ?organization
  when works_at ?b ?organization
  then coworker ?a ?b

The author then queries relation "coworker" with the declared roles. Used evidence is labelled memory, definition by the formalizer or assumption by the formalizer; contrary memory evidence defeats an assumption and reports session_conflicts. After execution one extra circuit-only author round sees status, cardinality and a deterministic circuit reading, never the answer values. It may revise once; the same validator checks the revision. Dropped names, quantifiers and comparisons are errors, not advice.

No refusal and no plumbing. The model always formalizes a readable request; an understood question without an engine gets the host answer "I understood the question as …; I cannot compute this kind of answer yet". It cannot declare clarify, fact, remember, pack, resolve, solve, cnl, value, jsEval or expand. These remain available in trusted general-runtime circuits.

Clarification is host-generated: when an unparsed span cannot be repaired, or a relation phrase, an entity string or a temporal expression cannot be linked uniquely, or a downstream required scalar is absent/nonunique, symbolic orchestration suspends dependent work and produces an inspectable clarify request. Lack of evidence for an otherwise well-formed question is a reasoning result, not a request for more input.

A supposition and a question

User: “Suppose Maria works at Alpha Lab. Would Maria work at Alpha Lab?” The model states the supposition and the question as strings. No generated answer or session write is embedded here:

@context stated
  relation "works at"
  role subject "Maria"
  role object "Alpha Lab"
  polarity affirmed
  certainty supposed

@question query
  where match
    relation "work at"
    role subject "Maria"
    role object "Alpha Lab"
    polarity affirmed
  end
  mode exists

The host links both phrases to works_at, resolves the names, and compiles a solve with the supposition as a temporary assumption: the result is conditional on it, and no observed fact is recorded. An asserted statement would instead be turn-local user evidence and the answer would not be hypothetical.

Canonical literals: every value is a JSON double-quoted string (or an integer); quotes keep spaces, commas, parentheses and escapes inside one value. Keep ?variable and keywords unquoted. See quoted text.

What stays outside the small model

jsEval, expressions in value and JavaScript generation are excluded; the model-surface admission rejects them. Models may author reviewed programs; invoking an approved abstraction through a bounded interface is distinct from writing its implementation. An approved host metaprogram may use expand to generate an inspectable circuit; that does not give the model authority to write its implementation.

Runtime bindings, linking, retrieval implementation choices, executable definition installation, and policy budgets belong to the host/system. Declarative AND/OR groups, comparisons, numeric requirements, and optimization objectives do not belong to this exclusion: they express the user's problem.
