solve

solve evaluates a query against selected evidence or a constraint against numeric requirements. The model's question is not its answer: the reasoning strategy produces a checked result, and optional output ports project values only when justified. A host-approved metaprogram generates this operation from a model-authored declarative request; the small model cannot author solve directly. Trusted general-runtime circuits may still use it explicitly.

Solve using a local claim, without recording it

@catalog constructs an unverified supplied claim; @question requires on_shelf ?book shelf_north; data $catalog admits that claim only for this one evaluation. If it is the sole complete matching fact, $book is book_a. No session write occurs.

@catalog fact
  holds on_shelf book_a shelf_north
  valid timeless
  source "catalog card 17"

@question query
  where on_shelf ?book shelf_north
  select ?book
  mode select

@answer solve
  query $question
  data $catalog
  output ?book one

Explicit negative evidence and status

@negative fact
  holds not open door_a
  valid timeless

@question query
  where not open door_a
  mode exists

@check solve
  query $question
  data $negative
  output ?state status

This asks for explicit negative support, not absence of positive evidence. ?state is a status port, not a query-selected variable. Incomplete/conflicting answers remain statuses rather than invented values.

Invalid input kind

@question query
  where open door_a
  mode exists

@message clarify
  text "Please identify the door."

@bad solve
  query $question
  data $message

The parser accepts the fields, but the linker rejects a clarification message as fact/rule evidence. See binding for output semantics.
