template

Defines a reusable, reviewed SOP subcircuit. template and procedure use the same parameterized circuit expansion mechanism; their names label intended library use, not distinct execution languages or extra permissions. A host may approve a definition so an expand wire can apply it to supplied arguments; declaring it alone produces only a definition handle.

Status and author: Host-approved declaration; a model-origin program cannot install this definition.

Accepted fields

Single means at most once, repeatable means zero or more, and required means at least once at parse time. Other field names are rejected.

FieldCardinalityAccepted values and current behavior
paramsAt most once; optional; default emptyWhitespace-separated distinct parameter names, default empty; names become expansion inputs.
yieldExactly once; requiredWire ID or declared output name produced by the body; determines the value exposed by expansion.
bodyExactly once; required| with four-space-indented SOP source; reviewed definition body expanded by an explicit invocation, not executed upon declaration.
descriptionAt most once; optional; default emptyPlain or JSON-quoted descriptive text, default empty; documentation metadata only.
cueRepeatable; optional; default nonePlain or JSON-quoted cue per line; optional metadata for locating a reviewed definition, not an execution trigger.

Execution and result

Each with name value binds one declared parameter, once. A value beginning with $ resolves an existing wire value; other text is unquoted (a JSON-quoted string is decoded). Missing or duplicate parameters, unknown names, a bad body, ID collisions, or a yield outside body/output are errors. At expansion, the runtime creates namespaced parameter value wires and body wires, substitutes references, renames body output ports, then aliases the expansion result to its yield. Definition metadata does not turn this into arbitrary code execution.

~id is a definition handle, not a mutable accumulator. An approved library entry is loaded only with a repository/session, exact ID, permitted library type and matching checksum; a trusted host can also supply a definition in its source. A trusted system/tool circuit may refer to an approved definition. Model-authored declarative input cannot invoke or define one. Body effects follow normal runtime authorizations if it contains effectful wires; a template itself does not write to memory.

Current SOP examples

Local trusted definition and invocation

@calc template
  description "Add a reviewed offset to an input"
  cue "adjust score"
  params base offset
  yield total
  body |
    @total value
      data $base + $offset

@input value
  data 7

@offset value
  data 3

@use expand
  using ~calc
  with base $input
  with offset $offset

In a trusted host program the body adds 7 and 3; the expansion value is 10. Model-authored declarative input cannot declare or invoke @calc template.

Yielding an output port

@approved template
  params route
  yield who
  body |
    @q query
      select ?who
      where serves $route ?who
    @s solve
      query $q
      output ?who one

@route value
  data "route_a"

@call expand
  using ~approved
  with route $route

A host-approved template can yield a solve output port. The query needs an admitted serves fact and one complete answer; no answer/multiple answers blocks the yielded value.

Invalid or unsafe example

@bad template
  params number
  yield missing
  body |
    @present value
      data $number + 1

@one value
  data 1

@use expand
  using ~bad
  with number $one

The outer source parses, but expansion rejects yield missing because there is no such body wire or output port.
