test

One executable check of a program: a call expression, the expected value and a kind. Run by the code-sandbox strategy against the code wire of the same task.

Status and author: Host or turn wire (the user's examples, the examples a model writes, generated checks). It is never knowledge approved from a source, never on the small-model surface (the formalizer never writes or sees it) and never evidence: it is not a claim about the world, so it stays outside the four-valued evidence system. It is not governed.

Accepted fields

Single means at most once, repeatable means zero or more, and required means at least once. Other field names are rejected (unknown_field). The table is generated from the grammar in sop/knowledge/grammar.mjs.

FieldCardinalityAccepted values and behavior
ofAt most once; requiredThe task symbol (a lowercase symbol such as t1) the test is about. A code wire for the same task is what the test runs against.
callAt most once; requiredA JavaScript expression, JSON-quoted, that calls the entry function: "mostFrequent([1, 2, 2, 3])". It is evaluated in the program's own sandbox context.
expectAt most once; requiredA JavaScript expression, JSON-quoted, for the expected value. It is evaluated in a separate clean context, never in the one that holds the program. Values are compared structurally: arrays, plain objects (key order ignored), Maps, Sets, Dates, NaN, undefined versus null.
kindAt most once; optionalexample|property|generated|sealed. Metadata for reporting; every kind runs the same way. A test of kind sealed belongs to eval/suites/ only and is refused everywhere else (sealed_test_in_knowledge).
timeoutAt most once; optionalA positive integer: milliseconds for this test (the sandbox caps it at four times its per-test budget).
sourceAt most once; optionalQuoted citation: where the example comes from (the user's instruction, the agent's reading of it).

What it is for and how to write it

Write one test per example of an instruction, one per implied edge case (the empty input, a boundary) and, in the host loop, nothing else. call and expect are JSON strings that hold a JavaScript expression each. A test that cannot evaluate its expect expression is reported as a bad test, never as a pass.

Sealed tests. The hidden tests of an evaluation suite are written with kind sealed and live in eval/suites/** only. The validator refuses them in knowledge, task and candidate files (sealed_test_in_knowledge), the proposer and the repair loop never see them, and the evaluation harness runs them after the program has been committed, so that a verified program that fails one is counted as a false verification.

What the engine does

Nothing in a reasoning route: a test is opaque to every engine. The code-sandbox strategy runs the program of the task on each test (one fresh context per test, a CPU timeout per test, a heap limit and a wall-clock limit for the whole run) and answers verified (every test passed, guarantee bounded, never exact), failed (the failing tests with call, expected and actual value or error) or budget_exhausted (reason wall or memory). Its trace is a list of closed facts: run r1, in_elem r1 3, out_elem r1 2, test_result r1 e1 passed.

Examples

A program and two tests; the sandbox answers verified.

@sum_list code
  of t1
  language javascript
  entry sumList
  body "function sumList(xs) {\n  let s = 0;\n  for (const x of xs) s += x;\n  return s;\n}\n"
  produced_by user
@e1 test
  of t1
  call "sumList([1, 2, 3])"
  expect "6"
  kind example
  source "the user's example 1"
@e2 test
  of t1
  call "sumList([])"
  expect "0"
  kind example

The same tests on a wrong program: the sandbox answers failed and names e1.

@sum_list code
  of t1
  language javascript
  entry sumList
  body "function sumList(xs) {\n  let s = 0;\n  for (const x of xs) s = x;\n  return s;\n}\n"
  produced_by user
@e1 test
  of t1
  call "sumList([1, 2, 3])"
  expect "6"
  kind example
  source "the user's example 1"
@e2 test
  of t1
  call "sumList([])"
  expect "0"
  kind example

Invalid: a sealed test in a knowledge file

@e1 test
  of t1
  call "sumList([1, 2, 3])"
  expect "6"
  kind sealed

Common mistakes

  1. Putting a hidden test in a task, candidate or knowledge file: the validator refuses kind sealed outside eval/suites/.
  2. Writing call or expect as bare text instead of a JSON string.
  3. Reading a passing test as a proof: a verified program passed these tests only (guarantee bounded).
  4. Asserting an example of the world as a fact: a test checks a program, a fact states something about the world.
