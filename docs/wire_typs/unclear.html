Wire index · stated · assumed · clarify · model/host roles

unclear

The small model emits unclear only for what it can recognise from the text itself, without context and without reasoning: an unintelligible message, a message with neither a statement nor a question, or a visible ambiguity it prefers not to resolve (kind ambiguous with one reading line per candidate reading). It belongs to the model language and must be the only wire of the output: mixing it with any other wire is rejected (unclear_not_alone). The host runs no circuit; it renders a fixed controlled-language reply for the kind, in English (another answer language is the translation of that reply at the output edge), and the packet has status: unclear. A semantically odd but readable message is formalized normally: the model does not judge contradictions, completeness or relevance. The normative contract is DS014.

unclear is not clarify. clarify stays host-generated: the message was formalized, and the host could not link or resolve a specific relation, entity, date or scalar (for example two people named Maria). unclear is the model's report that there is nothing to formalize. It is also not a refusal: the model always formalizes a readable request.

Every accepted keyword

KeywordCardinality / defaultAccepted value and concrete effect
kindExactly once; requiredOne of gibberish, no_request, ambiguous or relation_not_in_memory (written only by the formalizer, which sees the memory's vocabulary); the table below gives their use and replies. The kinds and their replies live in one table (UNCLEAR_KINDS in sop/unclear.mjs) so they are easy to change.
readingRepeatable; 2 to 4 lines with kind ambiguous, none otherwiseOne JSON-quoted short paraphrase of one candidate reading, in English (reading "Ana used the telescope", reading "Ana lives in Cluj"); names stay as written. The host lists the readings, numbered, after the fixed reply and returns next: choose_reading. Fewer than two or more than four readings, a repeated reading, an empty or unquoted reading, or a reading on another kind is rejected (unclear_readings).
languageAt most once; optionalOnly en: the core renders English (owner decision of 2026-10-01). The field has no effect; the answer language is selected by the caller (API language field or an explicit request in the message) and applied by translating the English reply.

Kinds and host replies

KindUse whenEnglish reply
gibberish The text is unintelligible.I did not understand the message. Could you rephrase?
no_request No statement and no question: "ok", "thanks", a greeting, or a request for something unrelated such as "write a poem".I did not find a statement or a question in the message. What would you like to know?
ambiguous The text itself shows two or more readings and none is clearly preferable: a pronoun after two parallel clauses, a bare homonym ("Is the court free?"), the scope of "all … not", a prepositional-phrase attachment. When one reading is preferable the model resolves it instead, with an assumed wire (basis disambiguation); the scope of "all … not" is always ambiguous.Your message can be read in more than one way. Which do you mean? (then the readings, numbered)
relation_not_in_memory Only the request parser that knows the memory's predicates (codingAgentQuery, DS022): the question is clear but none of the memory's predicates expresses it. The gap (message and closest predicates) is logged for the approved authoring path; the answer is an honest unknown, never an invented relation. The formalizer never writes it.The memory of this chat has no relation that expresses this question. Could you ask it in other words, or add the knowledge first?

Valid output

@u unclear
  kind gibberish

"asdf qwer zxcv": the reply is I did not understand the message. Could you rephrase?

@u unclear
  kind ambiguous
  reading "Ana saw the man who had the telescope"
  reading "Ana used the telescope to see the man"

"Did Ana see the man with the telescope?": no attachment is preferable, so the model lists both readings; the host asks which one is meant.

@u unclear
  kind ambiguous
  reading "Ana lives in Cluj"
  reading "Irina lives in Cluj"

"Ana works at Acme and Irina at Zeta. Does she live in Cluj?": two parallel clauses, so "she" has no preferable antecedent. The readings are written in English. Compare "Ana manages Irina. Does she live in Cluj?", where the convention prefers the subject and the model writes an assumed relation "refer to" instead (relation "refer to" and relation "mean" are the fixed English phrases of that convention). A phrasing whose readings the model may choose between ("what for": "why" or "for what") is formalized with one plausible reading rather than unclear; evaluation accepts each plausible reading (sop_targets_accepted, DS014).

@u unclear
  kind ambiguous
  reading "none of the invoices from Brenner GmbH were paid"
  reading "not all the invoices from Brenner GmbH were paid"

"All the invoices from Brenner GmbH were not paid, can I ask for a refund?": the scope of "all … not" is always ambiguous, even when the rest of the message makes one reading likely, because choosing would need reasoning about the situation (owner answer to Q-SYM-3). An explicit "not all" or "none" is not ambiguous: it is a query with quantifier not_all or quantifier none.

Invalid model output

@u unclear
  kind gibberish

@q query
  where match
    relation "works at"
    role subject "Maria"
    role object "Alpha Lab"
    polarity affirmed
  end

If a question can be formalized, the message is not unclear.

@u unclear
  kind contradictory

The model does not reason, so it cannot report contradictions or incompleteness; such a message is formalized as written.

@u unclear
  kind gibberish
  language de

The reply table is English only; there is no language to choose.

@u unclear
  kind ambiguous
  reading "the tennis court"

An ambiguity has at least two readings; with one reading the message is not ambiguous.

@u unclear
  kind no_request
  reading "a greeting"
  reading "a thank-you"

Only ambiguous carries readings.
