# Wire authoring guide (for an LLM that writes wires from a source)

Self-contained companion of `SKILL.md`. The full language manual is the section "Knowledge wires" of `docs/specs/DS004-sop.md` and the wire help pages (`docs/wire_types.html`). The grammar block in section 2 is generated by `node eval/smoke-reasoning/validator.mjs --grammar-compact` (the full table: `--grammar`) and checked by `tests/sop/knowledge-grammar.test.mjs`; every example below passes the validator, and `tests/docs/knowledge-docs.test.mjs` checks them.

## 0. Your job

Read a source (a manual, a regulation, an article) and write **knowledge wires**: predicates, facts, rules, defaults, aggregates, actions, methods, norms. The runtime stores them, a different system turns users' questions into queries, and exact engines answer. Your wires must be **checkable, one idea each, and faithful to the source** (keep the sentence in `source` or `quote`). Write what the source says, never what you know; if the source is silent, write nothing.

The loop is mandatory: (1) declare the vocabulary, (2) write the wires, (3) run `node eval/smoke-reasoning/validator.mjs --authoring knowledge.sop query.sop`, fix every error and warning, (4) write at least one test query per rule and per procedure, including a case that must be blocked or refuted, (5) report what you could not express. You never write `approval`, `approved_by` or `approved_at` (the runtime writes them when it accepts your wires); an amendment is composed by the runtime. The flag `--authoring` is the validator's mode for you: it ignores those three fields with the warning `governance_ignored` (remove them) and leaves the check `approval_incomplete` to ingestion, where the runtime has written them; without the flag the validator checks wires as they stand in memory, which is not your situation. `version` and `supersedes` are yours.

## 1. Format

```
@name type            # header at column one: letter, then letters, digits, underscore
  keyword value...    # exactly two leading spaces; one keyword per line
  when all            # a group opens with all or any and closes with end
    p ?x
    q ?x
  end
```

- Terms: a lowercase symbol (`paris`), a safe integer (`120`; money in cents, time in minutes, **no floats**), a JSON-quoted string (`"Alpha Lab"`), a `?variable`, a `$ref` to another wire. **Entities are always lowercase symbols; a string is only a text value (an argument of type `text`) or the content of `source`, `quote`, `speaker`, `description`, `message`.** A multi-word name becomes a symbol by lowercasing and joining the words with underscores ("Alpha Lab" becomes `alpha_lab`; "Dr. O'Neil" becomes `dr_oneil`); keep the original wording in `source` or `quote`, or, when the display form matters, state it once as a text fact (`display_name alpha_lab "Alpha Lab"` over a predicate `args subject:entity object:text`). An atom is `[not |absent ]predicate term...` with 0 to 6 terms. **No parentheses, no commas, no symbol operators** (`above`, `at_least`, `plus`, `times`, never `>`, `+`).
- Comments start with `#` at the start of a line. Ids and predicates share one namespace; `x_` is reserved. Facts `f1`, rules `r_...`, norms and methods are named by verb.
- Dates: `2026-01-15` or a timestamp; `beginning` and `open` are the open ends.

Condition leaves (inside `when`, `never`, `over`, `where`, `except`): an atom, `not ATOM`, `absent ATOM` (closed predicates only), `compare A WORD B` (`above below at_least at_most equal not_equal`), `compute ?v A WORD B` (`plus minus times divided_by`, integers), `start_of ?t ATOM`, `end_of ?t ATOM`, `order ?t1 before|after|same_time ?t2`, groups `all`/`any` closed by `end`. Argument roles on `predicate`: `subject object recipient location source destination instrument time topic`, types `entity integer text time value`; `args none` for arity 0. Query modes: `select exists count every explain why_not plan abduce conform procedure`.

## 3. Patterns, with worked examples

### 3.1 Declare predicates first, then facts

Every relation is a `predicate` wire whose id is the relation name; `args` fixes arity, which argument is the subject, and the types, so the validator catches an orientation slip (`works_at firm person` against `works_at person firm`).

```sop knowledge
@located_in predicate
  args subject:entity location:entity

@f1 fact
  holds located_in paris france
  source "Atlas p.12"
@f2 fact
  holds located_in lyon france
```

```sop knowledge-query
@q query
  where located_in ?city france
  select ?city
```

A fact is one ground atom. A fact true only for a period has `valid START END` (start inclusive, end exclusive). A reported or hedged claim says `status reported` with a `speaker` (and the `quote`), or `status hedged`; the answer will then be conditional on it:

```sop knowledge
@located_in predicate
  args subject:entity location:entity

@f9 fact
  holds located_in atlantis atlantic_ocean
  status reported
  speaker "Plato"
  quote "an island in front of the strait you call the Pillars of Hercules"
```

Prefer one general rule to many similar facts.

### 3.2 Rules

```sop knowledge
@parent predicate
  args subject:entity object:entity
@grandparent predicate
  args subject:entity object:entity

@f1 fact
  holds parent ann bob
@f2 fact
  holds parent bob cy

@r_grand rule
  when parent ?x ?y
  when parent ?y ?z
  then grandparent ?x ?z
```

`when` lines are a conjunction; `then` is one atom, possibly negative (`then not flies ?x`). Every head variable must occur in a positive `when` atom. A rule is a **law of the source** (no exceptions); a normal tendency with exceptions is a `default` (3.4).

### 3.3 The two negations, and `closed`

`not p a` is **explicit evidence** that `p a` is false (the source says so). `absent p a` means "no record of it", and is allowed **only for a predicate declared `closed true`** (the source says the list is exhaustive, quote that sentence). Absence of evidence otherwise is `unknown`, never false. If the source states a contrary, a positive and a negative together give status `both`; nothing breaks.

```sop knowledge
@node predicate
  args subject:entity
@blocked predicate
  args subject:entity
  closed true
@open_node predicate
  args subject:entity

@n1 fact
  holds node a
@n2 fact
  holds node b
@b1 fact
  holds blocked b

@r_open rule
  when node ?x
  when absent blocked ?x
  then open_node ?x
```

Wrong: `when not blocked ?x` where the source only lists blocked nodes (it would never fire). Right: `closed true` plus `absent`. Counts, sums and `every` over a predicate also need `closed`; otherwise the runtime returns a lower bound or `unknown`.

### 3.4 Defaults and exceptions

"Usually", "normally", "as a rule ... except" are defaults.

```sop knowledge
@bird predicate
  args subject:entity
@penguin predicate
  args subject:entity
@flies predicate
  args subject:entity

@f1 fact
  holds bird tweety
@f2 fact
  holds penguin pingu

@r_penguin_bird rule
  when penguin ?x
  then bird ?x

@birds_fly default
  when bird ?x
  then flies ?x
  except penguin ?x
```

`penguin` is **not** declared `closed`: an exception predicate needs *retrieval* completeness (the runtime looks up `penguin` for each candidate bird before it accepts a default conclusion), not a closed world. A strict fact `not flies tweety` beats the default (the answer is `refuted`). Two defaults of equal strength with contrary heads give `both`; resolve it with `overrides $other_default` (preferred to a global `priority` number, which does not compose across chapters). A default needs a contrary or an exception; without one, write a rule.

### 3.5 Aggregates

```sop knowledge
@salary predicate
  args subject:entity topic:entity object:integer
  closed true
  description "HR handbook 2.1: 'the table lists the salary of every employee'"
@dept_payroll predicate
  args subject:entity object:integer

@s1 fact
  holds salary ann dev 100
@s2 fact
  holds salary bob dev 120
@s3 fact
  holds salary di ops 80

@payroll aggregate
  over salary ?p ?d ?s
  group ?d
  sum ?s as ?total
  yields dept_payroll ?d ?total
```

Exactly one of `count`, `sum`, `min`, `max`, `collect`. Rows are the distinct bindings of all variables in `over`, so two people with the same salary count twice, because `?p` is a variable of `over` (it is not in `group`, but it distinguishes the rows). No aggregate inside a cycle.

### 3.6 Time

```sop knowledge
@works_at predicate
  args subject:entity object:entity

@f1 fact
  holds works_at ann alpha
  valid 2020-01-01 2023-01-01
@f2 fact
  holds works_at ann beta
  valid 2023-01-01 open
```

```sop knowledge-query
@q query
  where works_at ann ?c
  select ?c
  during 2021-06-01 2023-01-01
```

This answers `alpha` only: `at T` is one instant, `during S E` means **throughout** (every instant, end exclusive), `overlaps S E` means at some instant, `asof D` means as known at `D`. A derived atom holds at `t` when a rule body holds wholly at that same `t`.

### 3.7 Actions and methods (procedures from a manual)

An `action` is a primitive step with preconditions and effects. A `method` is the manual's own ordered procedure; the engine chooses only at the choice points you write (`choose`, `optional`, `if`).

```sop knowledge
@server predicate
  args subject:entity
@big_db predicate
  args subject:entity
@locked predicate
  args subject:entity
@image predicate
  args subject:entity
@backup_done predicate
  args subject:entity

@lock_db action
  params ?s
  requires server ?s
  adds locked ?s
  cost 1
@snapshot action
  params ?s
  requires locked ?s
  adds image ?s
  cost 2
@dump action
  params ?s
  requires locked ?s
  adds image ?s
  cost 4
@unlock_db action
  params ?s
  requires image ?s
  requires locked ?s
  adds backup_done ?s
  removes locked ?s
  cost 1

@do_backup method
  achieves backup_done ?s
  when server ?s
  binding strict
  step ~lock_db ?s
  step if big_db ?s
    ~snapshot ?s
  else
    ~dump ?s
  end
  step ~unlock_db ?s
```

Steps: `~action term...` (arity must match `params`), a sub-task atom, `achieve atom`, `optional STEP`, `choose ... end` (two or more branches), `any_order ... end`, `if ATOM ... else ... end`, `until ATOM max N ... end` (`max` is mandatory), `pick ?x where ATOM`. `binding strict` (the manual says "always do it this way") forbids leaving the method; `advisory` ("recommended") lets the engine fall back. Use `on_failure $other_method` for the manual's fallback. Unbounded loops cannot be expressed: say so in your report.

**No `jsEval`.** The runtime has a `jsEval {expr}` wire for runtime computation; it is trusted and runtime-only and is not in the grammar above. Do not write it unless the runtime marks the source as trusted code; arithmetic from a source goes in `compute`, `compare` and `aggregate`, and what they cannot express goes in your report as "not expressed".

### 3.8 Norms, severity, binding, versions

A `norm` has exactly one of `forbid`, `oblige`, `permit` over `~action term...` or a state atom, an optional `when`, and at most one qualifier.

| qualifier | on | meaning |
| --- | --- | --- |
| `always` (default) | forbid | the pattern never holds at any step |
| `before ~b` / `after ~b` | forbid, oblige | not (or only) before or after action `b` has occurred |
| `at_most_once` | forbid | at most one occurrence in the whole run |
| `sometime` | oblige | at some step after the trigger |
| `always` | oblige | maintained at every step from the trigger |
| `within N` | oblige | within N steps of the trigger (time units in a timestamped trace) |

An obligation is triggered per instance: tie its variable to the thing it concerns with a `when` atom (`when incident ?i`); the engine creates instances only for bindings that come from the goal or from an executed action. **`severity`** says what a violation does (`hard`: the plan is invalid; `soft`: it costs `cost N`). **`binding`** says whether the engine may relax the norm when it would otherwise block (`strict`: never; `advisory`: may, and says so); `binding` on a soft norm is vacuous (a warning).

A `permit` must name the prohibition it excepts with `overrides $norm`; under `binding strict`, two norms of equal strength in conflict give `blocked` with both ids, never a silent pick (under `binding advisory` the engine reports a violation instead). **`binding` defaults to `strict`** for norms and methods: it is the fail-safe choice, and the runtime policy may only tighten it; write `binding advisory` only when the source says "recommended" or "should". `message` is the reason returned when the norm blocks.

**Standing obligations.** A variable of an `oblige` pattern must be bound by a `when` atom, or the validator reports the error `unsafe_variable`. Such an obligation is created only for the thing the goal or an executed action concerns. If the source states a duty that holds for every binding of the `when` whatever the goal ("every incident must be logged within 3 steps"), say so with the marker line `standing`; the validator then warns `obligation_unscoped` once, so that you confirm the intent, and the runtime applies the duty to every binding and says so in the answer. `standing` exists only on `oblige`.

```sop knowledge
@router predicate
  args subject:entity
@business_hours predicate
  args none
@emergency predicate
  args subject:entity
@notified predicate
  args subject:entity
@reset_done predicate
  args subject:entity

@notify_oncall action
  params ?r
  requires router ?r
  adds notified ?r
  cost 1
@hard_reset action
  params ?r
  requires router ?r
  adds reset_done ?r
  cost 1

@no_hard_reset_in_hours norm
  forbid ~hard_reset ?r
  when business_hours
  severity hard
  binding strict
  source "Ops manual 4.3"
@notify_promptly norm
  oblige ~notify_oncall ?r
  when router ?r
  within 10
  severity soft
  cost 50
@emergency_hard_reset norm
  permit ~hard_reset ?r
  when emergency ?r
  overrides $no_hard_reset_in_hours
```

**Governance.** When the source revises a rule, write the new wire with `version N+1` and `supersedes $old`; never edit or delete the old one. `approval`, `approved_by`, `approved_at` are written by the runtime after review, and a wire you submit is *proposed* until then. A procedure is a named bundle: `@reset_procedure procedure` with `members $reset_router $no_hard_reset_in_hours ...` (it has no version of its own; its members do). An `action` is governed like a method, because its preconditions come from the manual too.

### 3.9 Test queries you write

`mode select` (the default; with `select ?x`), `exists`, `count`, `every`, `explain`, `plan` with a `where` goal, `why_not` with `via ~action term...`, `abduce` with `hypothesis` wires, `conform` with a `trace`. Examples: `@q query` / `mode plan` / `where backup_done s1`; `@q query` / `mode every` with a `scope` group; `@q query` / `mode why_not` / `where router_reset r7` / `via ~hard_reset r7`.

### 3.10 Reification: an event with many participants

A relation has at most six terms. An event with more participants, or with optional ones, is stored as an **event fact plus one fact per participant**, each with its role:

```sop knowledge
@shipment predicate
  args subject:entity
@shipment_from predicate
  args subject:entity source:entity
@shipment_to predicate
  args subject:entity destination:entity
@shipment_carrier predicate
  args subject:entity instrument:entity
@shipment_cargo predicate
  args subject:entity object:entity
@shipment_weight predicate
  args subject:entity object:integer

@e1 fact
  holds shipment s1
  source "Log 2026-03: shipment 1 left Oslo for Rome with Acme, 1200 kg of timber"
@e2 fact
  holds shipment_from s1 oslo
@e3 fact
  holds shipment_to s1 rome
@e4 fact
  holds shipment_carrier s1 acme
@e5 fact
  holds shipment_cargo s1 timber
@e6 fact
  holds shipment_weight s1 1200
```

```sop knowledge-query
@q query
  where shipment ?s
  where shipment_to ?s rome
  select ?s
```

The event symbol (`s1`) is a fresh lowercase symbol you invent; use the same one in every participant fact, and put the source sentence on the event fact.

### 3.11 Integrity constraints

An `integrity` wire names a pattern that must never hold; each match is reported with its `witness`, nothing breaks.

```sop knowledge
@lives_in predicate
  args subject:entity location:entity
@one_home integrity
  never all
    lives_in ?p ?a
    lives_in ?p ?b
    compare ?a not_equal ?b
  end
  witness ?p
  message "a person has one home"
  severity error
```

## 4. The seven mistakes the validator and lint look for

1. `not` where `absent` is meant (a never-firing rule); use `closed true` and `absent`, only if the source says the list is exhaustive.
2. Arity or argument-order drift: always declare `args` with roles and types.
3. Floats and units: integers only, money in cents, time in minutes.
4. Global `priority` numbers: use `overrides`.
5. Forgetting `closed` before a count, sum, `every` or `absent`.
6. A rule written for "usually" (a conflict becomes `both`), or a default written for an exceptionless law.
7. An event with more than six participants flattened ad hoc: reify it as an event fact with one fact per participant (3.10).

Report in plain text, at the end: the sentences you did not formalise, the predicates you declared `closed` and the sentence that justifies each, and any wire the validator warned about that you left.
